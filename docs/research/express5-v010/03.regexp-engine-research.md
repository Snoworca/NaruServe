# Native ECMAScript RegExp route paths on Java 8 and Android API 21

This is technical research for NaruServe T04 / GitHub #51. It is not an SRS, an implemented contract, an engine selection, or authorization to narrow the user's full-parity goal. All research artifacts reside outside the repository. The user requires Express 5 common HTTP-routing semantics while retaining NaruServe extensions; WebSocket equivalence is excluded and existing WebSocket behavior must remain covered by regression tests.

## Result

Direct delegation to `java.util.regex.Pattern` is not a complete representation of native ECMAScript RegExp semantics. The public Java spelling may differ, but matching results, capture participation and object state must remain equivalent. A Java Pattern overload can remain an explicitly identified NaruServe extension; it cannot silently replace the ECMAScript path object.

Two architectures preserve the full-parity goal: an engine-neutral ECMAScript RegExp object backed by a validated native backend, or a dedicated/backported Java 8 ECMAScript parser and VM. Neither architecture is selected or proven complete by this report. A QuickJS native binding is a concrete candidate requiring compatibility work and platform validation. The examined Java-8-compatible Rhino version is already disproven as a complete backend.

## What router 2.2.0 observes

The pinned [Layer source](https://raw.githubusercontent.com/pillarjs/router/v2.2.0/lib/layer.js) retains the RegExp object and calls its native `exec` on the raw pathname. It reads the full matched string and positional captures, derives capture keys by separately scanning `.source`, and URI-decodes participating captures. It does not use `.groups` directly. String routing options do not overwrite the RegExp object's flags or turn it into a whole-path match.

The observable native-RegExp contract therefore includes:

- Search position and full match text, not just a boolean result.
- Capture order, empty versus nonparticipating captures, and numeric/named parameter mapping.
- Compile-time acceptance/rejection under the pinned Node/V8 reference.
- Flag behavior: `i`, `m`, `s`, `u`, `v`, plus persistent `g`/`y` state. `d` is valid although router does not consume indices.
- UTF-16 indexing, Unicode code-point mode, property/case tables, and matching semantics for lookarounds and backreferences.
- RegExp object identity: reusing the same object in multiple routes shares its mutable `lastIndex`.

The ordinary built-in `exec` state algorithm is specified by [ECMAScript RegExpBuiltinExec](https://tc39.es/ecma262/2024/multipage/text-processing.html#sec-regexpbuiltinexec). This research concerns native RegExp path objects, not arbitrary application JavaScript or user-overridden `exec` methods.

### Object-state probes

A single `/^\/x\/(foo)/g` or `y` object matched against `/x/foo` three times yields true, false, true and `lastIndex` 6, 0, 6. Creating a fresh Java Matcher or resetting state per request would change that result.

The pinned router's source scan also matters. The source `\(abc\)(?<id>foo)` matching `/(abc)foo/bar/b` exposes capture `foo` under numeric key `0`, not `id`, because escaped parentheses affect its key scan. A clean engine group-name map is not by itself the pinned router's mapping.

These observations are reproduced in [node.cjs](node.cjs) and [node.jsonl](node.jsonl), with invocation outputs also captured under `invocation-logs/`.

## Java Pattern counterexamples

[Java 8 Pattern](https://docs.oracle.com/javase/8/docs/api/java/util/regex/Pattern.html) is an immutable compiled pattern with execution state in Matcher. [Android Pattern](https://developer.android.com/reference/java/util/regex/Pattern) documents Unicode-aware case-insensitive matching. Cross-platform behavior must not be inferred solely from a Java API signature or bytecode target.

Actual Java 8 and Node probes show:

| Source and input | Pinned Node | Java 8 Pattern |
|---|---|---|
| `\a`, input `a` | Matches identity escape | Does not match; Java escape means bell |
| `^(a|(b))\2$`, input `a` | Matches with a nonparticipating second capture | Does not match |
| `^.$`, input U+1F600, without `u` | Does not match two UTF-16 code units | Matches |
| `(?<user_id>\w+)`, input `abc` | Accepted and matched | PatternSyntaxException |
| `[^]`, input `a` | Accepted and matched | PatternSyntaxException |
| `[a-z&&[^b]]`, input `c`, no `v` | Does not match | Matches as Java intersection syntax |

The portable Node probe separately verifies that `\u{61}` with `u`, Unicode set intersection with `v`, lookbehind, Unicode property escapes and `d` are accepted by the reference. The Java `\u{61}` probe tests native Java acceptance of that source, not an unimplemented flag translator.

The table is based on [RegexProbes.java](RegexProbes.java), [java8-rhino.txt](java8-rhino.txt), [portable.js](portable.js) and [node-portable.jsonl](node-portable.jsonl). JSON serialization of an unmatched array capture produces null; the router-specific tests retain the distinction by omitting the corresponding params key.

A larger translation may optimize proven cases, but accepting a few common patterns with `Matcher.find()` does not establish complete equivalence. General lookaround, backreference, Unicode and code-unit semantics require more than replacing flag letters and escape sequences.

## Existing backend investigation

### Rhino

The exact `org.mozilla:rhino:1.7.15.1` JAR was compiled against and executed using real Java 8 with ES6 mode and interpreter mode. `g`, `y` and `s` were accepted. `u`, `d`, `v`, named captures and lookbehind were rejected. These failures are in `invocation-logs/java8-rhino-run.stdout`; they are not inferred from a compatibility chart.

The [1.7.15.1 RegExp source](https://raw.githubusercontent.com/mozilla/rhino/Rhino1_7_15_1_Release/src/org/mozilla/javascript/regexp/NativeRegExp.java) identifies its supported flags. The [current Rhino README](https://raw.githubusercontent.com/mozilla/rhino/master/README.md) requires Java 17 or later. Neither observation proves that a custom backport is impossible, but neither investigated release is a proven complete Java8/API21 backend. Android execution was not tested.

### QuickJS

The official [QuickJS source archive](https://bellard.org/quickjs/quickjs-2026-06-04.tar.xz) was downloaded and compiled with `make -j4 qjs` on macOS AArch64. The initial build output is [quickjs-build.log](quickjs-build.log). The official project exposes standalone C RegExp and Unicode libraries under MIT licensing; its source includes modern flags and explicit memory/stack/timeout callbacks. See the [official project](https://bellard.org/quickjs/) and [libregexp interface](https://raw.githubusercontent.com/bellard/quickjs/master/libregexp.h).

The host binary passed this small portable sample's `u`, `v`, `d`, named groups, lookbehind, properties and case-folding examples. It also produced two concrete disagreements:

| Case | Pinned Node/V8 | QuickJS 2026-06-04 |
|---|---|---|
| `(?<id>a)|(?<id>b)` | SyntaxError | Accepted |
| Source containing 260 `(a)` captures | Accepted | SyntaxError |

The downloaded `libregexp.c` defines a capture-count limit of 255. Raising a superficial public constant without auditing bytecode representation would not establish correct support. The official source already has wider-language features than the pinned V8 in some areas, so a compatibility layer must validate the pinned grammar rather than simply accept the newest available language syntax.

Full test262/V8 differential conformance, Android cross-compilation, JNI binding and ABI packaging were not performed. This host build is evidence of a candidate, not proof of an approved engine architecture or Android compatibility.

## Proposed representation and implementation options

The proposed representation is engine-neutral and does not select an engine:

| Element | Required responsibility |
|---|---|
| ECMAScript RegExp route object | Source, ECMAScript flags, object identity, and mutable `lastIndex` |
| Internal compiled program | Engine-specific compiled code and owned resources |
| Exec result | Full match, UTF-16 positions, capture values with participation markers, and resulting state |
| router adapter | Pinned source-based capture-key extraction and per-capture URI decode |
| Concurrency boundary | Serialize exec and state updates per shared RegExp identity; do not reset or make g/y state thread-local |
| Lifecycle | Deterministic release and safe invocation after shutdown/abort; bounded allocation/cancellation design |

JNI must preserve Java UTF-16 data and offsets, including surrogate behavior, rather than accidentally using modified-UTF8 conversion semantics. Compile and exec ownership must remain separate so shared state does not duplicate compiled programs unnecessarily.

### Option 1: validated native backend

Use an ECMAScript facade with a native backend. QuickJS `libregexp`/`libunicode` or a V8-aligned native engine is a candidate. To retain full parity, this option must repair or otherwise eliminate the demonstrated capture-limit and grammar differences, validate Unicode/exec semantics against the pinned V8, and pass the platform proof below. It entails native packaging and lifecycle work; that architecture impact must be explicit.

### Option 2: portable Java 8 ECMAScript parser/VM

Implement or backport a complete ECMAScript regex parser and VM, with pinned Unicode data and the required flags/state/captures. This avoids a mandatory JNI distribution but is an engine project. An old Rhino release plus a few syntax translations is not demonstrated sufficient. This option still needs the same pinned conformance corpus and actual Android tests.

### Additional Java extension

A Java Pattern analogue can coexist as an extra NaruServe route-input API. It must be named and documented as Java-native behavior and must not be counted as completed native ECMAScript RegExp parity. Selecting this alone would narrow the user goal and is not authorized by this report.

## Evidence required before T04 design freeze

1. Freeze engine architecture and dependency/module effects without silently reducing the input language.
2. Compare syntax acceptance and native exec results with pinned V8, including flags, invalid flag combinations, named/numeric captures, nonparticipation, empty captures, large capture counts, lookaround and backreferences.
3. Exercise g/y across repeated requests, initial and changed `lastIndex`, reused RegExp objects, and alternative-array ordering.
4. Check router-specific source scanning and URI decoding separately from engine exec.
5. Run applicable native-RegExp test262 cases and explicit V8 differential probes. Engine marketing claims are not a substitute.
6. Test UTF-16/surrogate boundaries and the pinned Unicode property/case tables.
7. Compile and run the backend on Java 8; build the required Android ABIs and run API 21 JNI/device or emulator cases, R8/resource/loading checks, and teardown/concurrency tests.
8. Measure allocation, stack, timeout/cancellation and shutdown behavior. Any operational resource ceiling affecting accepted regexes or match outcomes must be an explicit contract rather than a hidden compatibility waiver.
