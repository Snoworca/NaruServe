# NaruServe 0.10.0 — Express 5 routing research

This document records engineering analysis and user decisions. Requirements remain authoritative only in `docs/spec/`. No implementation contract is substituted by this report.

## Scope and input provenance

The user selected Express 5 as the common HTTP-routing reference, retained NaruServe's additional APIs, and explicitly excluded WebSocket equivalence. The earlier mixed Express 4/5 request is superseded by those conversation decisions. The current `docs/next/request.md` describes an unrelated chatbot product; it is preserved and was not used as the implementation input. Its digest and the source checkout are recorded in `source-context.json`. Clarification is pending.

The investigated reference is Express 5.1.0, router 2.2.0 and path-to-regexp 8.4.2 on Node.js 22.22.0. Supporting programs and observations are in `evidence/`. These observations establish Express behavior; they do not demonstrate that the current Java implementation already passes.

## Independent research result

Three independent researchers inspected current code, upstream behavior, and architecture/lifecycle risks. The common routing architecture is implementable, but both the matcher and dispatcher need substantial replacement; the subsequent explicit user decision selects Java Pattern semantics, excluding ECMAScript engine equivalence. Existing response/body/JSON/upload/service/WebSocket components can be retained behind new request-lifetime and routing boundaries.

## Reproduced Express 5 behavior

- `/:id/:id` is valid; `/a/b` produces `id=b`. Unicode unquoted names are supported.
- Wildcards produce arrays; optional nonparticipating parameters are absent.
- String paths match raw pathname, then decode captures. `/x/a%2Fb`, `/x/%00`, `/x/%2e` and `/x/%2e%2e` can reach handlers. Malformed percent escapes/UTF-8 fail during matching capture decode.
- Path arrays select one alternative's params. RegExp paths use search semantics, own flags and numeric/named captures; they are not string paths with implicit whole-path anchors.
- `route('/a').get(h1).get(h2)` has one Route identity; separate `app.get` calls have distinct identities.
- `next('route')` skips the rest of the Route, while `next('router')` exits a mounted router. Calling `next('route')` in `use` acts like ordinary continuation.
- HEAD fallback is local to each Route and respects stack order.
- OPTIONS is synthesized only after the stack falls through, with deduplicated alphabetically sorted methods joined by comma+space and a matching plain-text body.
- Mounted `use('/api/:version')` changes the current path/url/baseUrl and params. Params are replaced rather than blindly accumulated; nested routers can opt into mergeParams.
- Parameter callbacks are cached for the same request/name/value across matching routes.
- Delayed next works; fulfilled asynchronous results do not automatically continue or finish a request; rejected results enter error handling.

## External transport dependency

The pinned TinyHttpd 3.1.0 parser decodes the path before invoking the adapter and rejects encoded slashes, NUL and dot segments. `RequestParser.java:30-31,90-94` and `PercentCodec.java:39-41` explain why `TinyHttpdExchange.rawPath()` cannot bypass it. Local dependency HEAD `e638586` has the same relevant parser/codec code as verified `165f365`.

An explicit opt-in raw-routing policy is the proposed upstream seam. Existing TinyHttpd defaults and framing/header/Host limits remain protected. Filesystem root, traversal and symlink protection remain at file-access boundaries. A NaruServe-only matcher fix or test-only engine replacement does not establish actual socket parity. External repository changes await the user decision required by the orchestrator gate; publication/signing is a distinct action, not assumed authorized by implementation.

## Request lifetime and Android constraints

`HttpExchange` and `ExchangeHandler` already permit the exchange to outlive the initial callback. TinyHttpd's bridge waits for completion. Servlet ordinary requests currently do not enter AsyncContext, so deferred ordinary response support needs a real adapter lifecycle change.

A shared request execution object can serialize continuations, maintain layer/Route cursors and param/mount frames, and complete/abort/log/clean resources exactly once. Restoring params at every next return is not assumed: same-Router after-next state differs from mounted-Router completion and is fixed by the oracle. Explicit next after response completion and repeated next remain executable according to Express traces, independently of prohibiting a second response. Request body/cache/attributes are not reconstructed per layer. Deferred callbacks reinstall lifecycle request context so shutdown called inside them does not wait on itself. Existing middleware before/after behavior, stream ownership, uploads, SSE and disconnect handling remain regression obligations.

CompletionStage/CompletableFuture are not a mandatory core API choice: Android adds those types at API 24. API 21 can retain a callback/custom-completion representation of resolve/reject behavior without requiring coroutines or raising minSdk. Blocking a worker on a latch and releasing the worker are separate resource claims and need separate evidence.

## Compatibility decisions to freeze

Confirmed: one Express 5 reference; no Express 4 inline regex extension; existing convenience/group/service/SSE/WS APIs retained; WebSocket parity excluded, existing WS behavior tested.

The user subsequently chose Java Pattern semantics for regex routes. ECMAScript RegExp engine equivalence, g/y lastIndex emulation, JNI and engine qualification are no longer implementation goals. See 04.java-pattern-decision.md for the current decision. Historical engine probes in 03.regexp-engine-research.md remain research evidence only. Express common HTTP behavior outside the explicitly selected regex-language boundary remains in scope.

Default routing errors can follow Express finalhandler semantics while preserving NaruServe JSON error utilities/configuration as an extension. Platform-dependent Java versus Node stack traces require a declared comparison of equivalent error information, not an arbitrary blanket difference waiver. Extensions cannot override common routing silently; group and WS contracts retain their own identified behavior.

## Test strategy

1. Pin reference package locks, upstream source digests, fixture generator command and environment.
2. Commit deterministic oracle cases and expected JSON; run their Java replay in ordinary builds without Node.
3. Run live Express differential generation separately and detect stale expected values.
4. Compare registration errors, selected handler traces, layer params/path/mount views, status, essential headers/body and completion/error transitions. An unexplained difference fails; it is not retroactively labeled intentional.
5. Separate pure matcher tests, actual raw-socket tests, and Servlet tests to expose transport normalization.
6. Test adversarial patterns/input in subprocesses with deadlines/memory bounds on Java 8 and 17. Porting JavaScript `recheck` tests alone does not prove Java regex performance. Include path-combination limits from path-to-regexp security fixes.
7. Preserve all unchanged regression obligations: body/cache/JSON, upload lifetime, file root/symlink security/Range, CORS preflight, service lifecycle, stream ownership, SSE, WS, access-log/request-ID and shutdown.
8. Retain Java8 bytecode, real Java8 runs, API21 animal-sniffer and dependency/reference boundaries, plus Java/Kotlin API compilation.
