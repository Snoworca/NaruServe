## 0. 요약

1. **refresh "회전"이 실제로는 회전이 아니다.** 서버 상태가 `ver` 하나뿐이라 회전 뒤에도 이전 refresh가 14일 동안 유효하다. 훔친 refresh는 재사용 탐지 없이 계속 새 쌍을 받는다. 01이 v2로 미룬 `RefreshTokenStore`(jti 계열 + 재사용 탐지)를 v1 필수로 올려야 한다.
2. **PBKDF2 600,000회는 Android 5 기기에서 쓸 수 없다.** M4에서 449 ms를 쟀다. 2013년 플래그십의 공개 수치로 환산하면 Android 5 기기에서 **약 10–20초**로 추정된다. 기기별 보정(목표 시간), 해시 동시 실행 상한, 해시 전 속도 제한을 함께 넣어야 한다.
3. **기기에서 도는 서버는 평문 HTTP다.** NaruServe TinyHttpd 어댑터는 v1에서 TLS를 열지 않는다(`docs/api/defaults.md`). LAN에서 비밀번호와 bearer 토큰이 그대로 보인다. `Secure` 쿠키도 http에서는 동작하지 않으므로 01의 `refreshCookie`·`requireHttps`는 기기 배포에서 성립하지 않는다.
4. **사용자 직접 역할을 토큰에 넣는 결정**은 강등·비활성화·삭제를 15분 늦춘다. 03의 "철회 즉시 반영" 원칙과도 모순된다. 토큰에는 `sub`·`ver`만 넣고, 역할은 가드가 처음 물을 때 store에서 읽어 요청 단위로 메모하는 쪽(그룹과 같은 방식)이 맞다.
5. **`publicPaths`를 문자열 접두사로 구현하면 열려 버린다**(`/healthz`, `/health.`, `/auth/users`). 코어는 `..`·`%2F`를 미들웨어 전에 거부하므로 안전하다. 남는 위험은 auth가 코어와 다른 매칭을 쓰는 것이다. 코어의 `PrefixMatcher`를 그대로 타도록 `app.use("/health", auth.permit())` 형태로 바꾼다.
6. **토큰 scope와의 교집합(03 §3.1)을 집합 교집합으로 구현하면 틀린다.** 와일드카드 부여 `posts:*` ∩ 토큰 `posts:read`가 공집합이 된다. 규칙은 "부여 집합도 만족하고 토큰 집합도 만족" 두 번의 매칭이어야 한다.
7. **auth 모듈은 앱의 `JsonCodec`을 얻을 공개 경로가 없다**(`ApplicationContext`에 codec 접근자가 없다). 00 §6의 코어 변경 표에 세 번째 항목으로 넣거나, `Auth.builder().json(codec)`으로 받아야 한다.
8. **틀린 인용이 있다.** OWASP PBKDF2-SHA1 반복 수는 현재 1,400,000이다(01은 1,300,000). "nimbus가 가장 무겁다"는 것도 틀렸다. 전이 의존을 합치면 java-jwt + Jackson(약 2.4 MB)이 가장 크다. 나머지 핵심 수치(OpenFGA 25, SpiceDB 50, AWS 10, RFC 6750)는 맞다. 다만 02가 붙인 출처 URL에는 그 수치가 없다.

## 2. 측정

### 2.1 환경과 명령

- 기기: Apple M4(10코어), `openjdk 17.0.20.1 (Homebrew)`, HotSpot JIT. 소스는 `--release 8`로 컴파일했다.
- 프로그램(저장소 밖): `/private/tmp/claude-501/-Users-beom-work-git-NaruServe/7b3c8583-a5c6-4ed8-9242-866f904fa0ab/scratchpad/bench/AuthBench.java`
  - 직접 구현은 RFC 8018 §5.2를 따른다. `Mac.init`은 한 번만 부르고, 반복마다 `update(u)` + `doFinal(u,0)` + XOR을 한다.
  - JDK 쪽은 `SecretKeyFactory("PBKDF2WithHmacSHA256")`이다.
  - 수치는 반복 3회 중 최솟값이고, 워밍업을 따로 했다.

```

javac --release 8 AuthBench.java && java -cp . AuthBench 3
java -XX:+UnlockDiagnosticVMOptions -XX:-UseSHA -XX:-UseSHA256Intrinsics -cp . AuthBench 2
java -Xint -cp . XintBench 10000 ; java -Xint -cp . XintBench 30000
```

해석:

- 직접 구현과 JDK 구현의 속도 차이는 1% 안이다. 반복 하나에 약 **0.75 µs**가 든다.
- 01의 직접 구현이 속도에서 손해를 보지 않는다는 점은 확인했다. 단, 이는 HotSpot에서의 결과다.
- HS256 서명·검증은 호출당 약 1.1–1.3 µs다(JSON 디코드 제외). 기기에서 수십 배 느려도 수십 µs이므로 access 토큰 검증을 stateless로 두는 판단은 비용 면에서 문제없다.
- `-Xint` 수치(42 µs/반복)는 JIT이 없을 때의 상한을 보여 준다. Android 5의 ART는 AOT로 컴파일하고 `Mac`은 Conscrypt(네이티브)라서 이 수치를 그대로 쓰면 안 된다.

비율은 약 23–28배(2013 플래그십 대비 M4)다. Android 5 시대 보급형(Cortex-A7/A53 1.2 GHz, 예: Snapdragon 200/400/410)은 이보다 느리다고 보고, 직접 구현에서 생기는 반복당 JNI 경계 두 번(update·doFinal)을 더해 **반복당 15–35 µs**로 잡았다.

| 반복 수 | M4 실측 | Android 5 기기 추정 |
|---|---|---|
| 100,000 | 75 ms | **1.5–3.5초** |
| 310,000 | 232 ms | **5–11초** |
| 600,000 | 449 ms | **9–21초** |

- 로그인 한 번이 작업 스레드 하나와 CPU 코어 하나를 그만큼 잡는다.
- 4코어 기기에 동시 로그인 4건이 들어오면 그동안 다른 요청이 사실상 멈춘다. 기본 `maxWorkers`는 64다.
- 이 수치는 반드시 실기기로 다시 재야 한다. Android 기기 검증은 v1 범위 밖이므로 지금은 확인할 수 없다.

### 2.4 반복 수 정책 권고

1. **기본값은 고정 수가 아니라 목표 시간이다.**
   - `passwordHashing(PasswordPolicy.target(500, MILLISECONDS))`(제안): 기동할 때 2,000회를 3번 재서 반복 수를 정한다.
   - 상한은 OWASP 600,000이다. 하한은 사람이 정한 `floor`이고 기본 50,000이다.
   - 정한 값이 600,000보다 작으면 WARN을 한 번 남긴다. 로그에는 측정값과 OWASP 권고를 같이 쓴다.
   - JVM 서버에서는 대개 600,000이 된다(M4에서 449 ms).
2. **명시 설정** `iterations(n)`도 허용한다. 해시 문자열에 반복 수를 넣으므로(01 §3.6) 나중에 올려도 로그인할 때 다시 해시된다.
3. **해시 동시 실행 상한**: 기본 `max(1, 코어 수 / 2)`. 넘으면 기다리지 않고 `503 + Retry-After: 1`로 답한다. 이렇게 해야 PBKDF2가 앱 전체 DoS 증폭기가 되지 않는다.
4. **속도 제한은 해시보다 먼저 검사한다.** 01 §5의 표에는 순서가 없다.
5. **SHA1로 갈아타는 방안은 버린다.** 1,400,000회 기준이라 SHA256 600,000회보다 1.7배 느리다(측정: 1.3M에서 757 ms).
6. 기기 배포에서 600,000에 못 미치는 것은 "해시 파일 유출 시 오프라인 공격 저항"이 약해지는 것이다. 기기 안 DB 유출에는 기기 탈취가 필요하므로 위협이 상대적으로 작다. 문서에는 이 trade-off를 숨기지 않고 쓴다. 더 강하게 하려면 `PasswordHasher` SPI로 pepper(앱이 Android Keystore에 둔 HMAC 키)를 끼울 수 있다고 안내한다(Core는 `android.*`를 모른다).
7. 직접 구현의 함정 두 개
   - `SecretKeySpec`은 빈 키에 `IllegalArgumentException`을 던진다. 빈 비밀번호는 해시 전에 400으로 거부한다.
   - `Mac.init`을 반복마다 다시 하면 64바이트를 넘는 비밀번호의 사전 해시가 반복마다 일어나 긴 비밀번호 DoS가 된다. OWASP가 경고하는 그 경로다. `init`은 한 번만 한다.

### 4.2 안전하지 않거나 불완전한 결정

- **U1. 토큰의 `roles`.**
  - 권고: access payload는 `{sub, ver, typ, iat, exp, jti}`만 담는다.
  - `AuthPrincipal.getRoles()`는 처음 부를 때 `findById`로 읽어 요청 단위로 메모한다. 그룹(02 §5.1)과 같은 지연 계산이다.
  - 그러면 로그인만 요구하는 라우트는 지금처럼 DB 호출 0이고, 역할·스코프 가드가 있는 라우트만 1회를 쓴다.
  - 같은 조회에서 `enabled`와 `ver`도 확인하므로 비활성화와 로그아웃이 즉시 반영된다. `checkUserOnEveryRequest`가 필요 없어진다.
  - 비용이 걱정되면 `userCacheTtl(5s)`를 둔다.
- **U2. `Map<String,String>` attributes.**
  - Gson의 `Double` 문제를 피하는 장점은 맞다.
  - 하지만 숫자·불리언·목록을 문자열로 직렬화하는 규칙이 앱마다 달라진다.
  - 크기 제한과 키 예약도 없다(T2).
  - 유지하되 문법·크기 상한을 계약에 넣고, `GET /me` 응답에서는 "허용 목록 키만" 내보낸다. 관리자 응답도 같은 목록을 쓴다.
- **U3. 그룹 ID 대소문자 구분.**
  - `Admins`와 `admins`가 다른 그룹이 되면 관리 화면에서 혼동을 노린 공격이 가능하다.
  - AWS는 대소문자 없이 유일하게 다룬다(F17).
  - 저장은 `[a-z0-9._-]{1,64}` 소문자만 허용해 문제 자체를 없앤다. 03의 스코프 문법(코드 쪽 소문자만)과도 맞다.
- **U4. `checkUserOnEveryRequest`를 옵션으로 둔 것.** U1을 받으면 지운다.
- **U5. leeway 60초 기본.** 발급과 검증이 같은 프로세스·시계라면 60초는 이유 없이 수명을 늘린다(E8).
- **U6. 로그아웃이 모든 기기 로그아웃이다.**
  - `tokenVersion++`는 한 기기의 로그아웃으로 모든 기기를 끊는다. Express 사용자는 대개 "이 기기만"을 기대한다.
  - S3의 `RefreshTokenStore`가 들어오면 `/logout`은 family 하나만, `/logout?all=true`는 `ver++`로 나눈다.
  - 또 `/logout`이 "인증 필요"(access)라서 access가 만료된 클라이언트는 로그아웃하지 못한다. refresh로도 로그아웃할 수 있어야 한다.
- **U7. 비밀번호 변경·관리자 재설정.** `/password`는 `tokenVersion++`를 하지만 현재 요청의 새 토큰 쌍을 돌려주지 않는다. 바꾼 사람도 즉시 로그아웃된다. 새 쌍을 응답에 넣는다.
- **U8. 코어 접근 경로 두 개가 빠졌다.**
  - `JsonCodec`: `DefaultRestApp.jsonCodec()`은 internal이고 `ApplicationContext`에는 없다.
  - `RouterPolicy`: getter가 없다.
  - 00 §6의 코어 변경 표에 "codec 조회(또는 builder 주입)"를 추가해야 한다.

### 4.3 기본 거부와 경로 트릭 — 코드로 확인한 사실

코어가 이미 하는 일(확인):

- `docs/api/routing.md` "경로 거부와 디코딩"에 따르면 매칭 **전에** 다음을 거부한다.
  - 잘못된 퍼센트 인코딩, 인코딩된 `/`(`%2F`, `%2f`), `NUL`
  - 그대로이거나 인코딩된 `.`·`..` 세그먼트(`/health/../admin`, `/a/%2e`, `/a/.%2e/b`)
  - 공백, 제어 문자, `#`, U+007F보다 큰 그대로인 문자
- TinyHttpd 어댑터에서는 이 400이 엔진 단계에서 나가므로 **미들웨어(auth 포함)가 돌기 전**이다.
- `app.use(prefix, mw)`는 `internal/PrefixMatcher`가 처리한다.
  - `Router.decodeSegments(req.rawPath(), policy)`로 나눈 세그먼트를 세그먼트 단위로 비교한다.
  - 앱의 `RouterPolicy`(대소문자 무시는 `UnicodeCase.equals`)를 따른다.
  - 그래서 `/api`는 `/apian`에 맞지 않는다.
- 결론: `/health/../admin`, `/health%2F..%2Fadmin`, `/health/%2e%2e/admin`은 auth까지 오지 않는다. **위험은 auth가 다른 매칭을 쓰는 데서만 생긴다.**

auth가 `req.path().startsWith(prefix)`로 구현하면 생기는 결과:

| 요청 | 라우터 정책 | 라우트 | startsWith("/health") | 결과 |
|---|---|---|---|---|
| `/healthz/secret` | 엄격 | `/healthz/secret` | 참 | **열림** |
| `/health./x` | 엄격 | `/health./x` | 참 | **열림**(끝 점 세그먼트는 거부 대상이 아니다. `.` 단독 세그먼트만 거부된다) |
| `/auth/users` (공개 prefix `/auth`) | — | 관리 CRUD | 참 | **열림** |
| `/HEALTH` | `caseInsensitive` | `/health` | 거짓 | 401(닫힘, 사용성 문제) |
| `//health` | `mergeSlashes` | `/health` | 거짓 | 401(닫힘) |
| `/health/` | `ignoreTrailingSlash` | `/health` | 참 | 공개(의도와 같음) |
| `/caf%C3%A9`, 공개 `/café` | 엄격 | `/café` | rawPath를 쓰면 거짓, path를 쓰면 참 | 구현에 따라 다르다 |

권고:

1. `publicPaths(...)`를 빼고 **`app.use("/health", auth.permit())`를 `app.use(auth)`보다 먼저 등록**하는 형태로 바꾼다. `permit()`은 요청에 "공개" 표시만 붙인다.
   - 코어 `PrefixMatcher`가 정책까지 포함해 매칭하므로 auth가 경로를 해석할 일이 없다.
   - 등록 순서 실수(permit을 auth 뒤에 둠)는 fail-closed(401)라 안전하다.
2. `publicPaths`를 꼭 유지하려면 코어에 `ApplicationContext.routerPolicy()` 같은 읽기 접근을 추가하고 `Router.decodeSegments`(이미 public)로 같은 비교를 한다. 이것은 코어 변경이다.
3. 공개 라우트로 마운트된 `auth.routes()` 안쪽(E2)은 경로 비교 없이 핸들러 단위로 처리한다.
4. 테스트 AUTH-T30–T33.

## 5. 인수 테스트 카탈로그

표기: **[보안]**은 보안 회귀 테스트다. 형식은 `Given / When / Then`이다. 모든 테스트는 JVM 단위 또는 `RestApp` 통합 테스트로 자동화할 수 있다. 기기 실측(AUTH-T41)은 예외다.

### 5.1 토큰 형식·검증

- AUTH-T01 **[보안]** 유효한 HS256 access / `alg` 를 `none` 으로 바꾸고 서명을 비워 보낸다 / 401, `WWW-Authenticate: Bearer error="invalid_token"`.
- AUTH-T02 **[보안]** 키 k1 / header `alg:"HS512"` 또는 `"hs256"` / 401.
- AUTH-T03 **[보안]** 유효 토큰 / 서명의 마지막 base64url 문자를 같은 바이트로 디코드되는 비정규 문자로 바꾼다 / 401.
- AUTH-T04 **[보안]** 토큰 / 점이 1개 또는 3개, 패딩 `=` 포함, `+`·`/` 포함 / 각각 401.
- AUTH-T05 **[보안]** payload에 `"exp"` 없음, `"exp":"1761700900"`(문자열), `"exp":1761700900.5`, `"exp":1e300` / 각각 401(500이 아님).
- AUTH-T06 **[보안]** header에 `"alg"`가 두 번 나온다 / 401.
- AUTH-T07 **[보안]** 깊이 100의 배열을 담은 payload(서명은 유효) / 401이며 codec까지 가지 않는다(사전 검사).
- AUTH-T08 **[보안]** 9 KiB 토큰 / 431(엔진) 또는 401. 어느 쪽이든 auth 코드는 2xx를 내지 않는다.
- AUTH-T09 **[보안]** refresh 토큰 / `Authorization: Bearer`로 보낸다 / 401. access 토큰을 `/auth/refresh`에 보낸다 / 401.
- AUTH-T10 **[보안]** `crit` header 또는 `jku`가 있는 토큰 / 검증한다 / `crit`는 401, `jku`는 무시하고 네트워크 호출 0.
- AUTH-T11 `TimeSource`를 exp+leeway−1과 exp+leeway+1에 둔다 / 검증한다 / 앞은 통과, 뒤는 401.
- AUTH-T12 **[보안]** `TimeSource`가 이전 값보다 작은 시각을 돌려준다 / 만료된 토큰을 검증한다 / 401(단조 보장).
- AUTH-T13 **[보안]** `Authorization` 헤더와 `access_token` 쿼리를 동시에 보낸다 / 400 `invalid_request`.

### 5.2 로그인·refresh·로그아웃

- AUTH-T14 **[보안]** refresh R1으로 회전해 R2를 받았다 / R1을 다시 쓴다 / 401, 같은 family의 R2도 401, `REFRESH_REUSE` 이벤트 1건.
- AUTH-T15 기기 A·B 세션 / A에서 `/logout` / A의 refresh는 401, B의 refresh는 200.
- AUTH-T16 access가 만료된 클라이언트 / refresh 토큰으로 `/logout` / 204.
- AUTH-T17 **[보안]** 사용자 삭제 뒤 같은 username으로 다시 만들었다 / 옛 refresh로 `/refresh` / 401(id 비재사용).
- AUTH-T18 **[보안]** 관리자가 사용자 roles에서 `admin`을 뺀다 / 그 사용자의 기존 access로 `requireRole("admin")` 라우트 / 403(15분 지연 없음, U1).
- AUTH-T19 **[보안]** `enabled=false` / 기존 access로 역할 가드 라우트 / 401. 로그인만 필요한 라우트의 동작은 결정에 따라 문서와 같다.
- AUTH-T20 `/password` 성공 / 응답에 새 토큰 쌍, 다른 세션의 refresh는 401.

### 5.3 비밀번호 해시

- AUTH-T21 RFC 7914 §11 벡터 / 직접 구현 PBKDF2 / 바이트까지 일치.
- AUTH-T22 저장 해시 `pbkdf2-sha256$100000$…`, 현재 설정 600000 / 로그인 성공 / `update`가 600000 해시로 한 번 불린다.
- AUTH-T23 **[보안]** 해시 동시 상한 1 / 동시 로그인 3건 / 1건은 처리, 나머지는 503 + `Retry-After`, 처리 시간 동안 다른 라우트 응답이 지연되지 않는다.
- AUTH-T24 **[보안]** 빈 비밀번호, 129자 비밀번호 / 로그인·가입 / 400이며 해시 호출 0.

### 5.4 열거·무차별 대입

- AUTH-T25 **[보안]** 없는 사용자, 비밀번호가 틀린 사용자, 비활성 사용자 / 로그인 / 셋 모두 같은 상태·본문, 더미 해시를 포함해 해시 호출 수가 같다(호출 수로 측정해 시간 대신 쓴다).
- AUTH-T26 **[보안]** IP 하나에서 11번 실패 / 11번째 / 429 + `Retry-After`, 해시 호출 없음(제한이 해시보다 먼저).
- AUTH-T27 **[보안]** `trustProxy(false)`인데 `X-Forwarded-For`를 매번 바꾼다 / 11번 실패 / 429(헤더를 무시).
- AUTH-T28 **[보안]** 서로 다른 IP 50개에서 같은 username으로 실패 / 다음 시도 / 지연이 걸리지만 올바른 비밀번호는 지연 뒤 성공(잠금 DoS 없음).
- AUTH-T29 **[보안]** 제한 맵이 상한에 닿았다 / 새 키 1만 개로 공격 / 기존 피해자 키의 카운트가 사라지지 않는다.

### 5.5 기본 거부·경로

- AUTH-T30 **[보안]** `app.use("/health", auth.permit())` / `GET /healthz`, `GET /health.` / 401.
- AUTH-T31 **[보안]** 같은 설정 / `GET /health/../admin`, `/health/%2e%2e/admin`, `/health%2Fadmin` / 400(엔진), auth 핸들러 미실행.
- AUTH-T32 `caseInsensitive` 정책 + `permit("/health")` / `GET /HEALTH` / 200(공개, 코어 매칭과 같음).
- AUTH-T33 **[보안]** `auth.routes()`를 `/api/auth`에 마운트 / `GET /api/auth/users` 무인증 / 401. `POST /api/auth/login` / 401이 아님(라우트 단위 공개).
- AUTH-T34 **[보안]** `app.use(auth)` 없이 `auth.require("posts:write")`만 붙인 라우트 / 무인증 요청 / 401.

### 5.6 스코프·역할

- AUTH-T35 03 §2.3 표 15행 전체 / 매칭 / 표와 같다.
- AUTH-T36 **[보안]** 부여 `posts:*`, 토큰 scope `posts:read` / `require("posts:read")`는 통과, `require("posts:write")`는 403.
- AUTH-T37 **[보안]** `trustTokenScopes(true)`, 토큰 scope `*` / `require("users:delete")` / 403(토큰 와일드카드 리터럴).
- AUTH-T38 **[보안]** `RoleStore`가 예외를 던진다 / 스코프 가드 / 500(403 아님), 핸들러 미실행.

### 5.7 그룹

- AUTH-T39 **[보안]** 깊이 7 사슬 위에 깊이 2 사슬을 붙이는 `PUT parents` / 요청 / 409(아래·위 합산 검사, T4).
- AUTH-T40 **[보안]** `groupsOfUser`가 300개를 돌려준다(상한 256) / 그룹 가드 / 500 + 로그, `parentsOf` 호출 0.
- AUTH-T41 **[보안]** 순환 A→B→A가 DB에 직접 들어 있다 / 확장 / 종료하고, 결과는 {A,B}.
- AUTH-T42 **[보안]** `group-admins` 사용자가 `admins` 그룹(역할 부여 그룹)에 자기를 추가한다 / 요청 / 403.

### 5.8 관리·운영

- AUTH-T43 **[보안]** 관리자가 하나뿐이다 / 자기 삭제, 자기 강등 / 409.
- AUTH-T44 **[보안]** 가입 본문에 `roles:["admin"]`, `enabled:true`, `attributes.passwordHash` / 가입 / 무시되거나 400. 저장된 사용자에게 admin이 없다.
- AUTH-T45 **[보안]** 모든 테스트의 로그를 수집한다 / 비밀번호 평문, JWT 서명 부분, 해시 문자열, 비밀키를 grep한다 / 0건.

## 6. 열린 질문

1. 역할을 토큰에서 빼는 U1은 "로그인만 필요한 라우트는 DB 0"을 지킨다. 반면 역할 가드 라우트는 요청당 `findById` 1회가 된다. 이 비용을 받아들일지, 아니면 짧은 TTL 사용자 캐시를 기본으로 켤지 정해야 한다.
2. `RefreshTokenStore`를 v1에 넣으면 주니어가 구현할 인터페이스가 하나 는다. `InMemory` 기본 + `UserStore` 확장 default 메서드로 숨길 수 있는지 확인해야 한다.
3. `publicPaths` 대신 `auth.permit()`으로 API를 바꾸는 것은 Express 관례(`app.use(express.static)`를 auth 앞에 두는 습관)와 맞는다. 다만 03의 "한 줄 설정"보다 한 줄이 늘어난다. 둘 다 둘지 결정해야 한다.
4. 기기 배포에서 평문 로그인을 기본 거부(I3)하면 주니어의 첫 실행이 깨진다. 루프백(에뮬레이터·`adb reverse`)은 허용하므로 대부분의 개발 흐름은 유지된다. 이 기본값을 받아들일지 정해야 한다.
5. PBKDF2 보정의 목표 시간 기본값: 500 ms인가 1초인가. 실기기 측정 전까지는 정할 근거가 없다.
6. 어댑터 TLS(TinyHttpd `TlsConfig`)를 auth보다 먼저 할지. `object.md` §14.3·§20.3의 API 21 TLS provider 시험과 묶여 있다.
7. `JsonCodec` 접근: 코어 변경(`ApplicationContext`에 codec 조회)으로 할지, `Auth.builder(secret).json(codec)`으로 받을지. 후자는 코어 변경이 없지만 앱 codec과 다른 codec을 쓰게 될 수 있다.
8. 02의 TTL 캐시를 그룹 가드가 있을 때 기본으로 켤지(D2). 켜면 관리 API 외 경로의 변경 반영이 늦어진다.
9. nimbus-jose-jwt 10.10은 의존 0, 843 KB, Gson 2.14.0 shade다. ~~직접 구현을 유지하더라도, OIDC·RS256이 필요해지는 v2에서 API 21 animal-sniffer를 통과하는지 확인할 가치가 있다.~~ **(정정: 새 의존성 0개 원칙에 따라 v2 RS256·ES256·JWKS도 `java.security.Signature`로 직접 구현한다. 00 §2.)**
