# 연구 04 — 초기 설정과 기존 시스템 맞추기

> **3판 안내:** 최종 결정본은 00 개요 33판이다(최종 규칙은 00 §6.3 R28–R47, 점검표 §6.4). 최종 결정과 이름은 [00 개요](00.overview.md)가 우선한다. 이 문서와 다른 부분은 00 §6(06 검토로 바뀐 결정), §7(최종 이름표), §11(정정 기록)을 본다.

> 상태: 연구 문서(설계 제안). 코드·빌드·`docs/spec/`은 바꾸지 않았다. 대응하는 SRS 요구사항은 아직 없다.
> 모듈 배치는 사용자 결정에 따라 바뀌었다. Gradle 모듈은 **`NaruServe-utils`**(`NaruServe-api`에만 의존, API 21 검사 대상)이고, 패키지는 `com.snoworca.naruserve.utils`, 인증은 `com.snoworca.naruserve.utils.auth`이다. 00~03의 `NaruServe-auth`는 이 모듈로 읽는다.
> `Auth`, `AuthUser`, `AuthPrincipal`, `UserStore`, `GroupStore`, `RolePolicy`, `RoleStore`, `InMemoryUserStore`, `PasswordHasher`, `TimeSource`는 00~03의 이름을 그대로 쓴다. 이 문서에서 새로 지은 이름에는 모두 **(제안)** 을 붙였다.
> 엔터프라이즈 연동(OIDC/SAML/LDAP, 멀티 테넌트, 클러스터)은 연구 07이 다룬다. 이 문서는 07과 만나는 지점만 적는다.

## 0. 요약

1. **설정 모델은 코드 빌더 하나다.** 환경변수와 `.properties`는 빌더에 값을 넣는 출처일 뿐이고, 별도 설정 언어(JSON 설정 파일, 마법사)는 두지 않는다. 마법사가 필요한 일은 첫 관리자 만들기 하나뿐이다.
2. **필수 값은 비밀키 하나다.** 나머지(토큰 수명, 해시 비용, 공개 경로, 가입 꺼짐, 기본 거부)는 안전한 기본값이 있다. 비밀키가 없으면 `prod`에서는 기동을 멈추고, `dev`에서는 임시 키를 만들되 루프백 요청만 받는다.
3. **기존 시스템은 `UserStore` 어댑터 하나로 맞춘다.** 컬럼 이름, ID 타입, 로그인 키, 역할 표현은 어댑터의 `toAuthUser` 한 곳에서 바꾼다. 해시는 `PasswordHasher` 체인이 맡아 bcrypt·MD5 같은 옛 해시를 검증하고, 로그인에 성공하면 PBKDF2로 다시 해시한다.
4. **스키마가 없는 새 시스템**에는 `utils` 안에 `FileUserStore`(제안, `java.io.File`, 수천 명 이하)를 두고, JDBC 구현과 참조 DDL은 JVM 전용 선택 모듈 `NaruServe-utils-jdbc`(제안)로 뺀다. Android SQLite 구현은 v1에서 문서 예제로만 준다.
5. **첫 관리자**는 환경변수(`NARU_ADMIN_PASSWORD`)가 있으면 그것으로 만들고, 없으면 일회용 설정 토큰을 만들어 로그에 찍고 `POST /auth/setup`을 **루프백에서만** 연다. 토큰은 한 번 쓰면 사라지고, 관리자가 생기면 엔드포인트는 영구히 404가 된다.
6. **`auth.install(app)`(제안)** 이 라우트 마운트, 기본 거부 미들웨어, `onStart` 자기 점검(doctor)을 한 번에 건다. doctor는 `onStart`에서 돌기 때문에 FAIL 항목이 있으면 포트를 열기 전에 기동이 멈춘다(lifecycle.md의 기존 동작).
7. Android에서는 PBKDF2 반복 수를 **기기에서 재서** 250 ms에 맞추고(하한·상한 있음), 시계가 틀린 기기와 네트워크 없는 키오스크를 doctor가 경고한다. 단일 사용자 기기에는 PIN 모드(제안)를 두되 6자리 이상과 영구 잠금을 강제한다.
8. 개인 앱, Android 기기 서버, 기존 DB가 있는 중견 회사, 엔터프라이즈 네 단계마다 무엇을 설정하는지 §9에 표로 정리했다. 주니어가 흔히 하는 실수 10가지와 모듈이 그것을 잡는 방법은 §8.3에 있다.

## 1. 설정 모델

### 1.1 후보 비교

| 후보 | 주니어 | Android | 오타 검출 | 비밀 처리 | 판정 |
|---|---|---|---|---|---|
| A. 코드 빌더만 | IDE 자동 완성, 컴파일 오류 | 그대로 | 컴파일 시점 | 코드에 하드코딩 위험 | **기본** |
| B. 설정 파일(`.properties` 또는 JSON) | 키 이름을 외워야 한다 | 파일 위치가 앱마다 다르다 | 실행 시점(모르는 키 무시 함정) | 파일에 평문 | 값 출처로만 |
| C. 환경변수 | 컨테이너에 맞다 | **Android 앱에는 환경변수가 없다** | 실행 시점 | 가장 흔한 운영 방식 | 값 출처로만 |
| D. 마법사·첫 실행 엔드포인트 | 화면이 안내 | 화면이 있어야 한다 | — | 네트워크로 비밀이 오간다 | **첫 관리자만** |

**권고: A를 유일한 진실 원천으로 두고, B와 C는 빌더에 값을 넣는 출처로 쓴다.** JSON 설정 파일은 두지 않는다. 설정을 읽으려고 `JsonCodec`을 앱에서 꺼내야 하는데(지금 `RestApp`에 codec getter가 없다) 그 대가에 비해 얻는 것이 적고, 키 오타가 조용히 무시되는 문제가 생긴다. `.properties`는 `java.util.Properties`라 API 21에서 그대로 돈다.

```java
// 운영(JVM): 환경변수에서 비밀키, 나머지는 기본값
Auth auth = Auth.builder(AuthSecret.env("NARU_AUTH_SECRET"))       // AuthSecret(제안)
    .users(users)
    .build();

// 설정 파일을 쓰고 싶은 팀: 값 출처만 바꾼다. 모르는 키는 build()에서 예외
Properties p = new Properties();
try (InputStream in = new FileInputStream("auth.properties")) { p.load(in); }
Auth auth2 = Auth.builder(AuthSecret.file(new File(p.getProperty("naru.auth.secretFile"))))
    .apply(AuthSettings.fromProperties(p, "naru.auth."))             // AuthSettings(제안)
    .users(users)
    .build();
```

```kotlin
val auth = Auth.builder(AuthSecret.env("NARU_AUTH_SECRET"))
    .users(users)
    .signup(false)
    .build()
```

`AuthSettings.fromProperties`(제안)가 받는 키는 빌더 메서드와 1:1이다(`naru.auth.accessTtl=15m`, `naru.auth.signup=false`, `naru.auth.publicPaths=/health,/docs`). 모르는 키(`naru.auth.sigunp`)는 경고가 아니라 **예외**다. Spring의 `relaxed binding`처럼 조용히 넘어가면 주니어는 설정이 먹었다고 믿는다.

### 1.3 `install` — 설치를 한 줄로 (제안)

00의 통합 예제는 `app.use("/auth", auth.routes())`와 `app.use(auth)` 두 줄을 쓴다. 두 줄의 순서와 경로를 틀리는 것이 가장 흔한 실수라서, 한 번에 거는 `install`을 둔다. 두 줄 방식은 그대로 남는다.

```java
Auth auth = Auth.builder(AuthSecret.env("NARU_AUTH_SECRET")).users(users).build();
auth.install(app);   // = app.use(routesAt, auth.routes()); app.use(auth); app.onStart(auth::doctor)
```

`install`이 하는 일은 기존 API만 쓴다. `HttpRoutes.use(Object, Router)`, `RestApp.use(Middleware)`, `RestApp.onStart(LifecycleCallback)`. `install`은 앱이 `NEW`일 때만 부를 수 있고(기존 규칙), 두 번 부르면 `IllegalStateException`이다.

## 2. 기존 시스템에 맞추기

### 2.1 원칙

**어댑터는 "우리 DB 행 ↔ `AuthUser`" 변환 한 곳이다.** 프레임워크는 컬럼 이름을 모른다. 이름 매핑 DSL(`column("mem_id").as(USERNAME)`)은 두지 않는다. 리플렉션이 없고 R8에 안전한 이유(00 §4.1)가 그대로 적용되며, 실제 레거시는 이름만 다른 것이 아니라 표현이 다르기 때문이다('Y'/'N' 플래그, 비트마스크, CSV, 해시 접두사 없음).

### 2.2 ID 타입

`AuthUser.getId()`가 `String`인 것은 **유지한다.** JWT `sub`가 문자열이고(RFC 7519 §4.1.2), Gson이 숫자를 `Double`로 읽는 문제(2^53 초과 long 손실)를 피하며, long·int·UUID·문자열 키를 하나의 타입으로 받는다.

| DB 키 | `toAuthUser`에서 | `findById(String id)`에서 | 주의 |
|---|---|---|---|
| `BIGINT`/`INT` | `String.valueOf(rs.getLong("id"))` | `AuthIds.parseLong(id)`(제안)가 `null`이면 `return null` | 숫자가 아닌 id(`/users/abc`)는 404가 되어야 한다. `NumberFormatException`을 그대로 던지면 500이 된다 |
| `UUID`/`CHAR(36)` | `uuid.toString()`(소문자 표준형) | `AuthIds.parseUuid(id)`(제안) | 대문자 UUID와 소문자 UUID를 같은 사용자로 볼지 어댑터가 정한다. 표준형만 받는 것을 권한다 |
| `BINARY(16)` UUID | 16바이트 → 표준형 문자열 | 문자열 → 16바이트 | 변환 함수 하나 |
| 문자열 키(사번 `E0012`) | 그대로 | 그대로 | `sub`에 사번이 들어가므로 사번이 재사용되는 조직이면 내부 번호를 쓴다 |

`AuthIds`(제안)는 `@Nullable Long parseLong(String)`, `@Nullable Integer parseInt(String)`, `@Nullable UUID parseUuid(String)` 세 함수뿐이다. 앞자리 0, 부호, 공백을 거부해 `"007"`과 `"7"`이 같은 사용자를 가리키지 않게 한다.

### 2.3 로그인 키: username, email, phone

```java
Auth.builder(secret)
    .loginKey(LoginKey.EMAIL)                       // LoginKey(제안): USERNAME(기본) | EMAIL | PHONE | ANY
    .phoneRegion("+82")                             // PHONE/ANY일 때 0으로 시작하는 국내 번호의 국가 코드
    .normalizeLogin(raw -> raw.trim().toLowerCase(Locale.ROOT))   // 직접 정할 때(제안, @FunctionalInterface)
```

| 키 | 기본 정규화 | 근거 |
|---|---|---|
| USERNAME | trim → `Normalizer.normalize(NFKC)` → `toLowerCase(Locale.ROOT)` | 전각 문자·합자 변형으로 같은 이름이 둘 생기는 것을 막는다. `Locale.ROOT`가 없으면 터키어 기기에서 `"ADMIN".toLowerCase()`가 점 없는 ı를 만든다. `java.text.Normalizer`는 API 9부터 있다 |
| EMAIL | trim → 전체 소문자 | RFC 5321은 로컬 부분 대소문자를 구분하지만 실제 메일 서버는 거의 구분하지 않는다. Gmail의 점·`+태그` 제거는 하지 않는다(다른 사람의 주소가 될 수 있다) |
| PHONE | 숫자와 앞 `+`만 남김 → 0으로 시작하면 `phoneRegion`으로 바꿈 → E.164(`+821012345678`) | libphonenumber(수 MB)는 넣지 않는다. 정교한 검증은 앱이 한다 |
| ANY | `@`가 있으면 EMAIL, 숫자와 기호만이면 PHONE, 아니면 USERNAME | 레거시 회원 사이트의 "아이디 또는 이메일" 로그인 |

정규화된 키만 `UserStore.findByUsername(key)`에 들어간다. 어댑터는 같은 정규화로 저장된 컬럼과 비교해야 한다. 기존 DB에 대소문자만 다른 중복(`Kim@x.com`, `kim@x.com`)이 있으면 정규화가 두 계정을 하나로 합친다. 프레임워크는 DB를 훑을 수 없으므로 문서에 점검 SQL을 준다.

```sql
SELECT LOWER(TRIM(mem_email)) k, COUNT(*) FROM members GROUP BY k HAVING COUNT(*) > 1;
```

MySQL의 기본 `*_ci` 콜레이션은 이미 대소문자를 무시하므로 `WHERE mem_email = ?`가 그대로 맞는다. PostgreSQL은 `lower(email)` 함수 인덱스나 `citext`가 필요하다.

### 2.4 기존 비밀번호 해시: `PasswordHasher` 체인과 로그인 시 재해시

01 §3.6의 `PasswordHasher`(`hash`, `verify`, `needsRehash`)에 **접두사 판별** 메서드 하나를 더한다(제안).

```java
public interface PasswordHasher {
    boolean accepts(String stored);                 // 이 형식을 읽을 수 있나 (예: "$2a$", "pbkdf2-sha256$")
    String hash(char[] password);
    boolean verify(char[] password, String stored);
    boolean needsRehash(String stored);             // 기본 해시기가 아니면 프레임워크가 true로 본다
}
```

```java
Auth.builder(secret)
    .passwordHasher(PasswordHashers.pbkdf2())                // 새 해시는 언제나 이것(첫 번째)
    .legacyHasher(PasswordHashers.bcrypt())                  // 직접 구현, 외부 라이브러리 없음 (§2.4.1)
    .legacyHasher(PasswordHashers.digest("legacy-md5", "MD5", Hex.LOWER))   // 접두사 없는 32자 hex
```

로그인 흐름(프레임워크가 한다):

1. `stored = user.getPasswordHash()`. 체인에서 `accepts(stored)`가 참인 첫 해시기를 고른다. 없으면 로그인 실패(401)이고, 같은 접두사에 대해 **한 번만** ERROR 로그를 남긴다: `no PasswordHasher accepts stored hash format "$2y$…"(접두사 4자만)`. 해시 전체는 로그에 남기지 않는다.
2. `verify`가 성공하고 그 해시기가 기본 해시기가 아니거나 `needsRehash`가 참이면, 기본 해시기로 다시 해시해 `store.update(user.toBuilder().passwordHash(newHash).build())`를 부른다.
3. 재해시 `update`가 실패해도 로그인은 성공시킨다. 대신 WARN을 남긴다: `rehash failed for user 42: column too short? new hash is 107 chars`. 레거시 `VARCHAR(32)` 비밀번호 컬럼이 가장 흔한 원인이다.

옛 해시가 접두사 없이 저장돼 있으면 어댑터가 읽을 때 붙인다(`"legacy-md5$" + rs.getString("mem_pw")`). 쓸 때는 프레임워크가 만든 PBKDF2 문자열을 그대로 저장한다. 그래서 한 컬럼에 옛 형식과 새 형식이 섞여도 접두사로 구분된다.

| 레거시 | 처리 | 비고 |
|---|---|---|
| bcrypt(`$2a$`/`$2b$`/`$2y$`) | `PasswordHashers.bcrypt()`로 검증 → PBKDF2로 재해시. 또는 bcrypt를 기본으로 두고 그대로 유지 | **`utils.auth.password`에 직접 구현한다**(새 의존성 0개, §2.4.1). ~~외부 라이브러리를 감싸는 예제~~는 쓰지 않는다 |
| 솔트 없는 MD5/SHA-1/SHA-256 | `PasswordHashers.digest(prefix, algorithm, encoding)`(제안). `MessageDigest`는 API 1부터 | 검증은 상수 시간 비교. **이 해시기는 `hash()`를 지원하지 않는다**(새 비밀번호를 약한 형식으로 만들 수 없다) |
| 솔트 컬럼이 따로 있는 SHA-256 | 어댑터가 `"legacy-sha256$" + salt + "$" + hash`로 합쳐 넘기고, `PasswordHashers.saltedDigest(...)`(제안)가 `salt+pw` 또는 `pw+salt` 순서를 받는다 | 순서는 레거시 코드를 보고 정한다 |
| 로그인하지 않는 휴면 계정의 MD5 | **감싸기**(OWASP의 legacy hash wrapping): 배치로 `pbkdf2(md5hex)`를 계산해 `pbkdf2-md5$…`로 바꿔 두고, 로그인 때 `md5(pw)`를 PBKDF2로 검증한 뒤 일반 PBKDF2로 재해시 | 로그인을 기다리지 않고 DB 유출 위험을 바로 줄인다. https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#upgrading-legacy-hashes |
| 평문 비밀번호 | `PasswordHashers.plaintextForMigration()`(제안)이 받되 기동마다 WARN, `prod`에서는 doctor가 사용자 수와 함께 경고 | 일괄 감싸기를 먼저 권한다 |

#### 2.4.1 bcrypt 직접 구현 (2026-10-29 추가)

JDK에는 bcrypt가 없다. `javax.crypto`의 Blowfish는 쓸 수 없다. bcrypt는 비용만큼 키 설정을 되풀이하는 변형 Blowfish(EksBlowfish)라서 키 스케줄을 직접 다뤄야 하기 때문이다. 그래서 Blowfish부터 직접 구현한다. int 배열과 비트 연산만 쓰므로 Java 8과 API 21에서 문제가 없다. 크기는 상수 표를 빼고 300줄 안팎으로 본다.

| 부분 | 내용 |
|---|---|
| Blowfish 코어 | P 배열 18개, S-box 4×256개(파이 16진수 자리값 상수, 약 4 KB), 16라운드 |
| EksBlowfish | salt와 비밀번호로 키를 설정하고 `2^cost`번 되풀이한다 |
| 출력 | `"OrpheanBeholderScryDoubt"`를 64번 암호화한 뒤 23바이트로 자른다 |
| 해시 문자열 | bcrypt 전용 base64 알파벳(`./A-Za-z0-9`). `$2a$10$` + salt 22자 + 해시 31자 |

공개 API(제안): `PasswordHashers.bcrypt()`가 기본 상한으로 만든 `BcryptPasswordHasher`를 돌려준다. `BcryptPasswordHasher.builder().maxCost(14)`로 상한을 바꾼다. 위치는 `utils.auth.password`이고, Blowfish 코어는 `utils.auth.internal.Blowfish`(비공개)에 둔다.

규칙:

1. **변형 표기:** `$2a$`, `$2b$`, `$2y$`(PHP)는 같은 알고리즘으로 검증한다. 옛 crypt_blowfish 부호 확장 버그가 있던 `$2x$`는 `accepts`가 거부한다.
2. **72바이트 제한:** UTF-8 72바이트를 넘는 비밀번호는 기존 구현과 똑같이 잘라서 검증한다. 새 해시는 PBKDF2로 만들므로 재해시 뒤에는 이 제한이 사라진다.
3. **비용 범위:** 4~31이 형식상 유효하다. 기본 상한은 14다. 상한을 넘는 저장 해시는 검증하지 않고 거부한 뒤 ERROR를 한 번 남긴다. DB에 심긴 cost 31 해시로 CPU를 묶는 서비스 거부를 막기 위해서다.
4. **비교와 동시 실행:** 비교는 상수 시간(`MessageDigest.isEqual`)으로 한다. bcrypt 검증도 PBKDF2와 같은 해시 동시 실행 제한(00 R5, 넘으면 503)을 받는다.
5. **역할:** 기본은 레거시 검증기로 체인에 넣는다. `hash()`도 같은 함수라 지원하지만, 기본 해시기는 PBKDF2로 유지한다. FIPS 140과 NIST 인증 목록에 있는 것은 PBKDF2다.

검증:

- **정답:** OpenBSD와 jBCrypt가 공개한 테스트 벡터, PHP `password_hash`로 만든 `$2y$` 샘플, 72바이트 경계 비밀번호, 비ASCII 비밀번호와 비교한다.
- **거부:** `$2x$`, 상한을 넘는 cost, 길이가 틀린 salt·해시 문자열을 거부하는지 확인한다.
- **라이선스:** 논문(Provos·Mazières 1999, "A Future-Adaptable Password Scheme")과 OpenBSD 명세를 보고 새로 작성한다. jBCrypt(ISC)를 옮겨 오면 저작권 고지를 남겨야 하므로 옮겨 오지 않는다.
- **측정 공백:** Android 5 기기의 cost 10 소요 시간은 재지 않았다. 레거시 해시는 저장된 cost를 그대로 따를 수밖에 없으므로 동시 실행 제한으로 위험을 덮는다.

솔트 없는 MD5·SHA-1·SHA-256(`PasswordHashers.digest`)과 솔트 SHA-256(`saltedDigest`)은 `MessageDigest` 몇 줄이면 된다. bcrypt까지 넣으면 위 표의 레거시 형식을 모두 외부 의존 없이 처리한다.

### 2.5 기존 역할 컬럼

| 표현 | `toAuthUser` | 쓰기(`update`) |
|---|---|---|
| CSV 문자열 `'board,shop'` | `split(",")` 후 trim, 빈 값 제거 | `String.join(",", roles)` (`String.join`은 Java 8 API지만 Android API 26+. 그래서 `AuthStrings.join`(제안)을 쓴다) |
| 조인 테이블 `member_roles(mem_no, role)` | 두 번째 쿼리, 또는 MySQL `GROUP_CONCAT`, PostgreSQL `array_agg` | 트랜잭션으로 지우고 다시 넣기 |
| 비트마스크 `perm INT` | `RoleBits.of().bit(1, "user").bit(4, "staff").bit(8, "admin")`(제안)의 `decode(int)` | `encode(roles)`. 모르는 역할 이름은 예외 |
| 등급 숫자 `mem_level` 1/5/9 | `level >= 9 ? "admin" : level >= 5 ? "staff" : "user"` | 역할 → 등급 역변환을 어댑터가 정한다. 관리자 API로 역할을 바꾸지 않을 거면 `update`에서 역할을 무시하고 doctor 경고를 받는다 |

역할 이름은 03의 규칙(소문자)을 따른다. 레거시 역할 이름(`ROLE_ADMIN`, `관리자`)은 어댑터에서 바꾼다.

### 2.8 실전 예: 레거시 MySQL `members` → `UserStore`

```sql
-- 10년 된 회원 사이트의 흔한 모습
CREATE TABLE members (
  mem_no     INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  mem_id     VARCHAR(30)  NOT NULL UNIQUE,      -- 로그인 아이디
  mem_pw     VARCHAR(255) NOT NULL,             -- 옛 회원은 MD5 hex 32자, 최근 회원은 PHP bcrypt $2y$
  mem_email  VARCHAR(100),
  mem_hp     VARCHAR(20),                       -- '010-1234-5678'
  mem_level  TINYINT NOT NULL DEFAULT 1,        -- 1 회원, 5 직원, 9 관리자
  dept_cd    VARCHAR(10),
  use_yn     CHAR(1) NOT NULL DEFAULT 'Y',
  reg_dt     DATETIME
);
ALTER TABLE members ADD naru_token_ver INT NOT NULL DEFAULT 0;   -- 이 한 줄만 추가
```

```java
public final class MembersUserStore implements UserStore {
    private final DataSource ds;
    public MembersUserStore(DataSource ds) { this.ds = ds; }

    @Override public @Nullable AuthUser findByUsername(String key) {          // loginKey(ANY): 아이디·이메일
        return one("SELECT * FROM members WHERE (mem_id = ? OR mem_email = ?) AND use_yn = 'Y'", key, key);
    }
    @Override public @Nullable AuthUser findById(String id) {
        Long no = AuthIds.parseLong(id);
        return no == null ? null : one("SELECT * FROM members WHERE mem_no = ?", no);
    }
    @Override public AuthUser create(AuthUser u) {
        long no = insert("INSERT INTO members(mem_id, mem_pw, mem_email, mem_level) VALUES (?,?,?,?)",
            u.getUsername(), u.getPasswordHash(), u.getAttributes().get("email"), level(u.getRoles()));
        return u.toBuilder().id(String.valueOf(no)).build();
    }
    @Override public AuthUser update(AuthUser u) {
        exec("UPDATE members SET mem_pw=?, mem_level=?, use_yn=?, naru_token_ver=? WHERE mem_no=?",
            u.getPasswordHash(), level(u.getRoles()), u.isEnabled() ? "Y" : "N",
            u.getTokenVersion(), Long.parseLong(u.getId()));
        return u;
    }
    @Override public void delete(String id) { exec("UPDATE members SET use_yn='N' WHERE mem_no=?", Long.parseLong(id)); }
    @Override public int countByRole(String role) {                         // 첫 관리자 판단용(§4, 제안)
        return "admin".equals(role) ? count("SELECT COUNT(*) FROM members WHERE mem_level >= 9 AND use_yn='Y'") : -1;
    }

    private static AuthUser toAuthUser(ResultSet rs) throws SQLException {   // 매핑은 여기 한 곳
        String pw = rs.getString("mem_pw");
        int level = rs.getInt("mem_level");
        return AuthUser.builder()
            .id(String.valueOf(rs.getLong("mem_no")))
            .username(rs.getString("mem_id"))
            .passwordHash(pw.matches("[0-9a-f]{32}") ? "legacy-md5$" + pw : pw)   // 접두사 없는 MD5에 표시
            .roles(level >= 9 ? "admin" : level >= 5 ? "staff" : "user")
            .enabled("Y".equals(rs.getString("use_yn")))
            .tokenVersion(rs.getLong("naru_token_ver"))
            .attribute("email", rs.getString("mem_email"))
            .attribute("dept", rs.getString("dept_cd"))
            .build();
    }
    private static int level(List<String> roles) { return roles.contains("admin") ? 9 : roles.contains("staff") ? 5 : 1; }
    // one/insert/exec/count: JDBC 보일러플레이트 20줄 (생략)
}
```

```java
Auth auth = Auth.builder(AuthSecret.env("NARU_AUTH_SECRET"))
    .users(new MembersUserStore(ds))
    .loginKey(LoginKey.ANY)
    .legacyHasher(PasswordHashers.digest("legacy-md5", "MD5", Hex.LOWER))
    .legacyHasher(PasswordHashers.bcrypt())    // $2y$(PHP 표기)도 그대로 검증한다 (§2.4.1)
    .roles(RolePolicy.builder().role("admin", "*").role("staff", "board:*").role("user", "board:read").build())
    .groups(new DeptGroupStore(ds))
    .build();
```

이 어댑터에서 `VARCHAR(255)` 비밀번호 컬럼은 PBKDF2 문자열(약 100자)을 받는다. 32자 컬럼이면 재해시가 실패하고 §2.4의 WARN이 나온다.

### 3.2 `FileUserStore` (제안, `utils` 안)

- 한 파일에 사용자 전체를 담는다. 형식은 줄마다 사용자 하나, 필드는 퍼센트 인코딩한 탭 구분이다. JSON을 쓰지 않는 이유는 `JsonCodec`을 앱에서 얻을 공개 경로가 없고(1.1), 이 파일은 사람이 고치는 설정이 아니라 저장소이기 때문이다.
- 쓰기는 같은 폴더의 임시 파일에 쓰고 `FileOutputStream.getFD().sync()` 후 `File.renameTo`로 바꾼다. 같은 폴더 안 rename은 Android(ext4/f2fs)와 일반 리눅스에서 원자적이다. Windows는 `renameTo`가 기존 파일을 덮지 못하므로 지우고 바꾸는 대체 경로와 `.bak`을 둔다.
- 모든 쓰기는 하나의 잠금으로 직렬화하고 메모리 사본을 읽기에 쓴다. 1,000명을 넘으면 doctor가 "DB store를 쓰라"고 WARN한다(쓰기마다 전체 파일을 다시 쓰기 때문).
- `FileGroupStore`도 같은 형식으로 둔다(그룹·중첩 몇백 개 규모).

### 3.3 참조 DDL과 `JdbcUserStore` (제안, `NaruServe-utils-jdbc`)

```sql
-- PostgreSQL (MySQL/MariaDB, SQLite 판을 같은 이름으로 docs에 둔다)
CREATE TABLE naru_users (
  id             BIGSERIAL PRIMARY KEY,
  username       VARCHAR(190) NOT NULL UNIQUE,   -- 정규화된 로그인 키. 190은 MySQL utf8mb4 인덱스 한도를 맞춘 값
  password_hash  VARCHAR(255) NOT NULL,
  roles          VARCHAR(1000) NOT NULL DEFAULT '',
  enabled        BOOLEAN NOT NULL DEFAULT TRUE,
  token_version  BIGINT  NOT NULL DEFAULT 0,
  attributes     TEXT    NOT NULL DEFAULT ''      -- 추가 필드(퍼센트 인코딩 key=value&...)
);
CREATE TABLE naru_groups        (id VARCHAR(190) PRIMARY KEY);
CREATE TABLE naru_group_members (group_id VARCHAR(190), user_id VARCHAR(190), PRIMARY KEY (group_id, user_id));
CREATE TABLE naru_group_parents (child_id VARCHAR(190), parent_id VARCHAR(190), PRIMARY KEY (child_id, parent_id));
```

```java
JdbcUserStore users = JdbcUserStore.builder(dataSource)
    .dialect(JdbcDialect.POSTGRESQL)          // MYSQL, SQLITE(JVM sqlite-jdbc용)
    .table("naru_users")                      // 접두사만 바꾸는 팀이 많다
    .build();
String ddl = users.ddl();                     // 적용은 Flyway/Liquibase/DBA가 한다
```

- **자동으로 테이블을 만들지 않는다.** better-auth의 `migrate`도 한 어댑터만 지원하고, 운영 DB의 스키마 변경은 팀의 마이그레이션 도구가 소유한다. 개발용으로 `users.createTablesIfMissing()`만 두고, `prod` 프로필에서 부르면 WARN을 남긴다.
- 컬럼 이름 매핑 옵션은 두지 않는다. 다른 이름이 필요하면 §2.8처럼 어댑터를 쓴다. 매핑 옵션을 두면 레거시 표현 차이(2.1)까지 옵션으로 늘어나기 때문이다.

### 3.4 Android SQLite는 문서 예제로

`android.*`는 `utils`에 들어갈 수 없다(CLAUDE.md). v1은 `SQLiteOpenHelper`나 Room DAO로 `UserStore`를 구현하는 40줄 예제를 `docs/api/`에 둔다. Room 예제는 01 §3.5의 `RoomUserStore`를 그대로 쓴다. 수요가 확인되면 `NaruServe-android`에 `SqliteUserStore`를 넣는다(Q3).

## 4. 첫 관리자 만들기

### 4.1 위험 모델

- **선점 경쟁**: 첫 등록자를 관리자로 삼으면, LAN의 다른 기기나 스캐너가 주인보다 먼저 `/setup`을 칠 수 있다. 기기 서버는 `bindAddress("0.0.0.0")`로 같은 Wi-Fi에 열리는 일이 흔하다.
- **노출**: 로그에 찍은 토큰은 로그를 볼 수 있는 사람에게 보인다. JVM에서는 서버 로그 파일과 수집기, Android에서는 `adb logcat`(USB 디버깅이 켜진 기기)과 버그 리포트다. 다른 앱은 Android 4.1부터 남의 로그를 읽지 못한다.
- **잔존**: 환경변수 비밀번호가 컨테이너 설정, 셸 기록, 프로세스 환경(`/proc/<pid>/environ`)에 남는다.
- **동시성**: 설정 요청 두 개가 동시에 와서 관리자가 둘 생길 수 있다.

### 4.2 후보 비교

| 방식 | 선점 경쟁 | 노출 | Android | 판정 |
|---|---|---|---|---|
| 환경변수 `NARU_ADMIN_USERNAME`/`NARU_ADMIN_PASSWORD` | 없음 | 환경변수 잔존 | 환경변수 없음 → 코드로 대체 | **JVM 기본 1순위** |
| 코드 `bootstrapAdmin(username, password)` | 없음 | 소스·APK에 비밀번호가 박힐 위험 | 사용자 입력(첫 화면)을 넘길 때 좋다 | **Android 1순위** |
| 일회용 설정 토큰(로그+파일) + `POST /auth/setup` | 토큰이 막는다 | 로그 열람자 | 앱이 토큰을 화면에 보여 준다 | **나머지 경우 기본** |
| 토큰 없는 첫 실행 엔드포인트(Strapi형) | **있다** | — | — | 채택 안 함 |
| CLI | 없음 | 셸 기록 | 해당 없음(기기에 셸이 없다) | 비채택. 라이브러리라 실행 진입점이 앱 것이다 |

### 4.3 권고 흐름 (제안)

```
기동(onStart, doctor 안)
 ├─ store.countByRole(adminRole) > 0  → 끝. /auth/setup은 404
 ├─ NARU_ADMIN_PASSWORD(또는 bootstrapAdmin(...))가 있다 → 관리자 생성, 끝
 │     · 다음 기동부터 그 값이 여전히 있으면 WARN "remove NARU_ADMIN_PASSWORD"(Keycloak 임시 관리자 배너와 같은 뜻)
 │     · 이미 관리자가 있으면 값을 무시한다(비밀번호를 덮어쓰지 않는다)
 ├─ countByRole이 -1(모름) → 자동 판단 불가. setup 모드를 열지 않고 WARN, bootstrapAdmin을 안내
 └─ 관리자 없음 → 설정 토큰 생성
       · 128비트 SecureRandom, base64url 22자
       · WARN 로그 한 줄 + dataDir/setup-token 파일(있으면) + auth.setupToken() getter
       · 유효: 30분 또는 프로세스 종료까지. 재시작하면 새 토큰
```

```
POST /auth/setup   {"token":"…", "username":"admin", "password":"…"}
 · 기본은 루프백(req.remoteAddress()가 127.0.0.1/::1)에서만. 아니면 404
   (LAN에서 받아야 하면 setupFromNetwork(true)를 명시. 그래도 토큰은 필요하다)
 · 토큰 비교는 상수 시간, 5회 틀리면 토큰 폐기(새 토큰은 재시작해야 생긴다)
 · 하나의 잠금 안에서: countByRole 재확인 → create(roles=[admin]) → 토큰 폐기
 · 성공하면 201 + 토큰 쌍(바로 로그인 상태). 이후 /auth/setup은 영구 404
```

```java
// Android: 앱의 첫 실행 화면이 PIN·비밀번호를 받아 넘긴다
Auth auth = Auth.builder(AuthSecret.file(new File(context.getFilesDir(), "naru-auth.key")))
    .users(new FileUserStore(new File(context.getFilesDir(), "users.db")))
    .bootstrapAdmin("admin", passwordFromFirstRunScreen)       // 관리자가 이미 있으면 무시
    .build();

// 또는 화면에 설정 토큰을 보여 주고 같은 기기 브라우저에서 /auth/setup
String token = auth.setupToken();   // @Nullable: 설정 모드가 아니면 null
```

```kotlin
val auth = Auth.builder(AuthSecret.env("NARU_AUTH_SECRET"))
    .users(users)
    .build()
auth.install(app)
// 로그: WARN  No admin user yet. Setup token (valid 30 min, loopback only): q3V…Zw
//       curl -X POST http://127.0.0.1:8080/auth/setup -d '{"token":"q3V…Zw","username":"admin","password":"…"}'
```

`countByRole`은 `UserStore`에 더하는 `default` 메서드다(제안, 기본 `-1` = 모름). 00이 정한 필수 메서드 5개를 늘리지 않으면서 첫 관리자 자동 판단이 필요한 store만 구현한다. `InMemoryUserStore`, `FileUserStore`, `JdbcUserStore`는 구현한다. 01 Q7의 `list(offset, limit)`와 같은 방식(선택 default)이다.

## 5. 비밀키와 키 관리

### 5.1 출처 `AuthSecret` (제안)

| 팩토리 | 동작 | 프로필 |
|---|---|---|
| `AuthSecret.of(String)` | 값 그대로(00의 `Auth.builder(String)`과 같음) | 둘 다 |
| `AuthSecret.env(name)` | `System.getenv(name)`. 없거나 비면 **예외 메시지에 변수 이름을 넣어** 던진다 | 둘 다 |
| `AuthSecret.file(File)` | 파일이 있으면 읽고, 없으면 32바이트를 만들어 저장한다(첫 기동 한 번) | 둘 다 |
| `AuthSecret.generated()` | 메모리에만 임의 키. 재시작하면 모든 토큰이 무효 | **dev만**. `prod`에서 build 예외 |

- `file`은 JVM에서는 앱이 정한 경로, Android에서는 개발자가 넘기는 `context.getFilesDir()` 아래다. 모듈은 `android.*`를 몰라도 된다. 새 파일은 `File.setReadable(false, false)` → `setReadable(true, true)`로 소유자 전용으로 만들고(Android 앱 폴더는 원래 앱 전용), JVM에서 다른 사용자가 읽을 수 있는 권한이면 doctor가 WARN한다. 쓰기는 §3.2처럼 임시 파일 → rename이고, 이미 있는 파일은 절대 덮지 않는다.
- Android Keystore는 v1 기본으로 쓰지 않는다. HMAC 키를 Keystore에서 만드는 `KeyGenParameterSpec`이 API 23부터이고, API 21~22에서는 RSA만 된다. 기기 루팅 위협까지 막아야 하는 앱은 `AuthSecret.of(...)`에 Keystore로 감싼 키를 직접 넘기면 된다(예제만 둔다).
- 파일과 키를 백업에서 빼라고 문서에 쓴다. Android 자동 백업이 `files/`를 다른 기기로 복원하면 같은 서명 키를 쓰는 두 서버가 생긴다.

### 5.2 약하거나 예제인 비밀키 거부

`build()`가 `IllegalArgumentException`을 던지는 조건:

- UTF-8 32바이트 미만(01 §2.2).
- 문서·예제에 나온 문자열과 흔한 값: `secret`, `changeme`, `change-me-now`, `your-256-bit-secret`(jwt.io 예제), 문서 샘플 상수 `AuthSecret.DOCS_SAMPLE`과 같은 값. 문서의 모든 예제는 일부러 이 샘플만 써서, 복사해 붙인 코드가 그대로 운영되지 않게 한다.
- 문자 종류가 극단적으로 적은 값(서로 다른 바이트 8개 미만, 예: `aaaa…`).

예외 메시지는 다음 행동을 알려 준다: `NARU_AUTH_SECRET is 12 bytes; need ≥ 32. Generate one: openssl rand -base64 32` (better-auth 문서와 같은 안내).

### 5.3 키 교체

01 §2.5의 `kid` 키 세트를 그대로 쓴다. 파일 출처에는 교체 도우미를 둔다(제안).

```java
Auth.builder(AuthSecret.rotating(new File(dataDir, "naru-auth.keys")))   // 여러 kid를 한 파일에 보관
// auth.rotateKey(): 새 kid 생성·서명키 전환, 이전 키는 refresh 최대 수명(14일) 뒤 자동 제거
```

환경변수 출처는 사람이 교체한다(`NARU_AUTH_SECRET`=새 키, `NARU_AUTH_SECRET_PREVIOUS`=이전 키). 두 변수를 읽는 것은 `AuthSecret.env`가 알아서 한다(제안).

### 5.4 dev와 prod

| | `AuthProfile.DEV`(제안) | `AuthProfile.PROD`(기본) |
|---|---|---|
| 비밀키 없음 | 임시 키 + WARN "개발용, 재시작하면 로그아웃" | build 예외 |
| 비루프백 요청 | **403**(Auth 미들웨어가 `req.remoteAddress()`로 거부) | 정상 처리 |
| doctor WARN 항목 | WARN 그대로 | 일부를 FAIL로 올림(§6.2) |
| `InMemoryUserStore` | 정상 | WARN "재시작하면 사용자를 잃는다" |
| `createTablesIfMissing` | 정상 | WARN |

프로필은 코드로 정하거나 `NARU_PROFILE=dev` 환경변수로 정한다(Android는 코드로, 예: `BuildConfig.DEBUG ? DEV : PROD`). dev가 루프백만 받게 한 이유는 dev 설정이 실수로 LAN이나 운영에 나가도 원격에서 쓸 수 없게 하려는 것이다. Spring의 생성 비밀번호는 "개발용"이라고 말할 뿐 막지 않는다.

## 6. 기동 자기 점검(doctor)

### 6.1 언제 도나

`auth.install(app)`이 `app.onStart(auth::doctor)`를 건다. lifecycle.md에 따라 `onStart`는 `listen()` 안에서 **포트를 열기 전에** 돌고, 여기서 예외가 나면 포트를 열지 않고 정리한 뒤 `listen()`이 그 예외(`AppStartException`)를 던진다. 그래서 FAIL은 "서버가 잘못된 설정으로 한 번도 요청을 받지 않는다"는 뜻이 된다. `install` 없이 두 줄로 붙인 앱은 `auth.doctor(ctx)`를 직접 `onStart`에 걸거나, 첫 요청 때 같은 점검을 한 번 돌린다(이때는 WARN만, 멈출 수 없다).

doctor가 지금 Core에서 알 수 없는 것이 둘 있다. 각각 Core 변경이고 별도 SRS가 필요하다(00 §6에 추가).

| 알고 싶은 것 | 지금 | 필요한 Core 변경(제안) | 없을 때 |
|---|---|---|---|
| 바인딩 주소(루프백인가) | `ServerSettings`는 SPI라 앱이 읽을 수 없고 `ServerHandle.address()`는 바인딩 뒤에야 있다 | `ApplicationContext`에서 설정된 바인딩 주소를 읽는 읽기 전용 접근자 | 첫 비루프백 요청에서 판단 |
| 가드 없는 라우트 | 라우트 목록 API 없음 | 00 §6의 읽기 전용 라우트 목록 | 첫 요청 때 경고(03 §7.2) |

### 6.2 항목과 판정

| 항목 | 점검 | DEV | PROD |
|---|---|---|---|
| 비밀키 | 출처, 길이, 예제 값, 파일 권한 | build 예외(약함) / WARN(생성) | build 예외 |
| 사용자 저장소 | 종류, `findByUsername("__naru_probe__")`가 예외 없이 `null`을 돌려주는지(연결·SQL 오류를 기동에 잡는다) | FAIL | FAIL |
| 저장소 종류 | `InMemoryUserStore`, 1,000명 넘는 `FileUserStore` | OK / WARN | WARN |
| 관리자 | `countByRole`, 부트스트랩 변수 잔존 | INFO | WARN |
| 공개 경로 | 목록 출력. `/`나 `/*`, `/api`처럼 넓은 prefix | WARN | **FAIL**(`allowBroadPublicPaths(true)`로 해제) |
| 라우트 마운트 | `routesAt`과 실제 마운트, 로그인 경로가 공개인지 | FAIL | FAIL |
| 가입 | on/off, 허용 속성 목록 | INFO | WARN(켜져 있으면) |
| 해시 비용 | 이 기기에서 잰 1회 검증 시간(§7.1) | INFO | 1초 넘으면 WARN, 반복 수가 100,000 미만이면 WARN |
| 레거시 해시기 | 등록된 접두사, 평문 이관 해시기 | INFO | WARN(평문·MD5) |
| 역할 정책 | `*` 부여 역할, 어떤 역할도 주지 않는 `require` 스코프(03 §3.2) | WARN | WARN |
| 시계 | 현재 시각이 모듈 빌드 시각보다 이른지(§7.2) | WARN | WARN |
| HTTP | `refreshCookie(true)` + 비루프백 + `trustProxy` 없음(Secure 쿠키가 평문 HTTP로 안 간다) | WARN | WARN |
| 키 교체 | 만료가 지난 verify 전용 키 | INFO | INFO |

출력은 한 블록이다. 비밀값은 출처와 길이만 보인다.

```
NaruServe auth doctor (profile=PROD)
  OK    secret        env NARU_AUTH_SECRET, 44 bytes, kid=default
  OK    users         MembersUserStore (probe 3 ms)
  WARN  admin         NARU_ADMIN_PASSWORD is still set; remove it after first start
  OK    routes        /auth (login, refresh, logout, me, password); signup OFF
  OK    public        /auth/login, /auth/refresh, /health
  OK    hashing       pbkdf2-sha256 600000 iter = 212 ms on this machine; legacy: legacy-md5, $2y$

  INFO  guards        route list unavailable; unguarded routes are reported on first request
  RESULT 0 FAIL, 2 WARN
```

FAIL이 하나라도 있으면 같은 블록을 ERROR로 찍고 `AuthConfigException`(제안, unchecked)을 던진다. WARN은 `doctor(DoctorPolicy.STRICT)`(제안)로 FAIL로 올릴 수 있다. CI에서 쓰라고 둔 옵션이다.

## 7. Android 특이사항

### 7.1 해시 비용 측정

01 Q2의 답이다. 600,000회는 최근 PC에서 약 0.1~0.3초지만, `Mac.doFinal`을 반복마다 부르는 직접 구현은 Android 5 시절 저가 기기(Cortex-A7급)에서 수 초가 걸릴 것으로 **추정**한다(측정 전). 그래서 고정값 대신 측정한다(제안).

```java
Auth.builder(secret)
    .hashCost(HashCost.calibrate(250, TimeUnit.MILLISECONDS))   // 기본: JVM은 고정 600,000, Android 프로필은 calibrate
    // .hashCost(HashCost.fixed(600_000))
```

- 방법: doctor 안에서 20,000회를 한 번 데워 버리고 다시 20,000회를 재서 1회당 시간을 구한 뒤 목표 시간에 맞는 반복 수를 계산한다. 10,000 단위로 내림하고 **하한 100,000**(그 아래면 WARN과 함께 하한을 쓴다), **상한 2,000,000**으로 자른다. 측정은 약 50~200 ms로, 기동 시간에 더해진다.
- 결과 반복 수는 해시 문자열에 이미 들어간다(`pbkdf2-sha256$<iter>$…`). 그래서 다른 기기로 DB를 옮겨도 검증이 되고, 기기를 바꿔 측정값이 올라가면 다음 로그인에서 `needsRehash`가 참이 되어 자동으로 올라간다. 측정값이 내려가도 해시를 낮추지는 않는다.
- 측정값을 `dataDir`에 저장해 두고(있으면) 다음 기동에는 그 값을 쓴다. 측정이 기기 부하 순간에 걸려 값이 크게 흔들리는 것을 막는다.
- 로그인 동시 실행 제한: 250 ms 해시가 64개 작업 스레드에서 동시에 돌면 저사양 기기가 멈춘다. 해시 동시 실행 수를 `hashConcurrency(n)`(제안, 기본 CPU 코어 수, 최대 8)으로 묶고, 기다리는 요청이 그 4배를 넘으면 503 + `Retry-After`로 답한다. 무차별 대입 제한(01 §5)과 별개인 자원 보호다.

### 7.2 시계가 틀린 기기

발급과 검증을 같은 서버가 하므로 서버 간 시계 차이는 없다. 문제는 **기기 시계가 뛰는 것**이다. 네트워크 없는 키오스크는 배터리가 빠지면 2000년이나 1970년으로 돌아가고, 사용자가 시간을 손으로 바꾸기도 한다.

| 상황 | 증상 | 대응(제안) |
|---|---|---|
| 시계가 뒤로 감 | 이미 낸 토큰의 `iat`가 미래 → leeway 밖이면 401 | 클라이언트는 다시 로그인한다. 정상 동작으로 둔다 |
| 시계가 앞으로 감 | 모든 토큰 즉시 만료, refresh도 만료 | 같음. 단 refresh 14일이 하루아침에 끝난다 |
| 시계가 아주 과거(빌드 시각보다 이전) | 위 둘 + 키 교체 일정이 틀어짐 | doctor WARN `device clock 2000-01-01 is before module build 2026-10; tokens will misbehave` |
| 실행 중 시계 점프 | — | `TimeSource` 기본 구현이 `System.currentTimeMillis()` 차이와 `System.nanoTime()` 차이를 비교해 5분 넘게 어긋나면 한 번 WARN |

토큰 시간을 `nanoTime` 기준으로 바꾸는 것은 하지 않는다. 재시작하면 기준이 사라져 14일 refresh를 표현할 수 없기 때문이다.

### 7.3 단일 사용자 기기 관리자: PIN 모드 (제안)

키오스크·POS 기기의 관리 페이지에는 사용자가 한 명뿐이고, 사람은 기기 앞에서 PIN을 누른다.

```java
Auth auth = Auth.builder(AuthSecret.file(new File(filesDir, "naru-auth.key")))
    .devicePin(new File(filesDir, "pin.db"))      // 사용자 store 대신 PIN 하나. 첫 설정은 bootstrapAdmin 또는 setup 토큰
    .build();
```

- PIN은 **6자리 이상**만 받는다. 6자리는 100만 경우뿐이라 오프라인 대입(파일 유출)에는 PBKDF2를 써도 약하므로, PIN 파일은 앱 전용 폴더에만 두고 백업에서 뺀다고 문서화한다.
- 온라인 대입 방지: 5회 실패하면 1분, 그다음부터 실패마다 두 배(최대 1시간) 잠근다. 잠금 상태는 **파일에 저장해** 재시작으로 풀리지 않게 한다.
- 기본 바인딩이 루프백이라 PIN 로그인은 기기 안 WebView·브라우저에서만 된다. LAN에서 PIN 로그인을 받으려면 `bindAddress`와 함께 `devicePinFromNetwork(true)`를 명시해야 한다.
- 내부적으로는 사용자 `admin` 하나짜리 `UserStore`라서 토큰·가드·`auth.user(req)`는 그대로다.

### 7.4 네트워크 없이

모듈은 외부 호출을 하지 않는다(JWKS 조회, 침해 비밀번호 API, 시간 서버 모두 없음). 오프라인 기기에서 바뀌는 것은 시계뿐이고 §7.2가 다룬다. 연구 07의 OIDC 연동은 네트워크가 필요하므로 기기 프로필과 같이 쓰면 doctor가 INFO로 알린다.

### 8.2 실제 DB 연결하기 (약 20줄)

`FileUserStore`를 `UserStore` 구현으로 바꾸면 끝이다. 라우트 코드는 바뀌지 않는다.

```kotlin
class MyUserStore(private val ds: DataSource) : UserStore {
    override fun findByUsername(username: String) =
        query("SELECT * FROM users WHERE lower(email) = ?", username)
    override fun findById(id: String) = AuthIds.parseLong(id)?.let { query("SELECT * FROM users WHERE id = ?", it) }
    override fun create(user: AuthUser): AuthUser {
        val id = insert("INSERT INTO users(email, pw, roles) VALUES (?,?,?)", user.username, user.passwordHash, user.roles.joinToString(","))
        return user.toBuilder().id(id.toString()).build()
    }
    override fun update(user: AuthUser): AuthUser {
        exec("UPDATE users SET pw=?, roles=?, active=?, ver=? WHERE id=?",
            user.passwordHash, user.roles.joinToString(","), user.isEnabled, user.tokenVersion, user.id!!.toLong())
        return user
    }
    override fun delete(id: String) { exec("DELETE FROM users WHERE id=?", id.toLong()) }
    override fun countByRole(role: String) = count("SELECT COUNT(*) FROM users WHERE roles LIKE ?", "%$role%")

    private fun ResultSet.toAuthUser() = AuthUser.builder()
        .id(getLong("id").toString()).username(getString("email")).passwordHash(getString("pw"))
        .roles(*getString("roles").split(',').filter { it.isNotBlank() }.toTypedArray())
        .enabled(getBoolean("active")).tokenVersion(getLong("ver")).build()
}
// Auth.builder(...).users(MyUserStore(ds)).loginKey(LoginKey.EMAIL)
```

(`query`/`insert`/`exec`/`count`는 JDBC 도우미. `roles LIKE`는 예제용이며 `editor`와 `editor2`를 구분하지 못하므로 실제로는 조인 테이블을 권한다.)

### 8.3 가장 흔한 설정 실수 10가지와 모듈의 감지

| # | 실수 | 모듈의 감지·대응 | 시점 |
|---|---|---|---|
| 1 | 비밀키 환경변수를 설정하지 않음(`getenv`가 `null`) | `AuthSecret.env`가 변수 이름과 생성 명령을 담은 예외 | build |
| 2 | 문서 예제·짧은 비밀키를 그대로 씀 | 32바이트·예제 목록·문자 종류 검사(§5.2) | build |

## 9. 시스템 규모별 설정 스펙트럼

같은 `Auth.builder`를 쓰고 바꾸는 것만 다르다. 앞 단계의 코드는 다음 단계에서도 그대로 돈다.

| | 개인·주니어 앱 | Android 기기 서버 | 기존 DB가 있는 중견 회사 | 엔터프라이즈 |
|---|---|---|---|---|
| 비밀키 | `AuthSecret.env` 또는 `file` | `AuthSecret.file(filesDir/…)` | `env`(비밀 관리 도구가 주입), 이전 키 변수로 교체 | `rotating` 또는 07의 외부 키·JWKS |
| 사용자 저장소 | `FileUserStore` | `FileUserStore`, 사용자 하나면 `devicePin` | 레거시 테이블 어댑터(§2.8) | 07: LDAP/OIDC 신원 + 로컬 store는 비상 관리자만 |
| 첫 관리자 | 설정 토큰(루프백) | 첫 실행 화면 → `bootstrapAdmin` | `NARU_ADMIN_PASSWORD` 또는 기존 관리자 그대로 | IdP 그룹 매핑(07) |
| 해시 | 기본 | `HashCost.calibrate(250ms)`, `hashConcurrency(2)` | `legacyHasher` 체인 + 재해시 | IdP가 맡음 |
| 역할·그룹 | `RolePolicy` 코드 표 | `RolePolicy` 두세 줄 | `RolePolicy` + 부서 `GroupStore` | `RoleStore`(DB) + IdP 그룹(07) |
| 네트워크 | 루프백 | 루프백, LAN이면 `bindAddress` + `allowedHosts` | 리버스 프록시 + `trustProxy` | 같음 + 클러스터(07) |
| doctor | 기본 | 기본(시계·해시 비용 확인) | `DoctorPolicy.STRICT`를 CI에서 | STRICT + 07의 점검 |
| 바꾸는 줄 수(앞 단계 대비) | — | 3~4줄 | store 클래스 하나 + 2~3줄 | 07 참조 |

```java
// Android 기기 서버 (Service 안, 작업 스레드)
File dir = getFilesDir();
Auth auth = Auth.builder(AuthSecret.file(new File(dir, "naru-auth.key")))
    .users(new FileUserStore(new File(dir, "users.db")))
    .hashCost(HashCost.calibrate(250, TimeUnit.MILLISECONDS))
    .hashConcurrency(2)
    .bootstrapAdmin("admin", firstRunPassword)          // null이면 setup 토큰 모드
    .profile(BuildConfig.DEBUG ? AuthProfile.DEV : AuthProfile.PROD)
    .build();
auth.install(app);
```

엔터프라이즈는 이 문서의 비밀키 거부, doctor, 첫 관리자 규칙을 그대로 쓰고, 신원 출처·테넌트·노드 간 상태(로그인 제한, 키 교체 동기화)는 연구 07을 따른다. 07이 `UserStore` 대신 다른 신원 SPI를 정하면 §6.2의 "사용자 저장소" 점검을 그 SPI에 맞춘다.

## 11. 미결 질문

1. **Core 읽기 API 두 개**: 바인딩 주소 접근자와 라우트 목록(§6.1). 없으면 doctor의 두 항목이 첫 요청으로 밀린다. 별도 SRS가 필요하다.
2. **`JsonCodec` 접근**: `RestApp`에 codec getter가 없어 `FileUserStore`가 자체 줄 형식을 쓴다. 01 Q1의 JWT 파싱도 같은 문제라, `ApplicationContext`에 codec을 서비스로 등록하는 Core 변경을 함께 검토한다.
3. **Android SQLite store**: `NaruServe-android`에 넣을지, 문서 예제로 둘지. 수요를 보고 정한다.
4. **`NaruServe-utils-jdbc`를 둘지**: 참조 DDL만 주고 JDBC 구현은 빼는 것이 더 작다. 중견 회사 단계에서 실제로 쓰일지가 관건이다.
5. **PBKDF2 측정값**: 하한 100,000이 OWASP 권고(600,000)보다 낮다. 저가 기기 실측 뒤 하한과 목표 시간(250 ms)을 확정한다. Android 기기 검증은 v1 범위 밖이므로(사용자 결정) 측정은 JVM 수치와 문서화된 추정에 머문다.
6. **설정 토큰을 파일에도 쓸지**: Jenkins처럼 파일에 쓰면 로그 수집기를 거치지 않고 꺼낼 수 있지만, `dataDir`을 정하지 않은 앱에는 쓸 곳이 없다. `dataDir`이 있을 때만 쓰는 안을 제안했다.
7. **PIN 모드의 최소 길이**: 6자리 숫자가 키오스크 현장에서 받아들여질지, 영문 혼합을 요구할지.
8. **`countByRole`의 이름과 모양**: `hasAdmin()` 같은 boolean이 더 단순하지만 "모름"을 표현하려면 `Boolean`(nullable)이 되어 Kotlin에서 어색하다. `int`와 `-1`로 제안했다.
9. **dev 프로필의 루프백 강제**: 같은 LAN의 휴대폰으로 개발 중인 앱을 시험하는 경우를 막는다. `devAllowNetwork(true)` 같은 탈출구를 둘지.
10. **연구 07과의 경계**: IdP를 쓰는 앱에서 로컬 비상 관리자를 기본으로 둘지, doctor가 OIDC 설정(발급자 도달 가능성)을 기동 때 확인할지.

## 검증 한계

- Spring Boot, Django, Keycloak, Jenkins, PocketBase, Strapi, better-auth, Laravel, Supabase 문서는 이번에 직접 열어 확인했다. Firebase 해시 가져오기 URL과 Android Keystore HMAC의 API 23 시작은 기억에 따른 것이다(Keystore 공식 문서는 알고리즘별 API 레벨을 적지 않는다).
- PBKDF2 시간, `FileUserStore` 규모 한계(1,000명)는 측정하지 않은 추정이다.
- `HttpRoutes.use`, `RestApp.use`, `onStart`, `ServerHandle.address()`, `Request.remoteAddress()`, `RestApp`에 codec getter가 없다는 점, `ServerSettings`가 SPI라는 점은 코드에서 확인했다. 나머지 이름은 모두 제안이다.
