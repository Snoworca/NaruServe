## 0. 요약 (권고 5줄)

1. **JWT는 직접 구현한다**(`javax.crypto.Mac` HmacSHA256 + 자체 base64url, 300줄 안팎). jjwt·java-jwt·nimbus는 API 21·Gson 2.14 고정·의존 무게 중 하나 이상에 걸린다. v1 알고리즘은 **HS256 하나**이고, `kid` 키 세트로 키를 교체한다. RS256은 슬롯만 남긴다.
2. **access 15분(JWT, stateless) + refresh 14일(JWT, `ver` 검사)**. 로그아웃·비밀번호 변경은 사용자의 `tokenVersion`을 올려 refresh를 무효로 만든다. 기기별 로그아웃은 v2로 미룬다.
3. 프레임워크가 **REST 엔드포인트**(`/auth/login`, `/refresh`, `/logout`, `/me`, `/password`, 관리자용 `/users`)를 `Router`로 제공한다. 사용자는 **동기 `UserStore` 인터페이스**(메서드 5개)만 DB에 연결한다. 비밀번호는 **프레임워크가 해시**하므로 store는 평문을 보지 못한다.
4. **사용자 정보 매핑은 (d) 프레임워크 값 클래스 `AuthUser` + 추가 필드 `Map`을 쓴다.** 리플렉션이 없어 R8에 안전하고, Kotlin에서 그대로 쓰며, 변환은 store 안 한 곳에서만 한다. 대안은 (b) 람다 매핑 어댑터다. 어노테이션 방식 (a)는 채택하지 않는다.
5. 주니어 최소 설정은 `InMemoryUserStore` + 비밀키 + `app.use(...)` 두 줄이다. 비밀번호 해시는 자체 구현한 **PBKDF2-HMAC-SHA256**(Mac 기반, API 21 OK)을 쓰고, bcrypt·argon2는 `PasswordHasher` SPI로 끼워 넣는다.

## 2. JWT 설계

### 2.1 직접 구현 vs 라이브러리

| 선택지 | Java 8 / API 21 | JSON | 무게 | 판정 |
|---|---|---|---|---|
| **jjwt** 0.12/0.13 (`jjwt-api` + `jjwt-impl` + `jjwt-gson`) | Java 7 대상, Android 지원 명시(0.13이 Java 7 마지막 라인). 자체 Base64 포함 | `jjwt-gson`이 Gson을 전이 의존으로 끌어온다. Gson 2.14.0 고정과 버전 충돌을 관리해야 한다(전이 버전 확인 필요) | jar 3개, impl이 큼(JWE/JWK 전체) | 가능하지만 무겁다. 0.x 계열은 API가 자주 바뀐다(0.11→0.12 대규모 deprecation) |
| **java-jwt (auth0)** 4.x | Java 8 | **jackson-databind 필수.** Jackson 2.13은 Android SDK 24+, 2.14 이상은 SDK 26+ | Jackson 약 2 MB | **불가.** API 21을 깬다 (https://github.com/FasterXML/jackson/wiki/Jackson-Release-2.14) |
| **nimbus-jose-jwt** 9.x/10.x | README 기준 Java 8+(구버전 Java 7). jcip-annotations 의존 이력이 있다 | 내장 JSON | 가장 큼(JOSE 전체) | 과하다. ~~OIDC가 필요해지면 그때 검토~~ **(정정: OIDC도 직접 구현, 00 §2)** |
| **직접 구현** (HS256만) | `Mac.getInstance("HmacSHA256")`는 API 1부터 있다. **`java.util.Base64`는 API 26이므로 base64url을 직접 쓴다** | `JsonCodec` SPI로 header/claims를 `Map`으로 처리 | 약 300줄, 추가 의존 0 | **권고** |

출처: jjwt CHANGELOG https://github.com/jwtk/jjwt/blob/master/CHANGELOG.md , java-jwt https://github.com/auth0/java-jwt , nimbus https://connect2id.com/products/nimbus-jose-jwt , Android `java.util.Base64`(API 26) https://developer.android.com/reference/java/util/Base64

직접 구현이 위험하지 않은 이유는 범위가 작기 때문이다. JWS compact 하나, 알고리즘 하나, header 고정이다. 가장 흔한 취약점(`alg` 신뢰, `none`, 알고리즘 혼동)은 **header의 `alg`를 읽어 알고리즘을 고르지 않는 것**만으로 구조적으로 없어진다(2.4). 라이브러리를 써도 결국 이 설정을 사용자가 맞게 해야 한다.

필요한 구성 요소(전부 `NaruServe-auth` 내부, 공개하지 않는다):

- `Base64Url` — 패딩 없는 encode, decode. decode는 `=` 패딩, 공백, 표준 알파벳(`+`, `/`)을 **거부**한다(비정규 인코딩 차단).
- `HmacSigner` — `Mac` 인스턴스는 스레드 안전하지 않으므로 호출마다 `Mac.getInstance`를 쓰거나 `ThreadLocal`에 둔다.
- 상수 시간 비교 — Android 구버전의 `MessageDigest.isEqual` 구현에 기대지 않도록 직접 XOR 누적 비교를 쓴다.
- claims 파싱 — `JsonCodec.decode(reader, Map.class)`. Gson은 숫자를 `Double`로 준다. `exp/iat/nbf`는 `Number.longValue()`로 읽고, 정수가 아니거나 2^53을 넘으면 거부한다.
- 시간 — `java.time.Clock`/`Instant`(API 26)와 `java.util.function.LongSupplier`(API 24)는 쓸 수 없다. 저장소 관례대로(`WebSocketSender`, `FileResponder` 주석 참고) 자체 `@FunctionalInterface TimeSource { long nowMillis(); }`를 둔다(**제안**). 테스트에서 시간을 고정하는 데 쓴다.

### 2.2 알고리즘: HS256 기본, RS256/ES256은?

- 같은 앱이 발급하고 검증하므로 대칭키 HS256으로 충분하다. 비밀키는 **32바이트 이상만** 받는다(RFC 7518 §3.2). 더 짧으면 `build()`에서 `IllegalArgumentException`을 던진다.
- RS256이 필요한 경우는 다른 서비스가 비밀키 없이 검증해야 할 때(JWKS 공개)다. `Signature.getInstance("SHA256withRSA")`는 API 21에 있다. v1에서는 구현하지 않고 내부 `JwtAlgorithm` 슬롯만 둔다.
- ES256은 Android `SHA256withECDSA`가 **DER** 서명을 내지만 JWS는 **R||S(64바이트)** 를 요구한다. `SHA256withECDSAinP1363Format`은 Java 9+ 전용이라 변환 코드를 직접 써야 한다. 수요가 생길 때까지 제외한다.

### 2.3 토큰 모양 (제안)

```
header : {"alg":"HS256","typ":"JWT","kid":"k1"}
access : {"sub":"<userId>","typ":"access","iat":..,"exp":..,"iss"?:..,"aud"?:..,"roles":["admin"]}
refresh: {"sub":"<userId>","typ":"refresh","iat":..,"exp":..,"ver":3,"jti":"<random>"}
```

- **access는 15분**이고 store를 조회하지 않는다(stateless). `roles`를 넣는 이유는 RBAC 미들웨어가 매 요청 DB를 읽지 않게 하려는 것이다. 역할 변경은 최대 15분 늦게 반영된다(문서화).
- **refresh는 14일**이다. `/auth/refresh`에서 store의 `findById`로 사용자를 읽고 `enabled`와 `ver == user.tokenVersion`을 확인한 뒤 새 access/refresh 쌍을 발급한다(회전).
- `typ` 클레임으로 access와 refresh를 구분한다. refresh 토큰을 `Authorization` 헤더에 넣어도 거부한다. access와 refresh에 서로 다른 HKDF 파생 키를 쓰는 것은 과하므로 `typ` 검사로 대신한다.
- 전달 방식: 기본은 JSON 응답 본문 `{accessToken, refreshToken, expiresIn, tokenType:"Bearer"}` + `Authorization: Bearer`다. 브라우저용 옵션 `refreshCookie(true)`는 refresh를 `HttpOnly; Secure; SameSite=Strict; Path=/auth` 쿠키로 보낸다(기존 `CookieOptions` 재사용). 이 옵션은 CSRF 고려가 필요하다(§5).

### 2.4 검증 순서 (모듈이 강제한다)

1. 점이 정확히 2개, 각 부분이 base64url이고 길이 상한(기본 8 KiB) 이하인지 확인한다. 아니면 401.
2. header를 디코드하고 `alg`가 **설정된 키의 알고리즘과 문자열로 정확히 같은지** 확인한다. `none`, `HS512`, `RS256`, 대소문자 변형은 전부 401이다. 알고리즘은 header가 아니라 **키 객체가 정한다**(알고리즘 혼동 방지). `crit`가 있으면 거부, `jku/jwk/x5u`는 무시하고 절대 따라가지 않는다.
3. `kid`로 키를 찾는다. 없으면 401. `kid`가 없을 때는 키가 하나뿐인 경우에만 그 키를 쓴다.
4. 서명을 상수 시간 비교로 확인한다. **서명 확인 전에는 claims를 신뢰하지 않는다.**
5. claims: `exp` 필수, `now - leeway < exp`. `nbf`/`iat`가 미래면 `now + leeway` 이내만 허용한다. leeway 기본값은 **60초**(설정 가능, 상한 5분). `typ` 일치, 설정된 `iss`/`aud` 일치를 확인한다.
6. 실패 응답은 이유를 노출하지 않는다. 항상 `HttpException(401)` + `WWW-Authenticate: Bearer error="invalid_token"`(RFC 6750)이고, 상세 이유는 DEBUG 로그로만 남긴다.

### 2.5 키 교체 (`kid`)

```java
Auth.builder().keys(k -> k
    .sign("k2", System.getenv("JWT_KEY_2"))     // 새 토큰은 k2로 서명
    .verify("k1", System.getenv("JWT_KEY_1")))  // k1 토큰은 만료될 때까지 검증만
```

교체 절차는 이렇다. k2를 추가해 서명키로 바꾸고, k1은 refresh 최대 수명(14일)이 지날 때까지 verify에 남겼다가 지운다. 주니어용 `.secret(s)`는 `kid="default"`인 키 하나에 대한 축약이다.

### 2.6 폐기와 로그아웃

| 동작 | v1 방식 | 비용 |
|---|---|---|
| 로그아웃 | `tokenVersion++` → 해당 사용자의 모든 refresh 무효. access는 최대 15분 유효 | store 필드 하나 |
| 비밀번호 변경·관리자 비활성화 | 같음(`tokenVersion++`, `enabled=false`) | 같음 |
| 기기 하나만 로그아웃 | **v2**. `RefreshTokenStore`(jti 해시 저장, 회전, 재사용 탐지 시 계열 전체 폐기) | 저장소 하나 더 |
| access 즉시 차단 | 선택 옵션 `checkUserOnEveryRequest(true)`: 매 요청 `findById`로 `ver`/`enabled`를 확인 | 요청당 DB 1회 |

`ver`만으로 폐기하는 이유는 사용자 store에 정수 필드 하나를 더하는 것으로 끝나고, 주니어가 저장소를 하나 더 구현할 필요가 없기 때문이다.

## 3. 사용자 관리: 엔드포인트와 `UserStore`

### 3.1 주니어 최소 예제 (가장 먼저 보여 줄 코드)

```java
InMemoryUserStore users = new InMemoryUserStore();
users.add("admin", "change-me-now", "admin");          // username, 평문 비밀번호, roles... (기동 시 해시됨)

Auth auth = Auth.create(System.getenv("JWT_SECRET"), users);   // 32바이트 미만이면 즉시 예외

RestApp.start(8080, app -> {
    app.use("/auth", auth.routes());                    // POST /auth/login, /refresh, /logout, GET /auth/me ...
    app.use("/api", auth.required());                   // 토큰이 없거나 틀리면 401
    app.get("/api/hello", (req, res) -> res.send("hi " + Auth.user(req).getUsername()));
});
```

```kotlin
val users = InMemoryUserStore().apply { add("admin", "change-me-now", "admin") }
val auth = Auth.create(System.getenv("JWT_SECRET"), users)

RestApp.start(8080) { app ->
    app.use("/auth", auth.routes())
    app.use("/api", auth.required())
    app.get("/api/hello") { req, res -> res.send("hi ${Auth.user(req).username}") }
}
```

- `auth.routes()`는 `Router`를 돌려준다. 기존 `HttpRoutes.use(Object path, Router child)`에 그대로 마운트한다.
- `auth.required()`는 `Middleware`다. 성공하면 `req.attribute("naruserve.auth.user", AuthPrincipal)`에 principal을 넣는다. 키 상수는 `Auth.USER_ATTRIBUTE`(**제안**)이고, `Auth.user(req)`는 `attributeAs`를 감싼 `@NonNull` 헬퍼다(없으면 401).
- 라우트 단위로 붙일 때는 기존 패턴을 그대로 쓴다: `app.route("/admin").use(auth.required()).use(auth.role("admin")).get(h)`. `role(...)`은 RBAC 연구에서 확정한다.
- `Auth.user(req)`가 주는 `AuthPrincipal`은 토큰에서 나온 `id`, `username`, `roles`만 담는다. 전체 사용자가 필요하면 `auth.currentUser(req)`가 store를 조회한다.

### 3.2 내장 엔드포인트 (제안, 경로는 마운트 prefix 기준)

| 메서드 경로 | 본문 | 결과 | 호출하는 store 메서드 |
|---|---|---|---|
| `POST /login` | `{username, password}` | 200 토큰 쌍 / 401 | `findByUsername` (+ 해시 업그레이드 시 `update`) |
| `POST /refresh` | `{refreshToken}` 또는 쿠키 | 200 새 쌍 / 401 | `findById` |
| `POST /logout` | 인증 필요 | 204 | `findById`, `update`(ver++) |
| `GET /me` | 인증 필요 | 200 사용자(해시 제외) | `findById` |
| `PATCH /me` | 허용된 추가 필드만 | 200 | `update` |
| `POST /password` | `{currentPassword, newPassword}` | 204, 모든 refresh 무효 | `findById`, `update` |
| `POST /signup` | `{username, password, ...허용 필드}` | 201 / 409 | `findByUsername`, `create` — **기본 꺼짐**, `.signup(true)`로 켠다 |
| `GET/POST/PATCH/DELETE /users[/:id]` | 관리자 | 사용자 CRUD | `create/update/delete/findById` — `adminRole("admin")` 역할이 있어야 한다 |

- 회원 가입은 기본으로 끈다. 내부 앱에 의도하지 않은 공개 가입이 열리는 것이 가장 흔한 사고이기 때문이다. 켜는 데 한 줄이면 된다.
- 응답 JSON에는 `passwordHash`와 `tokenVersion`을 절대 넣지 않는다. 직렬화 대상은 프레임워크가 만든 별도 `Map`이다.

### 3.3 `UserStore` 인터페이스 (제안)

```java
public interface UserStore {
    @Nullable AuthUser findByUsername(String username);   // 로그인 키. 대소문자 정규화는 프레임워크가 먼저 한다
    @Nullable AuthUser findById(String id);
    /** id를 정해 저장하고 저장된 사용자를 돌려준다. 이미 있으면 {@link DuplicateUserException}. */
    AuthUser create(AuthUser user);                       // user.getId()는 null
    AuthUser update(AuthUser user);                       // 전체 교체(필드 병합은 프레임워크가 끝낸 상태)
    void delete(String id);
}
```

- **동기 인터페이스를 권고한다.** 근거는 이렇다. ① 기존 `Deferred`는 값을 실어 나르지 않는다(`resolve()`에 인자가 없다). 값을 돌려주는 비동기 store를 만들려면 새 Promise 타입이 필요하다. ② `CompletableFuture`는 금지 목록에 있다. ③ JDBC, Room, JPA는 전부 동기 API다. 엔드포인트 핸들러는 요청 스레드에서 store를 부른다.
- 비동기가 필요해지면 나중에 `AsyncUserStore`와 콜백 `@FunctionalInterface UserCallback { void done(@Nullable AuthUser u, @Nullable Throwable e); }`를 추가하고, 내부에서 `getAsync`/`Deferred`로 연결한다(**미정, v2**).
- `default` 메서드는 두지 않는다. 메서드 5개가 전부 필수이고, `InMemoryUserStore`가 그 기본 구현 역할을 한다(재시작하면 데이터가 사라지므로 학습·테스트용이라고 문서화한다).
- 예외: store가 던진 예외는 그대로 전파돼 기존 `onError`에서 500이 된다. 프레임워크는 `DuplicateUserException`(→409)만 해석한다.
- **비밀번호 소유권**: store는 `AuthUser.getPasswordHash()`(예: `pbkdf2-sha256$600000$<salt>$<hash>`) 문자열만 저장하고 읽는다. 평문은 프레임워크 밖으로 나가지 않는다. `InMemoryUserStore.add(username, plainPassword, roles...)`만 예외로 평문을 받는데, 받는 즉시 해시한다.

### 3.4 `AuthUser` 값 클래스 (제안)

```java
public final class AuthUser {                    // 불변. 수정은 toBuilder()

    public String getUsername();
    public String getPasswordHash();
    public List<String> getRoles();             // 불변 리스트
```

`Map<String, Object>`를 쓰지 않고 `Map<String, String>`으로 둔 이유는 JSON 왕복 시 Gson의 `Double` 변환 문제를 피하고 DB 컬럼에 그대로 넣기 위해서다.

### 3.5 실제 DB를 연결하는 사용자 코드

```java
public final class JdbcUserStore implements UserStore {
    private final DataSource ds;
    public JdbcUserStore(DataSource ds) { this.ds = ds; }

    @Override public @Nullable AuthUser findByUsername(String username) {
        return queryOne("SELECT * FROM users WHERE username = ?", username);
    }
    @Override public @Nullable AuthUser findById(String id) {
        return queryOne("SELECT * FROM users WHERE id = ?", id);
    }
    @Override public AuthUser create(AuthUser u) { /* INSERT ... RETURNING id */ return u.toBuilder().id(newId).build(); }
    @Override public AuthUser update(AuthUser u) { /* UPDATE ... */ return u; }
    @Override public void delete(String id) { /* DELETE ... */ }

    private static AuthUser toAuthUser(ResultSet rs) throws SQLException {   // 매핑은 여기 한 곳
        return AuthUser.builder()
            .id(rs.getString("id")).username(rs.getString("username"))
            .passwordHash(rs.getString("password_hash"))
            .roles(rs.getString("roles").split(","))
            .enabled(rs.getBoolean("enabled")).tokenVersion(rs.getLong("token_version"))
            .attribute("email", rs.getString("email"))
            .build();
    }
}
```

```kotlin
class RoomUserStore(private val dao: UserDao) : UserStore {
    override fun findByUsername(username: String) = dao.byName(username)?.toAuthUser()
    override fun findById(id: String) = dao.byId(id.toLong())?.toAuthUser()
    override fun create(user: AuthUser): AuthUser = user.toBuilder().id(dao.insert(user.toEntity()).toString()).build()
    override fun update(user: AuthUser): AuthUser { dao.update(user.toEntity()); return user }
    override fun delete(id: String) = dao.delete(id.toLong())
}
```

### 3.6 비밀번호 해시

- 기본은 **PBKDF2-HMAC-SHA256**이다. `SecretKeyFactory "PBKDF2WithHmacSHA256"`은 API 26부터라서 쓸 수 없다. 대신 **`Mac("HmacSHA256")` 위에 PBKDF2(RFC 8018 §5.2)를 직접 구현**한다(약 30줄, RFC 7914 §11 테스트 벡터로 자기 검사). `PBKDF2WithHmacSHA1`도 API 21에 있지만, OWASP가 SHA1에 요구하는 반복 수(1,300,000)는 SHA256 기준(600,000)의 두 배라서 저사양 기기에서 손해다.
- 형식: `pbkdf2-sha256$<iter>$<salt b64>$<hash b64>`, salt 16바이트(`SecureRandom`), 출력 32바이트. 로그인에 성공했는데 저장된 반복 수가 현재 설정보다 낮으면 다시 해시해 `update`한다.
- 반복 수 기본값은 OWASP의 600,000을 제안한다. Android 5 기기에서는 로그인 한 번에 수 초가 걸릴 수 있으므로 `iterations(n)`으로 낮출 수 있게 하되, 100,000 미만이면 WARN 로그를 남긴다(→ 미결 질문 Q2).
- `PasswordHasher` SPI(`String hash(char[] pw)`, `boolean verify(char[] pw, String stored)`, `boolean needsRehash(String stored)`)로 bcrypt나 argon2를 끼울 수 있게 한다. **(정정: bcrypt 레거시 검증기는 직접 구현해 기본 제공한다, 04 §2.4.1. argon2는 사용자가 SPI로 끼운다.)** 접두사로 해시 형식을 구분하므로 여러 해시기를 함께 쓰며 옮겨 갈 수 있다.
- 사용자가 없을 때도 **같은 비용의 더미 verify**를 수행해 응답 시간으로 계정 존재 여부가 드러나지 않게 한다.

## 4. 사용자 정보 매핑: 어노테이션 vs 필드 매핑

### 4.1 후보 코드

```java
// (a) 어노테이션 + 리플렉션
class User { @UserId Long id; @Username String email; @PasswordHash String pw; @Roles List<String> roles; }
// Kotlin에서는 @field: 지정이 없으면 생성자 파라미터에 붙는다:  data class User(@field:UserId val id: Long, ...)

// (b) 람다 매핑
UserMapping<User> m = UserMapping.of(User::getId, User::getEmail, User::getPw, User::getRoles)
        .factory((username, hash) -> new User(username, hash));
UserStore store = UserStore.mapped(myRepo, m);   // myRepo: TypedUserRepository<User>

// (c) 프레임워크 인터페이스 구현
class User implements AuthUserDetails { public String getId() {...} public String getUsername() {...} ... }

// (d) 프레임워크 값 클래스 + Map  (3.4, 3.5)
AuthUser.builder().id(..).username(..).passwordHash(..).attribute("email", ..).build();
```

### 4.2 비교

| 기준 | (a) 어노테이션 | (b) 람다 매핑 | (c) 인터페이스 구현 | (d) 값 클래스 + Map |
|---|---|---|---|---|
| 주니어 사용성 | 처음에는 쉬워 보인다. 빠진 어노테이션은 **실행 시점**에 터진다 | 제네릭 `<U>` 하나, 람다 4~6개, 생성 팩토리 개념까지 알아야 한다 | 메서드를 구현하라는 컴파일 오류가 안내해 준다 | **배울 개념이 하나.** InMemory는 매핑 0줄, DB는 변환 함수 하나 |
| Kotlin data class | `@field:` 누락 함정, `val`이라 리플렉션 쓰기가 불가하거나 위험 | 메서드 참조 `User::email` 그대로. 좋음 | `override val`로 깔끔하다. 다만 엔티티가 프레임워크 타입을 상속한다 | 확장 함수 `toAuthUser()` 하나. 좋음 |
| R8/ProGuard | **나쁨.** 필드 이름 변경·제거, 어노테이션 제거를 막으려면 `-keep`/`-keepattributes RuntimeVisibleAnnotations` consumer rules가 필요하고, 실패가 릴리스 빌드에서만 드러난다 | 안전(리플렉션 없음) | 안전 | 안전 |
| 컴파일 타임 안전 | 없음(타입·누락 모두 실행 시점) | 높음(타입 일치) | 높음 | 높음(빌더 필수 필드는 `build()`에서 검사) |
| 보일러플레이트 | 최소(어노테이션 4개) | 중간(매핑 + 팩토리 + 타입 있는 저장소) | 중간(메서드 6~7개, 엔티티마다) | 변환 함수 5~8줄 |
| 도메인 결합 | 엔티티에 프레임워크 어노테이션이 붙는다 | 없음 | **강하다.** 엔티티가 프레임워크 인터페이스를 구현하고, Room/JPA 엔티티와 섞인다 | 없음(store 안에서만 변환) |
| 쓰기(create/update) | 리플렉션으로 필드를 써야 하고 불변 data class와 충돌한다 | 팩토리·copy 람다가 더 필요하다 | 프레임워크가 새 객체를 만들 수 없어 결국 팩토리가 필요하다 | 프레임워크가 직접 만들고 store가 저장한다 |
| 추가 필드(email 등) | 어노테이션을 하나 더 만들거나 전체 직렬화 | 람다 추가 | getter 추가 | `attributes` Map. 대신 타입은 문자열뿐 |
| 구현 비용(프레임워크) | 큼(스캐너, 캐시, 오류 메시지, keep rules) | 중간 | 작음 | **최소** |

### 4.3 권고

- **1안: (d) `AuthUser` 값 클래스 + `attributes` Map.** 쓰기 경로(create, update, 비밀번호 변경, `tokenVersion++`)를 프레임워크가 끝까지 소유할 수 있는 유일한 안이다. 리플렉션 0, R8 규칙 0, Kotlin에서도 자연스럽다. 비용은 store마다 변환 함수 하나이고, 그 함수가 "우리 DB 컬럼 ↔ 인증 필드"의 단일 지점이라 오히려 읽기 쉽다. better-auth와 Laravel GenericUser가 같은 방향이다.
- **대안: (b) 람다 매핑 어댑터.** 자기 엔티티를 그대로 돌려주는 저장소를 이미 가진 팀을 위해 v2에 `UserStore.mapped(...)`로 추가할 수 있다. (d) 위에 얹는 얇은 어댑터라서 1안을 바꾸지 않는다.
- **(a)는 채택하지 않는다.** Android 릴리스 빌드에서만 실패하는 설정 오류는 "주니어가 바로 쓸 수 있어야 한다"는 최우선 요구와 정면으로 충돌한다. (c)는 쓰기 경로에서 결국 팩토리가 필요해 (b)의 복잡도를 그대로 떠안는다.

## 5. 모듈이 책임질 보안 함정

| 함정 | 모듈의 대응 |
|---|---|
| `alg=none`, 알고리즘 혼동(RS 공개키를 HS 비밀로 사용) | header가 아니라 키가 알고리즘을 정한다. `alg`가 정확히 일치해야 한다(2.4) |
| 약한·기본 비밀키 | 32바이트 미만, 예제 문자열(`"secret"`, `"change-me"`)은 `build()`에서 예외. 비밀키는 로그에 남기지 않는다 |
| 서명 비교 타이밍 | 상수 시간 비교 |
| 만료 없는 토큰, 과도한 leeway | `exp` 필수, leeway 상한 5분 |
| refresh를 access로 사용 | `typ` 검사 |
| 사용자 열거(username 존재 여부) | 로그인 실패 메시지와 상태 코드를 같게 하고, 더미 해시 verify로 시간도 같게 한다. signup의 409는 피할 수 없으므로 문서화한다 |
| 무차별 대입 | 내장 로그인 제한(IP+username 기준 고정 창, 기본 10회/15분 → 429 + `Retry-After`, 메모리 맵 상한). 여러 인스턴스 환경에서는 사용자가 교체할 수 있는 SPI로 둔다(Q4) |
| 해시 비용 DoS | 비밀번호 길이 상한(기본 128자 정도) 넘으면 400. 로그인 본문은 기존 `jsonLimit`로 막는다 |
| 대량 할당(가입 본문에 `roles:["admin"]`) | 가입·`PATCH /me`는 `allowedAttributes("email","name")` 허용 목록만 받는다. `roles`, `enabled`, `tokenVersion`은 관리자 API로만 바꾼다 |
| 평문 비밀번호 노출 | 평문은 `char[]`로 받아 해시 후 0으로 지운다(best effort, `req.body`가 String을 만든 뒤라 완전하지 않다). 응답·로그·예외 메시지에 넣지 않는다 |
| 응답에 해시 포함 | 응답 Map은 프레임워크가 직접 만든다(`AuthUser`를 직접 직렬화하지 않는다) |
| HTTP 평문 전송 | `req.isSecure()`가 false인데 비루프백이면 기동 시 WARN 한 번. `requireHttps(true)` 옵션은 403 |
| 쿠키 refresh의 CSRF | 쿠키 모드는 `SameSite=Strict` + `Path=/auth` + `/refresh`에 커스텀 헤더(`X-Requested-With`)를 요구한다. 기본 Bearer 모드는 CSRF 대상이 아니다 |
| 비밀번호 변경 뒤 기존 세션 유지 | `tokenVersion++`, 현재 비밀번호 재확인 필수 |
| 시계 차이(Android 기기 시계) | 서버가 발급·검증을 모두 하므로 서버 시계만 쓴다. `TimeSource` 주입 |
| `kid` 경로 조작 | `kid`는 설정된 맵 조회에만 쓰고, 파일·URL 조회에는 절대 쓰지 않는다 |

## 6. 미결 질문 (구현하면서 정할 것)

- **Q1. 모듈 경계**: `NaruServe-auth`(API 21 검사 대상, `NaruServe-api`에만 의존)를 새 모듈로 둘지. JSON은 `req.body(Map.class)`와 앱의 `JsonCodec`을 쓰므로 Gson 의존 없이 가능해 보인다. 다만 JWT 파싱에 `JsonCodec`을 얻는 공개 경로가 필요하다(`req.application()`에서 꺼낼 수 있는지 확인 필요).
- **Q2. PBKDF2 반복 수 기본값**: OWASP 600,000을 그대로 쓸지, Android 기본값을 따로 둘지. 측정 후 정한다.
- **Q3. username 정규화**: 소문자화와 NFKC를 기본으로 할지, 로그인 키를 email로 고르는 옵션(`USERNAME_FIELD` 대응)을 둘지.
- **Q4. 로그인 제한 저장소**: 메모리 기본값의 SPI 이름과 모양.
- **Q5. 기기별 로그아웃(`RefreshTokenStore`)과 refresh 재사용 탐지**를 v1에 넣을지.
- **Q6. 비동기 store**: 수요가 확인되면 `AsyncUserStore` + 콜백 타입. `Deferred`에 값을 싣는 확장은 Core 변경이므로 별도 SRS가 필요하다.
- **Q7. 관리자 API 범위**: 목록 조회(`GET /users`)에는 페이지네이션이 필요해 `UserStore`에 `list(offset, limit)`를 더해야 한다. 이 메서드를 `default`(UnsupportedOperationException → 501)로 둘지.
- **Q8. RBAC와 `roles` 클레임 형식**(문자열 목록 vs 권한 문자열) — 별도 연구(02)와 맞춘다.
- **Q9. Servlet 어댑터**: `isSecure`와 쿠키 동작이 같은지 확인한다.
