# 연구 05 — 통합 API 계약과 흐름 (NaruServe-utils / auth)

> **3판 안내:** 최종 결정본은 00 개요 33판이다(최종 규칙은 00 §6.3 R28–R47, 점검표 §6.4). 최종 결정과 이름은 [00 개요](00.overview.md)가 우선한다. 이 문서와 다른 부분은 00 §6(06 검토로 바뀐 결정), §7(최종 이름표), §11(정정 기록)을 본다.

> 상태: 연구 문서(설계 제안). 코드·빌드·`docs/spec/`은 바꾸지 않았다. 대응하는 SRS 요구사항은 아직 없다. 구현하기 전에 `docs/spec/`에 요구사항부터 만든다.
> 기준: [00 개요](00.overview.md) §3의 통일 결정. 01–03의 본문 이름이 서로 다르면 이 문서가 우선한다.
> 모듈 배치(사용자 지시, 2026-10-29): `NaruServe-auth` 제안은 버리고 **`NaruServe-utils`** 모듈에 둔다. 이 모듈은 `NaruServe-api`에만 의존하고 API 21 animal-sniffer 검사 대상이다. 루트 패키지는 `com.snoworca.naruserve.utils`, 인증은 `com.snoworca.naruserve.utils.auth` 아래에 둔다.
> 기업 연동(OIDC/SAML/LDAP, 멀티 테넌트, 클러스터링)은 07에서 다룬다. 이 문서는 연동이 들어올 **이음매(SPI)만** 남긴다.

## 0. 요약

1. 진입 타입은 `Auth` 하나다. 최소 설정은 `Auth.create(secret, users)`, 그 밖의 설정은 `Auth.builder(secret)`로 한다. `Auth`는 `Middleware`를 구현하므로 `app.use(auth)` 한 줄로 기본 거부가 된다. 가드와 `user(req)`는 모두 **인스턴스 메서드**다.
2. 요청 주체는 `AuthPrincipal`(인터페이스, 그룹·스코프는 지연 계산), 저장 사용자는 `AuthUser`(불변 값 + 빌더)다. 요청 경로에서 신원은 토큰만으로 확인하고, store는 가드가 처음 물을 때만 부른다.
3. 관심사 9개(토큰 형식, 비밀번호 해시, 자격 증명 확인, 사용자·그룹·역할 store, 로그인 제한, refresh 폐기, 이벤트, 응답 JSON 모양)마다 **교체 가능한 SPI와 기본 구현**을 둔다(§2.2). JWT·비밀번호 유틸은 엔드포인트 없이 따로 쓸 수 있다.
4. 내장 엔드포인트는 `auth.routes()`(자기 계정 11개)와 `auth.adminRoutes()`(사용자·그룹 관리 15개)다. 오류는 기존 표준 오류 형식 `{"error":{"code","message","requestId"}}`를 따르고 인증 전용 `code`를 쓴다. 그러려면 Core를 한 줄 바꿔야 한다(C2).
5. refresh는 매번 회전한다. `RefreshTokenStore`를 연결하면 재사용 탐지(RFC 9700 §4.14)를 하고 계열 전체를 폐기한다. 연결하지 않으면 `tokenVersion`만으로 폐기한다(기본).
6. 이벤트 `AuthEvents`의 메서드는 전부 default no-op이다. `before*`는 동기로 돌고 예외를 던져 거부(veto)할 수 있다. `on*`은 store 쓰기가 끝난 뒤 동기로 알리며, 실패해도 응답을 바꾸지 않는다. 비동기는 `AuthEvents.async(listener, executor)`로 감싼다.
7. 전송 방식은 `.transport(TokenTransport.HEADER | COOKIE | BOTH)`이고 기본은 HEADER다. COOKIE는 서명된 double-submit CSRF 토큰, `Origin` 검사, SameSite=Strict를 자동으로 켠다.
8. 로그인 제한(IP와 계정 이중 키), 사용자 열거 방지(같은 상태·같은 본문·더미 해시), 비밀번호 정책, 유출 비밀번호 SPI, 재설정·이메일 검증 일회용 토큰을 모듈이 맡는다. 테스트는 `AuthTesting.tokenFor(auth, "alice", "posts:write")`로 한다.

### 2.2 확장점(SPI) 지도

| 관심사 | SPI | 기본 | 바꾸는 예 | 07 이음매 |
|---|---|---|---|---|
| 토큰 형식·검증 | `TokenCodec` | `JwtTokenCodec`(HS256, `kid`) | RS256/ES256, 불투명 토큰 + 조회 | OIDC 외부 IdP 토큰 검증 |
| 비밀번호 해시 | `PasswordHasher` | `Pbkdf2PasswordHasher` | bcrypt, argon2, 레거시 SHA 이전 | — |
| 자격 증명 확인 | `Authenticator` | `StoreAuthenticator` | LDAP bind, 외부 SSO | LDAP/AD |
| 사용자 | `UserStore` | `InMemoryUserStore` | JDBC, Room, JPA | 테넌트별 store |
| 그룹 | `GroupStore`/`GroupAdminStore` | `InMemoryGroupStore` | 재귀 CTE, LDAP 그룹 | LDAP `memberOf` |
| 역할 | `RoleStore` | `RolePolicy` | DB 역할표 | IdP 역할 매핑 |
| 로그인 제한 | `LoginThrottle` | `InMemoryLoginThrottle` | Redis(클러스터) | 클러스터링 |
| refresh 폐기 | `RefreshTokenStore` | 없음(`tokenVersion`) / `InMemoryRefreshTokenStore` | DB 테이블, Redis | 클러스터링 |
| 이벤트 | `AuthEvents` | no-op | 감사 로그, 메일, 메트릭 | SIEM |
| 응답 JSON | `AuthResponses` | `DefaultAuthResponses` | 사내 표준 봉투 `{data, meta}` | — |
| 시간 | `TimeSource` | `System.currentTimeMillis` | 테스트 고정 시계 | — |
| 비밀번호 유출 | `BreachedPasswordChecker` | 내장 흔한 비밀번호 목록(약 1,000개) | HIBP k-anonymity | — |

멀티 테넌트 이음매: `AuthEventContext`와 `TokenClaims`는 `getClaim("tid")`처럼 임의 클레임을 싣는다. 테넌트 해석기(`TenantResolver`)는 07에서 정한다. v1 API는 테넌트를 모르며, store를 테넌트별로 감싸는 방식으로 대응할 수 있다.

## 3. Java 시그니처

### 3.1 `Auth`와 `Auth.Builder`

```java
package com.snoworca.naruserve.utils.auth;

public final class Auth implements Middleware {
    public static final String DEFAULT_MOUNT = "/auth";

    // ---- 생성 ----
    /** 로그인만 쓰는 최소 설정. secret은 UTF-8 32바이트 이상, 아니면 IllegalArgumentException. */
    public static @NonNull Auth create(@NonNull String secret, @NonNull UserStore users);
    public static @NonNull Builder builder(@NonNull String secret);
    /** 키를 keys(...)나 tokenCodec(...)으로 줄 때. */
    public static @NonNull Builder builder();

    // ---- 미들웨어 ----
    /** app.use(auth): publicPaths 밖은 인증 필요(defaultDeny). 성공하면 주체를 요청에 붙인다. */
    @Override public void handle(@NonNull Request req, @NonNull Response res, @NonNull Next next) throws Exception;
    /** 이 미들웨어가 붙은 곳만 인증(defaultDeny(false) 앱용). */
    public @NonNull Middleware required();
    /** 토큰이 유효하면 주체를 붙이고, 없거나 틀려도 통과(공개 페이지의 "로그인 시 추가 정보"). */
    public @NonNull Middleware optional();

    // ---- 가드: 모두 스스로 인증을 보장한다(멱등) ----
    public @NonNull Middleware require(@NonNull String scope);
    public @NonNull Middleware requireAll(@NonNull String first, @NonNull String... more);
    public @NonNull Middleware requireAny(@NonNull String first, @NonNull String... more);
    public @NonNull Middleware requireGroup(@NonNull String groupId);
    public @NonNull Middleware requireRole(@NonNull String role);
    public @NonNull Middleware check(@NonNull AccessRule rule);

    // ---- 핸들러 안 ----
    /** 인증 안 됐으면 AuthException(401). */
    public @NonNull AuthPrincipal user(@NonNull Request req);
    public @Nullable AuthPrincipal userOrNull(@NonNull Request req);
    /** store에서 전체 사용자를 읽는다(요청 동안 메모). 삭제됐으면 401. */
    public @NonNull AuthUser currentUser(@NonNull Request req) throws Exception;
    /** 스코프가 없으면 AuthException(403, INSUFFICIENT_SCOPE)을 던진다. */
    public void demand(@NonNull Request req, @NonNull String scope);
    public @NonNull AuthException forbidden();
    public @NonNull AuthException unauthorized();

    // ---- 라우터 ----
    /** POST /login, /refresh, /logout, GET·PATCH /me, POST /password ... (§4.1). DEFAULT_MOUNT에 마운트. */
    public @NonNull Router routes();
    /** /users, /groups 관리(§4.2). 가드가 내장되어 있다. "/auth/admin"에 마운트. */
    public @NonNull Router adminRoutes();

    // ---- 유틸 ----
    public @NonNull TokenService tokens();
    public @NonNull PasswordHasher passwords();
    public @NonNull PasswordPolicy passwordPolicy();
    public @NonNull UserStore users();
    /** 그룹 캐시(groupCacheTtl)를 비운다. DB를 직접 고친 뒤 부른다. */
    public void invalidateGroupCache();

    public static final class Builder {
        public @NonNull Builder users(@NonNull UserStore users);
        public @NonNull Builder groups(@NonNull GroupStore groups);

`build()`가 거부하는 것: 비밀키가 32바이트 미만이거나 예제 문자열(`"secret"`, `"change-me"`)일 때, `users` 없음, `passwordReset(true)`나 `emailVerification(true, …)`인데 `events`가 하나도 없을 때(토큰을 보낼 곳이 없다), `adminRoutes()`의 그룹 관리를 쓰는데 store가 `GroupAdminStore`가 아닐 때(그룹 경로만 501로 둔다. 예외 아님), `transport(COOKIE)`인데 `trustedOrigins`가 없고 `defaultDeny`일 때(WARN만 내고 같은 출처만 허용).

**Kotlin과 오버로드 확인**

| 호출 | 고르는 오버로드 | 확인 |
|---|---|---|
| `app.use(auth)` | `RestApp.use(Middleware)` | `Auth`는 `Router`나 `ErrorMiddleware`를 구현하지 **않으므로** 모호하지 않다. 앞으로도 구현하지 않는다 |
| `app.use("/auth", auth.routes())` | `HttpRoutes.use(Object, Router)` | `Router`는 `Middleware`가 아니어서(`Router extends HttpRoutes<Router>`) `use(String, Middleware)`와 겹치지 않는다 |
| `app.post("/posts", auth.require("posts:write")) { req, res -> }` | `RestApp.post(String, Middleware, RouteHandler)` | 후행 람다의 인자가 2개라 `RouteHandler`만 맞는다. 가변 인자 `post(Object, Middleware...)`는 후행 람다를 받지 않는다 |
| `group.route("/x").use(auth.require("a:b")).get { req, res -> }` | `RouteBuilder.use(Middleware)` → `get(RouteHandler)` | `RouteGroup`에는 `(path, Middleware, RouteHandler)` 오버로드가 **없다.** 그룹 안에서는 이 형태를 쓴다고 문서에 적는다 |
| `auth.check { p, req -> p.can("x") }` | `AccessRule` SAM | OK |
| `auth.requireAll("a:b", "c:d")` | `(String, String...)` | 인자가 0개면 컴파일 오류(의도된 것) |

키워드 확인: `in`, `is`, `object`, `fun`, `when`, `val`, `var`를 메서드 이름으로 쓰지 않는다. 그룹 소속 검사는 `memberOf`다.

`AuthResponses`가 돌려주는 `Object`는 `res.json(...)`이 받는 값이다(`Map`/`List`/DTO). 그래서 앱의 `JsonCodec`이 직렬화한다. 기본 구현은 `LinkedHashMap`을 만든다. `passwordHash`와 `tokenVersion`은 절대 넣지 않는다.

## 4. 내장 엔드포인트 HTTP 계약

### 4.0 공통

- **오류 본문**: 표준 오류 형식 `{"error":{"code":"<code>","message":"<msg>","requestId":"..."}}`([middleware.md 표준 오류 형식](../../api/middleware.md)). 모듈은 `AuthException`을 던지고 기존 `onError` 경로를 탄다.
- **Core 의존**: 지금 표준 본문의 `code`는 `StandardErrors.code(status)`로 상태에서만 정해진다(`internal/ErrorPath.java`가 `StandardErrors.json(status, …)`를 부른다). 그래서 `AuthException.code()`를 재정의해도 본문에는 `HTTP_401`이 나간다. 제안은 두 가지다. **C1**: 표에 `401 UNAUTHORIZED`, `403 FORBIDDEN`, `409 CONFLICT`, `429 TOO_MANY_REQUESTS`를 더한다(00 §6). **C2**: 오류가 `HttpException`이면 본문 `code`에 `error.code()`를 쓴다. C2가 없는 동안에는 상태별 코드가 나가고, 앱은 `onError`에서 `((AuthException) e).authCode()`를 읽을 수 있다. 다른 봉투가 필요하면 `AuthResponses.error`를 재정의한다.
- **헤더**: 401에는 항상 `WWW-Authenticate: Bearer`(토큰이 틀렸으면 `error="invalid_token"`)를 붙인다. 403 스코프 부족은 `Bearer error="insufficient_scope", scope="<s>"`(RFC 6750 §3.1), 429에는 `Retry-After`를 붙인다. 토큰을 담은 응답에는 `Cache-Control: no-store`를 붙인다.
- **본문 파싱**: `req.body(Map.class)`(앱 `JsonCodec`, `jsonLimit`). 필드 타입이 틀리면 400 `BAD_REQUEST`, 모르는 필드는 무시한다. 허용되지 않은 속성(`roles` 등)은 422 `ATTRIBUTE_NOT_ALLOWED`다.
- **표기**: S = store 호출 순서, E = 이벤트 호출 순서. T = `LoginThrottle`, R = `RefreshTokenStore`(설정했을 때만), U = `UserStore`, G = `GroupAdminStore`, H = `PasswordHasher`, P = `PasswordPolicy`.

**`code` 표**

| 상태 | `code` | 쓰는 곳 |
|---|---|---|
| 400 | `BAD_REQUEST` | 본문 형식 오류(Core 기존) |
| 401 | `UNAUTHENTICATED` | 토큰 없음 |
| 401 | `INVALID_TOKEN` | access 서명·만료·형식 오류, 삭제된 사용자 |
| 401 | `INVALID_CREDENTIALS` | 로그인 실패(모르는 사용자·틀린 비밀번호·비활성 모두 같음) |
| 401 | `INVALID_REFRESH_TOKEN` | refresh 무효·만료·버전 불일치·**재사용**(구분하지 않음) |
| 403 | `INSUFFICIENT_SCOPE` / `FORBIDDEN` | 스코프 가드 / 그룹·역할·`check` 가드 |
| 403 | `CSRF_FAILED` | 쿠키 인증인데 CSRF 토큰이나 `Origin`이 틀림 |
| 403 | `CURRENT_PASSWORD_INVALID` | 비밀번호 변경 시 현재 비밀번호가 틀림(401을 쓰면 클라이언트가 refresh 루프에 빠진다) |
| 403 | `EMAIL_NOT_VERIFIED` | `emailVerification(true, true)`일 때 로그인 |
| 403 | `HTTPS_REQUIRED` | `requireHttps(true)` |
| 404 | `USER_NOT_FOUND` / `GROUP_NOT_FOUND` | 관리 API |
| 409 | `USER_EXISTS` / `GROUP_EXISTS` | 생성 중복 |
| 409 | `GROUP_CYCLE` / `GROUP_TOO_DEEP` | 중첩 거부 |
| 409 | `CANNOT_DELETE_SELF` | 관리자가 자기 계정을 삭제하려 함 |
| 422 | `WEAK_PASSWORD` | 정책 위반. `message`에는 위반 코드 목록을 쉼표로 넣는다 |
| 422 | `INVALID_USERNAME` / `INVALID_GROUP_ID` / `ATTRIBUTE_NOT_ALLOWED` | 입력 검증 |
| 429 | `TOO_MANY_ATTEMPTS` | 로그인 제한 |
| 501 | `NOT_SUPPORTED` | store가 기능 미구현(`list`, `GroupAdminStore` 아님) |
| 500 | `INTERNAL_ERROR` | store 예외(fail closed), `GroupLimitException` |

**사용자 응답 본문**(`DefaultAuthResponses.user`): `{"id":"u1","username":"alice","roles":["editor"],"enabled":true,"emailVerified":false,"attributes":{"email":"a@x.io"}}`
**토큰 응답 본문**(HEADER): `{"tokenType":"Bearer","accessToken":"…","expiresIn":900,"refreshToken":"…","refreshExpiresIn":1209600,"user":{…}}`. COOKIE 모드에서는 `accessToken`과 `refreshToken`을 본문에서 빼고 쿠키로 보내며, 본문에는 `"csrfToken":"…"`을 넣는다.

### 4.1 `auth.routes()` (마운트 `/auth`)

기본 공개 경로(`defaultDeny`의 예외)는 `/auth/login`, `/auth/refresh`, `/auth/signup`, `/auth/password/forgot`, `/auth/password/reset`, `/auth/verify-email`이다. `mountPath`를 바꾸면 이 목록도 함께 바뀐다. 라우터가 실제로 받은 `req.baseUrl()`이 `mountPath`와 다르면 첫 요청에서 ERROR 로그를 한 번 남긴다(00 §7 Q2 해결).

### 5.4 refresh 회전과 재사용 탐지

```
정상 회전 (R 설정)

|               | decode(rt1,"refresh") → sub, ver, jti1, fam                 |

RFC 9700 §2.2.2는 public client(Android 앱, 브라우저)의 refresh 토큰을 "sender-constrained하거나 §4.14의 회전을 써야 한다(MUST)"고 한다. 그래서 `transport`가 COOKIE·BOTH이거나 Android 클라이언트를 대상으로 하는데 R이 없으면, 기동할 때 WARN을 한 번 남겨 `InMemoryRefreshTokenStore` 또는 DB 구현을 권한다(https://datatracker.ietf.org/doc/html/rfc9700#section-4.14). R을 기본으로 켜지 않는 이유: 메모리 기본값이면 Android 프로세스가 죽을 때마다 모든 기기가 로그아웃된다(§11 Q3).

|              |-beforeSignup(candidate, ctx)------------------------------------>| (예외=거부, 예: 초대코드)
|              |-hash(pw)--------------------------------------------->|        |
|              |-create(user)---------------------->| DuplicateUserException → 409 (경쟁)

```

### 5.7 관리자의 사용자 삭제

```
C(admin)        A(adminRoutes)       U              G                 R           Ev
|-DELETE /auth/admin/users/u7->|     |              |                 |            |
|               | require("auth:users:write")        |                 |            |
|               | u7 == 본인? → 409 CANNOT_DELETE_SELF                 |            |
|               |-findById(u7)------>| 없으면 404    |                 |            |
|               |-beforeUserDelete(user, ctx)------------------------------------------>| (거부 가능)
|               |-revokeUser(u7)------------------------------------->| (R 설정 시)|
|               |-removeUser(u7)-------------------->| 소속 먼저 제거  |            |
|               |-delete(u7)-------->| true          |                 |            |
|               | 그룹 캐시 비움     |               |                 |            |
|               |-onUserDeleted(user, ctx)--------------------------------------------->|
|<-204
```

- **순서의 이유**: 소속을 먼저 지운다. 사용자 행을 먼저 지운 뒤 소속 삭제가 실패하면 고아 소속 행이 남는다. 그 id가 다시 쓰이면 새 사용자가 옛 그룹 권한을 물려받는다. `UserStore` 계약에 "id 재사용 금지"를 함께 적는다. 중간에 실패하면 500이고, 다시 호출해도 안전하다(각 단계가 멱등이다).
- **살아 있는 토큰**: refresh는 다음 `/refresh`에서 `findById`가 null이라 401이 된다(R이 없어도 된다). access는 만료(15분)까지 신원 검사를 통과한다. 그 동안 그룹 가드는 소속이 비어 있어 거부되지만, 토큰의 `roles`로 받은 스코프는 **여전히 통과한다**. 이것을 막으려면 `verifyUserOnEveryRequest(true)`를 켜거나 accessTtl을 줄인다. 문서에 표로 둔다.

### 5.8 그룹 중첩과 순환 거부

```
C(admin)       A                         G
|-PUT /auth/admin/groups/eng/parents/backend->|      (eng를 backend 아래에? 현재 backend ⊂ eng)
|              | ID 검사, groupExists(eng), groupExists(backend) → 없으면 404
|              | eng == backend? 아니오
|              | 위로 BFS (backend부터):
|              |-parentsOf({backend})---->| {eng}         ← child(eng) 발견
|              | → 409 GROUP_CYCLE  (addParent 호출 없음)
|<-409 {"error":{"code":"GROUP_CYCLE","message":"eng is already an ancestor of backend"}}

정상: PUT /groups/oncall/parents/sales
|              | BFS(sales 위로) depth a, 그 안에 oncall 없음
|              | 아래 높이: childrenOf(oncall) BFS → height b
|              | a + 1 + b > maxDepth(8) → 409 GROUP_TOO_DEEP
|              |-addParent(oncall, sales)->|
|              | 그룹 캐시 비움 → onGroupChanged(NESTED, oncall, sales)
|<-204
```

검사와 `addParent` 사이에 경쟁이 생겨 순환이 만들어질 수 있다. 그래도 읽기 확장이 visited 집합으로 끝나므로 인가는 멈추지 않는다(02 §6). `InMemoryGroupStore`는 검사와 추가를 한 락 안에서 한다.

| 결정 | 선택 | 이유 |
|---|---|---|
| 동기 vs 비동기 | **동기 기본**, `AuthEvents.async(...)` 래퍼 제공 | 감사 로그는 응답 전에 남아야 순서가 보장된다. 메일처럼 느린 일은 래퍼로 넘긴다. Core의 `ExecutorService`와 무관하고 API 21에서 문제 없다 |
| 거부(veto) | `before*` 3개만 가능 | 관심사를 분리하기 위해서다. 알림은 이미 일어난 사실이다. store 쓰기 뒤에 거부하면 상태가 반쯤 바뀐다 |
| 알림 실패 | 로그만 남기고 응답은 그대로 | 메일 서버 장애로 로그인이 실패하면 안 된다 |
| 호출 시점 | store 쓰기 성공 **후**, 응답 **전** | "이벤트가 왔으면 DB에 있다"를 보장한다 |
| 여러 리스너 | `.events(a).events(b)` 등록 순서 | `before*` 중 하나라도 던지면 뒤의 것은 부르지 않는다 |
| 일회용 토큰 | 이벤트 인자로만 넘김 | 프레임워크는 메일을 보내지 않고 토큰을 로그에 남기지 않는다 |

## 7. 토큰 전송

| 모드 | access 위치 | refresh 위치 | CSRF | 대상 |
|---|---|---|---|---|
| `HEADER`(기본) | `Authorization: Bearer` | 본문 JSON | 해당 없음(브라우저가 자동으로 붙이지 않는다) | Android/모바일, 서버 간, SPA가 메모리에 보관 |
| `COOKIE` | `naru_at` 쿠키 | `naru_rt` 쿠키(`Path=<mount>/refresh`) | **필수**: 서명된 double-submit + Origin 검사 | 기기가 띄운 웹 관리 화면, 같은 출처 웹 |
| `BOTH` | 헤더가 있으면 헤더, 없으면 쿠키 | 요청이 온 방식대로 | 쿠키로 인증된 요청에만 | 웹과 앱이 같은 서버 |

**쿠키 기본값**(`CookieOptions` 재사용, `.cookies(c -> ...)`로 덮어쓴다)

| 쿠키 | HttpOnly | Secure | SameSite | Path | Max-Age |
|---|---|---|---|---|---|
| `naru_at` | 예 | `req.isSecure()`일 때 | `STRICT` | `/` | accessTtl |
| `naru_rt` | 예 | 같음 | `STRICT` | `<mount>/refresh` | refreshTtl |
| `naru_csrf` | **아니오**(JS가 읽는다) | 같음 | `STRICT` | `/` | refreshTtl |

**CSRF 방어**(OWASP CSRF Cheat Sheet의 signed double-submit, https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

1. 로그인·refresh 때 `csrf = base64url(random16) + "." + HMAC(key, sub + "." + fam + "." + random16)`를 만들어 `naru_csrf` 쿠키와 응답 본문 `csrfToken`에 싣는다. 세션(계열)에 묶여 있어 다른 사용자의 쿠키를 심는 공격이 통하지 않는다.
2. 쿠키로 인증된 요청이 `POST`/`PUT`/`PATCH`/`DELETE`이면 `X-CSRF-Token` 헤더가 쿠키와 같은지(상수 시간 비교), HMAC이 현재 주체와 맞는지 확인한다. `GET`/`HEAD`/`OPTIONS`는 검사하지 않으므로 상태를 바꾸는 GET을 만들지 말라고 문서에 쓴다.
3. 추가 방어: `Origin`(없으면 `Referer`)이 같은 호스트이거나 `trustedOrigins`에 있어야 한다. 둘 다 없으면 쿠키 인증 쓰기를 거부한다.
4. 실패하면 403 `CSRF_FAILED`. `/login`은 쿠키 인증 전이므로 Origin 검사만 한다(로그인 CSRF 방지).

**CORS와의 관계**(`CorsOptions`)
- `app.cors(...)`를 `app.use(auth)`보다 **먼저** 등록한다(기존 규칙, `CorsOptions` Javadoc). preflight는 인증 전에 끝난다.
- HEADER 모드에서 다른 출처 SPA를 쓴다면 `allowedHeaders("Authorization", "Content-Type")`가 필요하다.
- COOKIE 모드에서 다른 출처를 쓴다면 `credentials(true)` + 정확한 `allowedOrigins(...)`(와일드카드는 Core가 거부) + `allowedHeaders("X-CSRF-Token", "Content-Type")`를 주고, 같은 출처 목록을 `trustedOrigins`에도 준다. 이때 SameSite=Strict 쿠키는 사이트가 다르면 전송되지 않으므로 `.cookies(c -> c.sameSite(SameSite.NONE))`도 바꿔야 한다(이 경우 Secure 필수). 문서에 "가능하면 같은 출처로 띄우라"고 첫 권고로 쓴다.

**평문 HTTP 기기 관리 화면**: LAN의 Android 기기는 HTTPS가 없는 경우가 많다. 이때 `Secure`를 강제하면 브라우저가 쿠키를 버리므로 `Secure`는 `req.isSecure()`를 따르게 하고, 평문이면서 루프백이 아니면 WARN을 한 번 남긴다. `requireHttps(true)`는 이 경우를 403으로 막는다.

**주니어 선택 기준(문서 첫 표)**: "앱이나 다른 서버가 부른다 → 아무것도 바꾸지 않는다(HEADER). 브라우저 화면을 같은 서버에서 띄운다 → `.transport(TokenTransport.COOKIE)`. 둘 다 → `BOTH`."

## 8. 남용 방지

### 8.1 로그인 제한과 잠금

- 키는 두 개다. `ip:<remoteAddress>`(한 IP의 무차별 대입)와 `user:<username>`(분산 IP 공격; OWASP는 계정 기준 추적을 권한다).
- `InMemoryLoginThrottle` 기본값: 15분 창에서 실패 5회째부터 지수 지연(1분 → 2분 → 4분, 상한 15분)이다. IP 키는 실패 20회/15분에서 15분 차단한다. 맵 크기 상한은 10,000키이고 넘으면 가장 오래된 것부터 버린다(메모리 DoS 방지). 시간은 `TimeSource`로 잰다.
- 영구 잠금은 하지 않는다. 남의 계정을 일부러 잠그는 DoS를 막고, 잠긴 사용자는 비밀번호 재설정으로 풀린다(9번 엔드포인트가 `T.reset(user)`). OWASP Authentication Cheat Sheet의 "lockout DoS 방지" 권고를 따른다(https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).
- 차단 중인 요청에는 store도 해시도 부르지 않는다(429 + `Retry-After`). 해시 비용을 공격 증폭에 쓰지 못하게 하기 위해서다.
- 프록시 뒤에서는 `remoteAddress`가 프록시 IP다. `X-Forwarded-For`는 신뢰 프록시 설정이 있을 때만 쓰는데, Core에 그 설정이 생기기 전까지 v1은 쓰지 않는다(§11 Q6).
- 클러스터: `LoginThrottle`을 Redis 등으로 바꾼다(07).

### 8.2 사용자 열거 방지

| 경로 | 대응 |
|---|---|
| `/login` | 모르는 사용자, 틀린 비밀번호, 비활성 사용자에게 같은 401, 같은 본문을 주고 `DUMMY_HASH`로 같은 반복 수의 verify를 돌린다. 모르는 username도 throttle 키를 쌓는다 |
| `/password/forgot` | 항상 202. 사용자가 없을 때도 일회용 토큰 생성과 같은 비용의 HMAC을 한 번 계산한다 |
| `/signup` | 409 `USER_EXISTS`는 피할 수 없다(OWASP도 인정). IP throttle로 대량 조회를 늦춘다. 완전 차단이 필요하면 `emailVerification(true, true)` + `beforeSignup`에서 중복이어도 202를 주는 방식을 앱이 고른다(§11 Q5) |
| `EMAIL_NOT_VERIFIED` | 비밀번호가 맞았을 때만 낸다(사실상 인증 성공이라 정보 누출이 아니다) |
| 관리 API | 인증된 관리자만 쓰므로 404를 그대로 쓴다 |

### 8.3 비밀번호 정책

- 기본은 최소 12자, 최대 128자다. 조합 규칙(대문자, 특수문자)은 두지 않는다. 내장 흔한 비밀번호 약 1,000개와 username 포함 여부를 거부한다. 비밀번호를 강제로 주기적으로 바꾸게 하지 않는다.
- 근거: OWASP는 MFA가 없으면 15자 미만, 있으면 8자 미만을 약하다고 보고, 최대 길이는 64자 이상 허용하라고 한다(NIST SP 800-63B). 12는 기기 관리 화면 입력 부담과 절충한 값이다(§11 Q4). 최대 128은 PBKDF2 입력 DoS를 막는다(01 §5).
- 유출 검사 SPI `BreachedPasswordChecker`: HIBP k-anonymity(`https://api.pwnedpasswords.com/range/<SHA1 앞 5자>`) 구현은 네트워크가 필요하므로 모듈에 넣지 않고 문서 예제로만 둔다. 오프라인 기기에서도 돌아야 하기 때문이다. SHA-1 `MessageDigest`는 API 1부터 있다.
- 적용 지점: signup, `/password`, `/password/reset`, 관리자 생성·비밀번호 변경. 로그인에는 적용하지 않는다(기존 사용자를 잠그지 않기 위해서). 다만 로그인 성공 시 위반이 있으면 응답에 `"passwordPolicyViolations":[...]`를 넣어 앱이 변경을 권할 수 있게 한다.

### 8.4 재설정과 이메일 검증

- 모듈이 일회용 토큰을 발급·검증하고(§4.1 8–11), 개발자는 이벤트에서 메일을 보낸다. 링크 URL은 앱이 만든다(모듈은 프런트 경로를 모른다).
- OWASP Forgot Password Cheat Sheet 기준을 지킨다: 같은 응답, 짧은 만료, 단일 사용, 재설정 후 모든 세션 무효(`ver+1`, `revokeUser`), 재설정 성공 후 자동 로그인 안 함(https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).
- 토큰을 URL 쿼리로 보내면 `Referer`로 샐 수 있다. 문서에 "재설정 화면은 외부 자원을 불러오지 말 것, 또는 `Referrer-Policy: no-referrer`"를 쓴다.

```

- 뒷문이 없다. `tokenFor`는 공개 `TokenService.issueAccess`로 **진짜 토큰**을 만들고, 검증은 운영과 같은 경로를 탄다. store가 InMemory가 아니면 `IllegalStateException("tokenFor needs InMemoryUserStore; issue with auth.tokens().issueAccess(user)")`를 던진다.
- 직접 스코프(`AuthUser.scopes`)를 쓰므로 역할 표가 없어도 `require("posts:write")`를 시험할 수 있다. 역할 매핑까지 시험하려면 `tokenForRoles`를 쓴다.

저장소 안 테스트(`NaruServe-utils`의 test는 `NaruServe-api` testFixtures의 `TestApp`을 쓴다. `TestApp`은 `RestApp.builder()` + `InMemoryHttpAdapter` + `StubJsonCodec`이며, `send(method, target, String... headerPairs)`가 `ClientResponse(status(), header(), text())`를 돌려준다):

```java
@Test void postsRequiresWriteScope() throws Exception {
    Auth auth = AuthTesting.builder().build();
    TestApp t = TestApp.create();
    t.app().use(auth);
    t.app().post("/posts", auth.require("posts:write"), (req, res) -> res.status(201).end());

    assertEquals(401, t.send("POST", "/posts").status());
    assertEquals(403, t.send("POST", "/posts", AuthTesting.bearer(AuthTesting.tokenFor(auth, "bob", "posts:read"))).status());
    assertEquals(201, t.send("POST", "/posts", AuthTesting.bearer(AuthTesting.tokenFor(auth, "alice", "posts:write"))).status());
}
```

```kotlin
@Test fun `expired token is 401`() {
    val clock = AuthTesting.clock(0)
    val auth = AuthTesting.builder().timeSource(clock).build()
    val t = TestApp.create().apply { app().use(auth); app().get("/me2") { _, res -> res.send("ok") } }
    val token = AuthTesting.tokenFor(auth, "alice")
    clock.advance(16 * 60_000L)
    assertEquals(401, t.send("GET", "/me2", *AuthTesting.bearer(token)).status())
}
```

- 확인할 점: `StubJsonCodec`이 `Map` 본문(`/login`)을 얼마나 지원하는지 봐야 한다. 엔드포인트 계약 테스트는 실제 `GsonJsonCodec`이 필요할 수 있다(testImplementation `NaruServe-gson`).
- 주니어 앱 쪽(`TestApp`이 공개되지 않은 경우): `app.listen(0)`과 아무 HTTP 클라이언트로 같은 `tokenFor`/`bearer`를 쓴다. `AuthTesting`은 어댑터와 무관하다.
- 계약 테스트 목록(구현 시 SRS AC 후보): §2.3의 스코프 매칭 표 15건(03), §4의 엔드포인트별 상태·`code`, §5의 순서(목 store로 호출 순서 기록), 열거 방지(모르는 사용자와 틀린 비밀번호의 응답 바이트가 같은지, `requestId` 마스킹은 `TestSupport.maskRequestId`), 재사용 탐지, CSRF(헤더 없음 → 403, 다른 Origin → 403), Kotlin 컴파일 테스트(T11 관례: §3.1 오버로드 표의 호출 전부).

## 10. 주니어 첫 화면 (통합 최종본)

```java
InMemoryUserStore users = new InMemoryUserStore();
users.add("admin", "correct-horse-battery", "admin");

Auth auth = Auth.builder(System.getenv("JWT_SECRET"))
    .users(users)
    .roles(RolePolicy.builder()
        .role("admin",  "posts:*", "auth:*")
        .role("editor", "posts:read", "posts:write")
        .build())
    .publicPaths("/health")
    .build();

RestApp.start(8080, app -> {
    app.use("/auth", auth.routes());
    app.use("/auth/admin", auth.adminRoutes());
    app.use(auth);
    app.get("/health", (req, res) -> res.send("ok"));
    app.post("/posts", auth.require("posts:write"), (req, res) ->
        res.status(201).json(posts.create(auth.user(req).getId(), req.body(Post.class))));
});
```

마운트 순서: `/auth` 라우터가 `app.use(auth)`보다 먼저 와도 되고 나중에 와도 된다. 기본 공개 경로가 `/auth/login` 등을 열어 두고, 관리 라우터는 자기 가드를 갖고 있다.

## 11. 열린 질문

1. **JsonCodec 얻기**: JWT 인코딩에 앱의 `JsonCodec`이 필요하지만, `ApplicationContext`에는 그것을 꺼내는 공개 경로가 없다. 후보는 셋이다. (a) Core가 codec을 `ServiceRegistry`에 등록한다(C3, 별도 SRS). (b) `.jsonCodec(codec)`을 필수로 한다. (c) 첫 요청까지 지연한다. 권고: C3. C3가 들어오기 전에는 `RestApp.create()` 사용자를 위해 `build()`가 "jsonCodec(new GsonJsonCodec()) 필요"라는 메시지로 실패한다.
2. **PBKDF2 반복 수**: Android 5 기기에서 측정한 뒤 정한다(00 Q1). 측정해서 2초를 넘으면 Android 기본값을 낮추고 WARN을 남긴다.
3. **refresh 기본 저장소**: 기본은 `tokenVersion`만(상태 없음)이고 R은 선택이다. 대안은 InMemory R을 기본으로 켜는 것(RFC 9700 준수, 대신 재시작하면 로그아웃)이다. 기기 재시작 빈도를 보고 정한다. `reuseGrace` 기본값(0 vs 몇 초. 여러 탭이 동시에 refresh하면 오탐이 난다)도 같이 정한다.
4. **최소 비밀번호 길이**: 12(현재 제안)와 OWASP·NIST의 단일 인자 기준 15 사이에서 정한다.
5. **가입 열거 완전 차단 모드**를 내장할지(항상 202 + 메일로 "이미 가입됨" 알림). 내장하지 않으면 앱이 `beforeSignup`으로 구현한다.
6. **신뢰 프록시**: `X-Forwarded-For`를 throttle 키에 쓰려면 Core의 trust-proxy 설정이 필요하다(Express `trust proxy`에 해당). 별도 SRS가 필요하다.
7. **Core 변경 C1·C2**(오류 `code`). C2가 없으면 인증 전용 `code`가 본문에 나가지 않는다. 우선순위가 가장 높다.
8. **삭제된 사용자의 access 토큰**(§5.7): `verifyUserOnEveryRequest`를 기본으로 켤지, 사용자별 폐기 목록(`RefreshTokenStore.isUserRevoked` 같은 확장)을 둘지.
9. **`AuthTesting` 위치**: main(현재 제안)과 testFixtures 산출물 사이에서 정한다. main이면 운영 jar에 수 KB가 늘어난다.
10. **`/auth/admin` 경로와 스코프 이름 `auth:*`**: 앱 자체의 `auth:` 네임스페이스와 겹칠 수 있다. `adminScopePrefix`로 피할 수 있지만 기본값으로 `naru.auth:*`가 나은지 정한다.

### 검증 한계
- RFC 9700과 OWASP Authentication은 이번에 직접 열어 확인했다(§2.2.2, §4.14 번호, OWASP의 8/15/64 수치). 나머지 URL은 기억에 의존했고 열어 보지 않았다.
- Core 동작 중 오류 `code`가 상태로만 정해진다는 것(`internal/StandardErrors.code`, `internal/ErrorPath`), `Router`가 `Middleware`가 아니라는 것, `RouteGroup`에 `(path, Middleware, RouteHandler)` 오버로드가 없다는 것, `ApplicationContext`에 codec 접근자가 없다는 것, `Request`에 `requestId` 접근자가 없다는 것은 코드에서 확인했다. Kotlin 오버로드 해석(§3.1 표)은 추론이며 컴파일로 확인하지 않았다. 구현할 때 T11 Kotlin 테스트로 고정해야 한다.
