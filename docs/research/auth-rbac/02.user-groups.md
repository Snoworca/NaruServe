# 연구 02 — 사용자 그룹 관리 (중첩 그룹)

> **3판 안내:** 최종 결정본은 00 개요 33판이다(최종 규칙은 00 §6.3 R28–R47, 점검표 §6.4). 최종 결정과 이름은 [00 개요](00.overview.md)가 우선한다. 이 문서와 다른 부분은 00 §6(06 검토로 바뀐 결정), §7(최종 이름표), §11(정정 기록)을 본다.

> 범위: NaruServe 선택 auth 모듈의 그룹 계층 설계. 코드·빌드·`docs/spec` 변경 없음.
> 이 문서의 타입·메서드·경로 이름은 모두 **제안**이다(사양서 `object.md`에 없음). 관련 요구 ID는 아직 없다 — 구현 전 SRS 요구를 먼저 만들어야 한다.
> 형제 연구(`UserStore`: 프레임워크가 부르고 사용자가 DB에 연결하는 CRUD 인터페이스)와 같은 패턴을 따른다.

## 0. 요약 (권고 5줄)

1. 그룹 계층은 **DAG**(부모 여러 개 허용)로 두고, 순환은 쓰기 시점(중첩 추가 API)에서 거부하고 읽기 시점(확장)에서도 visited 집합으로 무해하게 끊는다.
2. 사용자가 구현하는 `GroupStore`(제안)는 **직접 관계만** 돌려주는 읽기 메서드 2개(`groupsOfUser`, `parentsOf`)가 최소다. 확장(전이 폐포)은 프레임워크가 레벨 단위 BFS로 계산한다. DB가 재귀 CTE를 쓸 수 있으면 `effectiveGroupsOfUser`를 override한다.
3. N+1을 막으려고 `parentsOf`는 **그룹 집합을 한 번에** 받는다. 그러면 DB 호출은 그룹 수가 아니라 깊이 수(기본 상한 8)만큼만 난다.
4. 기본 캐시는 **요청 단위 메모(`req.attribute`)**만 둔다. 앱 단위 TTL 캐시는 선택이고, 내장 관리 엔드포인트로 쓰면 바로 무효화된다. 확장된 그룹을 JWT에 넣는 것은 기본으로 끄고, 켜면 크기 상한과 짧은 토큰 수명을 같이 건다.
5. 그룹과 역할은 분리한다: **"그룹이 역할을 준다"**(Keycloak 방식). 다만 주니어가 바로 쓰도록 `requireGroup("admin")` 하나로도 인가할 수 있게 한다. 역할 계층(RBAC1)은 역할 연구 쪽에 맡긴다.

## 2. 데이터 모델

### 2.1 트리 vs DAG

```
트리 (부모 1개)                 DAG (부모 여럿, 권고)

      company                        company
      /     \                        /     \
    eng    sales                  eng     sales
    /  \                          /  \     /
backend frontend            backend  oncall      <- oncall 은 eng 와 sales 둘 다의 하위
   |                            |
 alice                        alice  (alice ∈ backend, oncall)
```

- 트리: 경로가 하나라 "왜 이 그룹에 속하나" 설명이 쉽다. 하지만 "on-call은 eng이면서 sales"를 표현하려면 그룹을 복제해야 한다.
- DAG: 실무 조직 구조에 맞는다. 다이아몬드(같은 조상에 두 길로 도달)는 visited 집합으로 한 번만 센다.
- **권고: DAG를 허용**한다. 트리로만 쓰고 싶은 사용자는 부모를 하나만 넣으면 되고, 프레임워크는 차이를 몰라도 된다. 트리 강제 옵션(`maxParents(1)`)은 요청이 오면 추가(지금은 생략).

### 2.2 저장 형태 (사용자 DB 예시, 강제 아님)

```
groups(id PK, name)
group_members(group_id, user_id)          -- 사용자 → 그룹 (직접)
group_parents(child_id, parent_id)        -- 그룹 → 부모 그룹 (직접, DAG 간선)
```

간선 방향은 **자식 → 부모**로 통일한다(`parentsOf`). 확장은 "사용자에서 위로" 올라가며, 이것이 인가 질의(이 사용자의 유효 그룹은?)에 필요한 유일한 방향이다. `childrenOf`는 관리 화면(그룹 트리 표시)용 선택 메서드다.

### 2.3 그룹 ID

`String`. 사용자 DB의 숫자 키도 문자열로 넘긴다(`UserStore`와 같은 규칙으로 맞춘다). 이름과 ID를 분리할지는 열린 질문(§9).

## 3. `GroupStore` 인터페이스 (제안)

### 3.1 주니어 최소 예제 — 먼저 이것만

메모리 구현이 기본 제공되어 DB 없이 바로 돈다.

```java
InMemoryGroupStore groups = new InMemoryGroupStore();   // 제안 이름
groups.addMember("admins", "alice");
groups.addMember("backend", "bob");
groups.nest("backend", "eng");        // backend 는 eng 의 하위 그룹

app.use(Auth.jwt(secret).users(userStore).groups(groups));   // Auth.* 는 형제 연구와 맞출 제안 이름
app.get("/admin/stats", Auth.requireGroup("admins"), (req, res) -> res.json(stats()));
app.get("/eng/docs",    Auth.requireGroup("eng"),    (req, res) -> res.send("ok")); // bob 통과 (backend ⊂ eng)
```

```kotlin
val groups = InMemoryGroupStore().apply {
    addMember("admins", "alice")
    nest("backend", "eng")
}
app.use(Auth.jwt(secret).users(userStore).groups(groups))
app.get("/eng/docs", Auth.requireGroup("eng")) { req, res -> res.send("ok") }
```

핸들러 안에서는 `Auth.groups(req)`(제안)가 확장된 `Set<String>`을 돌려준다.

### 3.2 DB 연결 — 읽기 2개만 구현

```java
// 제안. 프레임워크가 부르고, 사용자는 DB 호출만 채운다.
public interface GroupStore {
    /** 사용자가 직접 속한 그룹 ID. 없으면 빈 집합. */
    @NonNull Set<String> groupsOfUser(@NonNull String userId) throws Exception;

    /** 주어진 그룹들의 직접 부모 그룹 ID 합집합. 한 번의 IN 질의로 구현하라. */
    @NonNull Set<String> parentsOf(@NonNull Set<String> groupIds) throws Exception;

    /** 유효 그룹(직접 + 모든 조상). 기본은 프레임워크 BFS. 재귀 CTE가 있으면 override. */
    default @NonNull Set<String> effectiveGroupsOfUser(@NonNull String userId) throws Exception {
        return GroupExpander.expand(this, userId, GroupExpander.DEFAULT_LIMITS);
    }
}
```

```java
// JDBC 예시: 직접 관계만
public final class JdbcGroupStore implements GroupStore {
    public Set<String> groupsOfUser(String userId) throws Exception {
        return queryIds("SELECT group_id FROM group_members WHERE user_id = ?", userId);
    }
    public Set<String> parentsOf(Set<String> ids) throws Exception {
        return queryIdsIn("SELECT parent_id FROM group_parents WHERE child_id IN (%s)", ids);
    }
}
```

```kotlin
class JdbcGroupStore(private val db: Db) : GroupStore {
    override fun groupsOfUser(userId: String): Set<String> =
        db.ids("SELECT group_id FROM group_members WHERE user_id = ?", userId)
    override fun parentsOf(groupIds: Set<String>): Set<String> =
        db.idsIn("SELECT parent_id FROM group_parents WHERE child_id IN (%s)", groupIds)
}
```

확장 결과를 DB가 직접 계산하는 경우(PostgreSQL/MySQL 8/SQLite 3.8.3+ 재귀 CTE). `UNION`(ALL 아님)이 순환에서도 종료를 보장한다. 깊이 상한은 DB 쪽 책임이 된다는 점을 Javadoc에 쓴다.

```sql
WITH RECURSIVE g(id, depth) AS (
  SELECT group_id, 0 FROM group_members WHERE user_id = ?
  UNION
  SELECT p.parent_id, g.depth + 1 FROM group_parents p JOIN g ON p.child_id = g.id
  WHERE g.depth < 8
) SELECT DISTINCT id FROM g;
```

### 3.3 관리용 쓰기 — 별도 인터페이스

읽기만 필요한 사용자(그룹을 LDAP/외부 시스템에서 관리)는 쓰기를 구현할 이유가 없다. 내장 관리 엔드포인트를 켤 때만 요구한다.

```java
// 제안. app.use(Auth.groupAdmin("/auth/groups", store)) 가 요구
public interface GroupAdminStore extends GroupStore {
    void createGroup(@NonNull String groupId) throws Exception;          // 이미 있으면 GroupExistsException(→409)
    void deleteGroup(@NonNull String groupId) throws Exception;          // 소속·간선도 함께 삭제
    @NonNull List<String> listGroups() throws Exception;
    boolean groupExists(@NonNull String groupId) throws Exception;
    void addMember(@NonNull String groupId, @NonNull String userId) throws Exception;     // 멱등
    void removeMember(@NonNull String groupId, @NonNull String userId) throws Exception;  // 멱등
    @NonNull Set<String> membersOf(@NonNull String groupId) throws Exception;              // 직접 멤버
    void addParent(@NonNull String childId, @NonNull String parentId) throws Exception;   // 순환 검사는 프레임워크가 먼저
    void removeParent(@NonNull String childId, @NonNull String parentId) throws Exception;
    @NonNull Set<String> childrenOf(@NonNull String groupId) throws Exception;            // 트리 화면용
}
```

- 메서드 이름에 Kotlin 키워드 없음(`in`, `is` 피함 — `isMember` 대신 확장 집합 검사).
- 콜백이 아닌 다중 메서드 인터페이스라 `@FunctionalInterface` 대상 아님. 대신 `InMemoryGroupStore`가 `GroupAdminStore`를 구현해 주니어가 상속·위임으로 시작할 수 있게 한다.
- `throws Exception`: DB 예외를 사용자가 감쌀 필요 없게 한다. 프레임워크는 기존 오류 처리(`app.onError`)로 500에 넘긴다.
- Android/API 21: `Set`/`List`/`HashSet`/`ArrayDeque`만 쓰면 되며 문제 없다. `InMemoryGroupStore`는 `ConcurrentHashMap` + 쓰기 시 `synchronized`로 충분하다.

## 4. 확장 알고리즘

레벨 단위 BFS. 한 레벨의 모든 그룹을 `parentsOf(Set)` **한 번**에 묻는다.

```
expand(store, userId, limits):
    frontier = store.groupsOfUser(userId)
    result   = copy(frontier)                 # visited 겸 결과
    depth = 0
    while frontier not empty:
        if depth == limits.maxDepth:          # 기본 8
            throw GroupHierarchyTooDeepException(userId, depth)   # 조용히 잘라내지 않는다
        parents = store.parentsOf(frontier)
        frontier = parents - result           # 이미 본 그룹 제거 → 순환·다이아몬드 무해
        result += frontier
        if result.size > limits.maxGroups:    # 기본 256
            throw TooManyGroupsException(userId, result.size)
        depth += 1
    return unmodifiable(result)
```

- **순환**: `frontier = parents - result`라 순환이 있어도 반드시 끝난다(유한 그룹 수). 그래서 읽기 경로에서 순환은 오류가 아니라 무해하다. 대신 쓰기 경로(`addParent`)에서 막는다.
- **쓰기 시 순환 검사**: `addParent(child, parent)` 전에 `parent`에서 위로 BFS해 `child`가 나오면(또는 `child == parent`) 409로 거부. 같은 BFS를 재사용한다.
- **상한 초과 시 실패(fail-closed)**: 잘라낸 결과로 인가하면 "있어야 할 거부 그룹"이 아니라 "있어야 할 허용 그룹"이 빠지는 것이라 대체로 안전 쪽이지만, 원인을 숨긴다. Zanzibar 계열처럼 예외 → 500 + 로그로 알린다. 기본 상한은 `RestApp` 설정이 아니라 `Auth...groups(store, limits)`의 선택 인자(제안).
- **비용**: DB 왕복 = 1(`groupsOfUser`) + 깊이 d. 그룹 단위로 `parentsOf(String)`을 부르면 왕복이 그룹 수 n만큼 나는 N+1이 된다 — 그래서 단건 메서드를 아예 두지 않는다. 재귀 CTE override 시 1회.
- `parentsOf`에 넘어가는 집합 크기는 `maxGroups`로 묶여 SQL `IN` 목록 길이 한도(SQLite 기본 999 변수) 안에 든다.

## 5. 캐싱과 JWT 클레임

### 5.1 언제 무엇을 부르나 (요청당)

| 단계 | 호출 | 기본 |
|---|---|---|
| 인증 미들웨어 | 없음(그룹은 지연 계산) | — |
| `requireGroup`/`Auth.groups(req)` 첫 호출 | `effectiveGroupsOfUser` 1회 → DB 1+d 회 | 결과를 `req.attribute("naruserve.auth.groups", set)`에 메모 |
| 같은 요청의 두 번째 검사 | 없음(메모 사용) | — |
| 그룹 검사가 없는 라우트 | 없음 | — |

지연 계산이라 그룹이 필요 없는 라우트는 비용 0이다.

### 5.2 세 가지 선택지

| 방식 | 비용 | 소속 변경 반영 | 위험 |
|---|---|---|---|
| A. 요청마다 계산 + 요청 메모 (**기본**) | 요청당 DB 1+d | 즉시 | DB 부하. d가 작고 인덱스가 있으면 보통 충분 |
| B. 앱 단위 TTL 캐시 `userId → Set` (선택, 기본 TTL 30초, 최대 항목 수 제한) | 캐시 적중 시 0 | 내장 관리 API로 쓰면 즉시 무효화(전체 비움 — 그룹 간선 변경은 여러 사용자에 영향), DB를 직접 고치면 TTL만큼 지연 | 다중 인스턴스에서 인스턴스별 캐시라 TTL만큼 불일치 |
| C. 로그인 시 확장 그룹을 JWT `groups` 클레임에 넣음 (선택, 기본 끔) | 요청당 0 | **토큰 만료까지 반영 안 됨**(그룹에서 뺀 사용자가 계속 접근) | 토큰 크기: 그룹 ID 20자 × 100개 ≈ 2KB+, base64로 더 커져 헤더 한도(TinyHttpd/프록시 8KB 전후)에 근접. AD의 토큰 비대 문제와 같다 |

권고:
- 기본은 A. B는 `groupCacheTtl(30, SECONDS)` 같은 한 줄 옵션(제안)으로 켜고, 캐시는 `ConcurrentHashMap` + 만료 시각으로 충분하다(새 의존성 없음).
- C를 켜면 프레임워크가 `maxGroupsInToken`(기본 32)을 넘을 때 클레임을 **넣지 않고** A로 되돌아간다(잘라 넣지 않음). 또한 짧은 액세스 토큰 수명(≤15분) + 리프레시 시 재계산을 문서에 강제 권고한다. 토큰 검증은 형제 연구(JWT) 영역이며, 여기서는 클레임 이름만 맞추면 된다.
- 그룹 해제를 즉시 반영해야 하는 관리자 권한 같은 것은 C를 쓰지 말라고 문서에 쓴다.

## 6. 내장 관리 엔드포인트 (제안)

`app.use(Auth.groupAdmin("/auth/groups", store).guard(Auth.requireGroup("group-admins")))` — 가드 없이는 등록을 거부(보안 기본값). 모든 응답은 JSON(`JsonCodec` 경유), 오류는 표준 오류 형식(`docs/api/middleware.md` §표준 오류 형식)을 따른다.

| 메서드·경로 | 동작 | `GroupAdminStore` 호출 | 성공 / 실패 |
|---|---|---|---|
| `GET /auth/groups` | 그룹 목록 | `listGroups` | 200 `["admins",...]` |
| `POST /auth/groups` body `{"id":"eng"}` | 그룹 생성 | `createGroup` | 201 / 400 잘못된 ID, 409 존재 |
| `GET /auth/groups/:id` | 그룹 상세(직접 멤버·부모·자식) | `groupExists`, `membersOf`, `parentsOf({id})`, `childrenOf` | 200 / 404 |
| `DELETE /auth/groups/:id` | 그룹 삭제 | `deleteGroup` | 204 / 404 |
| `PUT /auth/groups/:id/members/:userId` | 멤버 추가(멱등) | `addMember` (+ `UserStore` 존재 확인) | 204 / 404 그룹 또는 사용자 없음 |
| `DELETE /auth/groups/:id/members/:userId` | 멤버 제거(멱등) | `removeMember` | 204 |
| `PUT /auth/groups/:id/parents/:parentId` | 중첩(`id`를 `parentId` 하위로) | 순환 검사 BFS → `addParent` | 204 / 404, **409 순환**, 409 깊이 초과 |
| `DELETE /auth/groups/:id/parents/:parentId` | 중첩 해제 | `removeParent` | 204 |
| `GET /auth/users/:userId/groups?effective=true` | 사용자 그룹(직접/유효) | `groupsOfUser` 또는 `effectiveGroupsOfUser` | 200 |

CRUD 이벤트 매핑: Create=`POST`(그룹)·`PUT`(멤버/간선, 관계는 경로로 식별되므로 멱등 PUT), Read=`GET`, Update=그룹 이름 변경은 ID 정책 확정 전까지 생략, Delete=`DELETE`. 모든 쓰기 성공 후 B 캐시를 비운다. 쓰기 훅(`onGroupChanged` 콜백, `@FunctionalInterface`)은 감사 로그 요청이 오면 추가(지금은 생략).

순환 검사와 `addParent` 사이 경쟁(두 관리자가 동시에 A→B, B→A): `InMemoryGroupStore`는 한 락 안에서 검사+추가한다. DB 구현은 원자성을 보장할 수 없으므로 문서에 "드문 경쟁으로 순환이 생겨도 읽기 확장은 visited로 끝나므로 인가가 멈추지 않는다"고 쓰고, 이것이 읽기 경로를 순환 안전하게 만든 이유다.

## 7. 그룹 vs 역할

| 모델 | 설명 | 장점 | 단점 |
|---|---|---|---|
| 그룹 = 역할 (Casbin `g`) | 하나의 개념, 계층 하나 | 가장 단순. 주니어가 이해하기 쉬움 | 조직 구조 변경이 곧 권한 변경. "eng 그룹"이 무슨 권한인지 코드에 흩어짐 |
| 그룹이 역할을 준다 (Keycloak) | 사용자→그룹(계층)→역할, 코드는 역할로 검사 | 조직(그룹)과 권한(역할) 분리. 역할 목록이 작고 안정적 | 매핑 테이블 하나 더. 설명할 개념이 둘 |
| 역할 계층 (NIST RBAC1, Spring `RoleHierarchy`) | 역할끼리 상속(`admin ≥ editor ≥ viewer`) | 권한 포함 관계 표현 | 그룹 계층과 섞으면 두 그래프를 다 따라가야 함 |

권고: **그룹이 역할을 준다**를 표준 모델로 하되 단계적으로 쓴다.
1. 시작: 그룹만. `Auth.requireGroup("admins")`. 역할 개념 몰라도 됨.
2. 성장: `GroupStore`에 선택 메서드 `default Set<String> rolesOfGroups(Set<String> groupIds) { return emptySet(); }`(제안)를 override하면 유효 역할 = 사용자 직접 역할 ∪ `rolesOfGroups(유효 그룹)`. 코드는 `Auth.requireRole("editor")`. 역할 저장·역할 계층은 역할 연구 문서와 맞춘다.
3. 역할 계층(RBAC1)은 그룹 계층과 별도 그래프로, 같은 `GroupExpander` 알고리즘(레벨 BFS·visited·상한)을 재사용한다.

이렇게 하면 1단계 코드가 2단계에서도 그대로 돈다(호환 유지).

## 8. 함정

- **N+1**: 그룹당 `parentsOf(String)` 단건 호출. → 단건 메서드를 두지 않고 집합 인자만 받는다.
- **`UNION ALL` 재귀 CTE**: 순환이 있으면 무한 루프(DB가 멈춤). → 예시에 `UNION` + 깊이 조건을 둔다.
- **상한 초과를 조용히 잘라내기**: 디버깅 불가. → 예외로 알린다.
- **JWT에 그룹 넣고 해제 반영 기대**: 만료 전까지 안 됨. → 기본 끔, 크기 상한, 짧은 수명.
- **그룹 삭제 시 매달린 간선/멤버**: 부모 간선이 남으면 삭제된 ID가 유효 그룹에 계속 나온다. → `deleteGroup` 계약에 "관련 행도 삭제"를 명시하고, `InMemoryGroupStore` 테스트로 고정.
- **ID 정규화 차이**: `"Admins"` vs `"admins"`. → 그룹 ID는 대소문자 구분, 허용 문자 `[A-Za-z0-9._-]{1,64}`(제안)로 쓰기 API에서 검증(신뢰 경계).
- **가드 없는 관리 엔드포인트**: 누구나 자신을 admins에 추가. → 가드 필수, 없으면 `listen()` 전 등록 단계에서 `IllegalStateException`.
- **자기 자신을 부모로**: `PUT /auth/groups/eng/parents/eng` → 순환 검사에서 `child == parent`도 409.
- **다중 인스턴스 캐시**: B 캐시는 인스턴스 로컬. 분산 무효화는 범위 밖이라고 문서에 쓴다.
- **스레드 안전**: `GroupStore`는 여러 요청 스레드에서 동시에 불린다. JDBC 구현은 요청마다 커넥션을 빌려야 한다는 점을 예제에 보인다.

## 9. 열린 질문

1. 그룹 ID와 표시 이름을 분리할지(이름 변경 = Update 엔드포인트 필요). 지금은 ID 하나로 시작하는 쪽을 권고.
2. 멀티 테넌트(Casbin domains처럼 `tenant:group`)를 1차 범위에 넣을지. 권고: 넣지 않고, 필요하면 ID 접두사 관례로 처리.
3. 기본 상한값(깊이 8, 그룹 256, 토큰 32)의 근거 — 실제 사용 사례로 조정 필요.
4. `effectiveGroupsOfUser` override 시 프레임워크가 상한을 사후 검사(크기만)할지.
5. 형제 연구 `UserStore`와 `GroupStore`를 한 인터페이스로 합칠지(주니어는 하나만 구현) vs 분리(읽기 전용 외부 그룹 소스). 권고: 분리하되 `InMemory*`는 둘 다 한 번에 만들 수 있는 팩토리(`Auth.inMemory()`, 제안) 제공.
6. 관리 엔드포인트 경로 접두사(`/auth/groups`)를 `UserStore` 엔드포인트와 같은 라우트 그룹 아래로 통일할지.
7. 이 기능의 SRS 요구 ID가 아직 없다 — 구현 전 `docs/spec/`에 요구를 만들어야 한다(CLAUDE.md SpecKiwi 규칙).
