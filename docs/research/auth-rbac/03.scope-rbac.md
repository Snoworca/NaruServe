# 03. 스코프 기반 RBAC 설계 연구

> **3판 안내:** 최종 결정본은 00 개요 33판이다(최종 규칙은 00 §6.3 R28–R47, 점검표 §6.4). 최종 결정과 이름은 [00 개요](00.overview.md)가 우선한다. 이 문서와 다른 부분은 00 §6(06 검토로 바뀐 결정), §7(최종 이름표), §11(정정 기록)을 본다.

> 상태: 연구 초안. 여기 나오는 `NaruAuth`, `AuthUser`, `RoleStore`, `RolePolicy`, `AccessRule`, `auth.require(...)` 등 **이름은 모두 제안**이며 사양서(`object.md`)·SRS(`docs/spec/`)에 없다. 구현 전에 SRS 요구로 등록해야 한다.
> 입력 전제: 형제 연구 01(JWT + `UserStore`)과 02(중첩 그룹 + `GroupStore`)가 요청에 인증된 주체(사용자 id, 유효 그룹, 역할/스코프)를 붙여 준다.

## 0. 요약 (권고 5줄)

1. 권한은 `리소스:동작` 스코프 문자열(`posts:read`)로 표현한다. 와일드카드는 **부여(grant) 쪽 마지막 세그먼트의 `*`만** 허용하고(`posts:*`, `*`), 요구(require) 쪽은 항상 구체 스코프다.
2. 역할→스코프 매핑은 기본으로 코드 안 정적 정책(`RolePolicy`)이고, 런타임에 바꿔야 하면 사용자가 구현하는 `RoleStore` 하나를 꽂는다(형제 연구와 같은 "프레임워크가 당신의 인터페이스를 부른다" 패턴).
3. 주 API는 **라우트 미들웨어 가드** `app.post("/posts", auth.require("posts:write"), handler)`, 묶음은 그룹 가드 `api.use(auth.require(...))`, 탈출구는 핸들러 안 `auth.user(req).can("posts:write")` 와 ABAC 훅 `auth.check(rule)`이다. 어노테이션은 채택하지 않는다.
4. 인증 없음 = 401(`WWW-Authenticate: Bearer`), 인증됐지만 스코프 부족 = 403(`error="insufficient_scope"`). `app.use(auth)` 한 줄로 **기본 거부(인증 필수)** 가 되고 공개 경로는 설정에 명시한다.
5. 주니어 실수 방어: 가드가 인증을 스스로 보장해 등록 순서와 무관하게 동작, 등록 시 스코프 문법·오타 검사, 가드 없는 라우트 경고(v1은 런타임 1회 경고, 시작 시 전체 보고는 코어 라우트 조회 API가 생길 때).

## 1. 선행 사례

| 사례 | 핵심 | 가져올 점 |
|---|---|---|
| OAuth 2.0 scope, RFC 6749 §3.3 <https://datatracker.ietf.org/doc/html/rfc6749#section-3.3> | 공백 구분, 대소문자 구분, 순서 무관 문자열 집합. 의미는 서버가 정의 | 문자열 형식·대소문자 구분·`scope` 클레임 |
| RFC 6750 §3.1 <https://datatracker.ietf.org/doc/html/rfc6750#section-3.1> | `invalid_token`→401, `insufficient_scope`→403 + `WWW-Authenticate` | 401/403 구분과 헤더 형식 그대로 |
| Spring Security <https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html> | JWT `scope`/`scp`를 `SCOPE_x` 권한으로 변환, `hasAuthority("SCOPE_x")`, `hasRole`은 `ROLE_` 접두사 | 접두사 혼동이 흔한 실수 → 우리는 접두사 없이 스코프·역할을 별도 메서드로 |
| Spring `authorizeHttpRequests` <https://docs.spring.io/spring-security/reference/servlet/authorization/authorize-http-requests.html> | `anyRequest().authenticated()`로 기본 거부, `permitAll()` 화이트리스트 | 기본 거부 + 공개 경로 목록 |
| Spring `@PreAuthorize` <https://docs.spring.io/spring-security/reference/servlet/authorization/method-security.html> | SpEL 어노테이션, 프록시 필요 | 람다 API엔 안 맞음(§5.4) |

| express-jwt-permissions <https://github.com/MichielDeMey/express-jwt-permissions> | `guard.check([['a','b'],['c']])` = (a AND b) OR c | 중첩 배열은 읽기 어렵다 → `allOf`/`anyOf` 명시 |

| Ktor `authenticate {}` <https://ktor.io/docs/server-auth.html> | 블록 안 라우트만 인증 | 우리 `group` + `use`가 같은 역할 |
| NestJS Guards + `@Roles` <https://docs.nestjs.com/guards> | `CanActivate`, 메타데이터 + `Reflector`, 전역 가드 + `@Public()` | 전역 가드 + 공개 표시 패턴 |
| Auth0 RBAC <https://auth0.com/docs/manage-users/access-control/rbac> | 역할에 permission 묶고 토큰 `permissions` 클레임에 실음 | 토큰에 권한을 실으면 철회가 늦다(§4) |

## 2. 스코프 문법과 매칭 규칙

### 2.1 문법 (제안)

```
scope    = segment *( ":" segment )
segment  = 1*( a-z / 0-9 / "_" / "-" / "." )
grant    = scope | scope ":" "*" | "*"
require  = scope            ; 와일드카드 금지
```

- 대소문자 구분(RFC 6749). 단 **코드에 쓰는** 스코프(`require`, `RolePolicy`)는 소문자만 허용해 `Posts:Read` 같은 오타를 등록 시 `IllegalArgumentException`으로 잡는다. 토큰에서 온 스코프는 그대로 비교만 한다.
- 공백, 빈 세그먼트(`posts::read`), 끝 콜론은 오류. RFC의 공백 구분 목록은 토큰 파싱 때만 쪼갠다.
- `*`는 세그먼트 전체일 때만, 그리고 부여 쪽 마지막 세그먼트에만 의미가 있다. `po*`, `*:read`는 오류.
- 동작 함의(`write`가 `read`를 포함)는 **두지 않는다**. 명시가 주니어에게 더 안전하다. 필요하면 역할에 둘 다 넣는다.

### 2.2 매칭 알고리즘

요구 스코프 `a:b:c`는 유효 부여 집합이 다음 중 하나를 포함하면 통과: `a:b:c`, `a:b:*`, `a:*`, `*`. 해시 조회 최대 (세그먼트 수 + 1)번, 정규식 없음(API 21에서도 가볍다).

### 2.3 테스트 케이스 표

| # | 부여(granted) | 요구(required) | 결과 | 이유 |
|---|---|---|---|---|
| 1 | `posts:read` | `posts:read` | 통과 | 정확 일치 |
| 2 | `posts:read` | `posts:write` | 거부 | 다른 동작 |
| 3 | `posts:*` | `posts:write` | 통과 | 하위 와일드카드 |
| 4 | `posts:*` | `posts:comments:delete` | 통과 | 와일드카드는 모든 깊이 |
| 5 | `posts:*` | `posts` | 거부 | `posts:*`는 `posts` 자신을 포함하지 않음 |
| 6 | `posts` | `posts:read` | 거부 | 접두사만으로는 함의 없음 |
| 7 | `admin:*` | `posts:write` | 거부 | `admin:*`는 admin 네임스페이스만. 슈퍼유저 아님 |
| 8 | `*` | `anything:here` | 통과 | 전체 부여(시작 시 경고 로그) |
| 9 | `Posts:Read`(토큰) | `posts:read` | 거부 | 대소문자 구분 |
| 10 | `posts:write` | `posts:write:own` | 거부 | 더 구체적인 요구는 상위 부여로 충족 안 됨 |
| 11 | (없음) | `posts:read` | 거부(403) | 인증은 됐으나 권한 없음 |
| 12 | 부여 `po*` | — | 등록 오류 | 부분 와일드카드 금지 |
| 13 | — | 요구 `posts:*` | 등록 오류 | 요구 쪽 와일드카드 금지 |
| 14 | — | 요구 `posts read` | 등록 오류 | 공백 |
| 15 | `posts:read posts:write`(토큰 `scope` 문자열) | `posts:write` | 통과 | 공백 분리 후 비교 |

## 3. 역할→스코프 매핑과 저장소 인터페이스

### 3.1 유효 스코프 계산

```
유효 역할  = user.roles ∪ (유효 그룹들의 roles)          ← 01/02 연구 결과
유효 스코프 = ⋃ RoleStore.scopesOf(role) ∪ user.directScopes
토큰에 scope 클레임이 있으면: 유효 스코프 = 위 ∩ 토큰 scope   ← 토큰은 좁히기만 함
```

요청마다 한 번 계산해 `AuthUser`에 담는다. 토큰 `scope`는 "이 토큰으로 할 수 있는 최대치"(OAuth 위임 의미)로만 쓰고 권한을 늘리지 않는다. 이렇게 하면 역할에서 스코프를 빼는 순간 철회가 반영된다.

### 3.2 정적 정책 (기본, 주니어 권장)

```java
RolePolicy roles = RolePolicy.builder()                 // 제안 이름
    .role("viewer", "posts:read")
    .role("editor", "posts:read", "posts:write")
    .role("admin",  "posts:*", "users:*")
    .build();                                           // 문법 오류는 여기서 예외
```

정적 정책은 모든 부여 스코프를 알기 때문에 시작 시 **오타 검사**가 된다: `auth.require("posts:wrte")`인데 어떤 역할도 그것을 부여하지 않으면 경고한다.

### 3.3 사용자 구현 저장소 (동적)

```java
@FunctionalInterface
public interface RoleStore {                            // 제안
    /** 역할이 부여하는 스코프. 모르는 역할이면 빈 집합. null 금지. */
    @NonNull Set<String> scopesOf(@NonNull String role) throws Exception;
}
```

- `RolePolicy`도 `RoleStore`를 구현한다. 메서드 하나라 Kotlin에서 `RoleStore { role -> db.scopes(role) }`로 쓴다.
- 예외를 던지면 **거부(fail closed)** 하고 500으로 처리한다(403이 아님 — 장애를 권한 문제로 숨기지 않기 위해).
- 캐시는 구현체 책임으로 둔다(v1 범위 밖). 요청당 역할 수만큼 호출되므로 DB 구현은 캐시를 권한다.
- 역할 상속(`admin`이 `editor` 포함)은 v1에 넣지 않는다. 그룹 중첩(02)이 이미 상속을 준다. 필요하면 `RolePolicy.role("admin", ...).includes("editor")`를 후보로 둔다(§10).
- `RoleStore`의 CRUD(역할 생성·수정)는 프레임워크가 부르지 않으므로 인터페이스에 넣지 않는다. 관리 화면은 앱이 자기 저장소로 만든다.

## 4. 스코프가 요청에 도달하는 경로

| 방식 | 장점 | 단점 | 권고 |
|---|---|---|---|
| A. 토큰에 `sub`(+역할)만, 서버가 `RoleStore`로 확장 | 철회 즉시 반영, 토큰 작음 | 요청당 조회 | **기본** |
| B. 토큰 `scope`/`permissions` 클레임을 그대로 신뢰 | 조회 없음, 외부 IdP(Auth0 등) 토큰 수용 | 토큰 만료까지 철회 안 됨 | 옵션 `trustTokenScopes(true)` |
| C. A ∩ 토큰 scope | 위임 토큰을 안전하게 좁힘 | 개념 하나 더 | 토큰에 `scope`가 있을 때 자동 |

정적 `RolePolicy`면 A의 조회 비용은 메모리 맵 조회뿐이라 주니어 기본값으로 문제가 없다.

## 5. 라우트 보호 API

### 5.1 주니어 최소 예제 (먼저 이것만 보면 된다)

```java
RestApp app = RestApp.create();
NaruAuth auth = NaruAuth.jwt(secret)                    // 01 연구의 설정
    .users(myUserStore)
    .roles(RolePolicy.builder()
        .role("editor", "posts:read", "posts:write")
        .build())
    .publicPaths("/login", "/health")                   // 이 밖은 모두 로그인 필요
    .build();

app.use(auth);                                          // 1줄: 인증 + 기본 거부

app.get("/health", (req, res) -> res.send("ok"));       // 공개
app.get("/posts", (req, res) -> res.json(posts.all())); // 로그인만 필요
app.post("/posts", auth.require("posts:write"), (req, res) -> {
    AuthUser me = auth.user(req);                       // 여기선 항상 non-null
    res.status(201).json(posts.create(me.getId(), req.body(Post.class)));
});
```

Kotlin (기존 `post(path, Middleware, RouteHandler)` 오버로드 + 끝 람다, DSL 불필요):

```kotlin
app.use(auth)
app.post("/posts", auth.require("posts:write")) { req, res ->
    val me = auth.user(req)
    res.status(201).json(posts.create(me.id, req.body(Post::class.java)))
}
```

`NaruAuth`는 `Middleware`를 구현하므로 `app.use(auth)`가 그대로 된다. 가드는 정적 메서드가 아니라 `auth` 인스턴스 메서드다. 그래서 가드가 자기 인증 엔진을 알고, 필요하면 스스로 인증한다(§8.2).

### 5.2 가드 조합 (AND/OR)

| 코드 (제안) | 의미 |
|---|---|
| `auth.require("posts:write")` | 스코프 하나 |
| `auth.requireAll("posts:write", "media:upload")` | 모두(AND) |
| `auth.requireAny("posts:write", "posts:moderate")` | 하나 이상(OR) |
| `auth.requireRole("admin")` | 역할 직접 검사(비권장, 마이그레이션·간단 앱용) |
| `auth.authenticated()` | 로그인만(기본 거부를 끈 앱에서) |
| `auth.check((user, req) -> ...)` | ABAC 규칙(§8) |

- `require(String...)` 가변 인자는 **두지 않는다**. AND인지 OR인지 이름이 말하게 한다(express-jwt-authz의 기본 OR 혼동 회피).
- 더 복잡한 식(`(a AND b) OR c`)은 가드를 여러 개 연결(`route(...).use(g1).use(g2)` = AND)하거나 `auth.check`로 쓴다. 표현식 언어는 만들지 않는다.
- 여러 가드를 붙일 때는 기존 `app.route(path).use(g1).use(g2).get(h)`를 쓴다(가드 = 평범한 `Middleware`).

### 5.3 그룹 가드

```java
app.group("/admin", admin -> {
    admin.use(auth.require("admin:access"));            // 그룹 안 모든 라우트
    admin.get("/users", listUsers);
    admin.route("/users/:id").use(auth.require("users:delete")).delete(deleteUser);
});
```

```kotlin
app.group("/admin") { admin ->
    admin.use(auth.require("admin:access"))
    admin.get("/users") { req, res -> res.json(users.all()) }
}
```

주의(기존 규칙 그대로): 그룹 밖에서 같은 prefix로 등록한 라우트에는 그룹 가드가 안 붙는다. prefix 전체를 막으려면 `app.use("/admin", auth.require("admin:access"))`. 문서에 이 차이를 경고로 둔다.

### 5.4 대안 비교

| 방식 | 판단 | 이유 |
|---|---|---|
| 라우트 미들웨어 가드 | **주 방식** | 기존 `get(path, mw, h)`·`route().use()` 그대로, 라우트 옆에 권한이 보임, Express 사용자에게 익숙 |
| 그룹 가드 | **주 방식(묶음)** | Ktor `authenticate {}`와 같은 효과, 중첩 규칙 이미 있음 |
| 핸들러 안 검사 `auth.user(req).can(..)` | **탈출구** | 조건부 응답(필드 숨김), 소유권 검사 |
| 어노테이션 `@RequiresScope` | **채택 안 함** | 람다에는 어노테이션을 읽을 메서드가 없다. 리플렉션·ProGuard/R8 규칙이 필요해 Android에서 깨지기 쉽고, 코어의 함수형 등록 모델과 두 길이 생긴다 |

### 5.5 핸들러 안 검사 (탈출구)

```java
AuthUser me = auth.user(req);              // 인증 안 됐으면 401 HttpException
AuthUser maybe = auth.userOrNull(req);     // 공개 라우트에서
if (me.can("posts:publish")) { ... }       // boolean
auth.demand(req, "posts:write");           // 없으면 403 HttpException을 던짐
```

`AuthUser`(01 연구와 공동 정의 필요)는 `getId()`, `getRoles()`, `getGroups()`, `getScopes()`(읽기 전용 `Set`) 와 `can(String)`, `canAll(String...)`, `canAny(String...)`을 가진다. 코어 `Request`에 `user()`를 추가하지 않는 이유: 인증은 선택 모듈이고 코어는 그 타입을 몰라야 한다. 내부적으로는 `req.attribute("naruserve.auth.user", ...)`에 저장하되 키 문자열은 공개하지 않는다(직접 꺼내 캐스팅하는 실수 방지).

## 6. 오류 의미

| 상황 | 상태 | 헤더 (RFC 6750) | 비고 |
|---|---|---|---|
| 토큰 없음, 공개 경로 아님 | 401 | `WWW-Authenticate: Bearer` | |
| 토큰 형식·서명·만료 오류 | 401 | `Bearer error="invalid_token"` | 설명은 로그에만 |
| 인증됨, 스코프 부족 | 403 | `Bearer error="insufficient_scope", scope="posts:write"` | 부족한 스코프 이름 공개 여부는 옵션(기본 공개, RFC 관례) |
| `RoleStore`/`UserStore` 예외 | 500 | — | fail closed, 403으로 바꾸지 않음 |
| ABAC 규칙이 리소스 존재를 숨기고 싶을 때 | 404 | — | 규칙이 `HttpException(404)`를 직접 던짐 |

- 전부 기존 `HttpException(status).withHeader(...)`로 던지므로 `app.onError`와 표준 오류 JSON을 그대로 탄다. 새 오류 경로 없음.
- 현재 코어 `StandardErrors`에 401/403 코드가 없어 `code`가 `HTTP_401`/`HTTP_403`이 된다. `UNAUTHORIZED`/`FORBIDDEN`을 표에 넣는 작은 코어 변경을 제안한다(§10, 별도 SRS 필요).
- CORS preflight는 이미 인증 전에 204로 끝나므로 `app.cors(...)`를 `app.use(auth)`보다 먼저 등록하라는 기존 문서 규칙을 따른다.

## 7. 기본 거부와 가드 보고

### 7.1 secure by default

- `app.use(auth)`는 **모든 요청에 인증을 요구**한다(Spring `anyRequest().authenticated()`, NestJS 전역 가드와 같음). 공개 경로는 `publicPaths(...)`에 적는다. prefix 의미는 `app.use(prefix, mw)`와 같다(`/login`은 `/login/x`도 포함, `/loginx`는 제외).
- 왜 설정 목록인가: 코어 실행 순서상 전역 미들웨어가 라우트 미들웨어보다 먼저 돌기 때문에, 라우트 쪽 `auth.permitAll()` 표시를 전역 미들웨어가 미리 볼 수 없다. 코어 변경 없이 되는 방식은 설정 목록뿐이다.
- 인증만으로 충분한 라우트와 스코프가 필요한 라우트는 다르다. 기본 거부는 "로그인 필수"까지이고, 스코프는 라우트마다 명시한다. 스코프까지 기본 거부(`requireExplicitGuard(true)`: 스코프 가드 없는 라우트 403)는 옵션으로 제공한다.
- 기본 거부를 끄려면 `.defaultPolicy(DefaultPolicy.ALLOW)`(제안). 로그에 경고 1회.
- 정적 파일(`app.staticFiles("/", dir)`)도 기본 거부 대상이다. 로그인 화면 자원은 `publicPaths("/assets")` 처럼 열어야 한다 — 문서 첫 화면 경고로 둔다.

### 7.2 가드 보고

| 단계 | 방법 | 코어 변경 |
|---|---|---|
| v1 | 전역 `auth` 미들웨어가 `next.run()` 반환 뒤 "이 요청에 스코프 가드가 실행됐는가" 표시를 확인. 공개 경로가 아니고 가드가 없었으면 `WARN no scope guard: GET /posts` 를 메서드+경로당 1회 기록(키 수 상한 둠) | 없음 |
| 후속 | 시작 시 `onStart`에서 전체 라우트를 훑어 가드 없는 라우트 표를 출력: `PUBLIC GET /health`, `AUTH-ONLY GET /posts`, `SCOPE POST /posts [posts:write]` | 코어에 읽기 전용 라우트 조회(예: `app.routes()` → 메서드·패턴·미들웨어 목록) 필요. 가드는 `auth`가 만든 인스턴스라 `instanceof`로 식별 |

v1 방식은 요청이 와야 경고가 나므로 테스트 실행 중 로그로 잡는 용도다. 경로 패턴이 아니라 실제 경로가 키라 `/posts/1`, `/posts/2`가 따로 잡히는 한계가 있다(코어가 매칭 패턴을 노출하면 해결).

## 8. ABAC 확장점 (내장하지 않음)

### 8.1 훅

```java
@FunctionalInterface
public interface AccessRule {                         // 제안
    boolean allows(@NonNull AuthUser user, @NonNull Request req) throws Exception;
}

app.put("/posts/:id", auth.check((user, req) ->
        user.can("posts:write:any")
        || posts.authorOf(req.param("id")).equals(user.getId())),
    updatePost);
```

```kotlin
app.put("/posts/:id", auth.check { user, req ->
    user.can("posts:write:any") || posts.authorOf(req.param("id")) == user.id
}) { req, res -> /* ... */ }
```

- `false` → 403. 규칙이 `HttpException`을 던지면 그 상태를 그대로 쓴다(존재를 숨기는 404 등).
- 소유권 검사는 보통 리소스를 읽어야 하므로 **핸들러 안**에서 하는 편이 한 번만 읽는다: `Post p = posts.find(id); if (!p.isAuthor(me) && !me.can("posts:write:any")) throw auth.forbidden();`. 가드 훅은 "읽지 않고 판단 가능한 규칙"에 쓴다.
- 관례 스코프 `리소스:동작:any` = 남의 것까지(관리자), 소유 규칙은 앱 코드. 프레임워크는 소유 개념을 모른다(CASL 조건·Casbin ABAC 같은 정책 언어는 범위 밖).

### 8.2 등록 순서 실수 방지

가드(`require`/`check`)는 요청에 `auth`가 인증한 표시가 없으면 **스스로 인증을 먼저 수행**한다(같은 인스턴스라 가능, 멱등). 그래서 `app.use(auth)`를 빠뜨리거나 다른 미들웨어 뒤에 두어도 가드가 붙은 라우트는 열리지 않는다. 다른 인스턴스의 가드가 섞이면(인스턴스 두 개 생성) 시작 경고.

## 9. 주니어 함정과 방어

| 함정 | 방어 |
|---|---|
| 가드를 빠뜨림 | 기본 거부(로그인 필수) + `requireExplicitGuard` 옵션 + 가드 없음 경고(§7.2) |
| 미들웨어 순서를 잘못 둠 | 가드가 스스로 인증(§8.2). CORS는 인증 앞이라는 기존 규칙 문서화 |
| 클라이언트(앱 화면)에서만 역할 검사 | 문서 첫 문단: "버튼 숨김은 보안이 아니다. 서버 라우트에 `auth.require`". 가드 보고가 서버 쪽 누락을 보여 줌 |
| `admin:*`를 슈퍼유저로 오해 | 매칭 표 #7을 문서에 그대로, `*` 부여 시 시작 경고 |
| AND/OR 혼동 | 가변 인자 `require` 없음, `requireAll`/`requireAny` |
| 스코프 오타(`posts:wrte`) | 소문자 문법 검사 + 정적 정책 대비 미부여 경고(§3.2) |
| 그룹 가드가 그룹 밖 같은 prefix 라우트에 붙는다고 착각 | 문서 경고 + `app.use(prefix, guard)` 안내 + 가드 보고에 표시 |
| `req.attribute("user")`를 직접 캐스팅 | 키 비공개, `auth.user(req)`만 제공 |
| 역할 검사 남발(`requireRole`) | 문서에서 스코프 우선 권장, 역할은 매핑에만 |
| 저장소 장애를 403으로 오인 | 500 fail closed(§6) |
| 정적 파일·로그인 페이지가 막힘 | 첫 실행 401 로그에 "공개하려면 publicPaths" 힌트 |

## 10. 열린 질문

1. 코어 변경 두 건을 받을지: (a) `StandardErrors`에 `UNAUTHORIZED`/`FORBIDDEN`, (b) 읽기 전용 라우트 조회 API(시작 시 가드 보고용)와 요청의 매칭 패턴 노출. 둘 다 별도 SRS 요구가 필요하다.
2. 403 응답에 부족한 스코프 이름을 기본 공개할지(RFC 관례는 공개, 내부망 앱은 숨김 선호).
3. 역할 상속(`includes`)을 v1에 넣을지, 그룹 중첩(02)으로 충분한지.
4. 그룹→역할 매핑의 소유자: `GroupStore`(02)가 그룹의 역할을 돌려줄지, `RoleStore`가 그룹도 키로 받을지. 02와 합의 필요.
5. `trustTokenScopes`를 켰을 때 외부 IdP의 `permissions`(Auth0)·`scp`(Azure) 클레임 이름 매핑을 어디까지 기본 지원할지.
6. Kotlin 편의(`req.user` 확장 프로퍼티)를 둘 위치: 인증 모듈 안 Kotlin 파일은 Core의 "Kotlin stdlib 비의존" 원칙과 충돌하므로 `NaruServe-auth-kotlin` 같은 별도 모듈이 필요한지.
7. 모듈 이름과 진입점 이름(`NaruServe-auth`, `NaruAuth`)은 01 연구와 통일해야 한다.
8. WebSocket: Upgrade 요청에만 가드가 돈다(기존 규칙). 연결 뒤 스코프 철회를 반영할지는 범위 밖으로 둘지.
