## 0. 요약 (8줄)

1. **한 모듈, 세 층의 설정면**: ① `Auth.create(secret, users)` 3줄 → ② `Auth.builder()`의 값 설정 → ③ SPI 교체. 주니어는 ①만 보고, 엔터프라이즈는 ③까지 내려간다. 아래 층은 위 층의 코드를 바꾸지 않는다.
2. **시스템 유형 프리셋(`Auth.preset(SAAS)`)은 두지 않는다.** 저장소·연동 선택을 숨기기 때문이다. 대신 **보안 수준 프로필**(`AuthProfile.BASELINE/STANDARD/STRICT`, OWASP ASVS L1/L2/L3에 대응)만 둔다. 이것은 숫자 정책(비밀번호·잠금·타임아웃)만 정하고 `auth.describe()`로 실제 값을 모두 출력한다.
3. **교체 가능한 이음새는 11개**다: 토큰 코덱, 키 소스, 비밀번호 해시 체인, 자격 증명 인증기, 사용자/그룹/역할 store, 폐기 store, 시도 제한 store, 감사 sink, 오류 응답 모양, 클레임 매핑, 테넌트 해석기. 모두 기본 구현이 있어 아무것도 바꾸지 않아도 동작한다.
4. **외부 IdP 토큰 수용(OIDC Resource Server)은 코어 utils에 둔다**(v2). RS256/ES256 검증과 JWKS 조회는 API 21의 `java.security.Signature`·`HttpURLConnection`으로 된다. 브라우저 로그인 흐름(OIDC RP)과 SAML은 **리버스 프록시**(oauth2-proxy, Keycloak Gatekeeper 류)에 맡긴다.
5. **LDAP/AD는 JVM 전용 선택 모듈 `NaruServe-utils-ldap`** 에 둔다. `javax.naming`(JNDI)은 Android 런타임에 없어서 코어에 넣으면 API 21 검사를 깬다.
6. **멀티 테넌시는 `TenantResolver` 하나와 "store에 tenantId를 넘기는" 규칙**으로 푼다. 토큰의 `tid`와 요청에서 해석한 테넌트가 다르면 신원은 유효하므로 401이 아니라 **403으로 거부**하고 감사 이벤트를 남긴다(404로 숨길지는 Q5).
7. **클러스터는 "stateless access + 공유 RevocationStore/RateLimitStore + `kid` 키 세트"** 로 대응한다. 기본은 인메모리이고, 여러 인스턴스에서 인메모리 store를 쓰면 시작 경고를 낸다. Redis/DB 구현은 프레임워크 밖(사용자 구현 또는 예제)에 둔다.
8. **감사·컴플라이언스**: 고정 스키마 `AuditEvent` + `AuditSink` SPI, 기본은 기존 `Logger`. 비밀번호 정책은 NIST SP 800-63B-4(단일 요소 15자, 다요소 8자, 조합 규칙 금지, 정기 변경 금지, 차단 목록)를 `STANDARD` 기본값으로 삼는다. 개인정보 내보내기/삭제는 `UserStore`의 선택 default 메서드로 연다.

### 1.2 아키타입별 설정 코드

모든 예제는 같은 라우트 코드(`app.use("/auth", auth.routes()); app.use(auth); ...`, 00 §2)를 쓴다. **바뀌는 것은 `Auth`를 만드는 부분뿐**이다.

**A. 1인·주니어 앱** — 00 §2 그대로.

```java
Auth auth = Auth.create(System.getenv("JWT_SECRET"), new InMemoryUserStore()
        .add("admin", "change-me-now", "admin"));
```

**B. 기기 내장 Android 서버**

```java
Auth auth = Auth.builder(KeySources.fromBytes(deviceSecret))   // 앱이 Android Keystore에서 꺼낸 바이트. 코어는 android.*를 모른다
    .users(new SqliteUserStore(db))                             // 사용자 구현(Room 등)
    .passwords(PasswordPolicy.builder().minLength(6).allowNumericPin(true).build()) // PIN은 다요소가 아니면 WARN
    .hasher(Pbkdf2Hasher.iterations(120_000))                   // 저사양 기기 측정값으로 낮춤(00 Q1)
    .lockout(Lockout.after(5).forMinutes(15))
    .accessTtlMinutes(30).refreshTtlDays(1)                     // 화면 앞 사람이 자주 바뀜
    .build();
```

```kotlin
val auth = Auth.builder(KeySources.fromBytes(deviceSecret))
    .users(RoomUserStore(dao))
    .lockout(Lockout.after(5).forMinutes(15))
    .build()
```

**C. 스타트업 SaaS**

```java
Auth auth = Auth.builder(KeySources.fromEnv("JWT_KEYS"))       // "k2:base64,k1:base64" — 첫 키로 서명, 전부로 검증
    .profile(AuthProfile.STANDARD)
    .users(new JdbcUserStore(ds)).groups(new JdbcGroupStore(ds)).roles(new JdbcRoleStore(ds))
    .tenants(TenantResolver.subdomain("app.example.com"))       // acme.app.example.com → tenant "acme"
    .revocations(new RedisRevocationStore(redis))               // 사용자 구현 또는 예제 복사
    .rateLimits(new RedisRateLimitStore(redis))
    .authenticators(Authenticators.password(), Authenticators.apiKey(new JdbcApiKeyStore(ds)))
    .mfa(Totp.optional())                                       // 사용자가 켜면 로그인 2단계
    .build();
```

**D. 레거시 DB 중견 기업**

```java
Auth auth = Auth.builder(KeySources.fromFile(new File("/etc/app/jwt.keys")))
    .profile(AuthProfile.STANDARD)
    .users(new LegacyUserStore(ds))                             // TB_USER.EMP_NO → username, USE_YN → enabled
    .hasher(PasswordHashers.chain(
        Pbkdf2Hasher.defaults(),                                // 새 해시(첫 번째 = 재해시 목표)
        new LegacySha1Hasher()))                                // 기존 "{SHA1}..." 검증만. 로그인 성공 시 PBKDF2로 재해시
    .roles(RoleStore.mapping(legacyCodes -> map("R001", "posts:*")))   // 기존 권한 코드 → 스코프
    .build();
```

**E. 엔터프라이즈**

```java
Auth auth = Auth.builder(AuthConfig.load(new File("/etc/app/auth.properties")))  // 설정 파일 + 환경 변수 덮어쓰기
    .profile(AuthProfile.STRICT)
    .localPasswords(false)                                      // /auth/login 비활성. 사람은 IdP로만
    .tokens(TokenCodecs.oidc(OidcIssuer.discover("https://login.microsoftonline.com/<tid>/v2.0")
        .audience("api://orders")))                             // RS256 + JWKS 캐시
    .claims(ClaimMapping.entraId())                             // roles/scp/groups/tid → AuthPrincipal
    .tenants(TenantResolver.claim("tid"))
    .authenticators(Authenticators.clientCertHeader("X-Client-Cert", trustedProxyCidrs)) // 서비스 간 mTLS(프록시 종료)
    .revocations(sharedRevocations).rateLimits(sharedLimits)
    .audit(new SiemAuditSink(kafkaProducer))                    // 사용자 구현
    .build();
```

### 1.3 프리셋 판단: 시스템 프리셋은 **없음**, 보안 프로필은 **있음**

| 후보 | 장점 | 단점 | 판정 |
|---|---|---|---|
| `Auth.preset(Archetype.SAAS)` | 한 줄 | 어떤 store·연동이 켜졌는지 숨긴다. SaaS마다 Redis/DB가 달라 결국 덮어써야 하고, 덮어쓰기 규칙이 또 하나의 개념이 된다. 주니어가 "왜 Redis를 찾지?"에서 막힌다 | **채택 안 함** |
| `.profile(AuthProfile.STANDARD)` | 정책 숫자(비밀번호 길이, 잠금, TTL, 클럭 허용 오차, 감사 수준)를 표준에 맞춰 한 번에 정한다. 외부 의존을 켜지 않는다 | 값이 숨는다 | **채택**. `auth.describe()`가 모든 실제 값을 출처(`profile`/`builder`/`config file`/`env`)와 함께 출력하고, 시작 로그 INFO 한 줄에 프로필 이름을 남긴다 |

- 프로필은 **기본값만** 바꾼다. 빌더에서 명시한 값이 항상 이긴다. 다만 `STRICT`에서 `minLength(8)`처럼 프로필 하한보다 약하게 낮추면 `build()`가 예외를 던진다(약화는 `allowWeakerThanProfile()`로만 허용, 시작 WARN).
- 사다리 근거: OWASP ASVS 5.0(2025-05)은 L1 ⊂ L2 ⊂ L3 누적 구조이고, L2가 일반 업무 앱, L3가 금융·의료 같은 고보증 대상이다. NIST 800-63B-4의 AAL1/2/3 재인증 시간과 맞춘다(§6.3).

| 값 | `BASELINE`(≈ASVS L1, AAL1) | `STANDARD`(≈L2, AAL2) — **기본** | `STRICT`(≈L3, AAL3 지향) |
|---|---|---|---|
| 비밀번호 최소 길이 | 8 | 15(MFA 사용자는 8) | 15, MFA 필수 |
| 차단 목록 | 내장 소형 목록 | 내장 + 사용자 목록 | 내장 + 사용자 목록 + 유출 검사 훅 |
| 연속 실패 잠금 | 10회/15분 | 10회/15분 + 계정당 누적 100회 상한 | 5회/30분 + 관리자 해제 |
| access TTL / refresh TTL | 15분 / 14일 | 15분 / 1일(절대 수명 24시간 규칙 반영) | 5분 / 12시간 |
| 비활동 타임아웃(refresh 기준) | 없음 | 60분 | 15분 |
| 클럭 허용 오차 | 60초 | 60초 | 30초 |
| 감사 | 인증 실패만 | 인증·권한 변경 전부 | 전부 + 읽기 민감 엔드포인트 |

> `STANDARD`를 기본으로 할지 `BASELINE`을 기본으로 할지는 열린 질문 Q1이다. 이 연구는 **`STANDARD` 기본 + 15자 규칙만 `BASELINE` 수준(8)으로 완화**를 권고한다. 주니어 예제의 `change-me-now`(13자)가 기본값에서 막히면 첫 경험이 나빠지기 때문이다. 대신 `InMemoryUserStore.add`는 짧은 비밀번호에 WARN을 낸다.

## 2. 확장 지점(SPI) 지도

### 2.1 표

| # | 이음새 | 인터페이스 | 빌더 위치 | 기본 구현 | 엔터프라이즈 구현 | 위치 |
|---|---|---|---|---|---|---|
| 1 | 토큰 코덱 | `TokenCodec` | `.tokens(...)` | `Hs256TokenCodec`(00 §4.2) | `JwksTokenCodec`(RS256/ES256, JWKS), `IntrospectionTokenCodec`(RFC 7662 opaque) | 코어 / v2 |
| 2 | 키 소스 | `KeySource` | `Auth.builder(KeySource)` | `KeySources.fromEnv/fromFile/fromBytes` | KMS·HSM·Vault 구현(사용자), `AndroidKeystoreKeySource`(Android 모듈) | 코어 / 외부 |

| 4 | 자격 증명 인증기 | `CredentialAuthenticator` | `.authenticators(...)` | `Authenticators.password()` + Bearer | LDAP bind, OIDC ID 토큰 교환, API 키, mTLS 헤더 | 코어(LDAP 제외) |

| 6 | 그룹 store | `GroupStore`/`GroupAdminStore` | `.groups(...)` | `InMemoryGroupStore` | DB 재귀 CTE, `LdapGroupStore`(memberOf) | 코어 / ldap 모듈 |
| 7 | 역할 store | `RoleStore` | `.roles(...)` | `RolePolicy`(정적) | DB, IdP 클레임에서 받은 역할 매핑 | 코어 |
| 8 | 폐기·세션 store | `RevocationStore` | `.revocations(...)` | `InMemoryRevocationStore` | Redis/DB(사용자) | 코어 SPI |
| 9 | 시도 제한 store | `RateLimitStore` | `.rateLimits(...)` | `InMemoryRateLimitStore`(고정 창) | Redis `INCR`+`EXPIRE`(사용자) | 코어 SPI |
| 10 | 감사 sink | `AuditSink` | `.audit(...)` | `AuditSinks.logger(app.logger())` | SIEM·Kafka·DB(사용자) | 코어 SPI |
| 11 | 오류 응답 모양 | `AuthErrorRenderer` | `.errors(...)` | 기존 `HttpException` → `StandardErrors` JSON + `WWW-Authenticate` | RFC 9457 problem+json, 사내 공통 오류 포맷 | 코어 |
| 12 | 클레임 매핑 | `ClaimMapping` | `.claims(...)` | 자체 토큰 클레임(`sub`/`roles`/`tid`) | `ClaimMapping.keycloak()/entraId()/okta()/google()`, 표현식 매핑 | 코어 / v2 |
| 13 | 테넌트 해석기 | `TenantResolver` | `.tenants(...)` | `TenantResolver.none()` | subdomain/header/path/claim | 코어 / v2 |

(11개 이음새라고 요약했지만 store 셋을 나눠 세면 13행이다.)

### 2.2 인터페이스 스케치

API 21 제약 때문에 `java.util.function.*`(API 24)와 `java.time`(API 26)을 쓰지 않는다. 모든 콜백은 자체 `@FunctionalInterface`다. 진화는 **default 메서드 추가**로만 한다(§7.4).

```java
// 1. 토큰 코덱 — 발급(sign)은 자체 토큰만, 외부 IdP 코덱은 verify만
public interface TokenCodec {
    /** 서명·exp·nbf·iss·aud 검증까지 끝낸 클레임. 실패는 TokenRejectedException(→401). */
    @NonNull TokenClaims verify(@NonNull String token) throws TokenRejectedException;
    /** 발급 가능 여부. 외부 IdP 코덱은 false → /auth/login 등 발급 라우트가 시작 시 꺼진다. */
    default boolean canIssue() { return false; }
    default @NonNull String issue(@NonNull TokenClaims claims) { throw new UnsupportedOperationException(); }
}

// 2. 키 소스 — 키 교체를 위해 "지금 서명할 키" + "검증 가능한 키 전부"
public interface KeySource {
    @NonNull SigningKey current();                 // kid + 알고리즘 + 키 재료
    @Nullable VerificationKey find(@NonNull String kid);
    /** KMS처럼 원격 서명만 허용하는 경우: 키 재료 대신 서명 함수를 준다. */
    default boolean exportsMaterial() { return true; }
}

// 3. 해시 체인 — 01 §3.6의 SPI에 "형식 인식" 추가
public interface PasswordHasher {
    @NonNull String hash(@NonNull char[] pw);
    boolean verify(@NonNull char[] pw, @NonNull String stored);
    boolean needsRehash(@NonNull String stored);
    /** 이 해시기가 읽을 수 있는 저장 형식인가(접두사 검사). 체인이 고를 때 쓴다. */
    boolean recognizes(@NonNull String stored);
}

// 4. 자격 증명 인증기 — 요청에서 자격 증명을 찾아 주체로 바꾼다. 못 찾으면 null(다음 인증기로)
@FunctionalInterface
public interface CredentialAuthenticator {
    @Nullable AuthPrincipal authenticate(@NonNull Request req, @NonNull AuthContext ctx) throws Exception;
}

// 8. 폐기 store
public interface RevocationStore {
    void revoke(@NonNull String jti, long expiresAtMillis) throws Exception;     // 만료 후 자동 삭제 가능
    boolean isRevoked(@NonNull String jti) throws Exception;
    /** 사용자 전체 로그아웃: 이 시각 이전에 발급된 토큰 무효. tokenVersion의 클러스터판. */
    default void revokeAllBefore(@NonNull String userId, long issuedBeforeMillis) throws Exception {
        throw new UnsupportedOperationException();
    }
}

// 9. 시도 제한 store — 원자적 증가가 핵심
@FunctionalInterface
public interface RateLimitStore {
    /** key의 창 안 누적 횟수를 1 올리고 올린 값을 돌려준다. */
    long increment(@NonNull String key, long windowMillis) throws Exception;
}

// 10. 감사
@FunctionalInterface
public interface AuditSink { void record(@NonNull AuditEvent event); }   // 예외를 던지지 않는다(삼켜서 Logger로)

// 11. 오류 모양
@FunctionalInterface
public interface AuthErrorRenderer {
    void render(@NonNull AuthFailure failure, @NonNull Request req, @NonNull Response res) throws Exception;
}

// 12. 클레임 매핑
@FunctionalInterface
public interface ClaimMapping { @NonNull AuthPrincipal map(@NonNull TokenClaims claims) throws TokenRejectedException; }

// 13. 테넌트 해석
@FunctionalInterface
public interface TenantResolver { @Nullable String resolve(@NonNull Request req); }
```

### 2.3 인증 흐름에서 이음새가 끼는 순서

```
요청 → TenantResolver → [CredentialAuthenticator 목록: Bearer(TokenCodec→ClaimMapping) | API 키 | mTLS 헤더 | ...]
     → RevocationStore.isRevoked(jti)  (STANDARD 이상 또는 공유 store 설정 시에만)
     → 테넌트 일치 검사 → AuthPrincipal을 요청에 붙임 → 가드(require) → RoleStore/GroupStore(필요할 때만)
     → 실패 시 AuthErrorRenderer, 모든 판단은 AuditSink로
로그인(/auth/login) → RateLimitStore → UserStore.findByUsername → PasswordHasher 체인 → MFA → TokenCodec.issue
```

- 인증기 목록은 **순서대로**, 처음 non-null 주체가 이긴다(Spring Security `ProviderManager`, Shiro 다중 realm의 FirstSuccessful 전략과 같다). 어떤 인증기가 "자격 증명이 있는데 틀렸다"고 판단하면 `null`이 아니라 예외를 던져 즉시 401 — 다음 인증기로 넘기지 않는다(자격 증명 혼동 방지).
- `RevocationStore`를 매 요청 부르면 stateless 장점이 사라진다. 기본은 refresh에서만 확인하고, access 검사는 `.checkRevocationOnEveryRequest(true)`(STRICT 기본값)로 켠다.

| SAML 2.0 | **범위 밖. 프록시 사용** | 외부 | — |

| mTLS 클라이언트 인증서(프록시 헤더) | 지원 | 코어 utils | v2 |

### 3.1 OIDC — 외부 IdP 토큰 수용

- 흐름: `OidcIssuer.discover(issuer)`가 `/.well-known/openid-configuration`을 읽어 `jwks_uri`를 얻고 JWKS(RFC 7517)를 캐시한다. 검증은 `iss` 정확 일치, `aud` 포함, `exp/nbf`(허용 오차), `alg ∈ 허용 목록`(키의 `kty`와 일치 강제), `typ`가 있으면 `at+jwt`(RFC 9068) 확인.
- API 21 가능성: RSA 공개키는 `KeyFactory("RSA")` + `RSAPublicKeySpec(n, e)`, 서명은 `Signature("SHA256withRSA")`로 API 1부터 있다. ES256은 01 §2.2대로 DER↔R||S 변환을 직접 써야 한다. JWKS 조회는 `java.net.HttpURLConnection`(금지 목록 아님)으로 하고, 응답 파싱은 `JsonCodec`.
- JWKS 캐시 규칙: 모르는 `kid`가 오면 **한 번만** 재조회(최소 간격 5분, 단일 비행), 실패하면 이전 키 세트 유지. 매 요청 재조회로 IdP를 DoS하지 않게 한다.
- IdP별 클레임 매핑 프리셋(`ClaimMapping.*`)은 **매핑 표일 뿐**이라 숨김 문제가 작으므로 둔다.

| IdP | 역할 | 스코프 | 그룹 | 테넌트 | 함정 |
|---|---|---|---|---|---|
| Entra ID | `roles`(앱 역할) | `scp`(공백 구분 문자열) | `groups`(GUID) | `tid` | JWT 그룹 200개 초과 시 `groups` 대신 `_claim_names`/`_claim_sources` overage. **조용히 "그룹 없음"으로 처리하면 안 된다** → 기본은 거부+WARN, Graph 조회는 사용자 훅. `preferred_username`·`name`은 변경 가능하므로 인가에 쓰지 않고 `oid`/`sub`를 ID로 |
| Keycloak | `realm_access.roles`, `resource_access.<client>.roles` | `scope`(공백 구분) | `groups`(매퍼 설정 시) | realm = `iss` 경로 | 표준 OIDC 클레임이 아니라 중첩 경로. 클라이언트 역할은 매퍼 설정이 없으면 안 나온다 |
| Okta | 커스텀(`groups` 클레임 정의 필요) | `scp`(배열) | `groups` | 조직 = `iss` | 커스텀 인가 서버만 access 토큰을 우리 API용으로 검증 가능 |
| Google | 없음 | 없음 | 없음(Workspace는 `hd`) | `hd` 도메인 | access 토큰이 JWT가 아니다. **ID 토큰 교환**(§3.1.1)만 지원 |

```java
ClaimMapping custom = ClaimMapping.builder()
    .id("oid").username("preferred_username")
    .roles("realm_access.roles")                 // 점 경로. 배열 또는 공백 구분 문자열 모두 허용
    .scopes("scp", "scope")                      // 먼저 있는 것
    .groups("groups").tenant("tid")
    .rolePrefix("idp:")                          // 외부 역할이 로컬 역할 "admin"과 충돌하지 않게
    .build();
```

- `rolePrefix`는 엔터프라이즈 필수다. IdP에서 누군가 `admin` 그룹을 만들면 로컬 `admin`을 얻는 사고(권한 상승)를 막는다. 프리셋은 접두사를 기본으로 켠다.
- 외부 역할 → 로컬 스코프는 기존 `RolePolicy`가 그대로 처리한다(`.role("idp:Orders.Writer", "orders:write")`). 03 Q5의 답이 된다.

#### 3.1.1 ID 토큰 교환(로그인 대체)

모바일 앱이 Google/Apple/Entra에서 받은 ID 토큰을 `POST /auth/oidc/exchange`로 보내면 검증 후 **자체 HS256 토큰**을 발급한다(`Authenticators.oidcIdToken(issuer, clientId)`). `nonce` 검증, `email_verified` 확인, 처음 보는 사용자의 자동 생성(JIT)은 `.jitProvisioning(UserFactory)`로 명시적으로만 켠다.

#### 3.1.2 Opaque 토큰 — RFC 7662 introspection

`IntrospectionTokenCodec(endpoint, clientId, secret)`가 `POST token=...`으로 `active`를 확인한다. 응답을 `exp`까지(최대 상한 60초) 캐시한다. 매 요청 네트워크 왕복이 생기므로 JWT IdP가 있으면 JWKS를 우선하라고 문서화한다. Spring Security도 `JwtDecoder`와 `OpaqueTokenIntrospector`를 별도 이음새로 둔다.

### 3.2 SAML — 범위 밖, 프록시 권장

- 이유 ① XML 서명 검증(XML-DSig, 정규화 C14N)은 서명 래핑 공격(XSW) 역사가 긴 영역이라 직접 구현 위험이 JWT보다 훨씬 크다. ② Android에서 안전한 XML 서명 스택(`javax.xml.crypto`)이 없다. ③ 브라우저 리다이렉트·세션이 필요해 REST 프레임워크 범위를 벗어난다.
- 권장 배치: Keycloak을 SAML IdP와 연결하는 **브로커**로 두고 앱은 Keycloak의 OIDC 토큰만 수용하거나, 리버스 프록시가 SAML을 처리하고 서명된 JWT/헤더를 앱에 넘긴다. 이때 앱은 `Authenticators.trustedHeader(...)`를 **신뢰 프록시 CIDR**과 함께 쓴다(기존 `trustProxy`와 같은 신뢰 경계).

### 3.3 LDAP/AD — JVM 전용 모듈

- `javax.naming`(JNDI, `javax.naming.ldap.LdapName` 포함)은 Android 런타임에 없다. Jetty·Apache HttpClient가 이 클래스 의존 때문에 Android에서 `NoClassDefFoundError`를 낸 이력이 있다. 따라서 코어 utils에 넣으면 animal-sniffer 검사를 깬다.
- 배치: **`NaruServe-utils-ldap`**(JVM 전용, 외부 의존 0 — JDK JNDI만). `NaruServe-servlet`/`NaruServe-slf4j`처럼 API 21 검사 대상에서 뺀다. Android에서 AD가 꼭 필요하면 UnboundID LDAP SDK로 사용자가 `CredentialAuthenticator`를 구현한다(문서 예제만).
- 제공 기능: `LdapAuthenticator`(사용자 DN 검색 → bind로 비밀번호 확인, **bind 결과만 신뢰**하고 비밀번호를 비교하지 않음), `LdapGroupStore`(`memberOf` 또는 그룹 검색, AD는 `LDAP_MATCHING_RULE_IN_CHAIN` 1.2.840.113556.1.4.1941로 중첩 확장), LDAPS/StartTLS 강제, 필터 인젝션 이스케이프(RFC 4515).
- 로컬 store와의 관계: LDAP 사용자는 로그인 때 `UserStore`에 그림자 레코드(ID·tokenVersion만)를 만들 수 있다(`.shadowUsers(true)`). 그래야 refresh·로그아웃·감사가 로컬 사용자와 같게 돈다.

### 3.4 SCIM 2.0 — 프로비저닝

- RFC 7643(스키마) / 7644(프로토콜). Entra ID·Okta가 앱에 사용자·그룹을 밀어 넣는 표준이다.
- 매핑: `/scim/v2/Users` ↔ `UserStore`, `/scim/v2/Groups` ↔ `GroupAdminStore`. `userName`→`username`, `active`→`enabled`, `externalId`·`emails`→`attributes`. 비활성화(`active:false`)는 `tokenVersion++`까지 수행해 즉시 로그아웃시킨다.
- v1 범위 밖인 이유: PATCH 연산 문법(`path` 필터), `filter=userName eq "x"` 파서, 페이지네이션, ETag가 필요해 표면이 크다. **별도 선택 모듈 `NaruServe-utils-scim`**(순수 Java라 API 21 가능)으로 v3에 둔다. 그 전까지는 기존 관리 엔드포인트(01 §3.2, 02 §6)로 충분하다.
- SCIM 엔드포인트는 사람 토큰이 아니라 **서비스 계정 토큰 + `scim:write` 스코프**로만 연다.

### 3.5 MFA/TOTP

- RFC 6238 = HOTP(RFC 4226) + 30초 단계. `Mac("HmacSHA1")`은 API 1부터 있으므로 코어 utils에서 약 60줄로 구현한다. Base32(시크릿 표기)도 직접 쓴다.
- 규칙: ±1 단계 허용, **같은 단계 코드 재사용 금지**(마지막 사용 단계를 `UserStore` 속성에 저장), 시도 제한은 로그인과 같은 `RateLimitStore`, 복구 코드 10개(해시 저장).
- 흐름: 비밀번호 성공 → `mfa_required` + 5분짜리 `typ=mfa` 토큰 → `POST /auth/mfa` 성공 시 정식 토큰. access 토큰에 `amr:["pwd","otp"]`를 넣어 `auth.requireMfa()` 가드가 쓴다(Entra의 `amr`과 같은 값 체계).
- WebAuthn/passkey는 CBOR·attestation 검증이 커서 v3 이후 별도 모듈 후보.

### 3.6 API 키와 서비스 계정

- API 키: 형식 `nk_<prefix8>_<secret32>`(제안). 서버는 **prefix로 찾고 secret의 SHA-256만 저장**(비밀번호와 달리 고엔트로피라 느린 해시 불필요). 키마다 스코프·만료·마지막 사용 시각. `ApiKeyStore`(find/create/revoke) SPI + 인메모리 기본.
- 서비스 계정: `AuthUser`에 `kind=service` 속성을 두고 비밀번호 로그인 금지, OAuth2 client credentials 대신 **API 키 또는 mTLS**로만 인증. 감사 이벤트에 사람과 구분해 남긴다.
- mTLS: TinyHttpd가 TLS를 직접 종료하지 않는 배치가 일반적이므로 **프록시가 검증한 인증서를 헤더로 전달**(예: nginx `$ssl_client_escaped_cert`, Envoy `x-forwarded-client-cert`)하는 방식을 지원한다. 요청 원격 주소가 신뢰 프록시 CIDR일 때만 헤더를 읽고, 아니면 헤더가 있다는 사실만으로 401+감사. 인증서 지문→주체 매핑은 `CertificatePrincipalMapper`(RFC 8705의 `x5t#S256`과 같은 지문).

## 4. 멀티 테넌시

### 4.1 테넌트 해석

| 방식 | 예 | 장점 | 위험 | 제공 |
|---|---|---|---|---|
| 서브도메인 | `acme.app.com` | 브라우저 쿠키 격리 | `Host` 헤더 위조 → 허용 기반 도메인 suffix 검사 필수 | `TenantResolver.subdomain(base)` |
| 헤더 | `X-Tenant-Id: acme` | 내부 API에 단순 | 클라이언트가 마음대로 바꿈 → **토큰 테넌트와 반드시 대조** | `.header(name)` |
| 경로 | `/t/acme/orders` | 라우팅에 보임 | 라우트마다 `:tenant` 필요 | `.path("tenant")` (라우트 파라미터) |
| 토큰 클레임 | `tid` | 위조 불가 | 테넌트 전환 시 재로그인 | `.claim("tid")` |

권고: **신원은 토큰 클레임, 요청 대상은 서브도메인/경로**. 둘이 다르면 거부한다. `TenantResolver.claim`만 쓰면 대조할 대상이 없으므로 한 테넌트 사용자 모델(대부분의 B2B SaaS)이 된다.

### 4.2 테넌트 범위 store와 역할

- 테넌트는 `AuthPrincipal.getTenantId()`(`@Nullable`, 단일 테넌트 앱은 `null`)로 노출한다.
- store 시그니처를 바꾸지 않기 위해 **`TenantScopedUserStore`** 래퍼를 둔다: `UserStores.perTenant(tenantId -> new JdbcUserStore(ds, tenantId))`. 프레임워크가 요청 테넌트로 store를 고르므로 사용자 코드가 `WHERE tenant_id = ?`를 빠뜨려도 다른 테넌트 store에 닿지 않는다(스키마/DB 분리형). 행 단위 분리형은 store 생성자에 tenantId를 받는 관례로 같은 효과를 낸다.
- 역할은 Casbin의 "domains" 모델과 같다: 같은 사용자가 테넌트마다 다른 역할을 가진다(`g = _, _, _`의 세 번째가 도메인). 여기서는 `RoleStore.scopesOf(role)`를 유지하고 **사용자→역할 조회를 테넌트별**로 한다(`AuthUser.getRoles()`가 그 테넌트 store의 값). 전역 역할(플랫폼 운영자)은 별도 접두사 `platform:`으로만 부여하고 테넌트 store에서는 거부한다.
- Keycloak realm 모델(테넌트마다 IdP 하나)은 `TokenCodecs.multiIssuer(iss -> OidcIssuer...)`로 지원한다. 허용 `iss` 목록을 명시해야 하며 **`iss`에서 JWKS URL을 유도하지 않는다**(임의 issuer 수용 = 인증 우회).

### 4.3 교차 테넌트 유출 방어

1. 토큰 `tid` ≠ 요청 테넌트 → 403 + `AuditEvent(TENANT_MISMATCH)`. 401이 아닌 이유: 신원은 유효하다.
2. refresh·API 키·MFA 토큰 모두 `tid`를 담고 같은 규칙을 적용한다.
3. 그룹 ID는 테넌트 범위다. `GroupStore`를 테넌트별로 고르므로 `eng` 그룹이 테넌트 간 섞이지 않는다.
4. 캐시 키(JWKS 제외 모든 인증 캐시, 요청 메모)에 tenantId를 포함한다.
5. 존재 노출: 다른 테넌트 리소스를 조회하면 403 대신 404를 줄지는 앱 결정(03 §8.1 `HttpException`)으로 남긴다.
6. 테스트 도구: `AuthTestKit.crossTenantProbe(app)`(제안, v2)가 등록 라우트를 다른 테넌트 토큰으로 호출해 2xx가 나오면 실패시킨다.

## 5. 클러스터와 고가용성

| 문제 | 단일 인스턴스 기본 | 클러스터 대응 |
|---|---|---|
| access 검증 | stateless, 키만 있으면 됨 | 모든 인스턴스가 같은 `KeySource` |
| 로그아웃·폐기 | `tokenVersion`(store) + 인메모리 jti | 공유 `RevocationStore`. access 만료(15분)까지의 창은 `checkRevocationOnEveryRequest`로 닫는다 |
| refresh 회전 재사용 탐지 | 인메모리 | 공유 store에서 원자적 "사용됨" 표시(`SETNX`). 재사용 감지 시 그 사용자 전체 폐기 |
| 시도 제한·잠금 | 인메모리 | 공유 `RateLimitStore`. 인스턴스별 인메모리면 N대일 때 실제 한도가 N배 |
| 키 교체 | `kid` 키 세트 | ① 새 키를 **검증 전용**으로 전 인스턴스 배포 → ② access TTL 이상 기다림 → ③ 서명 키로 승격 → ④ 옛 키는 refresh TTL 뒤 제거. `KeySource`가 키 목록을 주기적으로 다시 읽게(`KeySources.reloading(src, minutes)`) 해 재시작 없이 돈다 |
| 클럭 차이 | 60초 허용 | NTP 전제를 문서화. 허용 오차는 프로필 값, 최대 5분 상한 |
| 감사 순서 | 단일 로그 | 이벤트에 `instanceId`, 단조 증가 `seq`, 밀리초 시각을 넣는다 |

- **인메모리 store를 클러스터에서 쓰는 실수 방지**: 설정에 `instances(n>1)` 또는 환경 변수 `NARU_AUTH_CLUSTER=true`가 있는데 폐기·시도 제한 store가 인메모리면 `build()` 예외(STRICT) / WARN(그 외).
- Redis·DB 구현을 왜 모듈로 제공하지 않나: 클라이언트 라이브러리(Jedis/Lettuce/JDBC 드라이버) 선택이 회사마다 다르고 API 21 대상도 아니다. SPI가 메서드 1~3개라 예제 30줄로 충분하다(`examples/`에 두는 것을 제안).
- 단일 장애점: 공유 store 장애 시 **fail closed**(03 §6 원칙과 같이 500) 기본. 가용성이 더 중요한 시스템을 위해 `.revocationFailure(FailMode.OPEN_WITH_AUDIT)`를 둘 수 있으나 STRICT에서는 금지.

## 6. 컴플라이언스와 감사

### 6.1 감사 이벤트 스키마

```java
public final class AuditEvent {                // 불변 값 객체. Kotlin 프로퍼티 문법을 위해 getX()
    public long getTimestampMillis();
    public @NonNull String getType();          // AUTH_LOGIN_SUCCESS, AUTH_LOGIN_FAILURE, TOKEN_REFRESH, TOKEN_REVOKED,
                                               // ACCESS_DENIED, MFA_*, USER_CREATED/UPDATED/DELETED, ROLE_CHANGED,
                                               // GROUP_CHANGED, PASSWORD_CHANGED, LOCKOUT, TENANT_MISMATCH, KEY_ROTATED, PII_EXPORT/ERASE
    public @NonNull AuditOutcome getOutcome(); // SUCCESS / FAILURE / DENIED / ERROR
    public @Nullable String getActorId();      // 누가(사용자 ID 또는 service 계정 ID). username은 넣지 않는다
    public @Nullable String getTenantId();
    public @Nullable String getTargetId();     // 무엇을(대상 사용자·그룹·리소스 ID)
    public @NonNull String getAction();        // "POST /auth/users" 같은 매칭 패턴(실제 경로 아님 — ID가 경로에 있으면 PII)
    public @Nullable String getSourceIp();     // 어디서(trustProxy 반영). 마스킹 옵션
    public @Nullable String getRequestId();    // 기존 RequestIds와 연결
    public @Nullable String getReason();       // 실패 사유 코드(bad_password, locked, insufficient_scope ...)
    public @NonNull Map<String, String> getDetails();
}
```

- 필드명은 OpenTelemetry·ECS(`event.outcome`, `user.id`, `source.ip`)와 1:1로 바꿀 수 있게 골랐다. JSON 직렬화는 `AuditSinks.json(writer, jsonCodec)`이 `JsonCodec`으로 한다.
- 실패 로그인에서 **존재하지 않는 username**은 actorId가 없다. 입력된 username은 `details.usernameHash`(HMAC, 키는 감사 전용)로만 남겨 계정 열거 분석은 가능하되 평문은 남지 않게 한다.
- `AuditSink`는 요청 스레드에서 불린다. 느린 sink를 위해 `AuditSinks.async(sink, queueSize)`(`java.util.concurrent` 큐, 가득 차면 드롭 카운터 + WARN) 제공.

### 6.2 PII 최소화

| 데이터 | 로그/감사 | 근거 |
|---|---|---|
| 비밀번호·토큰·API 키 secret·TOTP 코드 | **절대 금지**. `Authorization` 헤더는 기존 접근 로그에서도 마스킹 | OWASP Logging Cheat Sheet |
| 이메일·이름·전화 | 금지(ID만) | 개인정보보호법 최소 수집 원칙, GDPR 데이터 최소화 |
| IP | 기본 기록, `.auditIpMasking(true)`로 /24 마스킹 | 접속 기록 보관 의무(국내 안전성 확보조치 기준)와 최소화의 균형 |
| User-Agent | 길이 제한 256자 | 로그 인젝션·비대화 |
| 제어 문자 | 모든 문자열 필드에서 이스케이프 | 로그 인젝션(CRLF) |

### 6.3 정책 설정 가능성

```java
.passwords(PasswordPolicy.builder()
    .minLength(15).minLengthWithMfa(8).maxLength(128)       // 800-63B-4: 단일 요소 15, MFA 8, 최대 ≥64
    .blocklist(Blocklists.builtIn(), Blocklists.fromFile(f))// 전체 문자열 비교(부분 문자열 아님)
    .noCompositionRules()                                   // 기본. 조합 규칙은 800-63B-4가 금지(SHALL NOT)
    .breachCheck(pw -> hibp.isPwned(pw))                    // 선택 훅(k-익명성 API는 사용자 구현)
    .build())
.lockout(Lockout.after(10).forMinutes(15).maxPerAccount(100)) // 800-63B-4: 연속 실패 100회 이하
.sessions(SessionPolicy.builder()
    .absoluteHours(24).idleMinutes(60)                      // AAL2: 전체 ≤24h, 비활동 ≤1h / AAL3: ≤12h, ≤15분
    .build())
```

- 정기 변경 강제는 800-63B-4가 금지하므로 **기본 없음**. 그러나 국내 금융·공공 감사에서 요구하는 경우가 있어 `.passwordMaxAgeDays(90)`을 두되 Javadoc과 시작 INFO에 "NIST 비권장"을 쓴다(사용자 시스템에 맞추라는 요구 반영).
- 길이는 유니코드 코드 포인트로 센다(800-63B-4). Java `String.length()`는 UTF-16 단위라 `codePointCount`를 쓴다. 정규화(NFKC)는 `java.text.Normalizer`(API 9)로 가능하다.
- 잠금은 **계정 + IP 이중 키**(`login:acct:<id>`, `login:ip:<ip>`). 계정만 잠그면 공격자가 피해자를 잠그는 DoS가 되므로 기본은 점진 지연(1→2→4초…) 후 잠금, 성공 시 초기화.

### 6.4 개인정보 내보내기·삭제(GDPR/PIPA)

```java
public interface UserStore {
    // ... 01 §3.3의 5개 메서드 ...
    /** 정보주체 열람·이동 요구. 기본: findById + 그룹 목록을 Map으로. 앱 데이터는 앱이 덧붙인다. */
    default @NonNull Map<String, Object> exportPersonalData(@NonNull String userId) throws Exception { ... }
    /** 삭제 요구. 기본: delete(userId). 감사 보관 의무가 있으면 익명화로 재정의. */
    default void erasePersonalData(@NonNull String userId) throws Exception { delete(userId); }
}
```

- `auth.routes()`에 선택 엔드포인트 `GET /auth/me/export`, `DELETE /auth/me`(재인증 필요)를 `.selfServicePrivacy(true)`로 연다. 관리자용은 `privacy:export`/`privacy:erase` 스코프.
- 삭제 시 순서: `tokenVersion++`·폐기 → 그룹 멤버십 제거 → `erasePersonalData` → `AuditEvent(PII_ERASE)`(대상 ID만). 감사 로그 자체의 actorId 보존 기간은 사용자 정책으로 둔다(법정 보관 vs 삭제 요구 충돌은 앱/법무 결정).
- 앱 도메인 데이터(주문·게시글)는 프레임워크가 모른다. `auth.onUserErased(userId -> ...)` 리스너(`@FunctionalInterface`)로 앱에 알린다.

## 7. 설정 표면 설계 원칙

### 7.1 점진적 공개(progressive disclosure)

| 층 | 누가 | 보는 API 수 | 규칙 |
|---|---|---|---|
| ① `Auth.create(secret, users)` | 주니어 | 2 | 추가 설정 0으로 안전(기본 거부, STANDARD 정책) |
| ② `Auth.builder(...)`의 값 메서드 | 대부분 | 문서 첫 페이지 10개(`users/groups/roles/publicPaths/profile/accessTtl/refreshTtl/lockout/passwords/routesAt`) | 나머지 빌더 메서드는 문서의 "고급" 절과 Javadoc에만 |
| ③ SPI 교체 | 엔터프라이즈 | 인터페이스 13종 | 각 SPI의 기본 구현이 공개 클래스라 위임·상속으로 시작 가능 |

- 문서 원칙: Express 사용자가 passport → passport-jwt → custom strategy로 내려가는 경험과 같게 배치한다. 각 층의 예제는 앞 층의 코드를 **지우지 않고 한 줄 추가**로만 보여 준다.
- 빌더 메서드 이름은 하위 객체를 받는 형태(`.lockout(Lockout...)`)로 묶어 자동 완성 목록을 짧게 한다. 평평한 `lockoutAttempts()/lockoutMinutes()`를 늘어놓지 않는다.

### 7.2 코드 설정 vs 외부 설정 파일

- 엔터프라이즈는 파일·환경 변수로 운영 값을 바꾸고 싶어 한다. 그러나 코어에 YAML 파서를 넣을 수 없다(의존 금지). → **`java.util.Properties` + 환경 변수**를 기본 포맷으로, JSON은 `JsonCodec`이 있을 때만.

```properties
# /etc/app/auth.properties
naru.auth.profile=STRICT
naru.auth.keys=env:JWT_KEYS              # 비밀은 값 대신 참조만: env:NAME | file:/run/secrets/x
naru.auth.access-ttl-minutes=5
naru.auth.lockout.after=5
naru.auth.lockout.minutes=30
naru.auth.oidc.issuer=https://login.microsoftonline.com/<tid>/v2.0
naru.auth.oidc.audience=api://orders
naru.auth.claims.preset=entra-id
```

- 우선순위: **코드의 명시 값 < 설정 파일 < 환경 변수(`NARU_AUTH_ACCESS_TTL_MINUTES`)** — 12-factor 관례. 다만 코드에서 `.lock("profile")`로 운영자가 바꾸지 못하게 고정할 수 있다(보안 하한 보호).
- 파일은 **값**만 설정한다. store·sink 같은 객체는 코드에서만(문자열 클래스 이름으로 리플렉션 생성은 R8에서 깨지므로 금지 — 00 §4.1과 같은 이유).
- 알 수 없는 키(`naru.auth.acess-ttl...` 오타)는 `build()` 예외. 조용히 무시하면 운영자가 보안 설정이 적용됐다고 착각한다.
- 파일 안 비밀 평문(`naru.auth.keys=abc...`)은 거부하고 `env:`/`file:` 참조를 요구한다(STANDARD 이상).

### 7.3 호환 불가 조합 검증

`build()`는 **모든 오류를 모아 한 번에** 던진다(`AuthConfigException`의 목록). 첫 오류에서 멈추면 운영자가 재시작을 반복한다.

| 조합 | 결과 |
|---|---|
| `localPasswords(false)` + 인증기 없음 + 외부 코덱 없음 | 오류: 아무도 로그인할 수 없음 |
| 외부 IdP 코덱(`canIssue()=false`) + `auth.routes()` 마운트 | `/auth/login`·`/refresh` 비활성, `/auth/me`만. 시작 INFO |
| `profile(STRICT)` + 인메모리 폐기/시도 제한 + 클러스터 표시 | 오류 |
| `trustTokenScopes(true)` + 자체 HS256 코덱만 | WARN(자체 토큰엔 scope가 없으니 무의미) |
| `mfa(required)` + TOTP 등록 엔드포인트 비활성 | 오류: 첫 로그인 불가 |
| mTLS 헤더 인증기 + `trustedProxyCidrs` 비어 있음 | 오류(누구나 헤더 위조 가능) |
| `TenantResolver.header` 단독 + 토큰에 tid 없음 | 오류: 대조 불가 → 클라이언트가 테넌트 선택 |
| HS256 + 키 길이 < 32바이트 | 오류(00 §4.2) |
| `rolePrefix` 없이 외부 IdP 역할을 로컬 `RolePolicy`와 같은 이름으로 사용 | STRICT 오류 / 그 외 WARN |
| `passwordMaxAgeDays` + `profile(STRICT)` | INFO(NIST 비권장 표시만) |

### 7.4 SPI 버전 관리와 호환

- 인터페이스에 메서드를 추가할 때는 **반드시 default 메서드**로 넣는다(Java 8 bytecode, Android API 21에서 default 메서드는 D8 desugaring으로 동작 — 이 저장소는 이미 default 메서드를 공개 API에 쓴다. 예: `Request.requireHeader`).
- 새 default 메서드의 기본 동작은 "예전과 같은 결과"여야 한다. 예외를 던지는 default(`revokeAllBefore`)는 그 기능을 켤 때만 불리고, 켰는데 미구현이면 `build()`에서 탐지한다(능력 질의 `default boolean supportsX()`).
- 콜백 SPI는 `@FunctionalInterface`로 유지하기 위해 추상 메서드를 늘리지 않는다. 확장이 필요하면 인자 객체(`AuthContext`)에 getter를 추가한다 — 인자 객체 패턴이 진화를 흡수한다.
- SPI 패키지(`...utils.auth.spi`)에 `@since` Javadoc 필수, 제거는 한 마이너 버전 `@Deprecated` 후. 이진 호환은 japicmp류 검사를 릴리스 게이트 후보로 둔다(열린 질문).
- 사용자 구현이 아닌 값 클래스(`AuditEvent`, `TokenClaims`)는 `final` + 빌더라 필드 추가가 호환을 깨지 않는다.

### 7.5 운영 가시성

- `auth.describe()` → 사람이 읽는 표(값과 출처), `auth.describeJson()` → 설정 감사용. 비밀은 `***`와 키 지문(SHA-256 앞 8자)만.
- 시작 INFO 한 줄 예: `auth: profile=STANDARD codec=hs256(kid=k2,k1) users=JdbcUserStore revocation=in-memory(WARN: single-instance only) tenants=subdomain`.

- **공개/내부 경계**: `internal` 패키지는 기존 `com.snoworca.naruserve.internal`과 같은 관례(Javadoc 제외, 호환 보장 없음). `spi`만 "구현해도 되는" 인터페이스이고, 나머지 공개 패키지의 인터페이스는 "호출만" 하는 것으로 문서에 구분한다.
- `testing`을 공개로 두는 이유: 엔터프라이즈의 통합 테스트가 HS256 비밀키를 테스트 코드에 복사하는 습관을 막는다.
- Redis/JDBC/Kafka 구현은 모듈로 두지 않는다(§5). `examples/auth-cluster`(제안)에 복사용 코드로 둔다.
- 루트 `build.gradle`만 모듈을 설정하는 규칙(CLAUDE.md)에 따라 새 모듈 셋(`utils`, `utils-ldap`, `utils-scim`)도 루트에 추가하고, `utils-ldap`은 `NaruServe-servlet`처럼 animal-sniffer 대상 목록에서 뺀다.

## 10. 열린 질문

1. **기본 프로필**: `STANDARD`를 기본으로 하되 최소 길이만 8로 완화(권고) vs 완전 `STANDARD`(15자) vs `BASELINE`. 주니어 첫 경험과 NIST 준수의 절충이다.
2. **`localPasswords(false)`일 때 `UserStore` 필수 여부**: 외부 IdP만 쓰는 시스템은 store가 없어도 되게 할지(그림자 사용자 없이 토큰만), refresh/로그아웃이 없어지는 대가를 받아들일지.
3. **OIDC 코덱을 코어 utils에 둘지 `NaruServe-utils-oidc`로 뺄지**: API 21에서 동작하므로 코어 권고지만, `HttpURLConnection` 네트워크 코드가 코어 utils에 들어오는 것이 주니어 모듈 크기에 주는 영향 측정이 필요하다.
4. **AndroidKeystoreKeySource 위치**: 기존 `NaruServe-android` AAR에 넣으면 그 AAR이 utils에 의존하게 된다. 별도 `NaruServe-utils-android`가 나은지.
5. **테넌트 불일치를 403 vs 404**: 리소스 존재 노출 방지를 위해 404를 기본으로 할지. 이 문서는 403 + 감사를 권고했다.
6. **Entra 그룹 overage 처리**: 기본 거부(권고) vs `GroupStore`로 대체 조회를 자동 시도. Graph 호출은 앱 자격 증명이 필요해 프레임워크가 할 수 없다.
7. **설정 파일 포맷**: Properties만(권고) vs JSON(`JsonCodec` 있을 때). HOCON/YAML은 의존 문제로 제외.
8. **SPI 이진 호환 검사 도구**(japicmp 등)를 릴리스 게이트(`gradle/release.gradle`)에 넣을지 — CLAUDE.md는 릴리스 설정을 그 파일 하나로 제한한다.
9. **`passwordMaxAgeDays`를 제공할지**: NIST는 금지하지만 국내 감사 요구가 있다. 제공하되 경고(권고) vs 미제공.
10. **감사 sink가 실패할 때**: 지금은 삼키고 Logger로(가용성 우선). STRICT에서 감사 실패 시 요청을 거부(감사 우선)할지.

## 12. 검증 한계

- 직접 열어 확인한 것: NIST 800-63B-4 수치, Entra ID 클레임 표와 overage 한도. 검색 결과 요약으로 확인한 것: ASVS 5.0 출시와 레벨 구조, Keycloak `realm_access`/`resource_access` 구조, Casbin 도메인 모델, Spring/Quarkus 이음새 이름, better-auth 플러그인 구성.
- `javax.naming`이 Android에 없다는 것은 공식 문서가 아니라 이슈 트래커 근거다. 구현 전에 animal-sniffer `android-api-level-21` 서명으로 직접 확인한다(검사가 실패하면 결론이 맞는 것).
- Shiro·pac4j·Micronaut·Okta·Google 관련 URL과 동작은 기억에 기반하며 이번에 열어 보지 않았다.
- 프로필별 수치(§1.3 표)는 이 연구의 제안이며 ASVS 항목 번호와 1:1 대조하지 않았다.
