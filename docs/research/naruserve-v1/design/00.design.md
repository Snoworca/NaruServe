# NaruServe v1 — run design

This document is the frozen design for the orchestrated NaruServe v1 run. It turns `object.md`, the `docs/api/` contract, epic #20 with sub-issues #1–#19 and the committee answers Q-1 to Q-5 into numbered, testable design items grouped by implementation wave. Items marked (미확정) in `docs/api/` are decided by the wave that owns them; this design names the behaviour those decisions cover, not the names.

## 1. Build foundation

Covers issue #1; its gate is the root `./gradlew build` with one Java and one Kotlin smoke test, and it has no acceptance test ID of its own. Depends on sections: none.

### Gradle wrapper and module layout

- [D-001] The build SHALL use only the Gradle 8.14.3 wrapper, with no Maven or other build tool files added to the repository.
- [D-002] The root `settings.gradle` SHALL include, next to `NaruServe-api` and `NaruServe-servlet`, one module each for the TinyHttpd `HttpAdapter`, the Gson `JsonCodec`, the default bootstrap that backs `RestApp.create()`, the Kotlin extensions, the SLF4J `Logger` adapter, the rotating file `Logger` and the Logcat `Logger`, with final names decided in #1 (the issue proposes `NaruServe-tinyhttpd`, `NaruServe-gson`, `NaruServe`, `NaruServe-kotlin`, and the logger modules take the same `NaruServe-` prefix).
- [D-003] Every module of the root build SHALL be configured from the root `build.gradle`.
- [D-004] Modules of the root build MUST NOT carry their own per-module build files.
- [D-005] Wave 1 SHALL declare every module's main dependencies up front, so later waves add only test-scope dependencies or the release plugins owned by #18.
- [D-006] Java compilation in every module SHALL use `options.release = 8`.
- [D-007] Kotlin compilation in every module and test source set SHALL use `jvmTarget = 1.8`.
- [D-008] The Maven group and the Java package root SHALL be fixed once in #1 (temporary value `com.snoworca.naruserve`) and used by every module.
- [D-009] `NaruServe-api` MUST NOT declare any runtime dependency outside the JDK.
- [D-010] The Gson module SHALL depend on exactly `com.google.code.gson:gson:2.14.0`.
- [D-011] `kotlin-stdlib` SHALL be a runtime dependency only of the Kotlin extension module, with other modules using it at most in test scope.
- [D-012] `NaruServe-servlet` SHALL depend on `javax.servlet:javax.servlet-api:3.1.0` and `javax.websocket:javax.websocket-api:1.1`, both in `compileOnly` scope only and declared in wave 1, so a later decision for container WebSocket support needs no new main dependency.
- [D-384] The SLF4J adapter module SHALL have `org.slf4j:slf4j-api:1.7.36` as its only main dependency besides `NaruServe-api`, declared in wave 1.
- [D-385] The Logcat `Logger` module SHALL reach `android.util.Log` only through reflection at runtime, with no compile-time Android dependency, so the root build compiles and tests it without an Android SDK.
- [D-386] The bootstrap module SHALL declare in wave 1 a main dependency on the Logcat `Logger` module, so wave 5 selects Logcat as the Android default without a later build change.

### TinyHttpd composite build

Answers Q-1 (composite build through a Gradle property) and Q-2 (TinyHttpd is read-only).

- [D-013] `settings.gradle` SHALL include TinyHttpd with `includeBuild`, reading its directory from a Gradle property whose default is `/Users/beom/work/git/TinyHttpd`.
- [D-014] The TinyHttpd `includeBuild` path MUST NOT be a hard-coded relative path, so builds inside git worktrees resolve it.
- [D-015] When the configured TinyHttpd directory is missing, the build SHALL fail during configuration with a message naming the property and the path it tried.
- [D-016] NaruServe modules SHALL reference TinyHttpd only through its Maven coordinates (`com.snoworca.tinyhttpd:tinyhttpd-core`, `com.snoworca.tinyhttpd:tinyhttpd-websocket`) so Gradle substitutes the included projects.
- [D-017] Only the TinyHttpd adapter module SHALL depend on TinyHttpd artifacts.
- [D-018] NaruServe modules MUST NOT depend on `tinyhttpd-router` or `tinyhttpd-session`.
- [D-019] No wave of this run SHALL modify any file inside the TinyHttpd checkout.
- [D-020] A TinyHttpd gap that the NaruServe adapter cannot fill SHALL be recorded as a deferred issue instead of being patched in TinyHttpd.
- [D-021] Project documentation SHALL record the TinyHttpd commit the run builds against (46b973e at investigation time).

### Test infrastructure

- [D-022] Every Java module SHALL use JUnit 4.13.2 for tests.
- [D-023] The build SHALL apply Kotlin Gradle Plugin 2.x so Kotlin test sources compile and run inside `./gradlew build`.
- [D-024] Wave 1 SHALL add one Java smoke test and one Kotlin smoke test, and both execute during `./gradlew build`.
- [D-025] The root `./gradlew build` SHALL pass on the local JDK 17 without an Android SDK.
- [D-387] `gradle.properties` SHALL set `kotlin.stdlib.default.dependency=false`, so applying the Kotlin Gradle Plugin adds `kotlin-stdlib` to no main configuration.
- [D-388] A build check SHALL fail when any module other than the Kotlin extension module has `kotlin-stdlib` on its `runtimeClasspath`.

### Nullability and API 21 checks

- [D-026] Wave 1 SHALL add a nullability annotation library that the Kotlin compiler recognises, in `compileOnly` scope with no runtime dependency, chosen in #1.
- [D-027] animal-sniffer with the `android-api-level-21` signature SHALL run on the main source set of `NaruServe-api`, the TinyHttpd adapter module, the Gson module, the bootstrap module, the Kotlin extension module, the Logcat `Logger` module and the rotating file `Logger` module as part of `check`.
- [D-028] The animal-sniffer API 21 check MUST NOT be applied to `NaruServe-servlet`, which is JVM-only.

### Wave 1 documentation

- [D-029] `docs/api/README.md`, `docs/api/app.md`, `docs/api/json.md`, `docs/api/kotlin.md` and `docs/api/logging.md` SHALL name the final module names and dependency coordinates fixed in #1, so wave 1 removes every (미확정) module-name marker in `docs/api/`.
- [D-448] Wave 1 SHALL update the module line of `CLAUDE.md` to list every module fixed in #1, mark the modules under the animal-sniffer API 21 check of D-027 as API 21 check targets and keep `NaruServe-servlet` marked JVM-only.

## 2. Routing core

Covers the engine-free router of issues #2 and #3; router-level parts of T01, T02, T03 and T04, with the HTTP-level assertions in section 3. Depends on sections: 1.

### Method enum

- [D-030] `Method` SHALL be a Java enum with exactly the constants `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`, `TRACE`, `CONNECT`.
- [D-031] `Method` SHALL provide the static factories `get()`, `any()` and `of(Method...)`, each returning a `MethodSet`.
- [D-032] `Method` MUST NOT expose instance methods named after HTTP methods, so `Method.GET.delete()` does not compile.

### MethodSet

- [D-033] `MethodSet` SHALL be immutable, with every combinator returning a new instance and leaving the receiver unchanged (T01).
- [D-034] `MethodSet` SHALL provide `get()`, `head()`, `post()`, `put()`, `patch()`, `delete()` and `options()`, each returning a new set with that method added (T01).
- [D-035] `MethodSet.except(Method)` SHALL return a new set without the given method (T02).
- [D-036] `Method.any()` SHALL contain exactly `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE` and `OPTIONS`, leaving out `TRACE` and `CONNECT`.
- [D-037] `Method.any().except(Method.DELETE)` SHALL equal the set of `GET`, `HEAD`, `POST`, `PUT`, `PATCH` and `OPTIONS` (T02).
- [D-038] `MethodSet` SHALL expose membership and an iteration in enum declaration order through accessors whose names are decided in #2.
- [D-039] Two `MethodSet` values with the same members SHALL be equal and have equal hash codes.

### Path patterns and URL decoding

- [D-047] A route pattern SHALL consist of literal segments and `:name` variable segments, where a variable matches exactly one non-empty path segment and never crosses `/`.
- [D-048] Registering a pattern that contains Express wildcard or regular-expression syntax (`?`, `*`, `+`, parentheses) SHALL fail with a configuration error.
- [D-049] The router SHALL ignore the query string when matching.
- [D-050] Matching SHALL be case-sensitive and trailing-slash-sensitive by default, so `/Users` and `/users/` do not match `/users`.
- [D-051] The request path SHALL be percent-decoded exactly once before matching, so `%252e` reaches the router as the literal text `%2e`.
- [D-052] A request path with malformed percent-encoding, invalid UTF-8, raw non-ASCII bytes, an encoded `/`, an encoded or raw `NUL`, or any `.` or `..` segment in raw or encoded form SHALL be rejected with `400` before routing on every adapter, matching the rules TinyHttpd's parser applies before NaruServe sees the request.
- [D-053] The router SHALL support switching the handling of `//`, trailing slashes and case away from the strict default through a router option, which wave 3 exposes on `RestApp` under a name decided in #3.

### Priority and conflicts

- [D-054] A literal segment SHALL win over a variable segment at the same position regardless of registration order (T04).
- [D-055] Pattern priority SHALL be compared segment by segment from the left, with the first differing segment deciding.
- [D-056] Registering the same method and pattern twice SHALL be reported as a configuration error when the route table is frozen, which `listen()` triggers before binding (T03).
- [D-057] Two patterns that differ only in variable names and share a method SHALL be reported as a configuration error when the route table is frozen.
- [D-058] A routing configuration error SHALL name both conflicting registrations and be raised by the route-table freeze that wave 4 runs inside `listen()` before any socket is bound.
- [D-059] The router SHALL be engine-free code inside `NaruServe-api`.

### Router contract

- [D-389] The router SHALL store each registration with an opaque handler type parameter, so wave 2 compiles and tests without `Request`, `Response`, `RouteHandler` or `RestApp`.
- [D-390] A route lookup SHALL return an engine-free match result that is exactly one of matched (handler, path parameters, actual method, automatic-`HEAD` flag), method mismatch, automatic OPTIONS, WebSocket-only, unsupported method or no match.

### Router results for automatic responses

- [D-060] For a path that matches no route the router SHALL return the no-match result (T06).
- [D-061] For a path that matches but has no registration for the request method, the router SHALL return the method-mismatch result carrying every method the path accepts, including automatic `HEAD` and `OPTIONS` (T02, T06).
- [D-062] For a `HEAD` request to a path with only a `GET` registration, the router SHALL return the `GET` registration marked as automatic `HEAD` (T05).
- [D-063] An explicit `HEAD` registration SHALL take precedence over automatic `HEAD` resolution in the router.
- [D-064] For an `OPTIONS` request to a path without an explicit `OPTIONS` registration, the router SHALL return the automatic-OPTIONS result carrying the accepted methods (T05).
- [D-065] An explicit `OPTIONS` registration SHALL take precedence over the automatic-OPTIONS result.
- [D-066] A request whose method token is not one of the `Method` constants SHALL yield the unsupported-method result from the router (T06).
- [D-067] `TRACE` and `CONNECT` SHALL yield the unsupported-method result and reach no route unless an explicit policy, whose semantics wave 2 decides, enables them, a policy that on the TinyHttpd adapter also governs a `CONNECT` with an origin-form or absolute-form target, because TinyHttpd's parser answers `501` before dispatch only for a `CONNECT` with an authority-form target, which is recorded as a deferred TinyHttpd gap under D-020.

### WebSocket routes in the router

- [D-068] The router SHALL resolve a `GET` request carrying `Upgrade: websocket` against WebSocket registrations separately from `GET` registrations, so a WebSocket route and a `GET` route coexist on one path.
- [D-069] For a request without `Upgrade` to a path that has only WebSocket registrations, the router SHALL return the WebSocket-only result, which the wave 3 dispatcher answers with `426 Upgrade Required` carrying `Upgrade: websocket` and `Connection: Upgrade`, and wave 7 asserts end to end.
- [D-441] An `Upgrade: websocket` request to a path with no WebSocket registration SHALL be resolved as an ordinary `GET` without upgrading, reaching that path's `GET` registration or else the method-mismatch or no-match result, as a router test asserts for a path with only a `GET` route and a path with no route.
- [D-391] The router SHALL accept WebSocket registrations through an internal hook that marks a pattern as WebSocket, so wave 7 adds `app.ws` without changing the router.

### Wave 2 open items

- [D-070] Wave 2 SHALL decide the (미확정) routing policy semantics owned by #3 (`//`, trailing-slash and case handling, the `TRACE`/`CONNECT` enable policy) and update `docs/api/routing.md`, removing those markers.

## 3. Request and response core

Covers issue #4 plus route registration and dispatch from #2 and #3; acceptance tests T01, T02, T03, T05, T06 (HTTP level through the in-memory adapter) and T07 (in-memory part; the socket part follows in section 5). Depends on sections: 1, 2.

### Public surface ownership

- [D-071] Wave 3 SHALL create the `Request` and `Response` interfaces holding the `docs/api/request.md` and `docs/api/response.md` methods whose parameter and return types exist by the end of wave 3, leaving every other method to the wave that owns its types (D-392).
- [D-072] Every public method parameter and return value of reference type in `Request` and `Response` SHALL carry `@Nullable` or `@NonNull`.
- [D-392] The remaining `Request` and `Response` methods SHALL be added by their owning waves: `req.service` and `req.application` in wave 4, `req.body`, `res.json`, `req.cookie`, `req.getCookies` and `res.addCookie` in wave 5, `req.form`, `req.file`, `req.files`, `req.parts`, `res.file`, `res.download` and `res.cache` in wave 6, and `res.sse` in wave 7.

### Route registration API

- [D-040] `RestApp` SHALL provide `get`, `post`, `put`, `patch`, `delete`, `head` and `options` taking `(String path, RouteHandler handler)` and returning `RestApp`.
- [D-041] `route(Method, path, handler)` and `route(MethodSet, path, handler)` SHALL register the one handler for every method in the argument and return `RestApp` (T01).
- [D-042] A request dispatched to a handler registered for several methods SHALL report its actual method through `req.method()` (T01).
- [D-043] `route(path)` SHALL return a `RouteBuilder` whose `get`, `post`, `put`, `patch`, `delete`, `head` and `options` each register a separate handler on that path (T03).
- [D-044] `app.get(path, h)` and `app.route(path).get(h)` SHALL produce the same registration, so registering both for one path is a duplicate (T03).
- [D-045] `RouteHandler` SHALL be a `@FunctionalInterface` with the single method `void handle(Request req, Response res) throws Exception`.
- [D-046] `RestApp` MUST NOT expose a `serve(...)` registration method.
- [D-393] Wave 3 SHALL create the `RestApp` interface with the route registration and routing policy methods, and each later wave adds the `RestApp` methods of its own features.

### Dispatcher and automatic responses

- [D-394] Wave 3 SHALL own the dispatcher, the single engine-free component in `NaruServe-api` that takes a request from an `HttpAdapter`, looks it up in the router and either calls the matched handler with `Request` and `Response` or writes the automatic response.
- [D-395] The dispatcher SHALL answer the no-match result with `404`, the method-mismatch result with `405` and an `Allow` header listing the accepted methods including automatic `HEAD` and `OPTIONS`, the automatic-OPTIONS result with `204` and `Allow`, the unsupported-method result with `501` and the WebSocket-only result with `426` plus the headers `Upgrade: websocket` and `Connection: Upgrade` required by RFC 9110 section 15.5.22 (T02, T05, T06).
- [D-396] For an automatic-`HEAD` result the dispatcher SHALL run the `GET` handler and send its status and headers without a body under D-102 (T05).
- [D-442] The dispatcher SHALL answer the asterisk-form request `OPTIONS *`, whose raw path TinyHttpd passes as `*`, with `204` and an `Allow` header listing the methods of `Method.any()` (D-036) without route lookup or the path rejection of D-052, and answer any other raw path that does not start with `/` with `400`, identically on the in-memory and TinyHttpd adapters.
- [D-397] The HTTP-level assertions of T01, T02, T03, T05 and T06 SHALL run through the in-memory adapter in wave 3.

### Request accessors

- [D-073] `req.path()` SHALL return the decoded path without the query string.
- [D-074] `req.rawPath()` SHALL return the path as received before decoding, with the inclusion of the query string decided in #4.
- [D-075] `req.param(name)` for a name absent from the matched pattern SHALL throw an exception.
- [D-076] `req.query(name)` SHALL return the first value for the name or `null`, and `req.queries(name)` returns every value in request order or an empty list (T07).
- [D-077] Query names and values SHALL be decoded as UTF-8 `application/x-www-form-urlencoded` text, with `+` read as a space (T07).
- [D-078] A query string with malformed percent-encoding or invalid UTF-8 SHALL make the request fail with `400` (T07).
- [D-079] `req.header(name)` SHALL match names case-insensitively and return the first value or `null`, and `req.headers(name)` returns every value or an empty list (T07).
- [D-080] `req.remoteAddress()` and `req.isSecure()` SHALL ignore `X-Forwarded-*` and `Forwarded` headers unless proxy trust is configured through the API decided in #8.
- [D-081] `req.lastEventId()` SHALL return the `Last-Event-ID` header value or `null`.
- [D-082] `req.attribute(key, value)` and `req.attribute(key, type)` SHALL store values per request, returning `null` for a missing key and never sharing values with another request.
- [D-083] The request attribute store SHALL be safe for concurrent writes from several threads serving the same request.
- [D-084] A mutating `Response` call (`status`, `header`, `addCookie`, `cache` or a body write) after the response completed SHALL throw an `IllegalStateException`, while the read accessors of `Request` and `Response`, `isCommitted()` and `abort()` stay usable after completion, including in middleware after `next.run()` returned and in `onError` (`docs/api/middleware.md`).

### Body ownership

- [D-085] Each request SHALL track its body with an internal `BodyState` moving from `UNREAD` through `PARSING` to `CONSUMED` or `CLOSED`.
- [D-086] Any body read after the first one (JSON, form, multipart or raw), including a repeated `req.body(...)` call through the same JSON reader, SHALL throw `BodyAlreadyConsumedException`, an unchecked exception in `NaruServe-api`, with the shared parse of D-087 as the only exemption.
- [D-087] Repeated calls of `form`, `file`, `files` and `parts` SHALL share one parse of the body.
- [D-088] Body size limits SHALL be enforced on the incoming byte stream before and during parsing, including chunked bodies without `Content-Length`, with `413` when exceeded.

### Response API

- [D-089] `res.status` and `res.header`, and `res.addCookie` and `res.cache` once waves 5 and 6 add them, SHALL return the same `Response` for chaining.
- [D-090] A response SHALL default to status `200`.
- [D-091] `res.send(String)` SHALL write UTF-8 text with `Content-Type: text/plain; charset=UTF-8` unless a `Content-Type` was set explicitly.
- [D-092] `res.html(String)` SHALL write UTF-8 text with `Content-Type: text/html; charset=UTF-8`.
- [D-093] `res.send(byte[])` SHALL write the bytes unchanged, with its default `Content-Type` decided in #4.
- [D-094] `res.stream(InputStream, contentType)` SHALL copy the stream to the end in bounded chunks, with closing of the stream decided in #4.
- [D-095] `res.end()` SHALL complete the response without a body.
- [D-096] `res.isCommitted()` SHALL return `true` once the status line and headers were handed to the transport.
- [D-097] `res.abort(error)` SHALL end the response abnormally by closing the connection and set the state to `ABORTED`.
- [D-098] `res.header(name, value)` SHALL reject a name or value containing CR or LF with an exception.

### Response state machine

- [D-099] A response SHALL move through the states `NEW`, `COMMITTED`, `STREAMING`, `COMPLETED` and `ABORTED`, committing at most once.
- [D-100] Calling `status` or `header` after commit, and `addCookie` or `cache` after commit once they exist, SHALL throw an exception.
- [D-101] Sending a second body after a body was sent SHALL throw an exception.
- [D-102] Responses with status `204` or `304`, and every response to a `HEAD` request, SHALL be sent without a message body, discarding any body the handler supplied.
- [D-103] A streaming response (`sse`, `file`, `download`, `stream`) SHALL stay in `STREAMING` after the handler returns until the transfer ends.

### HttpAdapter SPI

- [D-104] The `HttpAdapter` SPI SHALL live in `NaruServe-api` and use only JDK and NaruServe types.
- [D-105] The SPI SHALL give the core the request line, headers, a streaming body `InputStream`, remote address and secure flag, and accept status, headers and a streaming body `OutputStream`.
- [D-106] The SPI SHALL include extension points for file transfer, event streams and protocol upgrade, where the event-stream point hands the adapter a core-owned drain loop that keeps writing after the handler returned until the core reports the stream ended, and the adapter chooses the thread that runs that loop (the request worker on TinyHttpd, an `AsyncContext` on the Servlet adapter), so waves 6, 7 and 8 add adapter classes without changing the SPI.
- [D-107] The SPI SHALL let the core bind to an address and port synchronously, read the actual bound port, and stop in two calls: a blocking stop that stops accepting, waits for in-flight exchanges until a deadline the core passes and then force-closes the remaining connections, and a final release that waits at most a fixed margin for the adapter's threads to end.
- [D-108] `NaruServe-api` SHALL ship an in-memory `HttpAdapter` in a test fixtures source set that runs requests through the full core pipeline without sockets.
- [D-399] Every adapter SHALL pass the raw request-target path and the raw query string through the SPI for the core to decode once, with the TinyHttpd adapter taking them from `getRequestURI()` and `getQueryString()` and never from the decoded, `//`-merging `getPath()`.

### Wave 3 open items

- [D-109] Wave 3 SHALL decide the (미확정) items owned by #4 (query in `rawPath()`, default `Content-Type` of `send(byte[])`, stream closing in `stream()`, exception type for an attribute type mismatch) and update `docs/api/request.md` and `docs/api/response.md`.
- [D-398] Wave 3 SHALL decide the `RestApp` names of the routing policy APIs and the value of `req.method()` during automatic `HEAD`, and update `docs/api/routing.md` and `docs/api/app.md`, removing those markers.

## 4. App assembly, middleware, lifecycle, logging

Covers issues #5, #6 and #7; acceptance tests T35 (dispatcher part), T36, T37, T38 (HTTP part), T39, T40, T41, T42, T43, T45, T46. Depends on sections: 1, 2, 3.

### RestApp assembly

- [D-110] `RestApp.create()` SHALL be a static interface method that returns an app assembled by the bootstrap module (section 5).
- [D-111] `NaruServe-api` SHALL offer an explicit initialisation entry point that accepts an `HttpAdapter` and a `JsonCodec`, with its name and methods decided in #5.
- [D-112] Wave 4 SHALL create the `JsonCodec` SPI interface in `NaruServe-api` with the signatures of D-182, so the explicit entry point compiles, while wave 5 adds `TypeRef`, the JSON request and response methods and the Gson implementation.
- [D-182] `JsonCodec` SHALL declare `<T> T decode(Reader reader, Type type) throws IOException` and `void encode(Object value, Writer writer) throws IOException`, with no Gson type in its signatures.
- [D-113] Each `RestApp` instance SHALL own its configuration, registry and context, with no static state shared between instances.
- [D-114] Every registration and configuration method of `RestApp` (routes, `use`, `accessLog`, `logger(l)`, `onStart`, `onStop`, `onError`, and `ws`, `staticFiles`, `multipart` and `jsonCodec` once later waves add them) SHALL throw an `IllegalStateException` when the app state is not `NEW`, through one state guard that wave 4 provides and later waves call.

### Middleware chain

- [D-115] `Middleware` SHALL be a `@FunctionalInterface` with `void handle(Request req, Response res, Next next) throws Exception`.
- [D-116] `Next` SHALL provide `run()` to continue the chain and `error(Throwable)` to pass an error to error handling.
- [D-117] `app.use(mw)` SHALL apply the middleware to every request that reaches the dispatcher, including requests that end in `404` or `405`, with the static-file and WebSocket-upgrade cases asserted in waves 6 and 7 (T35).
- [D-118] `app.use(prefix, mw)` SHALL apply the middleware to the prefix path and paths below it on a segment boundary, so `/api` covers `/api` and `/api/users` but not `/apix` (T35).
- [D-119] Each route registration method SHALL have an overload that takes one route middleware before the handler, such as `app.get(path, mw, handler)` (T35).
- [D-120] The pipeline SHALL run all global middleware in registration order, then all matching prefix middleware in registration order, then route middleware in registration order, then the handler (T35).
- [D-121] A request with no explicit route SHALL reach the dispatcher's fallback point after global and prefix middleware ran, which answers `404` until wave 6 adds static mounts in front of it.
- [D-122] A second `next.run()` call within one middleware invocation SHALL throw an exception (T35).
- [D-123] Calling `next.run()` after the response completed or after the request ended SHALL throw an exception.
- [D-124] `next.run()` SHALL return only after every downstream middleware and the handler returned.
- [D-125] A middleware that stops the chain by responding without calling `next.run()` SHALL have its response delivered with no later middleware or handler run (T36).
- [D-126] When the chain returns with no response and no `next.run()`, the framework SHALL log a developer warning through the app logger and finish the request without waiting for a timeout, with the finishing behaviour decided in #5.
- [D-127] An exception thrown from a middleware or handler, and an error passed to `next.error(e)`, SHALL reach the same error handling path (T36).
- [D-128] Middleware execution in v1 SHALL be synchronous, with no API for continuing the chain from another thread.

### Error handling and standard error JSON

- [D-129] `app.onError((error, req, res) -> ...)` SHALL receive every unhandled exception of a request that reached the dispatcher, including framework errors for `400`, `413` and `415`.
- [D-130] Framework-raised errors SHALL expose their HTTP status to `onError` through a mechanism decided in #5.
- [D-131] When the response is already committed, the framework MUST NOT write an error body and aborts the connection instead (T37).
- [D-132] Without a registered `onError`, an error of a request that reached the dispatcher SHALL be answered with the body `{"error":{"code":...,"message":...,"requestId":...}}` and `Content-Type: application/json; charset=UTF-8`.
- [D-133] Error responses MUST NOT contain stack traces or exception class names.
- [D-134] The default status mapping SHALL be: parse failure `400`, validation failure `400` or an explicit `422`, unmatched path `404`, unmatched method `405`, size limit `413`, unsupported media type `415`, request arriving during `STOPPING` `503`, any other exception `500`, with transport-level `503` rejections left to D-400.
- [D-135] The `requestId` field of a standard error body SHALL hold the same request identifier that the access log records for that request.
- [D-136] An exception during `res.json` serialisation SHALL turn into an error response only while the response is uncommitted, asserted in wave 5 once `res.json` exists.
- [D-137] Wave 4 SHALL decide the (미확정) items owned by #5 (entry point name and methods, multi-middleware overloads, `RouteBuilder.use(middleware)`, `onError` chaining, `code` values per status, custom `404`/`405` bodies, callback interface names and `throws Exception`) and update `docs/api/middleware.md`, `docs/api/app.md` and `docs/api/express-migration.md`.

### ServiceRegistry and ApplicationContext

- [D-138] `ServiceRegistry` SHALL provide `register(Class<T>, T)`, `get(Class<T>)`, `getOrNull(Class<T>)` and `contains(Class<?>)`, with `get` throwing `ServiceNotFoundException` for a missing type.
- [D-139] `ctx.register` SHALL succeed only inside `onStart` callbacks while the app is `STARTING`, and throws otherwise (T42).

## Integration

Cross-wave items that hold for the run as a whole; they are checked at every merge and at the end of the run. Depends on sections: 1, 2, 3, 4, 5, 6, 7, 8.

### Platform boundaries

- [I-001] animal-sniffer API 21 checks SHALL pass on every Android-targeted module in `./gradlew build`.
- [I-002] An automated check SHALL fail the build when `NaruServe-api` classes reference `android.*`, `javax.servlet.*`, `jakarta.servlet.*`, `com.google.gson.*`, `com.snoworca.tinyhttpd.*` or `kotlin.*`.
- [I-003] The public API of `NaruServe-api` MUST NOT expose `java.nio.file`, `CompletableFuture` or `java.net.http` types.
- [I-004] Every Android-targeted module SHALL be free of `javax.servlet` references.
- [I-005] Dependency resolution of every module and the Android sample SHALL select Gson 2.14.0 and no other Gson version.
- [I-006] The TinyHttpd checkout SHALL show no modified files at the end of the run.

### API contract consistency

- [I-007] Every public callback type SHALL be annotated `@FunctionalInterface`.
- [I-008] Every change to a public API SHALL update the matching `docs/api/` file in the same wave.
- [I-009] Every JVM Java example in `docs/api/` SHALL compile as part of the root test suite, and the Android-only examples compile in the `samples/android` build.
- [I-010] The Kotlin tests for T11 SHALL be updated whenever a public API changes.
- [I-011] The default values in `docs/api/defaults.md` SHALL equal the defaults in the configuration classes, checked by a test.
- [I-021] The path-rejection cases of D-052 and the asterisk-form `OPTIONS *` case of D-442 SHALL run against both the in-memory adapter and the TinyHttpd adapter with identical status results.
- [I-012] No size, count or time limit SHALL default to unlimited.
- [I-013] Each (미확정) decision SHALL be recorded with its reason in the commit or pull request that makes it.
- [I-014] A wave MUST NOT remove or change a public signature of `RestApp`, `Request`, `Response` or the `HttpAdapter` SPI that an earlier wave added, and adds new methods only.

### Resource and security invariants

- [I-015] Every test that starts a server SHALL assert after shutdown that no server thread and no temporary upload file of that app remains.
- [I-016] Security-related log messages MUST NOT contain tokens, passwords, session ids or file content.
- [I-017] Header values produced by the framework (`res.header`, `Set-Cookie`, `Content-Disposition`) SHALL never contain CR or LF.

### Final gate

- [I-018] Every acceptance test T01–T50 SHALL exist as an automated test or a recorded manual check before the run closes.
- [I-019] The full automated suite SHALL pass in `./gradlew build` at the end of the run.
- [I-020] A requirement covering a manual-pending check MUST NOT be promoted to verified.
