## 1. Scope Overview

This scope covers Server-Sent Events of NaruServe (issue #14, wave 7): `res.sse()`, `SseClient`, `SseEvent` and `app.sse(...)` settings, the `text/event-stream` response start, event serialisation with line splitting and field order, `req.lastEventId()` for reconnecting clients, the bounded per-stream outbound queue drained by the core drain loop with heartbeats, the TinyHttpd event-stream class that writes a chunked streaming body on the request's worker thread, the NaruServe SSE stream counter, `HEAD` on SSE routes, the stream lifetime with `onClose`, and the closing notice at shutdown. It holds T24, T25 and the SSE parts of T38 and T44.

## 2. Scope Boundaries

### In Scope

- SSE types and methods of wave 7 in `NaruServe-api` under `com.snoworca.naruserve` and their internal implementation in `com.snoworca.naruserve.internal`.
- The TinyHttpd event-stream class of `NaruServe-tinyhttpd`.
- The (미확정) markers owned by #14 in `docs/api/sse.md` and `docs/api/defaults.md`.

### Out of Scope

- TinyHttpd's own `startEventStream()` (D-335: never used).
- Storing or replaying events (the app keeps them; `docs/api/sse.md`).
- WebSocket (scope WS) and the shutdown coordination shared with WebSocket (scope APP).
- Kotlin, Servlet and Android sample-app items (wave 8).

## 3. Assumptions and Constraints

- Core code is engine-free code in `NaruServe-api`: it references no TinyHttpd, Servlet, Gson, SLF4J, `android.*` or Kotlin stdlib type, uses `java.io` and `java.util.concurrent` and never `java.nio.file` or `CompletableFuture`, compiles to Java 8 bytecode and passes the wave 1 animal-sniffer API 21 checks.
- Public types follow the wave 1 conventions: nullability annotations on public signatures, `@FunctionalInterface` callbacks, Express-style short method names, no Kotlin keywords as method names, and no removed or changed public signature of `RestApp`, `Request`, `Response` or the `HttpAdapter` SPI: those types gain new methods and types only (I-014, D-106 read as "without breaking the SPI").
- Where the design leaves a choice open, the wave decisions and the residual section of `docs/research/naruserve-v1/waves/wave-7/design.md` apply; otherwise the implementer decides under standing rule C-07, choosing what is most natural to an Express user without contradicting `object.md`.
- Source of the requirements: `docs/research/naruserve-v1/waves/wave-7/design.md`, `docs/research/naruserve-v1/waves/wave-7/excerpt.md` and `object.md`.
- TinyHttpd at `/Users/beom/work/git/TinyHttpd` (commit `46b973e`) stays read-only; gaps become deferred TinyHttpd-gap issues under D-020.

#### Requirement

The system shall provide `SseClient Response.sse()`, the `SseClient` interface with `send(String event, String data)`, `send(String data)`, `send(SseEvent event)`, `close()`, `isOpen()` and `onClose(SseClient.CloseListener)`, the `SseEvent` type built through `SseEvent.event(name)` with `id`, `data` and `retry`, and `RestApp sse(Configurer<SseOptions> configurer)` with the settings `heartbeatInterval` and `sendQueueSize`, each bounded and defaulted as the acceptance criteria state.

#### Rationale

Covers D-326 (API part), D-330 (API part), D-339 (heartbeat, data-only send and explicit close APIs), D-419 (SSE setting name) and the C-07 choices of the authoring plan; T11/C-03 for Kotlin. Measured: `Response.java:9` says "No sse method yet; a later wave adds it", and `json` (`:55`) and `addCookie` (`:66`) are `default` methods throwing `UnsupportedOperationException`, so `sse()` follows the same add-only pattern (I-014: no changed public signature). `Request.java:47` already declares `lastEventId()` (FR-HTTP-011 AC-3), reused by FR-SSE-001. The configurer follows IR-APP-007 and IR-MULTIPART-001 (copy swapped in after it returned; message `sendQueueSize must be in 1..16777216: <value>` for the size and `heartbeatInterval must be in 1 s..1 h: <time> <unit>` for the duration, as AC-6 states), and the ranges keep I-012 (no unlimited value). Decision on defaults: heartbeat 15 s, below the 30 s to 60 s idle cutoffs of common proxies and load balancers; send queue 256 KiB from D-406. Pitfall: a `send` that throws on an ended client would force every broadcaster to catch; `send` returns `false` instead, like the `ws` library's send on a closed socket. Rejected alternative: a fluent `SseEvent` with a public constructor; the factory keeps `event` mandatory and matches `docs/api/sse.md`, reopen if data-only `SseEvent` objects are requested. Rejected alternative: Express-style `res.write` of raw event text; it leaves line splitting to the app and breaks D-329. Express mapping: `res.writeHead(200, {'Content-Type': 'text/event-stream'})` plus `res.write('event: x\ndata: y\n\n')` and `req.on('close')`. Test to re-point: `HttpApiSurfaceTest` (the `LATER_WAVE_NAMES` entry `sse` and the `Response` method set) moves to IR-SSE-001.

### FR-SSE-001 — SSE stream start and event serialisation: 200 with event-stream headers, field order, line splitting, name and id checks, data-only events and Last-Event-ID

| Field | Value |

#### Requirement

The system shall, on `res.sse()`, commit status `200` with `Content-Type: text/event-stream; charset=UTF-8` and `Cache-Control: no-cache, no-transform`, put the response in `STREAMING` and return an `SseClient`, serialise each event as its `event`, `id`, `retry` and `data` lines in that order followed by a blank line with the data split at CR, LF and CRLF into one `data:` line per line, reject event names and ids that contain CR, LF or NUL, and expose a reconnecting client's `Last-Event-ID` through `req.lastEventId()`.

#### Rationale

Covers D-326, D-328, D-329, D-330, D-331, D-337 and the data-only send of D-339; test T24. Measured: `Request.java:47` declares `lastEventId()` (verified under FR-HTTP-011 AC-3), so D-337 needs only an end-to-end check inside an SSE handler; `Response` has no `sse` method (`Response.java:9`). The event-stream format follows the WHATWG HTML "Server-sent events" parsing rules: a line `data: x` and `data:x` parse the same, an empty data line contributes an empty line, and EventSource dispatches an event without `event:` as `message`. Decision: each data line, including an empty one, is written as `data: ` followed by the line, so the data `a` followed by LF becomes the lines `data: a` and `data: `, and EventSource rebuilds the same string; lines end with LF; the fields are written in the fixed order `event`, `id`, `retry`, `data` whatever the setter order. Pitfall: a name or id with LF would inject a forged field; D-331 rejects it before anything is queued. Pitfall: `res.sse()` after `res.send(...)` must not write a second status line; it throws `IllegalStateException` like the other writers on a committed response (FR-HTTP-016). Rejected alternative: escaping CR/LF in names instead of rejecting them; silent rewriting hides app bugs, reopen never in v1.

#### Acceptance Criteria

- [x] AC-1: A handler calling `res.sse()` gives the client status `200` with `Content-Type: text/event-stream; charset=UTF-8` and `Cache-Control: no-cache, no-transform`, each header present exactly once, and after the call `res.isCommitted()` is `true` and the response state is `STREAMING`, over the in-memory adapter and over TinyHttpd (T24). [D-326] Decision: `res.sse()` replaces any app-set `Content-Type` and `Cache-Control`, removes `Content-Length` and `Transfer-Encoding`, and sets status `200` whatever status was set. [SDS 2026-10-19.naruserve.naruserve-v1-wave-7-9 SDS-AC-6] Decision: when `ex.eventStream` throws a `RuntimeException`, the client is removed from the registry, the state stays `NEW` and the exception is rethrown so that the error path commits a `503`; an `IOException` aborts the response and returns an ended client. [SDS 2026-10-19.naruserve.naruserve-v1-wave-7-9 SDS-AC-8]
- [x] AC-2: `res.sse()` on a response that is already committed throws `IllegalStateException` and writes nothing, and a second `res.sse()` on the same response throws `IllegalStateException`. Decision: `res.sse()` follows the single-commit rule of FR-HTTP-016. [D-326]
- [x] AC-3: `client.send("connected", "ready")` writes exactly the bytes `event: connected\ndata: ready\n\n` to the client (T24). [D-328]

### FR-SSE-002 — SSE outbound queue, drain loop and heartbeat: any-thread sends in call order, handler-thread writes before the drain starts and the overflow policy

#### Requirement

The system shall give each SSE stream a bounded outbound queue of `sendQueueSize` bytes that `SseClient.send` from any thread fills with whole serialised events, which the core drain loop of the event-stream extension point writes to the socket in call order, write a `: ping` comment after each heartbeat interval in which nothing was written, write a send made on the handler's own thread before the drain loop starts, after every event already queued, straight to the stream the adapter handed over through `StreamDrain.attach(out)` (falling back to the bounded queue when the adapter attached no stream), and end the stream when a queued send would make the queued bytes exceed `sendQueueSize`.

#### Rationale

Covers D-332, D-333, D-406 and D-339 (overflow policy), wave decision Sends inside the SSE handler (r4 W2-001) and residual SSE send order before the drain starts (r5 W2-001); test T25. Measured: `spi/StreamDrain.java` is the core-owned drain loop type of the D-106 event-stream point (IR-HTTP-007 AC-3), and `HttpExchange.eventStream(int, List, StreamDrain)` (`spi/HttpExchange.java:89`) lets the adapter choose the thread (FR-SSE-003: the TinyHttpd request worker). Deviation (recorded): D-406 says `SseClient.send` from any thread fills the outbound queue; until the drain loop starts, a send on the handler's own thread first writes every event already queued, in queue order, and then its own event straight to the committed stream under the exchange lock, so a replay loop inside the handler is paced by the socket and never trips the overflow policy, and the queue limit applies only to other threads' sends until then (r4 W2-001, r5 W2-001); `docs/api/sse.md` records it. Decision: overflow drops the event, discards the queued events, ends the stream and makes that `send` return `false` (no exception), so a broadcaster loop needs no `try`. Decision: queued bytes count the serialised UTF-8 bytes of each event. Decision: the heartbeat is the comment `: ping` followed by a blank line, written after one heartbeat interval with no write. Pitfall: a heartbeat timer that fires on a separate thread would need its own lock; the drain loop waits on the queue with the heartbeat interval as timeout and writes the comment itself. Rejected alternative: blocking the sender when the queue is full; it stalls app threads that broadcast to many clients, reopen on demand for a blocking `send` variant. Rejected alternative: queueing handler-thread sends before the drain starts; a handler replaying more than 256 KiB of missed events would overflow its own stream before the drain could run.
- [2026-10-20] Deviation (recorded), committee decision StreamDrain.attach (wave-7 feasibility B-1): handler-thread sends before the drain (r4 W2-001, r5 W2-001) go to the stream each adapter hands over via the add-only `default` `StreamDrain.attach(OutputStream)` (IR-HTTP-007 AC-4), a second default method beyond W2-001's "one default method" wording. AC-5 now latches the handler so the test proves the write reaches the socket while it runs; AC-8 covers the in-memory attach and the queue fallback.

### FR-SSE-003 — TinyHttpd event-stream class: chunked body on the request worker, NaruServe SSE counter with 503 before start, drain writes synchronized on the exchange

#### Requirement

The system shall implement `HttpExchange.eventStream` on the TinyHttpd adapter as a chunked streaming body written through TinyHttpd's `Response.setHeader`, `flushBuffer()` and `getOutputStream()` on the request's worker thread and never through `startEventStream()`, run the core drain loop on that worker after the handler returns until the core reports the stream ended, count each open stream against a NaruServe counter bounded by `maxSseStreams` that answers `503` before the exchange is marked started, and hold the exchange lock only to check abort and mark the response started while every drain and handler-thread write synchronizes on the exchange.

#### Rationale

Covers D-335, D-336, wave decisions TinyHttpd feature hooks (W2-003, SSE part: `eventStream` commits the headers and registers the drain, `TinyHttpdExchange.run` runs that drain on the same worker after the handler returns, drain writes synchronize on the exchange), maxEventStreams (W2-009), SSE limit answer (r3 W2-001) and carried wave 5 drain synchronization (w5-P2-002, commit 387db8c). Measured: `tinyhttpd/TinyHttpdFeatures.java:51` `eventStream(Response, int, List, StreamDrain)` throws `UnsupportedOperationException` naming wave 7; `TinyHttpdExchange.java:240` `eventStream` is `synchronized` and takes the commit bookkeeping; `TinyHttpdAdapter.java:105-116` maps `maxSseStreams` onto TinyHttpd's `maxEventStreams` and sizes the worker pool `maxWorkers + maxSseStreams` (defaults.md: 192), so one worker per stream never takes the `maxWorkers` share (FR-ENGINE-004). TinyHttpd's `startEventStream()` writes a fixed `Cache-Control: no-cache` and its own `retry` block, which cannot meet D-326 and D-330 (D-335). Pitfall: checking the counter after the exchange is marked started would leave the dispatcher unable to commit the `503` (r3 W2-001). Pitfall: a drain write outside `synchronized (exchange)` races the abort path of wave 5. Rejected alternative: a dedicated SSE writer thread pool; it would add threads beyond D-416's budget, reopen if a non-TinyHttpd adapter needs it.

#### Requirement

The system shall keep an SSE stream open after its handler returns until the client disconnects, the app calls `close()`, the stream overflows, an error ends it or shutdown runs, run its `onClose` listeners exactly once when it ends, answer `HEAD` on an SSE route with the event-stream headers, no body and a client that has already ended, give the SSE handler the services registered in `onStart`, and keep the request mark across the drain loop and the `onClose` listeners it runs.

#### Rationale

Covers D-327, D-334, wave decision HEAD on an SSE route (r3 W2-002), carried D-142 SSE case (T41, from wave 4) and residual shutdown from an SSE onClose listener (r5 W2-004); test T25. Measured: `internal/AppLifecycle.java:110-115` provides `enterRequest()`/`exitRequest()`, which `internal/GatedExchangeHandler.java:46` calls around a dispatch; `docs/api/lifecycle.md` ("요청 핸들러 안에서 shutdown") promises that `shutdown` called during a request returns at once, so the mark must span the drain loop and its `onClose` listeners for that promise to hold when a listener calls `shutdown` (r5 W2-004). The mark is thread-local, and the in-memory adapter runs the drain on its own worker thread (IR-HTTP-007 AC-3), so the drain thread enters the mark itself (AC-8). FR-HTTP-017 keeps `HEAD` bodyless; for `HEAD` `res.sse()` takes no SSE slot and runs no drain, so no worker is held after the handler returns (r3 W2-002). Decision: an `onClose` registered on an ended client runs at once, once, on the calling thread (removes the `docs/api/sse.md` marker); listener exceptions are logged at ERROR with the request id and the other listeners still run. Decision: `close()` ends the stream normally: the drain writes queued events, ends the chunked body and runs `onClose`. Pitfall: a client disconnect is seen only on a write, and the first write after the peer closed may still succeed, so the heartbeat bounds detection to two intervals plus 1 s. Rejected alternative: a background reader thread per stream to detect disconnects at once; it doubles SSE threads against D-416, reopen never in v1.

### FR-SSE-005 — Shutdown of SSE streams: before-wait participant appends the closing notice, marks streams ended and does not wait

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-7 |
| Status | verified |
| Priority | high |
| Tags | wave-7, feasibility:high, sse, shutdown |
| Risk | high |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/14 |

#### Requirement

The system shall register a before-wait shutdown participant that sets the SSE stream registry's closed flag under its lock, then snapshots every open stream and, without waiting, appends to each stream's outbound queue the closing notice `event: shutdown` with `data: shutdown`, exempt from the queue limit, and marks the stream ended, so that its drain loop writes the queued events and the notice, ends the chunked body, runs the `onClose` listeners once and returns its worker.

#### Rationale

Covers D-341, D-436, D-343 (SSE part) and the SSE part of D-445 (flag before snapshot; the behaviour of `res.sse()` after the flag is FR-APP-020); tests T44 (SSE parts). Measured: `internal/ShutdownParticipants.java:19-26` defines the `BEFORE_WAIT` phase "After STOPPING began, before the adapter stop waits", and `internal/DefaultRestApp.java:617-619` runs it before `adapter.stop(left(deadline))` (FR-APP-011). TinyHttpd's stop closes only its own event streams and upgraded connections and otherwise waits for a D-335 stream until the deadline, so without this participant every open stream would hold `shutdown` to the timeout. Decision: the closing notice is `event: shutdown\ndata: shutdown\n\n`, dispatched to EventSource listeners of `shutdown`, with non-empty data because EventSource drops events whose data is empty; it is exempt from `sendQueueSize`. Pitfall: waiting for the drains inside the participant would spend the D-344 budget twice; the participant returns at once and the adapter stop waits for the workers. Pitfall: a stream stalled on a full socket never finishes its drain; TinyHttpd aborts it at the deadline (D-343). Rejected alternative: closing sockets without a notice; the client could not tell shutdown from a network failure and would reconnect at once to a stopping server.

#### Acceptance Criteria

- [x] AC-1: The SSE closing participant is registered in the before-wait phase of the shutdown participants of FR-APP-011 and, when run, first sets the stream registry's closed flag under the registry lock and then takes its snapshot, so a stream registered before the flag is in the snapshot, which an in-memory test asserts by registering a stream from another thread blocked on the registry lock. [D-436; D-445] Decision: the SSE `closeAll` is registered in `BEFORE_WAIT` before the WebSocket `closeAll`, and `terminate` in `FORCE_CLOSE`, once per app. [SDS 2026-10-19.naruserve.naruserve-v1-wave-7-11 SDS-AC-13]
- [x] AC-2: During shutdown, the client of an open stream with two events queued receives those two events, then exactly `event: shutdown\ndata: shutdown\n\n`, then the end of the chunked body, and the stream's `onClose` listeners run once (T44). Decision: the closing notice is the `shutdown` event with data `shutdown`. [D-341; D-436]
- [x] AC-3: A stream whose queued bytes are within 10 bytes of `sendQueueSize` still receives the closing notice and ends normally, without the overflow end of FR-SSE-002, because the notice is exempt from the queue limit. [D-436]
- [x] AC-4: With 50 open streams, one of whose clients stopped reading so its drain write blocks, the participant returns within 200 ms, because it only appends the notice and marks each stream ended without waiting for any drain. [D-436]
- [x] AC-5: A stream whose client stopped reading is force-closed by the adapter stop at the shutdown deadline: its client socket reaches end of stream or reset within the shutdown timeout plus the D-344 margin, its `onClose` listeners run once, and the FR-APP-019 line of the stream carries `cause=shutdown`, the end reason the closing participant recorded first, although its drain write then fails with an `IOException`. [D-343; D-338]
- [x] AC-6: After `shutdown` returns, the SSE stream registry is empty and no stream holds a queued event, which a test reads through the internal registry. [D-341; D-343]
