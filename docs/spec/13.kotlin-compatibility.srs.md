## 1. Scope Overview

This scope covers the Kotlin compatibility of NaruServe (issue #16, wave 8): the automated nullability and Kotlin-keyword checks over the public API of `NaruServe-api`, the Kotlin tests for T11 (SAM lambdas, nullable accessors, property syntax, the Gson limit for data classes, every Kotlin example of `docs/api`), the reified `Request.body<T>()` extension in `NaruServe-kotlin`, the ban on `runBlocking` as an asynchronous adapter, and the corrections of `docs/api/kotlin.md`.

## 2. Scope Boundaries

### In Scope

- The nullability check of the public API packages, the Kotlin-keyword check of public method names and the `getX`/`setX`/`isX` property-syntax rule (D-348, D-352, D-353).
- Kotlin tests of SAM lambdas, nullable accessors, property syntax, the Gson no-argument-constructor limit and the Kotlin examples of `docs/api` (D-349, D-350, D-351, D-355).
- `inline fun <reified T : Any> Request.body(): T` in `NaruServe-kotlin` (D-354).
- The `runBlocking` ban and the `docs/api/kotlin.md` corrections and module-name verification (D-356, D-357).

### Out of Scope

- The Android sample and its Kotlin sources (D-412), and every device or emulator run: out of v1 scope by user decision of 2026-10-20.
- Coroutine (`suspend`) handler support: documented in `docs/api/kotlin.md` as not supported in v1.
- Any change to `RestApp`, `Request`, `Response` or the `HttpAdapter` SPI signatures: wave 8 adds nothing there (I-014).

## 3. Assumptions and Constraints

- Core stays Kotlin-free: only `NaruServe-kotlin` has `kotlin-stdlib` on its `runtimeClasspath` (CON-BUILD-007), and the Kotlin plugin version is the one wave 1 fixed (CON-BUILD-004).
- The public API packages of `NaruServe-api` are `com.snoworca.naruserve`, `com.snoworca.naruserve.spi` and `com.snoworca.naruserve.routing`; `com.snoworca.naruserve.internal` is outside the method-level checks but keeps its `@NullMarked` (wave decision r1 W2-005).
- Kotlin reads the JSpecify annotations strictly (`-Xjspecify-annotations=strict`, CON-BUILD-011), so `@NullMarked` makes an unannotated reference type non-null and `@Nullable` makes it nullable.
- The Android sample build and the Android device verification are out of v1 scope by user decision of 2026-10-20 (D-364 to D-374 and D-412): no requirement of this scope covers them, and no requirement in this scope may call T10, T12 or T47 verified.
- Source of the requirements: `docs/research/naruserve-v1/waves/wave-8/design.md` (frozen design items, wave decisions of loop W rounds 1 to 5, residual), `docs/research/naruserve-v1/waves/wave-8/excerpt.md`, `docs/research/naruserve-v1/waves/carried-into-wave-8.md` and `object.md`.

#### Requirement

The system shall run, as part of `./gradlew build`, an automated check over the public API packages of `NaruServe-api` (`com.snoworca.naruserve`, `com.snoworca.naruserve.spi`, `com.snoworca.naruserve.routing`) that fails when a package lacks `@NullMarked`, when a method named in the nullable-accessor table of `docs/api/kotlin.md` lacks `@Nullable` on its return value, or when the public API carries `@NonNull`, so that every reference-typed return value and parameter of a public method has a nullability annotation by contract: non-null through the package default, nullable through `@Nullable`.

#### Rationale

Covers D-348, wave decisions Nullability check (r1 W2-005) and its second reading (r2 W2-004), and the Kotlin-visible part of I-007 and I-010; supports T11. Measured (2026-10-20): `package-info.java` of `com.snoworca.naruserve`, `.spi`, `.routing` and `.internal` each carries `@org.jspecify.annotations.NullMarked`; `grep -rn NonNull NaruServe-*/src/main` finds no `@NonNull` (only `Objects.requireNonNull`); the nullable `Request` accessors are `query`, `header`, `lastEventId`, `attribute(String, Class)`, `body(Class)`, `body(TypeRef)`, `cookie`, `form` and `file` (`Request.java:29-127`). Decision: "has a nullability annotation" is satisfied by the package default plus `@Nullable`, because under `@NullMarked` an unannotated reference type is non-null by contract and Kotlin reads it as `T`; no `@NonNull` exists. The round-1 test "a null-capable type without `@Nullable`" is dropped because it cannot be derived from signatures. Pitfall: the test class path of `NaruServe-api` also holds classes of package `com.snoworca.naruserve` (for example `NullabilityFixture`, which carries `@NonNull` on purpose, CON-BUILD-011 AC-2); every enumeration of this requirement and of FR-KT-002 and FR-KT-003 therefore reads the classes of the main jar given by the existing system property `naruserve.apiJar` (`build.gradle:179-183`), never the test class path. Pitfall: JSpecify `@Nullable` is a type-use annotation, so on `<T> @Nullable T attribute(...)` it sits on the return type, not the method; reflection must read `getAnnotatedReturnType()`. Rejected alternative: adding `@NonNull` to every signature; it is redundant under `@NullMarked` and the wave 1 convention (CON-BUILD-011) already drops it; reopen only if Kotlin stops reading the package default.

[D-348]
- [x] AC-2: The same test parses the nullable-accessor table of `docs/api/kotlin.md` and, for every row whose Kotlin type column ends in `?`, finds every public overload of that name that returns a value (for example `Request.query`, `header`, `form`, `cookie`, `file`, `lastEventId`, `attribute(String, Class)`, `body(Class)` and `body(TypeRef)`; the void overload `attribute(String, Object)` is skipped) and fails when `getAnnotatedReturnType()` lacks `@Nullable`; for every row without `?` it fails when such an overload's return type is `@Nullable`. ### FR-KT-002 — Public method names of NaruServe-api avoid the Kotlin hard keywords

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-8 |
| Status | verified |
| Priority | high |
| Tags | wave-8, feasibility:high, kotlin, keywords, T11 |
| Risk | low |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/16 |
| Related Docs | - |

#### Requirement

The system shall run, as part of `./gradlew build`, an automated check that fails, naming `Type.method`, when a public or protected method of a public type in the public API packages of `NaruServe-api` is named with a Kotlin hard keyword that is a legal Java identifier — `as`, `fun`, `in`, `is`, `object`, `typealias`, `typeof`, `val`, `var` or `when` — so that no Kotlin call needs backticks.

#### Rationale

Covers D-352 and wave decision Kotlin keywords (r1 W2-006); supports T11. Measured (2026-10-20): a source scan of the method declarations of `NaruServe-api/src/main/java` and the other published modules finds no method named with one of the ten words. Decision: the check list is the ten words that are Kotlin hard keywords and legal Java identifiers; the other Kotlin hard keywords (`break`, `class`, `do`, `else`, `for`, `if`, `interface`, `package`, `return`, `super`, `this`, `throw`, `try`, `while`, `continue`, `null`, `true`, `false`) are Java keywords or literals and cannot be method names. Pitfall: Kotlin soft and modifier keywords (`get`, `set`, `by`, `value`, `where`, `open`, `field`) are legal names and `app.get(...)` depends on it; adding them to the list would forbid the Express-style `get`. Pitfall: the rule is on method names only, because Java parameter names are invisible to Kotlin. Rejected alternative: also scanning every other published module; their public classes (`TinyHttpdAdapter`, `GsonJsonCodec`, loggers, servlet classes) are implementation classes that app code rarely calls; reopen if one of them gains a keyword-named public method.

#### Acceptance Criteria

- [x] AC-1: A test in `NaruServe-api` enumerates by reflection, from the main jar named by `naruserve.apiJar`, every public and protected method of every public class, interface and enum of `com.snoworca.naruserve`, `com.snoworca.naruserve.spi` and `com.snoworca.naruserve.routing`, including nested types, and fails with the message `Type.method` when a name is one of `as`, `fun`, `in`, `is`, `object`, `typealias`, `typeof`, `val`, `var` or `when`. [D-352]
- [x] AC-2: The check is a reusable function proved by a negative fixture: a fixture type with a method named each of the ten words makes it fail once per word, and a fixture type with methods `get`, `set`, `use`, `value` and `isSecure` passes, so soft keywords and `is`-prefixed names are not flagged. [D-352]
- [x] AC-3: The check passes on the wave 8 API and runs in `./gradlew build`; a Kotlin test calls one method of each of `RestApp`, `Request`, `Response`, `RouteBuilder` and `WebSocketSession` without a backtick. [D-352; I-010]

| Field | Value |

#### Requirement

The system shall accept a Kotlin lambda, without a DSL builder, for every callback parameter of the public API: each interface used as a callback parameter type of a public method is a Java functional interface annotated `@FunctionalInterface` with exactly one abstract method, and a Kotlin test passes a trailing lambda to each such parameter, for example `app.get("/x") { req, res -> }`.

#### Rationale

Covers D-350 and the callback part of I-007 and I-010; supports T11. Measured (2026-10-20): `@FunctionalInterface` appears 18 times in 14 files of `NaruServe-api/src/main/java`, on `RouteHandler`, `Middleware`, `ErrorHandler`, `LifecycleCallback`, `Configurer`, `WebSocketHandler`, the `SseClient` and `WebSocketSession` listener types, the SPI types `ExchangeHandler`, `ErrorRenderer`, `StreamDrain`, `UpgradeHandler` and the internal `ShutdownParticipants` and `MultipartParser` callbacks; earlier waves already compile lambdas for subsets in `HttpApiKotlinTest`, `AppEntryKotlinTest`, `WebSocketKotlinTest`, `SseKotlinTest` and `WaveSixKotlinTest`. Decision: the inventory test lists every interface that is a parameter type of a public method and has exactly one abstract method, and the Kotlin matrix names each of them, so a new callback type fails the build until it has a Kotlin lambda test. Pitfall: SAM conversion needs exactly one abstract method; a callback interface that gains a second abstract method silently loses lambda syntax in Kotlin (a `default` method does not). Rejected alternative: a Kotlin DSL builder (`routes { get("/x") { } }`); it is forbidden by C-03 and would put `kotlin.*` in Core.

#### Acceptance Criteria

- [x] AC-1: A reflection test over the main jar named by `naruserve.apiJar` finds every interface declared in `com.snoworca.naruserve`, `.spi` or `.routing` that is the parameter type of a public method of those packages and has exactly one abstract method (ignoring `Object` methods and `default` methods) and fails, naming it, when it lacks `@FunctionalInterface`. [D-350; I-007]
- [x] AC-2: The same test fails, naming the interface, when an interface that is a callback parameter type has no abstract method or more than one, which would stop Kotlin SAM conversion. [D-350] [SDS 2026-10-19.naruserve.naruserve-v1-wave-8-2 SDS-AC-2] Decision: an interface with two abstract methods cannot carry @FunctionalInterface, so the declared list of callback type names is the marker that makes an interface a callback parameter type for this check, and a name of that list that is an interface with zero or two abstract methods fails naming it.
- [x] AC-3: A Kotlin test passes a lambda to each callback parameter of the matrix: `app.get`/`post`/`route` with `RouteHandler`, `app.use(path) { req, res, next -> }` with `Middleware`, `app.onError`, `app.onStart`, `app.onStop`, `app.server`, `app.multipart`, `app.webSocket`, `app.sse`, `app.ws`, `ws.onText`, `ws.onClose { code, reason -> }` and `res.sse().onClose { }`, each without a receiver DSL, and runs a request or session through the in-memory harness that reaches the lambda; the matrix covers every interface of the AC-1 inventory (16 on 2026-10-20, including the `WebSocketSession` listener types and the SPI types `ExchangeHandler`, `ErrorRenderer`, `StreamDrain` and `UpgradeHandler`, which the test implements as Kotlin lambdas). [D-350; I-010]

#### Requirement

The system shall keep every fenced `kotlin` block of `docs/api/*.md` as a Kotlin test that compiles and runs in `./gradlew build`, and a docs test shall fail, naming `<file>#<n>`, when a block has no matching Kotlin test or a marker names a block that no longer exists.

#### Rationale

Covers D-349, the Kotlin part of I-009 and I-010; supports T11. Measured (2026-10-20): `docs/api/*.md` holds 45 ```kotlin blocks (`kotlin.md` 10, `websocket.md` 7, `sse.md` 5, `app.md`, `middleware.md`, `response.md` and `routing.md` 3 each, `json.md` and `request.md` 2 each, `cookie.md`, `express-migration.md`, `logging.md`, `multipart.md`, `static.md`, `README.md` and `lifecycle.md` 1 each); waves 5 and 7 already compile subsets in `JsonDocsKotlinTest`, `SseDocsKotlinTest` and `WebSocketDocsKotlinTest`. #### Requirement

#### Rationale

#### Requirement

#### Rationale

The system shall name the accessors of value objects such as `Cookie` with the Servlet-style `getX()`, `setX(value)` and `isX()` rules so that Kotlin property syntax compiles — `cookie.maxAge = 60`, `cookie.isHttpOnly = true`, `cookie.secure = true`, `res.isCommitted` and `req.isSecure` — while the Express-style short methods (`req.param`, `req.path`, `res.status`) stay ordinary methods.

#### Rationale

Covers D-353 and wave decisions of waves 3 and 5 on `Cookie`; supports T11. Measured (2026-10-20): `Cookie.java:90-151` declares `getName`, `getValue`/`setValue`, `getPath`/`setPath`, `getDomain`/`setDomain`, `getMaxAge`/`setMaxAge`, `getSecure`/`setSecure`, `isHttpOnly`/`setHttpOnly` and `getSameSite`/`setSameSite`; `docs/api/kotlin.md` already shows `isHttpOnly = true`, `secure = true`, `maxAge = 3600` and `res.isCommitted`. Pitfall: Kotlin synthesises a property from a `boolean getX()` as `x` and from `boolean isX()` as `isX`; the pair `getSecure`/`setSecure` therefore reads `secure`, not `isSecure`, and a rename to `isSecure()` would break `kotlin.md`. Pitfall: a getter without a matching setter gives a read-only `val`; a setter whose parameter type differs from the getter's return type gives no property. Rejected alternative: fluent setters (`cookie.maxAge(60)`) as in Express; they would not form Kotlin properties and C-03 requires property syntax.

#### Requirement

The system shall correct and verify `docs/api/kotlin.md`: it names the Kotlin module `NaruServe-kotlin` and its coordinate exactly as wave 1 fixed them, its null-handling paragraph names `@NullMarked` (non-null by default) and `@Nullable` without `@NonNull`, its nullable-accessor table is the one that FR-KT-001 and FR-KT-005 check, and its Coroutine section states that `suspend` handlers are unsupported in v1 and that the framework does not use `runBlocking` as an asynchronous adapter.

#### Rationale

Covers D-357, the docs part of D-348, D-351, D-354 and D-356, wave decision Nullability check second reading (r2 W2-004: line 59 names `@NullMarked` and `@Nullable` and no longer mentions `@NonNull`) and the post-v1 rewrite rule of D-380. Measured (2026-10-20): `docs/api/kotlin.md:59` reads "공개 API에는 `@Nullable` / `@NonNull`이 붙어 있어"; the file has no (미확정) marker; `BuildLayoutTest` (OPS-BUILD-003 AC-2 and AC-4) already asserts the module name, the coordinate `com.snoworca.naruserve:NaruServe-kotlin:` and the absence of `rest-kotlin`; the last sentence of the Coroutine section says coroutine support is "별도 모듈로 검토 중입니다". Decision: the sentence about the separate module becomes an explicit post-v1 item with its reason (a non-blocking coroutine adapter is a separate design; v1 handlers are synchronous). Pitfall: the pinned wave 5 lines stay byte-identical (the `T?` row of `req.body(type)`, the `inline fun <reified T : Any> Request.body(): T = ` line and `val user = req.body<User>()`), asserted by `JsonDocsKotlinTest`, so the import line is added above them without editing them.
