# Cookie

| Field | Value |
|---|---|

## 1. Scope Overview

This scope covers cookies of NaruServe (issue #10, wave 5): the `Cookie` value class and the `SameSite` enum in `NaruServe-api`, `res.addCookie` with its `Set-Cookie` serialisation and validation, the lenient request-cookie parser behind `req.cookie(name)` and `req.getCookies()`, and the `maxAge`, `Expires` and signed-cookie decisions recorded in `docs/api/cookie.md`. It holds T33 and T34.

## 2. Scope Boundaries

### In Scope

- `Cookie`, `SameSite` and the cookie methods of `Request` and `Response` in `NaruServe-api`, and the internal request-cookie parser.
- The (미확정) markers owned by #10 in `docs/api/cookie.md` and `docs/api/express-migration.md`.

### Out of Scope

- Signed cookies and automatic value encoding (decided absent in v1; the app does them in middleware).
- Session management and CSRF protection (the app's middleware, `docs/api/defaults.md`).

## 3. Assumptions and Constraints

- Core code is engine-free code in `NaruServe-api`: it references no TinyHttpd, Servlet, Gson, SLF4J, `android.*` or Kotlin stdlib type, compiles to Java 8 bytecode and passes the wave 1 animal-sniffer API 21 checks.
- Public types follow the wave 1 conventions: nullability annotations on public signatures, `@FunctionalInterface` callbacks, Express-style short method names, getter/setter names on value objects, no Kotlin keywords as method names, and no removed or changed public signature of `RestApp`, `Request`, `Response` or the `HttpAdapter` SPI that an earlier wave added: those types gain new methods only, and new public types such as `Cookie`, `SameSite`, `TypeRef`, `ServerOptions`, `ServerSettings` and `ErrorRenderer` are additions (I-014).
- Where the design leaves a choice open, the wave decisions and the residual section of `docs/research/naruserve-v1/waves/wave-5/design.md` apply; otherwise the implementer decides under standing rule C-07, following RFC 9110 and, between equally valid options, Express behaviour.
- Source of the requirements: `docs/research/naruserve-v1/waves/wave-5/design.md`, `docs/research/naruserve-v1/waves/wave-5/excerpt.md`, `docs/research/naruserve-v1/waves/carried-into-wave-5.md` and `object.md`.

#### Requirement

The system shall provide in package `com.snoworca.naruserve` of `NaruServe-api` the public final class `Cookie` with the constructor `Cookie(String name, String value)`, a name fixed at construction, the accessor pairs `getValue`/`setValue`, `getPath`/`setPath`, `getDomain`/`setDomain`, `getMaxAge`/`setMaxAge(int seconds)`, `getSecure`/`setSecure`, `isHttpOnly`/`setHttpOnly` and `getSameSite`/`setSameSite`, and the public enum `SameSite` with `STRICT`, `LAX` and `NONE`; the constructor and every setter reject a name or value outside the RFC 6265 cookie grammar with `IllegalArgumentException`.

#### Rationale

Covers D-200, D-201, D-202, the set-time half of D-205, the `maxAge` part of D-208 and the residual "Building request cookies" (package-private non-validating factory). The accessor names follow the Servlet `Cookie` model so Kotlin uses property syntax (C-03, CLAUDE.md Kotlin rules). Pitfall: the request-cookie parser must not go through the validating constructor, or a client cookie with an odd value turns `req.getCookies()` into a `500`; rejected alternative: a public lenient factory (adds public API; reopen only if a later wave needs to build unvalidated cookies outside the core).

#### Acceptance Criteria

- [ ] AC-1: Reflection finds `com.snoworca.naruserve.Cookie` public and final with exactly one public constructor `(String, String)`, a `getName()` method and no `setName` method; `new Cookie("sid", "abc").getName()` returns `sid` and `getValue()` returns `abc`; `new Cookie(null, "v")` and `new Cookie("n", null)` throw `NullPointerException`. [D-200]
- [ ] AC-2: `Cookie` declares `String getValue()`/`void setValue(String)`, `@Nullable String getPath()`/`void setPath(@Nullable String)`, `@Nullable String getDomain()`/`void setDomain(@Nullable String)`, `int getMaxAge()`/`void setMaxAge(int)`, `boolean getSecure()`/`void setSecure(boolean)`, `boolean isHttpOnly()`/`void setHttpOnly(boolean)` and `@Nullable SameSite getSameSite()`/`void setSameSite(@Nullable SameSite)`; a new cookie has path, domain and SameSite `null`, `getSecure()` and `isHttpOnly()` `false` and `getMaxAge()` `-1`. [D-201; D-208] Decision: setters return `void` like the Servlet `Cookie`, and an unset path, domain or SameSite is `null`.
- [ ] AC-3: `SameSite.values()` is exactly `STRICT, LAX, NONE` in that order. [D-202]
- [ ] AC-4: `setMaxAge(int)` accepts every `int`: a negative value (the default `-1`) means the attribute is not set, so the cookie is a session cookie, `0` means delete and a positive value is a lifetime in seconds. [D-208] Decision: the default `maxAge` is `-1`, and every negative value means "no `Max-Age`" as in the Servlet `Cookie`.
- [ ] AC-5: The constructor rejects with `IllegalArgumentException` a name that is empty or not an RFC 7230 token (for example containing a space, `=`, `;`, `,`, CR or LF), and the constructor and `setValue` reject a value with any character outside RFC 6265 `cookie-octet` (CR, LF, `;`, `,`, space, `\\`, a control character or non-ASCII), except that one pair of surrounding double quotes is accepted; `setPath` and `setDomain` reject CR, LF, `;` and every control character; the exception message names the rejected attribute. [D-205; I-017] Decision: an empty value is allowed, so `new Cookie("sid", "")` is valid.
- [ ] AC-6: `Cookie` has a package-private static factory method that builds a cookie from a name and a value without validation; the request-cookie parser in `com.snoworca.naruserve.internal` reaches it through the internal class `CookieFactoryHook`, whose `private static final java.lang.reflect.Method` field is resolved once with `Class.forName("com.snoworca.naruserve.Cookie")` (which also initialises `Cookie`) and `setAccessible(true)`, so no mutable static field exists and the no-mutable-static check of FR-APP-002 AC-2 still passes; the `NaruServe-api` consumer rules of IR-JSON-001 AC-3 also keep that factory method by name; reflection finds no public or protected member of `Cookie` other than those of AC-1 and AC-2 and the `Object` methods. [residual: Building request cookies; wave decision: Request cookies are parsed leniently; FR-APP-002] Decision: the bridge is a reflective, immutable `Method` handle in `internal.CookieFactoryHook`, with no `java.util.function` type (absent from API 21).
- [ ] AC-7: A Kotlin test compiles and runs `val c = Cookie("sid", "v"); c.maxAge = 60; c.secure = true; c.isHttpOnly = true; c.sameSite = SameSite.LAX; c.path = "/"; val p: String? = c.path; val n: String = c.name`. [D-201; C-03; I-010]

### FR-COOKIE-001 — res.addCookie serialises one Set-Cookie header per call

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-5 |
| Status | implemented |
| Priority | high |
| Tags | wave-5, feasibility:high, cookie |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/10 |
| Related Docs | - |

#### Requirement

The system shall add to `Response` the method `Response addCookie(Cookie cookie)` that validates the cookie's name, value, path and domain again and appends one `Set-Cookie` header per call, serialising `name=value` followed by `Path`, `Domain`, `Max-Age` in seconds, `Secure`, `HttpOnly` and `SameSite=Strict|Lax|None` for each attribute that is set.

#### Rationale

Covers D-203, D-204, the send-time half of D-205, the `Expires` part of D-208 and I-017, with the wave decision "Request cookies are parsed leniently" (a request cookie echoed back is validated when sent). Pitfall: a cookie read from a request was built without validation (IR-COOKIE-001 AC-6), so `addCookie` must validate again instead of trusting the object. Rejected alternative: emitting `Expires` beside `Max-Age` for old clients (needs an HTTP date formatter and clock; reopen only if a supported client ignores `Max-Age`).

#### Acceptance Criteria

- [ ] AC-1: `Response` declares `Response addCookie(Cookie)` returning the receiver; `addCookie(null)` throws `NullPointerException`; two calls add two `Set-Cookie` header lines in call order and never merge them. [D-203; T33] Decision: `addCookie` returns the response for chaining like `status` and `header`.
- [ ] AC-2: A cookie `sid=abc` with path `/`, domain `example.com`, `maxAge` 3600, secure, httpOnly and `SameSite.LAX` produces exactly `Set-Cookie: sid=abc; Path=/; Domain=example.com; Max-Age=3600; Secure; HttpOnly; SameSite=Lax`; a cookie with only name and value produces `sid=abc`; `SameSite.STRICT` and `SameSite.NONE` produce `SameSite=Strict` and `SameSite=None`. [D-203; T33] Decision: attributes appear in the order `Path`, `Domain`, `Max-Age`, `Secure`, `HttpOnly`, `SameSite`.
- [ ] AC-3: A cookie with `maxAge` 0, path `/` and domain `example.com` produces `Set-Cookie: sid=; Path=/; Domain=example.com; Max-Age=0` when its value is empty, which deletes the cookie in browsers. [D-204; T33]
- [ ] AC-4: A cookie whose `maxAge` is negative (the default `-1`, or `-5`) produces no `Max-Age` attribute, and no cookie ever produces an `Expires` attribute. [D-208] Decision: v1 has no `Expires` support; a lifetime is set only through `Max-Age`.
- [ ] AC-5: A cookie built by the request-cookie parser with a value containing a space, `,`, `;` or a control character makes `res.addCookie(cookie)` throw `IllegalArgumentException` and adds no `Set-Cookie` header, and no `Set-Cookie` value the framework writes contains CR or LF. [D-205; I-017; wave decision: Request cookies are parsed leniently]
- [ ] AC-6: `addCookie` follows the commit rule of `res.header`: on a committed or completed response it throws `IllegalStateException` and adds nothing. [D-203; FR-HTTP-015; FR-HTTP-018]
- [ ] AC-7: A Kotlin test compiles and runs `res.addCookie(Cookie("s", "").apply { maxAge = 0; path = "/" })` inside a route lambda. [D-204; C-03; I-010]

### FR-COOKIE-002 — Lenient request-cookie parsing behind req.cookie and req.getCookies

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-5 |
| Status | implemented |
| Priority | high |
| Tags | wave-5, feasibility:high, cookie |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/10 |
| Related Docs | - |

#### Requirement

The system shall add to `Request` the methods `@Nullable Cookie cookie(String name)` and `Cookie[] getCookies()`, backed by a parser of the request `Cookie` headers in `com.snoworca.naruserve.internal` that never throws, skips a pair whose name is not an RFC 6265 token or that has no `=`, keeps every value exactly as the client sent it and builds each `Cookie` with only its name and value set.

#### Rationale

Covers D-206, D-207, the parse-time rule of the wave decision "Request cookies are parsed leniently" and the residual "Building request cookies". Pitfall: percent-decoding or quote stripping would break the round trip `res.addCookie(req.cookie("x"))`; one bad client cookie must never turn `req.getCookies()` into a `500`. Rejected alternative: Express-style automatic `decodeURIComponent` of values (breaks the Servlet model this class follows; reopen only together with a v2 encoding option).

#### Acceptance Criteria

- [ ] AC-1: For `Cookie: a=1; b=2; a=3`, `req.cookie("a").getValue()` is `1`, `req.cookie("zz")` is `null` and `req.getCookies()` holds `a=1`, `b=2`, `a=3` in that order. [D-206; T34] Decision: duplicate names are all returned in header order, `cookie(name)` returns the first, and several `Cookie` header lines are read in header order.
- [ ] AC-2: Without a `Cookie` header `req.getCookies()` returns an array of length 0, and every call returns a new array, so changing it does not change a later result. [D-206; T34]
- [ ] AC-3: Every parsed cookie has `getPath()`, `getDomain()` and `getSameSite()` `null`, `getMaxAge()` `-1`, `getSecure()` `false` and `isHttpOnly()` `false`. [D-207; T34]
- [ ] AC-4: For `Cookie: bad name=1; ok=2; =3; noeq; q="x y"; p=a%2Cb` no exception is thrown, the pairs `bad name=1`, `=3` and `noeq` are skipped, `ok` is `2`, `q` is `"x y"` with its quotes and `p` is `a%2Cb`; whitespace around each pair is trimmed and nothing inside a value is decoded. [wave decision: Request cookies are parsed leniently; residual: Building request cookies]
- [ ] AC-5: A T34 test sets `x=a%2Cb` through `res.addCookie`, sends it back as a request `Cookie` header, reads `req.cookie("x").getValue()` as `a%2Cb` and sends it again with `res.addCookie(req.cookie("x"))`, which writes `Set-Cookie: x=a%2Cb`. [wave decision: Request cookies are parsed leniently; T34]
- [ ] AC-6: `cookie(null)` throws `NullPointerException`; the parser builds cookies through the non-validating factory of IR-COOKIE-001 AC-6, so a value the public constructor would reject is returned without an exception. [D-206; residual: Building request cookies]
- [ ] AC-7: A Kotlin test compiles and runs `val token: String? = req.cookie("session")?.value` and `val all: Array<Cookie> = req.getCookies()` without platform types. [D-206; C-03; I-010]
- [ ] AC-8: The wave 3 surface tests in `HttpApiSurfaceTest` (statements about the wave 3 merge) are re-pointed: the exact `Request` and `Response` method sets of IR-HTTP-001 AC-1 and AC-2 gain `cookie(String)`, `getCookies()` and `addCookie(Cookie)`, these three names leave the later-wave name list of IR-HTTP-001 AC-3, and the `@Nullable` position set of IR-HTTP-001 AC-4 gains exactly the return of `cookie(String)`, every wave 3 position staying as verified. [I-014; D-072; D-392; D-206; D-203]

The system shall record in `docs/api/cookie.md` and `docs/api/express-migration.md` the wave 5 cookie decisions — the `maxAge` default and negative meaning, the absence of `Expires` and signed cookies, the unencoded value model and the lenient request parsing — each with its reason, remove the (미확정) markers these decisions settle, and keep every Java example of these files compiling in the root docs test.

#### Rationale

Covers the documentation half of D-208, the docs statement of the wave decision "Request cookies are parsed leniently", I-008, I-009 and I-013 for issue #10. Signed cookies are absent in v1 because object.md names no secret-management API and an app can sign values in middleware; reopen if a later issue adds a key store.

- [ ] AC-1: `docs/api/cookie.md` states that `getMaxAge()` defaults to `-1`, that every negative value omits `Max-Age` (a session cookie), that `0` deletes and that a positive value is seconds, with its reason (the Servlet `Cookie` model), and the `getMaxAge()` row has no (미확정) marker. [D-208; I-013]
- [ ] AC-2: `docs/api/cookie.md` states that v1 writes no `Expires` attribute (lifetimes use `Max-Age`) and has no signed cookies (an app signs values itself, for example with an HMAC in middleware), each with its reason, and the `Expires` marker line is gone. [D-208; I-013]
- [ ] AC-3: `docs/api/cookie.md` states that NaruServe neither encodes nor decodes cookie values, unlike Express's `res.cookie`, that an app encodes other characters itself (for example with `URLEncoder`), that request cookies with an invalid name or without `=` are skipped instead of failing the request, and that `res.addCookie` throws `IllegalArgumentException` for an invalid name or value. [wave decision: Request cookies are parsed leniently; D-205]
