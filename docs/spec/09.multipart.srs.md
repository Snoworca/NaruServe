## 1. Scope Overview

This scope covers multipart uploads and form bodies of NaruServe (issue #11, wave 6): `app.multipart(config -> ...)` with its file, request, part-count, memory-threshold and part-header limits and the temp directory, the bounded `application/x-www-form-urlencoded` body limit, the engine-free multipart parser shared by every adapter, `req.form`, `req.file`, `req.files` and `req.parts`, memory/disk spooling with server-generated temp names, `UploadFile`, and temporary-file cleanup at request end, after `save`, after `413`, on client disconnect and at shutdown through an after-`onStop` participant. It holds T13, T14, T15, T16, T17 and T18.

## 2. Scope Boundaries

### In Scope

- Multipart and form types and methods of wave 6 in `NaruServe-api` under `com.snoworca.naruserve` and their internal implementation in `com.snoworca.naruserve.internal`.
- The TinyHttpd adapter's use of the core parser (TinyHttpd's `MultipartReader` stays unused).
- The (미확정) markers owned by #11 in `docs/api/multipart.md`, `docs/api/request.md` and `docs/api/defaults.md`.

### Out of Scope

- Recursive parsing of nested `multipart/*` parts (D-237 exposes them as ordinary parts).
- Static files, `res.file` and `res.download` (scope STATIC).
- WebSocket, SSE and the Android sample app (waves 7 and 8).

## 3. Assumptions and Constraints

- Core code is engine-free code in `NaruServe-api`: it references no TinyHttpd, Servlet, Gson, SLF4J, `android.*` or Kotlin stdlib type, uses `java.io.File` and streams and never `java.nio.file`, compiles to Java 8 bytecode and passes the wave 1 animal-sniffer API 21 checks.
- Public types follow the wave 1 conventions: nullability annotations on public signatures, `@FunctionalInterface` callbacks, Express-style short method names, getter/setter names on value objects, no Kotlin keywords as method names, and no removed or changed public signature of `RestApp`, `Request`, `Response` or the `HttpAdapter` SPI that an earlier wave added: those types gain new methods only (I-014, D-106).
- Where the design leaves a choice open, the wave decisions and the residual section of `docs/research/naruserve-v1/waves/wave-6/design.md` apply; otherwise the implementer decides under standing rule C-07, following RFC 9110 and, between equally valid options, Express behaviour.
- Source of the requirements: `docs/research/naruserve-v1/waves/wave-6/design.md`, `docs/research/naruserve-v1/waves/wave-6/excerpt.md` and `object.md`.
- TinyHttpd at `/Users/beom/work/git/TinyHttpd` stays read-only; gaps become deferred issues under D-020.

#### Requirement

The system shall provide `RestApp multipart(Configurer<MultipartOptions> configurer)` with the settings `maxFileSize`, `maxRequestSize`, `maxParts`, `memoryThreshold` and `tempDirectory`, defaulting to 32 MiB per file, 64 MiB per request, 20 parts, a 64 KiB memory threshold and the JVM temporary directory, and `RestApp formLimit(long bytes)` defaulting to 1 MiB, where every size and count setting rejects values outside its bounded range and no value means unlimited.

#### Rationale

Covers D-231, D-232, D-238 (API part), D-239 (default tempDirectory, unlimited limits not allowed) and the fixed part-header limits of D-235 (wave decision: Oversized part headers). The config entry follows the wave 4 `Configurer` pattern of IR-APP-007 and the `jsonLimit` pattern of IR-JSON-002. Pitfall: allowing an unlimited value would make OPS-ENGINE-001 AC-2 ("no setting accepts an unlimited value") false and contradict I-012; rejected. Rejected alternative: configurable part-header limits; reopen if a real client needs headers above 8192 bytes per line. C-07 decisions are stated in the ACs.

#### Acceptance Criteria

- [x] AC-1: `RestApp` declares `multipart(Configurer<MultipartOptions> configurer)` returning the same `RestApp`, and the public interface `com.snoworca.naruserve.MultipartOptions` declares the fluent setters `maxFileSize(long bytes)`, `maxRequestSize(long bytes)`, `maxParts(int count)`, `memoryThreshold(int bytes)` and `tempDirectory(File dir)`, each returning `MultipartOptions`; a configurer that sets all five values is applied, which a test reads back through the internal settings. Decision: the configurer is the `Configurer` functional interface of IR-APP-007. [D-231] Decision: the configurer runs on a copy of the settings that is swapped in only after it returned, so a configurer that throws propagates its exception and leaves every earlier setting unchanged. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-1 SDS-AC-1]
- [x] AC-2: An app that never calls `multipart` uses `maxFileSize` 33554432, `maxRequestSize` 67108864, `maxParts` 20, `memoryThreshold` 65536 and `tempDirectory` equal to `new File(System.getProperty("java.io.tmpdir"))`. Decision: the default temp directory is `java.io.tmpdir`, which on Android is the app's cache directory. [D-232; D-239] Decision: `java.io.tmpdir` is read once when the app is constructed, not at each parse. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-1 SDS-AC-4]
- [x] AC-3: `maxFileSize` and `maxRequestSize` accept 1 to 4294967296, `maxParts` accepts 1 to 10000 and `memoryThreshold` accepts 1 to 16777216, all inclusive; `0`, a negative value or a value above the upper bound throws `IllegalArgumentException` whose message names the setting, and `tempDirectory(null)` throws `NullPointerException`. Decision: unlimited multipart limits are not allowed, so no value means unlimited. [D-239] Decision: the message has the form `<setting> must be in <lo>..<hi>: <value>` and is thrown by that setter. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-1 SDS-AC-2]
- [x] AC-4: `RestApp` declares `formLimit(long bytes)` returning the same `RestApp`, with default 1048576 and inclusive range 1 to 1073741824; a value outside the range throws `IllegalArgumentException` naming the setting. Decision: the urlencoded limit API is `formLimit`, mirroring `jsonLimit` and Express `express.urlencoded({ limit })`. [D-238]
- [x] AC-5: The part header limits are fixed at 8192 bytes per part header line and 16384 bytes of total header size per part, and reflection finds no setter for them on `MultipartOptions` or `RestApp`. Decision: the two part header limits are not configurable. [D-235; wave decision: Oversized part headers]
- [x] AC-6: `multipart(...)` and `formLimit(...)` called after `listen()` throw `IllegalStateException` from the `NEW`-state guard of FR-APP-002, and leave the settings unchanged. [D-231; D-238] Decision: the `NEW`-state guard throws before the configurer is invoked. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-1 SDS-AC-3]
- [x] AC-7: A Kotlin test compiles and runs `app.multipart { o -> o.maxFileSize(1024).maxParts(3) }` and `app.formLimit(2048)` as SAM lambdas without a DSL, and the returned `MultipartOptions` and `RestApp` are non-platform types (`@NonNull`). [D-231; D-238; C-03; T11]

#### Requirement

The system shall add to `Request` the accessors `form(name)`, `file(name)`, `files(name)` and `parts()`, and provide the public `UploadFile` interface extending `AutoCloseable` with `name`, `filename`, `contentType`, `size`, `inputStream`, `save(File)`, `transferTo(OutputStream)` and `bytes`, using only `java.io` types, while every `Request` signature of earlier waves stays unchanged.

#### Rationale

Covers D-240, D-241, D-248, D-253 and the D-239 decisions on the element type of `parts()` and the in-memory limit of `UploadFile.bytes()`. Builds on IR-HTTP-001 (Request surface) and FR-HTTP-019 (exclusive body kinds; `Kind.FORM` covers form and multipart). Re-point convention: the wave 3 to 5 surface ACs (IR-HTTP-001, IR-JSON-002 AC-8, FR-HTTP-019 AC-5) are statements about their own merges, so `HttpApiSurfaceTest` and `BodyStateTest` are re-pointed from AC-6 here instead of superseding them. Rejected alternative: a separate `FormField` type for text parts in `parts()`; reopen if Kotlin users need a sealed hierarchy.

#### Acceptance Criteria

- [x] AC-1: `Request` declares `@Nullable String form(String name)`, `@Nullable UploadFile file(String name)`, `List<UploadFile> files(String name)` and `List<UploadFile> parts()`, and reflection finds each with exactly that signature. [D-240; D-241]
- [x] AC-2: The public interface `com.snoworca.naruserve.UploadFile` extends `AutoCloseable` and declares `String name()`, `@Nullable String filename()`, `@Nullable String contentType()`, `long size()`, `InputStream inputStream()`, `void save(File destination)`, `void transferTo(OutputStream target)`, `byte[] bytes()` and `void close()`, the content methods declaring `throws IOException` and `close()` declaring no checked exception. Decision: `filename()` and `contentType()` return `null` when the part header has no `filename` parameter or no `Content-Type`. [D-248]
- [x] AC-3: Decision: `parts()` returns every part of a multipart body in body order, text fields included (their `filename()` is `null`), as an unmodifiable `List<UploadFile>`, and returns an empty list for a urlencoded or non-form body. [D-239] Decision: repeated `parts()` calls return the same unmodifiable list instance, while `files(name)` returns a new unmodifiable list on each call. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-3 SDS-AC-4]
- [x] AC-4: Decision: the in-memory limit of `UploadFile.bytes()` is fixed at 8388608 bytes (8 MiB); a part above it makes `bytes()` throw `IllegalStateException` whose message names the part size and the limit. [D-239; D-251]
- [x] AC-5: No public or protected signature of `UploadFile`, `MultipartOptions` or the new `Request` methods names a `java.nio.file` type, which a reflection test checks, and the API 21 animal-sniffer check of CON-BUILD-012 passes on `NaruServe-api`. [D-253]
- [x] AC-6: `HttpApiSurfaceTest`, re-pointed to this requirement, checks the wave 6 `Request` set: the wave 5 methods plus `form`, `file`, `files` and `parts`, with every earlier signature unchanged; `LATER_WAVE_NAMES` no longer lists `form`, `file`, `files` or `parts`; and the listed `@Nullable` positions gain exactly the returns of `form(String)` and `file(String)` and of `UploadFile#filename()` and `UploadFile#contentType()`. `BodyStateTest#sdsAc11_FR_HTTP_019_AC5_requestHasNoPublicBodyReadingMethod`, re-pointed to this requirement, accepts exactly `form`, `file`, `files` and `parts` as additional readers, which read through the `FORM` body kind, and still finds no `InputStream`, `byte[]`, raw or text reader on `Request`. [D-240; D-241; D-242; I-014]
- [x] AC-7: A Kotlin test compiles and runs a handler that reads `val name: String = req.form("name") ?: ""`, `val f: UploadFile? = req.file("avatar")`, `f?.filename()` and `for (p in req.parts())`, and closes an upload with `f?.use { it.save(dest) }`, with no platform type left on these positions. [D-240; D-241; D-248; C-03; T11]

### FR-MULTIPART-001 — Engine-free multipart parser shared by every adapter: boundary 400, nested parts, part-header limits 413

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-6 |

| Priority | high |

#### Requirement

The system shall parse `multipart/form-data` bodies with one engine-free parser in `NaruServe-api` that serves every adapter, including the TinyHttpd adapter, answer a missing or malformed boundary with `400`, expose a nested `multipart/*` part as an ordinary part without recursive parsing, and answer a part header line above 8192 bytes or a part header section above 16384 bytes with `413`.

#### Rationale

Covers D-235, D-236, D-237, D-247 and the wave decision "Oversized part headers" (D-235, D-233). Builds on CON-HTTP-001 and CON-BUILD-013 (engine-free core; no TinyHttpd `MultipartReader` in api), FR-HTTP-020 (limit stream) and FR-ENGINE-003 AC-7 (the adapter never sets `maxRequestBodyBytes`, TinyHttpd's default `-1` means no cap). Pitfall: using TinyHttpd's `MultipartReader` would give two parsers whose limits differ between adapters (T13-T17 would test only one); rejected. Risk answered from code_context.json: a 64 MiB upload over TinyHttpd needs no adapter change.

#### Acceptance Criteria

- [x] AC-1: The multipart parser is a class of `com.snoworca.naruserve.internal` that references no adapter, TinyHttpd, Servlet or `java.nio.file` type, no class of `NaruServe-tinyhttpd` references TinyHttpd's `MultipartReader` (class-reference test), and the T13 to T16 tests and the T17 cases other than the mid-upload disconnect run both over a TinyHttpd socket and over the in-memory test adapter with the same results; the T17 mid-upload disconnect case of FR-MULTIPART-006 AC-1 runs over a TinyHttpd socket only. [D-247]
- [x] AC-2: A `multipart/form-data` request without a `boundary` parameter, or whose boundary is empty, longer than 70 characters or contains a character outside the RFC 2046 `bchars` set, or whose body lacks the first delimiter or the close delimiter, is answered `400` with the standard error body of FR-APP-006 through `onError` when an accessor reads it, and the handler's accessor call throws `HttpException(400)`. Decision: a body truncated before the close delimiter is malformed and gets `400`. [D-236] Decision: the `boundary` parameter name is matched case-insensitively, a quoted-string value is unquoted, and the value must consist of RFC 2046 `bchars` with no trailing space. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-2 SDS-AC-1] Decision: a part without a `Content-Disposition: form-data` carrying a `name` parameter is also malformed and answered `400`, and every temporary file of that parse is deleted before the `HttpException(400)` is thrown. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-2 SDS-AC-2] Decision: bytes before the first delimiter and after the close delimiter are ignored as preamble and epilogue. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-2 SDS-AC-3]
- [x] AC-3: A part whose `Content-Type` is `multipart/mixed` inside a `multipart/form-data` body appears in `parts()` as one entry whose `contentType()` is `multipart/mixed` and whose content is the raw nested body bytes, and the parser does not split it into further parts. [D-237]
- [x] AC-4: A part header line of 8192 bytes is accepted, a part header line of 8193 bytes is answered `413`, and a part whose header lines total more than 16384 bytes is answered `413`, both with the standard error body, like the other multipart limits. [D-235; D-233; wave decision: Oversized part headers] Decision: a header line is counted in bytes without its CRLF for the 8192 line limit, and the 16384 total is the sum of those line lengths. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-2 SDS-AC-4]
- [x] AC-5: Over TinyHttpd with default settings, a multipart body of 67108864 bytes in total holding a file part of 33554432 bytes is parsed and both reach the handler, while a body one byte above 67108864 is answered `413` by the core, because TinyHttpd's default body limit stays `-1` (no cap) and the adapter never sets `maxRequestBodyBytes` (FR-ENGINE-003 AC-7). [D-232; D-247; wave-5: FR-ENGINE-003]

### FR-MULTIPART-002 — Multipart and urlencoded size limits on accumulated received bytes answered 413

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-6 |
| Status | verified |
| Priority | high |
| Tags | wave-6, feasibility:high, multipart, limits, security |
| Risk | high |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/11 |
| Related Docs | - |

#### Requirement

The system shall answer `413` when a multipart file part exceeds `maxFileSize`, a multipart body exceeds `maxRequestSize`, a multipart body holds more than `maxParts` parts, or an `application/x-www-form-urlencoded` body exceeds `formLimit`, counting accumulated received bytes so that chunked bodies and bodies without `Content-Length` are bounded the same way.

#### Rationale

Covers D-233, D-234 and D-238 (T15). Builds on FR-HTTP-020 (limit-enforcing stream and `BodyTooLargeException`), FR-APP-005 and FR-APP-006 (one error path, standard body) and IR-JSON-002 (bounded-limit pattern). Pitfall: trusting `Content-Length` alone lets a chunked body bypass the limit; the count is taken on bytes read.

#### Acceptance Criteria

- [x] AC-1: With `maxFileSize(1024)`, a file part of 1024 bytes is accepted and one of 1025 bytes is answered `413`; with `maxRequestSize(4096)`, a body of more than 4096 bytes is answered `413`; and with the default `maxParts` 20, a body of 20 parts is accepted and one of 21 parts is answered `413`; each `413` carries the standard error body of FR-APP-006 and passes through `onError`. [D-233; T15] Decision: under `maxParts` 20 the `413` is thrown when the 21st part delimiter is reached, before that part's headers are read. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-2 SDS-AC-5] Decision: a file part fails with `413` on the first byte above `maxFileSize`, and text parts never count against `maxFileSize`. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-2 SDS-AC-6]
- [x] AC-2: A chunked multipart body and a multipart body without `Content-Length` that exceed `maxRequestSize` are answered `413` once the accumulated received bytes pass the limit, the parser reads no more than the limit plus one internal read buffer of 8192 bytes of the body, and a body whose `Content-Length` already exceeds `maxRequestSize` is answered `413` before any part reaches the handler. Decision: the parser's internal read buffer is 8192 bytes. [D-234; T15] Decision: the body stream is wrapped in a limit counter bound to both `maxRequestSize` and `Content-Length`, so a `Content-Length` above the limit fails on the first read and a chunked body fails after the limit plus one read buffer. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-2 SDS-AC-7] With unknown Content-Length, bytes in the epilogue after the closing delimiter count toward maxRequestSize as well; consume the remaining request body through the bounded counter before accepting the parse and clean temporary parts on overflow.
- [x] AC-3: With the default `formLimit`, an urlencoded body of 1048576 bytes is parsed and one of 1048577 bytes is answered `413`, also when it is sent chunked without `Content-Length`. [D-238; D-234]

### FR-MULTIPART-003 — form, file, files and parts behaviour over urlencoded and multipart bodies with one shared parse

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-6 |
| Status | verified |
| Priority | high |
| Tags | wave-6, feasibility:high, multipart, request |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/11 |
| Related Docs | - |

#### Requirement

The system shall make `req.form(name)` return the first text field of that name from an urlencoded or multipart body or `null`, `req.file(name)` the first file part of that name or `null`, `req.files(name)` every file part of that name in body order or an empty list, and `req.parts()` every part, all four reading one shared parse of the body under the `FORM` body kind.

#### Rationale

Covers D-240, D-241 and D-242 (T13). Builds on FR-HTTP-019 (exclusive body kinds, cached shared form/multipart parse), FR-HTTP-025 (form-urlencoded decoding rules) and FR-JSON-001 (urlencoded and multipart are not JSON). Pitfall: reading the body for `form()` on a JSON request would consume it and break a later `req.body(...)`; the accessor returns `null` without reading. Rejected alternative: throwing `415` from `form()` on a non-form body; reopen if Express parity requires `req.body` semantics.

#### Acceptance Criteria

- [x] AC-1: For the urlencoded body `name=Kim+Lee&name=x&city=%EC%84%9C%EC%9A%B8`, `req.form("name")` returns `Kim Lee`, `req.form("city")` returns `서울` and `req.form("zip")` returns `null`, decoded by the form rules of FR-HTTP-025 (`+` as space, percent-decoded UTF-8); an urlencoded body with malformed percent-encoding (`a=%G1`, `a=%4`) or invalid UTF-8 (`a=%FF`) makes the accessor throw `HttpException(400)`, answered `400` with the standard error body of FR-APP-006, like the malformed query of FR-HTTP-025; for a multipart body, `form(name)` returns the first part of that name that has no `filename` parameter, and never a file part. [D-240] Decision: an urlencoded pair without `=` (such as `a`) yields the value `""` and an empty pair (as in `a&&b=1`) is skipped; a multipart text part is decoded as strict UTF-8 and malformed bytes make the accessor throw `HttpException(400)`. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-3 SDS-AC-2] Decision: for an urlencoded body `parts()` is empty and `file(name)` returns `null`, while `form(name)` returns the first decoded value. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-3 SDS-AC-3]
- [x] AC-2: Decision: on a request whose `Content-Type` is neither `application/x-www-form-urlencoded` nor `multipart/form-data` and whose body is still unread, `req.form(name)` returns `null`, `file(name)` returns `null`, `files(name)` and `parts()` return empty lists, none of them reads the body, and a later `req.body(...)` on a JSON body still reads it; once `req.body(...)` has read the body, a call of `form`, `file`, `files` or `parts` throws `BodyAlreadyConsumedException` (FR-HTTP-019 AC-3), as `docs/api/request.md` states. [D-240; D-241] Decision: the media type is the `Content-Type` text before `;`, trimmed and compared case-insensitively; for any other media type the accessors leave the body state untouched while it is unread and throw `BodyAlreadyConsumedException` once it is not. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-3 SDS-AC-1]
- [x] AC-3: Decision: a file part is a part whose `Content-Disposition` carries a `filename` parameter. `req.file("doc")` returns the first file part named `doc` or `null`, and `req.files("doc")` returns every file part named `doc` in body order, or an empty list when there is none. [D-241; T13]
- [x] AC-4: A multipart request holding the text fields `title` and `tag`, two files named `photos` and one file named `doc` exposes `form("title")`, `form("tag")`, `file("doc")`, `files("photos")` with both files in body order, and `parts()` with all five parts in body order, all inside one handler. [D-242; T13]
- [x] AC-5: Repeated calls of `form`, `file`, `files` and `parts` in one request parse the body once and return the same `UploadFile` instances, and after any of them a call of `req.body(...)` throws `BodyAlreadyConsumedException` because the body was read as the `FORM` kind (exclusive kinds of FR-HTTP-019 AC-3); the body-state check of `req.body` runs before the JSON media-type check of FR-JSON-001, so this case never yields `UnsupportedMediaTypeException`. Decision: the four accessors share one cached parse result. [D-242; D-240; D-241] Decision: when the shared parse failed with `400` or `413`, a later accessor call throws `BodyAlreadyConsumedException`. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-3 SDS-AC-5]

### FR-MULTIPART-004 — Memory and disk spooling with bounded heap, server-generated temp names and unchanged client filenames

| Field | Value |

#### Requirement

The system shall keep file part bytes up to `memoryThreshold` in memory and spool larger parts to a temporary file in the temp directory, keep heap growth bounded for uploads many times larger than the threshold, generate every temporary file name on the server without client input, and return the client's filename unchanged from `UploadFile.filename()` without ever using it to build a path.

#### Rationale

Covers D-243, D-244, D-245 and D-246 (T14, T16). Pitfall: deriving a temp name from the client filename allows path traversal (`../`) and name collisions; names come from `File.createTempFile`. Rejected alternative: sanitising `filename()`; Express multer also returns `originalname` unchanged, and sanitising would hide what the client sent.

#### Acceptance Criteria

- [x] AC-1: With `memoryThreshold(1024)`, a file part of 1024 bytes creates no file in the temp directory (the test lists the directory before and after), and a file part of 1025 bytes creates exactly one temporary file in the configured `tempDirectory` while its request runs. [D-243; T14] Decision: when byte `memoryThreshold`+1 of a file part arrives the temp file is created, the buffered bytes are flushed to it and the memory buffer is dropped. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-4 SDS-AC-1]
- [x] AC-2: Uploading a 32 MiB file with the default 64 KiB `memoryThreshold` keeps the used heap, measured after `System.gc()` before the upload and while the handler holds the `UploadFile`, from growing by 8 MiB or more. Decision: the asserted heap bound is 8 MiB for a 32 MiB upload. [D-244; T14]
- [x] AC-3: Every temporary file is created through `File.createTempFile` in `tempDirectory` with the prefix `naru-upload-` and the suffix `.tmp`; for a part whose filename is `../../evil.sh`, `a/b\c.txt` (one backslash) or a 300-character name, the temporary file name contains no part of the filename or the field name, and no file appears outside `tempDirectory`. Decision: the temp-name prefix is `naru-upload-` and the suffix `.tmp`. [D-245; T16]
- [x] AC-4: `UploadFile.filename()` returns the client's `filename` parameter unchanged, including `../../evil.sh` and a non-ASCII name, and `save(File)` writes only to the destination the app passes, so no framework code builds a path from the filename (a test checks that no file named after the client value appears anywhere under the temp directory or the working directory). [D-246; T16]
- [x] AC-5: Decision: a multipart text part (one without a `filename` parameter) is never spooled and is held in memory, and the total of the content bytes of all text parts of one multipart request is capped by the `formLimit` of IR-MULTIPART-001 (default 1 MiB, like multer's `fieldSize` but per request), so the heap held by text parts never exceeds the same bound as an urlencoded body; with the default `formLimit`, one text part of 1048576 bytes reaches `form(name)` and `parts()`, one text part of 1048577 bytes is answered `413`, and two text parts of 600000 bytes each are answered `413`, each `413` with the standard error body; text parts also count against `maxRequestSize` and `maxParts` but not against `maxFileSize`. [D-243; D-244; D-238]

| Field | Value |

#### Requirement

The system shall make `UploadFile.save(File)` write the full content to the destination and delete the temporary file after success, `transferTo(OutputStream)` copy the full content without closing the target, `bytes()` throw an exception above the 8 MiB in-memory limit, and every content method throw an exception once the request of the upload has ended.

#### Rationale

Covers D-248 (behaviour), D-249, D-250, D-251 and D-252 (T18). The 8 MiB limit of `bytes()` is the D-239 decision recorded in IR-MULTIPART-002 AC-4. Pitfall: closing the caller's `OutputStream` in `transferTo` would close a response stream the caller still writes to (T18).

#### Acceptance Criteria

- [x] AC-1: `save(dest)` writes content byte-equal to the uploaded part for an in-memory part and for a spooled part, replacing an existing `dest`, and after it returns the spooled part's temporary file no longer exists. Decision: `save` replaces an existing destination file. [D-249; T18] Decision: `save` copies through a truncating `FileOutputStream` and then deletes the temp file, never `File.renameTo`, so the result is the same across file systems. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-4 SDS-AC-3]
- [x] AC-2: `transferTo(out)` writes the full content of an in-memory part and of a spooled part into `out`, and a test stream that records `close()` shows that `transferTo` never closed it. [D-250; T18]
- [x] AC-3: `bytes()` returns the full content for a part of 8388608 bytes and throws `IllegalStateException` naming the part size and the 8388608-byte limit for a part of 8388609 bytes; `inputStream()` reads the full content and `size()` equals the number of content bytes. [D-251; D-248; D-239]
- [x] AC-4: After the request of an upload has ended, `inputStream()`, `save(File)`, `transferTo(OutputStream)` and `bytes()` throw `IllegalStateException`, while `name()`, `filename()`, `contentType()` and `size()` keep returning their values. Decision: only the content methods throw after the request ended. [D-252] Decision: when the request ends every `InputStream` handed out by `inputStream()` is closed, so a later read on it throws `IOException`. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-4 SDS-AC-4]
- [x] AC-5: Decision: after a successful `save(dest)`, a later `inputStream()`, `bytes()`, `transferTo(OutputStream)` or second `save(File)` on the same part throws `IllegalStateException` for in-memory and spooled parts alike, because the content now lives only at `dest`, while `name()`, `filename()`, `contentType()` and `size()` keep returning their values; a test calls `bytes()` after `save` on a spooled part and on an in-memory part. [D-249; D-252] Decision: `close()` called before the request ended releases the content like `save`, after which the content methods throw `IllegalStateException` and the metadata methods keep their values. [SDS 2026-10-19.naruserve.naruserve-v1-wave-6-4 SDS-AC-5]

#### Requirement

The system shall record the wave 6 multipart and form decisions (default `tempDirectory`, no unlimited limits, `parts()` element type, the `bytes()` in-memory limit, the fixed part-header limits and the `formLimit` API with its 1 MiB default) in `docs/api/multipart.md`, `docs/api/request.md`, `docs/api/defaults.md` and `docs/api/express-migration.md` without (미확정) markers, with compiling Java examples and Kotlin compile-and-run coverage.
