## 1. Scope Overview

The optional module `NaruServe-proxy` (Maven artifact `naruserve-proxy`, package `com.snoworca.naruserve.proxy`) provides `Proxy.to(url)`, an immutable `Middleware` that forwards a request to one backend origin and relays the response, so `app.use("/api/orders", Proxy.to("http://127.0.0.1:8081"))` gives a gateway mount with safe defaults. The module talks to the backend through its own minimal HTTP/1.1 client over `java.net.Socket`, keeps Java 8 bytecode and the Android API 21 signature, and uses only the public `NaruServe-api` surface, including the raw-access API added in target 0.12.0 (body stream, header enumeration, `res.append`, `req.isFromTrustedProxy()`, `res.onAbort`, `res.relay`, `HttpHeaderValues.isFieldValue`).

Source: `docs/prd/2026-11-14.naruserve-proxy.prd.md` (request B) and the run design `docs/research/naruserve-proxy/design/00.design.md`.

## 2. Scope Boundaries

### In Scope

- `Proxy.to(url)` and its option methods, `ProxyException` and its `Kind` enum.
- Request forwarding rules: method, path and query, headers, hop-by-hop removal, `Host`, `X-Forwarded-*`, body framing, path and request-target checks, target pinning.
- Response relaying rules: status, headers, `Location` rewrite, body framing through `res.relay`.
- Errors, timeouts, retries, the concurrency limit and the JVM-wide watchdog scheduler.
- The backend HTTP/1.1 client: request writing, response parsing, TLS with SNI and hostname verification.
- The proxy documentation page and its warnings.

### Out of Scope

- WebSocket proxying; WebSocket upgrade requests pass to `next()`.
- Load balancing, health checks and circuit breakers.
- Response caching.
- Response body transformation and path-rewrite functions beyond the `stripPrefix` option.
- Rewriting the `Path` attribute of `Set-Cookie` under `stripPrefix`.
- Immediate per-chunk flushing of streaming responses such as SSE.
- Backend connection pooling in the first version.
- Publishing an asynchronous middleware contract.
- A `java.net.http.HttpClient` based module and a pluggable backend-client SPI.

## 3. Assumptions and Constraints

- Java 8 bytecode and the Android API 21 signature (animal-sniffer) apply to the module, as to every Android-targeted module.
- The module depends on `NaruServe-api` only and references neither `com.snoworca.naruserve.internal` nor `com.snoworca.naruserve.spi`.
- `Proxy` runs as a synchronous `Middleware` and holds one worker thread for the whole exchange.

#### Requirement

The system shall provide `com.snoworca.naruserve.proxy.ProxyException`, a public final subclass of `HttpException` with a nested public enum `ProxyException.Kind` of the seven proxy failure kinds, an accessor `kind()`, a status derived from the kind, a `null` message, the cause kept in `getCause()`, and exactly one public constructor `ProxyException(ProxyException.Kind kind, @Nullable Throwable cause)`.

#### Rationale

AC-1 ← PRD-97, PRD-98; fills: PRD-98 / hole / for AC-1, the request names the kinds but not the enum's name or place, so the enum is nested as `ProxyException.Kind` (design D-049); AC-2 ← PRD-98 (design D-049); AC-3 ← PRD-98, PRD-99 (design D-049); AC-4 ← PRD-98; fills: PRD-98 / hole / for AC-4, the constructor shape is public API the request leaves open and apps and tests need one to exercise `onError` (design D-074). `kind()` mirrors the short accessor `HttpException.status()`; Express users compare it with `err.code` of `http-proxy-middleware`'s error event. The message stays `null` because the default error handler echoes non-500 `HttpException` messages into the response body, which would leak the backend address.

#### Acceptance Criteria

- [x] AC-1: `com.snoworca.naruserve.proxy.ProxyException` is a public final class extending `com.snoworca.naruserve.HttpException`, with a nested public enum `ProxyException.Kind` holding exactly `CONNECT_FAILED`, `CONNECT_TIMEOUT`, `WRITE_TIMEOUT`, `READ_TIMEOUT`, `TOTAL_TIMEOUT`, `INVALID_RESPONSE` and `CONCURRENCY_LIMIT`, and an accessor `kind()` returning the kind given at construction.
- [x] AC-2: `status()` derives from the kind: 502 for `CONNECT_FAILED` and `INVALID_RESPONSE`, 504 for `CONNECT_TIMEOUT`, `WRITE_TIMEOUT`, `READ_TIMEOUT` and `TOTAL_TIMEOUT`, and 503 for `CONCURRENCY_LIMIT`.
- [x] AC-3: For every kind `getMessage()` returns `null`, and `getCause()` returns the cause given to the constructor, `null` when `null` was given.
- [x] AC-4: `ProxyException` has exactly one public constructor, `ProxyException(ProxyException.Kind kind, @Nullable Throwable cause)`, pinned by a reflection test, and an app test can build `new ProxyException(ProxyException.Kind.READ_TIMEOUT, null)` and throw it through `next.error(e)` so that `onError` receives it with `kind()` `READ_TIMEOUT`.

### SEC-PROXY-001 — Proxy path and request-target checks: dangerous raw paths answer 400 before any backend connection, and the target origin is pinned

#### Requirement

The system shall make the proxy inspect the full raw `originalUrl()` path and query of every request before connecting to the backend, whatever `stripPrefix` says, and answer 400 without reaching the backend when a path segment is `.` or `..`, a segment is empty except one trailing `/`, a segment holds `;`, the path holds a percent-encoded unreserved character, `%2f`, `%5c`, `%00` or a raw backslash, a once-decoded path holds one of those encodings again, or the path or query holds a control character or space (0x00–0x20, 0x7F), a non-ASCII byte, `#` or a `%` not followed by two hexadecimal digits, with percent-encodings compared case-insensitively; every other character is forwarded unchanged, and no request path changes the scheme, host or port of the configured target.

#### Rationale

AC-1 ← PRD-76, PRD-77, PRD-78, PRD-80, PRD-202, PRD-239; AC-2 ← PRD-77, PRD-82, PRD-202; AC-3 ← PRD-80, PRD-81, PRD-202; AC-4 ← PRD-83, PRD-202; AC-5 ← PRD-79, PRD-202; AC-6 ← PRD-84, PRD-202, PRD-192; AC-7 ← PRD-86, PRD-201; AC-8 ← PRD-85, PRD-201, PRD-72; AC-9 ← PRD-76; fills: PRD-54 / hole / for AC-9, the request does not say which path is checked under stripPrefix (design D-052). Gateway route matching does not decode or normalise raw paths while many backends do, so `..`, `%70`, `;` and `//` could escape the mount or bypass a blocking middleware in front of the proxy; rejecting them is simpler than normalising and re-matching (decision 11), and the cost of rejecting clients that encode `~` as `%7E` is accepted.

#### Acceptance Criteria

- [x] AC-1: On a mount `app.use("/api/orders", Proxy.to(url))`, the requests `/api/orders/../other/x`, `/api/orders/%2e%2e/other/x`, `/api/orders/%2E%2E/other/x`, `/api/orders/..;/other/x`, `/api/orders/.;x/other/x` and `/api/orders/./x` each get 400 and no backend connection is opened.
- [x] AC-2: The requests `/api/orders/a%2fb`, `/api/orders/a%2Fb`, `/api/orders/a%5cb`, `/api/orders/a%00b` and a path holding one raw backslash byte (0x5C) between `a` and `b` each get 400 and no backend connection is opened.
- [x] AC-3: The requests `/api/orders/%70rivate/x`, `/api/orders/%7Ex`, `/api/orders/%41` and `/api/orders/private;x/y` each get 400 and no backend connection is opened.
- [x] AC-4: The double encodings `/api/orders/%252e%252e/other/x`, `/api/orders/a%252fb` and `/api/orders/%2570rivate` each get 400 and no backend connection is opened.
- [x] AC-5: The empty segments `/api/orders//private/x` and `/api/orders/private//x` each get 400 with no backend connection, while `/api/orders/x/` arrives at the backend as `/api/orders/x/`.
- [x] AC-6: A path or query holding a control character, a space, the byte 0x7F, a non-ASCII byte, `#` or a `%` not followed by two hexadecimal digits (for example `?q=%zz` or a path ending in `%`) gets 400 with no backend connection, while `?x=1&y=%ED%95%9C`, `@`, `:`, `!` and `$` in the path or query arrive at the backend byte for byte.
- [x] AC-7: `/api/orders/@evil.example/x` is forwarded to the configured target host, `/api/orders//evil.example/x` and `/api/orders/%2F%2Fevil.example` get 400, and in no case does the proxy open a connection to any host other than the configured target.
- [x] AC-8: On both the TinyHttpd adapter and the servlet adapter an absolute-form request `GET http://evil.example/api/orders/x` either gets 400, gets 421 from the adapter's default host allowlist before middleware, or is forwarded only to the configured target host, with no connection to `evil.example`, and `GET http://h/api/orders/%2e%2e/x` gets 400 whenever the adapter admits it to middleware.
- [x] AC-9: With `.stripPrefix(true)` every request rejected by AC-1 to AC-7 is still rejected with 400, because the checks run on the raw `originalUrl()` path and query and not on the stripped `url()`.

### FR-PROXY-001 — Proxy.to(url) accepts an http or https origin with an optional base path, strips trailing slashes and rejects every other URL at the call

| --- | --- |
| Type | functional |

| Priority | high |
| Tags | 0.12.0, feasibility:high, request-b, proxy, target-url |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |

#### Requirement

The system shall make `Proxy.to(String url)` accept only an `http` or `https` scheme (case-insensitive), a required ASCII host given as a name, an IPv4 literal or a bracketed IPv6 literal without a zone id, an optional port `1..65535` and an optional base path, remove every trailing `/` from the base path, require the remaining base path to pass the proxy's request-target character and path segment checks, prefix the base path to every forwarded path, throw `NullPointerException` for `null` and throw `IllegalArgumentException` at the call for every other URL, including one with a query, a fragment or user information.

#### Rationale

AC-1 ← PRD-46, PRD-222; AC-2 ← PRD-46; fills: PRD-46 / hole / for AC-2, the request lists rejected parts but not the accepted grammar (design D-048); AC-3 ← PRD-47, PRD-222; AC-4 ← PRD-47; AC-5 ← PRD-46; fills: PRD-46 / hole / for AC-5, AC-6, a base path holding `..` or `%2e` would reopen the traversal the path check closes, and a null URL needs a defined answer (design D-072); AC-6 ← PRD-46 (design D-072). #### Requirement

The system shall check every `Proxy` option value when the option method is called, throwing `IllegalArgumentException` for a value outside the option's range — timeouts above 0, `retries` and `retryDelay` at least 0, `bodyLimit` within `1..1073741824`, `maxConcurrent` at least 1 — and for a header name or value that fails the header check or is a name the proxy manages, throwing `NullPointerException` for a `null` argument, converting time options to socket milliseconds by rounding up to at least 1 ms and clamping to `Integer.MAX_VALUE` while keeping nanosecond precision saturated at `Long.MAX_VALUE` for the watchdog, and accepting `sslSocketFactory(factory)` on an `http` target without using it.

#### Rationale

AC-1 ← PRD-137, PRD-138, PRD-225; AC-2 ← PRD-139, PRD-140, PRD-225; AC-3 ← PRD-141, PRD-142, PRD-225; AC-4 ← PRD-143, PRD-225; fills: PRD-143 / hole / for AC-4, AC-6, header names compare case-insensitively (RFC 9110 §5.1), so a managed name written in another case is the same name; AC-5 ← PRD-143, PRD-225; AC-6 ← PRD-144, PRD-225; AC-7 ← PRD-137, PRD-225; AC-8 ← PRD-48; fills: PRD-48 / hole / for AC-8, sub-millisecond values would round to 0, which sockets read as no timeout (design D-047); AC-9 ← PRD-136; fills: PRD-136 / hole / for AC-9, call-time validation needs a defined answer for http targets (design D-075). #### Requirement

The system shall make the proxy forward the client's request headers to the backend in the order and with the duplicates the adapter reported, removing `Connection`, every header named in `Connection`, `Keep-Alive`, `Proxy-Connection`, `TE`, `Transfer-Encoding`, `Upgrade`, `Proxy-Authenticate`, `Proxy-Authorization`, `Trailer` and `Expect`, joining several `Cookie` lines with `; ` into one line in received order, adding no `Via`, passing `Max-Forwards` unchanged, answering 400 without connecting when a header name or value fails the header check, writing every header in ISO-8859-1, and laying out the backend header block as `Host`, the remaining client headers, the forwarding headers, the `.requestHeader` values, then the framing header and `Connection: close`.

#### Rationale

#### Acceptance Criteria

### FR-PROXY-007 — Proxy request body framing to the backend: the length header is rewritten for the body actually sent, streamed without buffering, with a one-byte pre-read for requests without length headers

| Type | functional |

| Priority | high |
| Tags | 0.12.0, feasibility:high, request-b, proxy, framing, body |

| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |

#### Requirement

The system shall make the proxy stream the request body from `req.bodyStream(...)` to the backend without collecting it in memory and write a framing header for the body it actually sends instead of copying the client's: chunked transfer for a `Transfer-Encoding: chunked` request, the same `Content-Length` for a `Content-Length` request, and, for a request with neither, a one-byte pre-read that sends no body when the stream ends at once (adding `Content-Length: 0` only for `POST`, `PUT` and `PATCH`) and chunked transfer otherwise, closing the backend connection when a `Content-Length` body ends early.

#### Rationale

AC-1 ← PRD-65, PRD-198; AC-2 ← PRD-198; AC-3 ← PRD-65, PRD-198; AC-4 ← PRD-65, PRD-198; AC-5 ← PRD-198; AC-6 ← PRD-199; AC-7 ← PRD-55, PRD-193; AC-8 ← PRD-119; fills: PRD-119 / hole / for AC-8, the request does not place the pre-read relative to the slot and the watchdog, so a client slow to send its first byte holds no slot (design D-056). The rules follow RFC 9112 §6.1 and §6.3; `Content-Length: 0` on bodiless POST, PUT and PATCH serves backends that answer 411 to a request without a length (RFC 9110 §8.6), and the pre-read keeps bodies that arrive without length headers, as over HTTP/2.

#### Acceptance Criteria

- [x] AC-1: A bodyless `GET` arrives at the backend with neither `Content-Length` nor `Transfer-Encoding`.
- [x] AC-2: `POST`, `PUT` and `PATCH` requests sent without length headers and without a body arrive with `Content-Length: 0`, while `DELETE`, `OPTIONS` and an extension method sent the same way arrive with no length header.
- [x] AC-3: A `Transfer-Encoding: chunked` request arrives chunked with no `Content-Length`, and the backend decodes exactly the body bytes the client sent.
- [x] AC-4: A `Content-Length: n` request arrives with the single line `Content-Length: n` and exactly those n body bytes.
- [x] AC-5: A request that carries a body but neither `Content-Length` nor `Transfer-Encoding`, such as a POST the servlet adapter received over HTTP/2, arrives chunked with the whole body.
- [x] AC-6: When a client sends `Content-Length: 10`, then 5 body bytes and then disconnects, the backend's connection is closed before it receives 10 body bytes, so the incomplete request is never complete at the backend.
- [x] AC-7: urlencoded, binary, chunked and large bodies arrive byte for byte, and a proxy JVM started with `-Xmx64m` forwards a 1 GiB body through a mount with `.bodyLimit(1073741824)` without an `OutOfMemoryError`.
- [x] AC-8: The one-byte pre-read runs after `req.bodyStream(...)` returns and before the concurrency slot is taken and the total-timeout watchdog starts, as a unit test that records the order of these steps shows.

#### Requirement

The system shall make the proxy relay the backend's final status code unchanged, including 3xx without following a redirect and 4xx and 5xx, without the backend reason phrase; copy the backend response headers in received order with duplicates, comparing names case-insensitively, by calling `res.header` for the first line of each name and `res.append` for its later lines, except `Set-Cookie` and `Vary`, every line of which is added with `res.append`; copy none of the hop-by-hop headers (`Connection`, every header named in `Connection`, `Keep-Alive`, `Proxy-Connection`, `TE`, `Transfer-Encoding`, `Upgrade`, `Proxy-Authenticate`, `Proxy-Authorization`, `Trailer`) and not `Content-Length`, which reaches the client only as the length argument of `res.relay`; and add no `Content-Type` the backend did not send.

#### Rationale

AC-1 ← PRD-207, PRD-208; AC-2 ← PRD-87, PRD-207; AC-3 ← PRD-207, PRD-153; AC-4 ← PRD-207; AC-5 ← PRD-89; AC-6 ← PRD-87, PRD-207; AC-7 ← PRD-88, PRD-207; AC-8 ← PRD-88, PRD-207; AC-9 ← PRD-207; fills: PRD-152 / hole / for AC-9, the request does not say what becomes of the backend reason phrase, and the public `Response` cannot set one, so the adapter's standard phrase replaces it (design D-059); AC-10 ← PRD-87, PRD-88; fills: PRD-87 / hole / for AC-10, header names compare case-insensitively (RFC 9110 §5.1), so lines that differ only in letter case are one name. | Field | Value |
| --- | --- |
| Type | functional |
| Target | 0.12.0 |

#### Requirement

The system shall, unless `.rewriteLocation(false)` is set (default `true`), rewrite a backend `Location` that is an absolute URL — or a network-path reference `//authority/...` resolved against the target scheme — whose origin equals the target's (scheme and host compared case-insensitively, a default port equal to an omitted one) and whose path equals the target base path or continues it with `/`, by replacing its origin and base path with the client-side prefix — `req.baseUrl()` under `.stripPrefix(true)` and the empty string otherwise — keeping the rest of the reference, using `/` when the resulting path is empty, never placing an origin or the received `Host` into the result, and leaving every other value, including relative references, unchanged.

#### Rationale

AC-1 ← PRD-92, PRD-93, PRD-209; AC-2 ← PRD-92, PRD-209; AC-3 ← PRD-94, PRD-209; AC-4 ← PRD-92, PRD-209; AC-5 ← PRD-92, PRD-209; AC-6 ← PRD-96; AC-7 ← PRD-94, PRD-95; AC-8 ← PRD-93, PRD-209; AC-9 ← PRD-92; fills: PRD-92 / hole / for AC-9, leaving a network-path Location unchanged would leak the backend address, so it is resolved against the target scheme and rewritten under the same rule (design D-061); AC-10 ← PRD-93. The rewrite is on by default because the proxy replaces `Host` with the target host, so a backend redirecting to an absolute URL would expose the internal address; it matches nginx's `proxy_redirect default` and Express users' `autoRewrite` of `http-proxy-middleware`. The result carries no origin because the received `Host` is client-chosen and a shared cache storing the 3xx would serve a forged host to other clients; RFC 9110 §10.2.2 lets `Location` be relative and the client resolves it against the request URI. Comparing origins follows RFC 3986 §6.2.2.1.

#### Acceptance Criteria

- [x] AC-1: On `app.use("/api/orders", Proxy.to("http://127.0.0.1:<port>"))` a backend `Location: http://127.0.0.1:<port>/api/orders/x` reaches the client as `Location: /api/orders/x`, while with `.rewriteLocation(false)` the client receives the original value, and the package-private accessor reports `rewriteLocation` `true` on `Proxy.to(url)`.
- [x] AC-2: A relative `Location` (`/x` and `x/y`), a URL of another host (`http://other.example/x`) and, for the target `http://h:808`, the URL `http://h:8080/x` each reach the client unchanged.
- [x] AC-3: With `.stripPrefix(true)` on a mount at `/api/orders`, a backend `Location: http://<target host:port>/x` reaches the client as `Location: /api/orders/x`.
- [x] AC-4: For the target `http://h/base` on a mount at `/api/orders`, `Location: http://h/base/api/orders/y` becomes `/api/orders/y`, while `http://h/basement/y` and `http://h/other/y` reach the client unchanged.
- [x] AC-5: For the target `http://h`, `Location: http://H:80/x` and `Location: HTTP://h/x` both become `/x`; for the target `https://h`, `Location: https://h:443/x` becomes `/x`; and for the target `http://h`, `Location: https://h/x` reaches the client unchanged.
- [x] AC-6: A rewrite whose resulting path is empty yields `/`: for the target `http://h/base`, `Location: http://h/base` becomes `/`, and for the target `http://h`, `Location: http://h` becomes `/`.
- [x] AC-7: Under `.stripPrefix(true)` the client-side prefix is the request's matched prefix `req.baseUrl()`, not the string given to `use`: a proxy mounted with `router.use("/orders", proxy)` on a router mounted with `app.use("/api", router)` turns `Location: http://<target host:port>/x` into `/api/orders/x`.

- [x] AC-9: A network-path `Location: //<target host:port>/api/orders/x` is resolved against the target scheme and becomes `/api/orders/x`, while `Location: //other.example/x` reaches the client unchanged.
- [x] AC-10: The part after the base path is kept unchanged: `Location: http://<target host:port>/api/orders/x?a=1#f` becomes `/api/orders/x?a=1#f`.
- [x] AC-11: A rewritten value that a client would read as a network-path reference (it would start with two `/` or `\` characters, tab, CR and LF ignored) gets a leading `/.`: for the target `http://h`, `Location: http://h//evil.example/x` becomes `/.//evil.example/x`; user information is dropped and an empty port is read as omitted before the origin comparison, and a value whose host or port the `Proxy.to` grammar refuses is left unchanged.

#### Requirement

The system shall make the proxy hand the backend response body to `res.relay(stream, length)` as a stream, passing the valid `Content-Length` value for a response framed by `Content-Length`, `-1` for a `Transfer-Encoding: chunked` response whose chunks it decodes, and `-1` for a response with neither header, which it reads until the backend closes the connection; and treat the response to a HEAD request, a 204 and a 304 as bodyless before any other framing rule, reading no body bytes in these three cases whatever their framing headers say, passing for HEAD and 304 the `Content-Length` value when, read with the same list parsing as SEC-PROXY-003 (every element digits that fit in a `long`, elements compared numerically), it yields one value, and `-1` otherwise, and passing `-1` for a 204.

#### Rationale

AC-1 ← PRD-89, PRD-150, PRD-157, PRD-207; AC-2 ← PRD-150, PRD-156; AC-3 ← PRD-150, PRD-158; AC-4 ← PRD-155, PRD-208; AC-5 ← PRD-155; fills: PRD-155 / hole / for AC-5, the request does not say which length a bodyless response passes to `relay` (design D-058); AC-6 ← PRD-155; fills: PRD-155 / hole / for AC-6, which length relay keeps when the bodyless response carries an unusable Content-Length. The order follows RFC 9112 §6.3 as the request's response table does (§3.9: the row "HEAD 요청에 대한 응답, 204, 304 — 본문을 읽지 않음" comes before the rows that make `Transfer-Encoding` with `Content-Length` and a malformed `Content-Length` an `INVALID_RESPONSE`): a HEAD response, 204 and 304 never carry a body whatever their length headers say, then `Transfer-Encoding`, then `Content-Length`, then read-until-close; PRD-155 records that these responses end without a body regardless of their length headers, so their framing headers can never make them malformed. Passing the length through `relay` keeps the backend's `Content-Length` for the client, which Express users get from `http-proxy-middleware` piping the backend response.

#### Implementation Notes

- Call `res.relay` only after the header copy, the `Location` rewrite and the fixed response headers are applied (FR-PROXY-011); `relay` copies the body after the middleware returns and closes the stream whatever the outcome (FR-HTTP-037), which is where the proxy releases the backend connection. ### SEC-PROXY-004 — Proxy backend response parser: ISO-8859-1 status line and headers, RFC 9112 §6.3 framing stricter than the RFC, interim 1xx skipped, and every malformed response an INVALID_RESPONSE

| Field | Value |
| --- | --- |
| Type | security |
| Target | 0.12.0 |
| Status | verified |
| Priority | high |
| Tags | 0.12.0, feasibility:high, request-b, proxy, security, response-parser, framing, smuggling |
| Risk | high |
| Stability | evolving |
| Verification Method | test |

#### Requirement

The system shall make the proxy's HTTP/1.1 client parse the backend status line and headers as ISO-8859-1, skip every 1xx interim response other than 101 and read the next one, determine the body length in the order of RFC 9112 §6.3 — a response to a HEAD request and a 204 or 304 response being bodyless before any framing header is considered (FR-PROXY-014) — while, for every other final response, rejecting every transfer coding other than a single `chunked`, reading `Content-Length` and `Transfer-Encoding` with the same list parsing as requests, and reading and discarding chunked trailers; and shall treat as `INVALID_RESPONSE` a malformed status line or a status outside `100..599`, a status line and headers together larger than 64 KiB, an obs-fold line, a header name or value failing the header check, a 101 response, a connection closed or reset before the header block is complete, a malformed chunk (including a chunk-size line longer than 4 KiB with its extensions and a trailer section larger than 64 KiB), and, on a final response that can carry a body, both `Content-Length` and `Transfer-Encoding`, `Content-Length` elements that are not digits or differ, or any `Transfer-Encoding` other than a single `chunked`.

#### Rationale

AC-1 ← PRD-152, PRD-221; fills: PRD-152 / hole / for AC-1, a three-digit status outside `100..599` is not a defined status class, so it counts as malformed (design D-059); AC-2 ← PRD-152, PRD-221; AC-3 ← PRD-152, PRD-221; AC-4 ← PRD-150, PRD-221; AC-5 ← PRD-150, PRD-221; fills: PRD-150 / hole / for AC-5, AC-7, coding parameters, empty values and padded or repeated list elements are not covered by the request, so they follow the request-side parsing (design D-054, D-073); AC-6 ← PRD-154, PRD-208, PRD-221; AC-7 ← PRD-150; AC-8 ← PRD-221; AC-9 ← PRD-151; AC-10 ← PRD-152, PRD-153, PRD-221; AC-11 ← PRD-177; fills: PRD-177 / hole / for AC-11, the request fixes the cases but not the test backends, so malformed and delayed responses come from raw sockets in test scope (design D-070). The response parser is security-sensitive: a gateway that reads a length differently from the client re-opens response splitting and desynchronisation, so the proxy is stricter than RFC 9112 by refusing every coding but `chunked` — it removes `Transfer-Encoding` as hop-by-hop, so passing other codings through would leave bytes the client cannot interpret. RFC 9112 §5.2 lets a proxy answer obs-fold with 502, and §6.3 lets it treat `Content-Length` with `Transfer-Encoding` as an error. Express users meet the same failures as `http-proxy-middleware` parse errors surfacing as 502.

#### Requirement

### FR-PROXY-015 — Proxy failures before the response: backend-side errors go to the app's error flow as ProxyException with kind and cause, without leaking the target, and an early backend response is relayed on a best-effort basis

| Field | Value |
| --- | --- |
| Type | functional |
| Target | 0.12.0 |
| Status | in_progress |
| Priority | high |
| Tags | 0.12.0, feasibility:high, request-b, proxy, errors, error-flow |
| Risk | medium |

#### Requirement

The system shall make the proxy throw every backend-side failure that happens before the response is handed to `res.relay` into the app's error flow as a `ProxyException` holding the failure's kind and the underlying exception as its cause — `CONNECT_FAILED` when the connection cannot be established for a reason other than a timeout (refused, unresolvable host, TLS failure other than a timeout) and `INVALID_RESPONSE` when the response is malformed or the connection ends before a complete header block — writing neither an error body nor an app-logger entry of its own; and shall deliver an early backend response on a best-effort basis: when writing the request body fails because the backend closed or reset the connection, it tries to read the response left on the socket, relays it when a complete status line and header block arrive, reports `INVALID_RESPONSE` otherwise, and in both cases stops the body transfer and reads no more of the client body. A write failure caused by the write-timeout or total-timeout watchdog closing the socket is not such a case: it is reported with the deadline the watchdog recorded, `WRITE_TIMEOUT` or `TOTAL_TIMEOUT` (FR-PROXY-017), and never as `INVALID_RESPONSE`.

#### Rationale

AC-1 ← PRD-13, PRD-97, PRD-98, PRD-211; AC-2 ← PRD-97, PRD-98; AC-3 ← PRD-9, PRD-97, PRD-230; AC-4 ← PRD-13, PRD-99, PRD-211; AC-5 ← PRD-230; fills: PRD-106 / hole / for AC-5, the request has the proxy log only failures after the response started and does not say who logs earlier ones, so they are left to the error flow and its logging (design D-062); AC-6 ← PRD-103, PRD-207; AC-7 ← PRD-103; AC-8 ← PRD-104; AC-9 ← PRD-103, PRD-109, PRD-111, PRD-211. Handing failures to the error flow (decision 5) keeps proxy errors consistent with NaruServe's default error handling and lets `onError` answer by kind, as Express users do in `http-proxy-middleware`'s `on.error` handler; a hand-made proxy that let a connect failure surface as 500 is one of the pitfalls the official proxy removes. A blocking client does not read while it writes the body, so a backend that answers 401 or 413 early and closes is caught only when the write fails; an RST discards the receive buffer, so that case stays untested best effort. The request (§3.4) scopes the early-response rule to a backend that sends a response and closes the connection, while its error table gives a write timeout 504 `WRITE_TIMEOUT` and an exceeded total limit 504 `TOTAL_TIMEOUT`; both deadlines are enforced by the watchdog closing the socket, so AC-9 keeps those write failures out of the `INVALID_RESPONSE` fallback.

- [ ] AC-1: When no backend listens on the target port, the client receives 502 and `onError` receives a `ProxyException` whose `kind()` is `CONNECT_FAILED` and whose `getCause()` is a `java.net.ConnectException`.
- [ ] AC-2: For a target whose host name does not resolve (for example `http://backend.invalid:8081`), the client receives 502 and `onError` receives a `ProxyException` with `kind()` `CONNECT_FAILED` whose `getCause()` is a `java.net.UnknownHostException`.

#### Requirement

The system shall make the proxy handle a backend-side failure that happens after the response was handed to `res.relay` — the connection ending before the declared length, a malformed chunk, a read timeout between body bytes or the total timeout — by logging a `ProxyException` of the failure's kind to `req.application().logger()` once and then throwing, from the relayed stream, an `IOException` whose cause is that `ProxyException`, so that the framework aborts the client connection, without the proxy calling `res.abort` itself.

#### Rationale

AC-1 ← PRD-105, PRD-106, PRD-221; AC-2 ← PRD-105, PRD-106, PRD-221; AC-3 ← PRD-105, PRD-110; AC-4 ← PRD-105; AC-5 ← PRD-106 (design D-062). Once the body is copied by the framework after the middleware returned, the proxy can no longer throw into the error flow and the status line is already sent, so the only correct signal is aborting the client connection; the framework's `abort(Throwable)` does not keep its cause, so the proxy writes the kind to the app logger before throwing. Express users see the same outcome as a destroyed client socket after `http-proxy-middleware` emits `error` mid-stream.

#### Acceptance Criteria

- [x] AC-1: When the backend sends `Content-Length: 100`, then 50 body bytes, and closes the connection, the client connection is closed before 100 body bytes arrive, and the app logger receives a `ProxyException` whose `kind()` is `INVALID_RESPONSE`.
- [x] AC-2: When a chunked backend body breaks mid-stream with a chunk-size line longer than 4 KiB, or with a trailer section larger than 64 KiB, the client connection is aborted before the chunked body completes, and the app logger receives a `ProxyException` with `kind()` `INVALID_RESPONSE`.
- [x] AC-3: With `.readTimeout(1, TimeUnit.SECONDS)`, a backend that sends its header block and part of the body and then stops sending makes the client connection abort after about 1 second, and the app logger receives a `ProxyException` with `kind()` `READ_TIMEOUT`.
- [x] AC-4: The `IOException` thrown by `read` of the stream the proxy passed to `res.relay` has as its `getCause()` a `ProxyException` of the failure's kind, and the proxy never calls `res.abort`, as a unit test with a recording `Response` shows.
- [x] AC-5: The proxy logs each such failure exactly once, through `Logger.error(String, Throwable)` with the `ProxyException` as the throwable, and the log call happens before the `IOException` leaves the relayed stream, as a unit test with a recording logger shows.

### FR-PROXY-017 — Proxy timeouts: connect 10 s, write 60 s, read 60 s and total 5 min by default, each finite and set per Proxy, the first one reached applies, 504 before the response and an aborted client connection after it

| Field | Value |
| --- | --- |
| Type | functional |
| Target | 0.12.0 |
| Status | implemented |
| Priority | high |
| Tags | 0.12.0, feasibility:high, request-b, proxy, timeouts |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |

#### Requirement

The system shall bound every proxied exchange with four finite timeouts set per `Proxy`: `connectTimeout` (default 10 seconds) for the TCP connect and, separately, the TLS handshake; `writeTimeout` (default 60 seconds) for a backend socket write that makes no progress, not counting time spent waiting for client body bytes; `readTimeout` (default 60 seconds) from the request being sent to the first response byte and between response bytes; and `totalTimeout` (default 5 minutes) from the first attempt to the end of the request, including retries and retry waits; whichever is reached first applies, and the proxy reports `CONNECT_TIMEOUT`, `WRITE_TIMEOUT`, `READ_TIMEOUT` or `TOTAL_TIMEOUT` as 504 before the response was handed to `res.relay` and aborts the client connection after it.

#### Rationale

AC-1 ← PRD-13, PRD-107, PRD-108, PRD-109, PRD-110, PRD-111, PRD-211, PRD-238 (design D-071); AC-2 ← PRD-108; AC-3 ← PRD-108, PRD-211; fills: PRD-160 / hole / for AC-3, the TCP connect and the TLS handshake are bounded separately by the connect timeout (design D-063); AC-4 ← PRD-110, PRD-211; AC-5 ← PRD-109, PRD-211; AC-6 ← PRD-109, PRD-211; AC-7 ← PRD-111, PRD-212, PRD-245; AC-8 ← PRD-112; AC-9 ← PRD-8, PRD-110; AC-10 ← PRD-211 (design D-071). No timeout defaults to unlimited, because a proxy without one holds a worker thread for as long as a backend stalls, one of the pitfalls a hand-made proxy had. A read timeout measures gaps between bytes, so it alone never bounds a request; the total timeout does, which also cuts downloads longer than 5 minutes unless the mount raises it. The option is named `totalTimeout` and the kind `TOTAL_TIMEOUT` because Node's `http-proxy` `timeout` means the incoming socket timeout (decision 14); Express users map `proxyTimeout` of `http-proxy-middleware` to `readTimeout`.

### FR-PROXY-018 — Proxy retries: off by default; with retries(n) connect failures retry for every method and 502 or 503 only for bodyless safe methods unless retryUnsafeMethods(true), with retryDelay waits inside the total timeout

| Risk | medium |

#### Requirement

The system shall make the proxy try each request once by default and, with `.retries(n)`, up to `n` more times on a new connection each: after a TCP-level connect failure that is neither a connect timeout nor a TLS failure, for every method; after a backend 502 or 503, only when the body sent to the backend was zero bytes and the method is `GET`, `HEAD` or `OPTIONS`, or any method under `.retryUnsafeMethods(true)`; and never after a connect timeout, a TLS failure, a write, read or total timeout, an `INVALID_RESPONSE` or any other status; waiting `.retryDelay` (default 200 milliseconds) before each retry, returning the last failure without waiting when the wait would end past the total-timeout deadline, and relaying the last backend response unchanged when 502 or 503 remains after the last retry.

#### Rationale

AC-1 ← PRD-114, PRD-227; AC-2 ← PRD-9, PRD-213, PRD-227; AC-3 ← PRD-227; AC-4 ← PRD-116, PRD-214; AC-5 ← PRD-9, PRD-214, PRD-227; AC-6 ← PRD-227, PRD-228; fills: PRD-227 / hole / for AC-6, the retry table names connection refused and name resolution failure as examples of one class, so every TCP-level connect failure other than a connect timeout or a TLS failure is retried (design D-064); AC-7 ← PRD-115, PRD-228; AC-8 ← PRD-215; AC-9 ← PRD-215; AC-10 ← PRD-111, PRD-212; AC-11 ← PRD-12. Retrying is off by default so no request is processed twice unasked. A connect failure happens before any request byte is sent, so the backend cannot have processed it; a backend 502 or 503 can follow processing, so only bodyless safe methods retry, and a streamed body cannot be resent. TLS failures repeat identically, a connect timeout retried would hold the worker thread for another full timeout (decision 3), and failures after the request was sent leave the processing state unknown. Express users enable the same behaviour by hand around `http-proxy-middleware`, which has no built-in retry.

#### Requirement

The system shall make `.maxConcurrent(n)` give its result a new counter with the limit `n`, shared by reference by every `Proxy` later derived from that result through another option method, and a new counter again whenever `.maxConcurrent` is called on a derived object; count against the counter every in-flight request of every mount of those objects, in any app, from the moment its slot is taken to the end of the request; answer a request that finds the counter at its limit at once with 503 and `kind()` `CONCURRENCY_LIMIT`, without waiting and without connecting to the backend; and count no request of a `Proxy` that has no limit, which is the default.

#### Rationale

AC-1 ← PRD-218, PRD-249; AC-2 ← PRD-218; AC-3 ← PRD-124, PRD-176, PRD-218; AC-4 ← PRD-123, PRD-125, PRD-218; AC-5 ← PRD-125; AC-6 ← PRD-218, PRD-249; AC-7 ← PRD-218, PRD-237, PRD-249 (design D-065); AC-8 ← PRD-126; AC-9 ← PRD-123, PRD-124, PRD-176. #### Requirement

The system shall make the proxy run synchronously on the request thread, holding it while connecting, sending the request and reading the response header block; take the concurrency slot and start the total-timeout watchdog only after every check and `req.bodyStream(...)` have passed; and, exactly once per request, return the slot, cancel the watchdog's reservations and close the backend socket — when the response was handed to `res.relay`, at the first of the relayed stream's `close()` and the `res.onAbort` notification, and otherwise just before the middleware throws or returns.

| Type | reliability |

#### Requirement

The system shall enforce the write timeout and the total timeout through one JVM-wide scheduler inside the proxy module, created lazily by the first proxy request that needs it and registered with no app lifecycle, running at most one daemon thread at a time whose context class loader is `null`, letting that thread end when idle so that none remains within 30 seconds after the last reservation ends, removing cancelled reservations from its queue, and firing a deadline by recording its kind and closing the plain backend socket — never the `SSLSocket` — without blocking.

#### Rationale

AC-1 ← PRD-172; AC-2 ← PRD-170, PRD-172; AC-3 ← PRD-173, PRD-175; AC-4 ← PRD-173, PRD-219, PRD-257 (design D-066); AC-5 ← PRD-172, PRD-219; AC-6 ← PRD-171, PRD-174; AC-7 ← PRD-169, PRD-170; AC-8 ← PRD-172, PRD-257 (design D-066); AC-9 ← PRD-169, PRD-170. `SO_TIMEOUT` bounds reads only, so a blocked write and the overall deadline need another thread that closes the socket. NaruServe 0.11.0 offers no public way to register an app-level resource during request handling — `ApplicationContext.own` refuses after start and `attribute` has no atomic put-if-absent — so the scheduler is JVM-wide and lazily created inside the module rather than widening request A (decision 18). A daemon thread with core-thread timeout and no context class loader leaves nothing behind after a redeploy once idle, with no shutdown hook. Closing the `SSLSocket` sends `close_notify` and could block behind a stuck writer, which would stall every proxy's timeouts on the one watchdog thread, so the plain socket is closed instead.

#### Acceptance Criteria

- [ ] AC-1: Loading the `Proxy` class, calling `Proxy.to(url)` with options and starting an app that mounts it create no scheduler and no watchdog thread until the first proxied request, as the package-private scheduler accessor and a thread listing show.
- [ ] AC-2: Proxies of two different apps in one JVM use the same scheduler instance, and while 20 proxied requests are in flight at most one watchdog thread exists.
- [ ] AC-3: The watchdog thread is a daemon thread and its context class loader is `null`.
- [ ] AC-4: After every proxied request has ended and no new one arrives, no watchdog thread remains within 30 seconds, and a request sent after that with `.totalTimeout(1, TimeUnit.SECONDS)` to a backend that never answers still gives 504 with `kind()` `TOTAL_TIMEOUT` after about 1 second.
- [ ] AC-5: The first proxied request after an app has started prepares the watchdog without calling `ApplicationContext.own` or setting an app attribute, throws no `IllegalStateException`, and its response is relayed.
- [ ] AC-6: After 1000 proxied requests completed under the default 5-minute total timeout, the scheduler queue holds no reservation, because each request cancels its reservations at its end and cancelled reservations are removed from the queue.
- [ ] AC-7: When a write timeout or the total timeout fires on an https exchange, the watchdog calls `close()` on the plain socket and never on the `SSLSocket`, as a unit test with recording sockets shows.
- [ ] AC-8: Stopping one app neither shuts down nor waits for the scheduler, and a proxy of a second app still running in the same JVM still gets 504 with `kind()` `TOTAL_TIMEOUT` from `.totalTimeout(1, TimeUnit.SECONDS)`.
- [ ] AC-9: While one proxied request is blocked writing a body to a backend that never reads it, the total timeout of another request still fires about on time, because a firing deadline only closes a plain socket and never waits on the blocked writer.

### FR-PROXY-020 — Proxy backend HTTP/1.1 client: its own client over java.net.Socket, a new connection for every attempt with Connection: close, no reuse, and no wait on a backend that keeps the connection open

#### Requirement

The system shall make the proxy talk to the backend through its own minimal HTTP/1.1 client over `java.net.Socket`, without `HttpURLConnection` or `java.net.http`, opening a new connection for every attempt, sending `Connection: close` on every request, never reusing a connection, and closing the connection at the end of the request; after the response has been read to its end it may wait briefly for the backend to close first, but a backend that keeps the connection open never delays the client's response or the release of the slot.

#### Rationale

AC-1 ← PRD-166, PRD-235; AC-2 ← PRD-149, PRD-166; AC-3 ← PRD-146, PRD-232; AC-4 ← PRD-167. `java.net.http.HttpClient` exists only on Java 11 and not on Android, and `HttpURLConnection` refuses `PATCH` and extension methods on the JDK, blocks restricted headers such as `Host` and cannot keep header order and duplicates, so neither can follow the forwarding rules (decision 7). A new connection per request avoids reusing a connection that holds an unread response, at the cost of a TCP (and TLS) handshake per request; connection pooling is left to a later version (decision 8). Letting the backend close first keeps TIME_WAIT sockets off the proxy host, whose ephemeral ports could otherwise run out; the proxy documentation states that risk. Express users get pooling from Node's `http.Agent` under `http-proxy-middleware`, which this first version does not offer.

#### Acceptance Criteria

- [ ] AC-1: Two sequential requests through one mount reach the backend over two separate TCP connections, and a request retried twice under `.retries(2)` reaches it over three separate connections.
- [ ] AC-2: Every backend request carries exactly one `Connection: close` line, and when the backend answers with `Connection: keep-alive` and a complete `Content-Length` body the proxy still closes that connection after the response and sends the next request over a new connection.
- [ ] AC-3: The main class files of `NaruServe-proxy` reference neither `java/net/HttpURLConnection` nor any class under `java/net/http/`, as a class-reference test shows, and backend connections are made through `java.net.Socket`.
- [ ] AC-4: When the backend sends a complete `Content-Length` response and then keeps the connection open without closing it, the client receives the complete response without waiting for the backend to close, and on a `.maxConcurrent(1)` mount the next request reaches the backend.

#### Requirement

The system shall record every proxied request in the app's access log exactly as it records any other request, with the status the client received and with `in=` counting the request body bytes the proxy read through `req.bodyStream(...)` and forwarded to the backend.

#### Acceptance Criteria
