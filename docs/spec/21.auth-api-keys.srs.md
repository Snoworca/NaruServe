# Auth API Keys

## 1. Scope Overview

API keys are the second credential of the auth module (`com.snoworca.naruserve.utils.auth`, package `apikey`), meant for service-to-service calls. They are off by default and exist only when the auth builder receives `.apiKeys(store)`. This scope covers how a key is presented and verified, how failures are counted, how a key actor is restricted, how keys are issued, listed and revoked (app facade, personal access token endpoints and admin endpoints), service accounts, the `ApiKeyStore` SPI with its value types and contract test, the in-memory store, and the atomic limit-insert contract an app-provided ApiKeyStore declares for MULTI_INSTANCE; no built-in database store is shipped (34판, 2026-11-03: built-in JDBC stores removed; persistence is SPI-only, CON-IAM-003). The source of truth is `docs/research/auth-rbac/00.overview.md` §6.3 R47 (editions 21–33) and its §6.4 rows that start with "R47".

## 2. Scope Boundaries

### In Scope

- `Authorization: <scheme> nk_<prefix8>_<secret32>` presentation, `.apiKeyScheme(String)` validation, multiple and merged `Authorization` headers, and the `WWW-Authenticate` shape when keys are on.
- The key verification order (steps 1–11), the key-only per-IP failure counter (default 100 per 15 min, 429 `too_many_attempts`), expiry, stale-key and ownerVer invariant handling, pending markers and off-request deletions in `SINGLE_INSTANCE` versus `MULTI_INSTANCE`.
- The key principal (key scopes intersected with the owner's scopes), the `*` and `auth-*` rules, `.allowAdminScopesOnApiKeys`, and the endpoints and writes a key actor may not use.
- `AuthApiKeys` (`auth.apiKeys()`), `GET/POST /auth/me/apikeys`, `DELETE /auth/me/apikeys/:id`, `GET/POST /auth/admin/apikeys`, `DELETE /auth/admin/apikeys/:id`, key limits and lifetimes, key status in listings.
- Service accounts (`AuthUser.isServiceAccount()`).
- `ApiKeyStore`, `StoredApiKey`, `ApiKey`, `IssuedApiKey`, `ApiKeyStatus`, `ApiKeyPrefixCollisionException`, `InMemoryApiKeyStore`, `AuthTesting.apiKeyFor` and `AuthTesting.verifyApiKeyStore`.
- WebSocket connections opened with an API key.
- The API key error codes and statuses collected in R47 (10).

### Out of Scope

- The auth pipeline, install order, public paths, error layer, doctor framework, events and cross-cutting build rules (scope AUTH).
- JWT, refresh tokens, password hashing and hash slots (scope TOKEN).
- Secure-transport rule, credential extraction for JWT and cookies, CSRF, the eight account endpoints, `LoginThrottle` base contract and login throttling (scope FLOW).
- Users, groups, roles, the grant rule R31, the principal cache, `UserStore` and the other store SPIs (scope IAM).
- Core changes C4, C6a, C6b, C7 (scopes APP, HTTP, ENGINE).
- A store method that finds keys by `issuedByUserId`, a list of all keys, and Kotlin `reified` helpers (not in v1).

## 3. Assumptions and Constraints

- Code lives in `NaruServe-api` under `com.snoworca.naruserve.utils.auth`; no new main dependency, no `internal` Core package, API 21 (no `java.time`, `java.util.Base64`, `java.nio.file`). These cross-cutting rules are owned by scope AUTH.
- All times in the public API are epoch-millisecond `long`/`Long`; the current time comes from `TimeSource`.
- `ApiKeyStore` is a user-implemented interface: its method table is fixed before the first release and only default methods are added afterwards (R20).
- No JDBC driver is used, tests included; the multi-instance key limit is checked with a test ApiKeyStore that implements the SPI and declares supportsAtomicLimitInsert the way an application store would (34판, 2026-11-03: built-in JDBC stores removed; persistence is SPI-only, CON-IAM-003).
- Names that 00 marks as not final (`.apiKeyFailureLimit`, the lastUsedAt update method) are settled during implementation and recorded in `docs/api/`.

#### Requirement

When keys are on, the auth module shall read an API key only from `Authorization: <scheme> nk_<prefix8>_<secret32>`, where the scheme is the configured `.apiKeyScheme` compared case-insensitively and the key is parsed strictly as one RFC 9110 `token68`, shall separate keys from JWTs by scheme and not by value shape, and shall never read a key from the query string or a cookie.

#### Rationale

00 §6.3 R47 (1) (22nd edition presentation change, 23rd edition key characters and refresh cookie, 24th edition token68 strictness, 27th edition public path); §6.4 rows "R47 × 키와 JWT 구분", "사용자 정의 스킴", "점 구분", "쿼리 문자열", "키와 refresh 쿠키".

#### Acceptance Criteria

- [x] AC-1: On a protected path, `Authorization: ApiKey nk_…` is verified as an API key, `Authorization: Bearer eyJ…` is verified as a JWT, and `Authorization: Bearer nk_…` is verified as a JWT and gets 401 `invalid_token`.
- [x] AC-2: With `.apiKeyScheme("ak")`, `Authorization: AK nk_…` is looked up as a key (case-insensitive scheme) and `Authorization: ApiKey nk_…` is treated as no credentials: 401 `unauthenticated` on a protected path, and the 401 `WWW-Authenticate` names both `Bearer` and `ak`.
- [x] AC-3: With `.apiKeyScheme("ak")`, `Authorization: ak.nk_…` is read as scheme `ak.nk_…`, i.e. no credentials: 401 on a protected path.
- [x] AC-4: In each of HEADER, COOKIE and BOTH mode, `GET /x?api_key=nk_…` or a cookie other than `naru_at` holding `nk_…`, with no other credential, on a protected path gets 401 `unauthenticated`; the query value and cookie are not looked up as a key.
- [x] AC-5: In COOKIE or BOTH mode, `Authorization: ApiKey nk_…` together with a cookie access token on a protected path gets 400 `invalid_request`; on a public path the request proceeds anonymously with no 400.
- [x] AC-6: In COOKIE or BOTH mode, `Authorization: ApiKey nk_…` plus a `naru_rt` refresh cookie on an ordinary protected path authenticates with the key (the refresh cookie is not counted as a second credential).
- [x] AC-7: An `Authorization` value of the configured scheme followed by an `#auth-param`-shaped value (for example `ApiKey a=b`) is a malformed key: 401 `invalid_api_key`.

#### Research / Analysis

- Decisive facts: the RFC 9110 §11.4 grammar `credentials = auth-scheme [ 1*SP ( token68 / #auth-param ) ]` is used; scheme compare is case-insensitive per RFC 9110 §11.1. The `nk_` prefix is kept only so secret scanners find leaked keys; it is not used to tell keys from JWTs, so `Bearer nk_…` is a bad JWT. Query and cookie keys are not read because they leak into logs. Keys are accepted by header whatever `transport` is configured, so no CSRF token applies to keys. Key plus cookie access token is a multi-path credential (400, R30). The refresh cookie `naru_rt` is not an access credential, so it does not trigger the multi-credential 400. WebSocket Upgrade uses the same header and scheme rules (R40). Pitfall: telling keys from JWTs by the `nk_` prefix would let a client switch verification path by value shape.

#### Implementation Notes

- Credential extraction lives in the auth authenticator chain (`spi.Authenticator`, scope AUTH/FLOW). Use `Request.headers("Authorization")` to see every header value. The multi-header 400 and public-path rules are in the companion requirement on multiple Authorization headers. No `java.util.Base64`.

- [x] AC-3: Two `Authorization` headers on `POST /auth/login` (a credential endpoint) get 400 `invalid_request`, regardless of `.permit`.
- [x] AC-4: One header `Authorization: Bearer eyJ…, ApiKey nk_…` (proxy-merged) on a protected path gets 401 `invalid_token`, not 400.

#### Research / Analysis

- Decisive facts: RFC 9110 §5.3 forbids combining non-list headers, so two `Authorization` headers are a client error (400). ### SEC-APIKEY-003 — API key format nk_prefix8_secret32 and SHA-256 storage

| Field | Value |
| --- | --- |
| Type | security |
| Target | 0.11.0 |
| Status | verified |
| Priority | high |
| Tags | 0.11.0, auth-rbac, feasibility:high, apikey-format |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | docs/research/auth-rbac/00.overview.md |

#### Requirement

The auth module shall generate keys as `nk_<prefix8>_<secret32>` where prefix8 and secret32 are base62 (`[A-Za-z0-9]`) and secret32 comes from `SecureRandom`, shall store only the SHA-256 of the secret as 64 lower-case hex characters, and shall return the plaintext key exactly once in the issuance result.

#### Rationale

00 §6.3 R47 (1) (23rd edition key characters, about 190 bits), R47 (3) (plaintext returned once, never stored or logged), §6.3 ApiKeyStore notes (secretHash lower-case hex 64); §6.4 row "R47 × 형식이 틀린 키".

#### Acceptance Criteria

#### Research / Analysis

- Decisive facts: autocommit stays on because turning it off lets the driver open its own transaction, so `BEGIN IMMEDIATE` fails with "within a transaction" or the write lock is taken late. `BEGIN IMMEDIATE` takes a database-wide write lock, so no lock row is needed. `JdbcApiKeyStore` shall implement `deleteExpired` as repeated statements, each in its own transaction, deleting at most 500 rows found through the `(expires_at)` index until a statement deletes fewer than 500 (MySQL `DELETE … ORDER BY expires_at, id LIMIT 500`, PostgreSQL and SQLite `DELETE … WHERE id IN (SELECT id … LIMIT 500)`), shall override `deleteFutureByOwner` as one `DELETE … WHERE owner_user_id = ? #### Research / Analysis

- Decisive facts: deleting all expired keys at once would hold long locks and a large undo log that block issuance. MySQL needs a total order (`expires_at, id`) so the source and replicas delete the same rows under STATEMENT binlog replication; `expires_at` alone does not order rows with equal values. Even with a deterministic order MySQL treats `DELETE … LIMIT` as unsafe under STATEMENT and logs warning 1592 (documented behaviour, not measured: 00 §12). The cleanup is driven by the R42 10-minute scheduler.

#### Implementation Notes

- Loop in Java, one autocommit statement per batch is sufficient (each statement is its own transaction). SQLite tests use the test-only driver; MySQL/PostgreSQL SQL checked as text.
