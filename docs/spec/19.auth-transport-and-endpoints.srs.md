# Auth Transport and Endpoints

| Field | Value |
|---|---|
| Document Type | scope_srs |
| Scope | FLOW |

## 1. Scope Overview

This document defines how the auth module (`com.snoworca.naruserve.utils.auth`, target 0.11.0) moves credentials over HTTP and protects its own account endpoints: the per-request secure-transport rule, which credentials each token transport mode reads, CSRF and Origin checks, the token delivery rule for token-issuing responses, auth cookies, the account endpoints of `auth.routes()` including the logout identity decision table, the `auth.webSocket(handler)` wrapper, and abuse protection for password login (login throttling, device trust, optional hard lockout and the per-user password attempt limit). The source of truth is `docs/research/auth-rbac/00.overview.md` edition 33, rules R29, R33, R34, R40 and R45 and the matching §6.4 rows.

## 2. Scope Boundaries

### In Scope

- Secure-transport rule (R33), the `allowInsecureTransport(reason)` opt-in and the eight credential endpoints split into anonymous-entry and subject-required endpoints
- Credential reading per transport mode `HEADER`, `COOKIE` and `BOTH`, multiple-credential handling and the `WWW-Authenticate` challenge shapes
- Request decision order and JSON-only POST bodies on auth endpoints
- CSRF (signed double-submit bound to `sub` and `fam`), Origin and Referer checks, cookie-planting responses and auth cookie attributes
- Token delivery for the five token-issuing responses (`login`, `register`, `setup`, `refresh`, `password`) and the CORS guidance for cross-origin clients
- Account endpoints `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`, `GET /auth/me`, `PATCH /auth/me`, `POST /auth/password`, `POST /auth/register` and the account endpoint table
- `auth.webSocket(handler)` expiry closing for JWT-authenticated connections and principal-recheck and revocation closing for every wrapped connection (key-specific closes are in the APIKEY scope)
- Login throttling keys and limits, `DeviceTrust` device tokens, optional `Lockout`, the per-user password attempt limit, the `LoginThrottle` SPI limit-argument methods and `ForwardingLoginThrottle`, and throttle counter storage limits

### Out of Scope

- Auth builder, install ordering, public path matching, error layer, error code catalog, events and packaging constraints (AUTH scope)
- JWT encoding, key sets, refresh token rotation store, password hashing, hash slots and timing equalization (TOKEN scope)
- User store contracts, `AuthUsers`, groups, roles, grant rules, admin user and group endpoints A1–A6 and G1–G8, and the user, group, refresh, throttle and device-trust store SPIs (IAM scope)
- API key presentation, verification chain, key-failure counter, key issuance endpoints and API-key WebSocket connections (APIKEY scope)
- Core changes C4, C6a, C6b and C7 (APP, HTTP and ENGINE scopes)
- `POST /auth/setup` behavior and recovery mode (AUTH scope); this scope only classifies it as a credential endpoint and applies the delivery rule
- Self-service password reset, email verification and email-change endpoints (v2)

## 3. Assumptions and Constraints

- Core supplies `req.isSecure()` and `req.remoteAddress()` resolved through C6b proxy trust and `req.socketAddress()` from C6a; auth reads only these public accessors.
- The auth package uses only the Core public API and JDK APIs available on Android API 21 (no `java.time`, `java.util.Base64` or `java.nio.file`); these cross-cutting constraints are owned by the AUTH scope.
- Values taken from research files 01–07 that 00 does not restate are marked `[INFERRED:med:advisory]` in acceptance criteria.
- Browser `Origin` behavior on old Android WebViews is unmeasured (00 §12); requirements relying on it carry `feasibility:medium`.
- Names that 00 marks as proposals are labelled "(name not final)" and are settled during implementation.

#### Requirement

In PROD mode the auth middleware shall process an authenticated request or any of the eight credential endpoints only when req.isSecure() is true or the request is local (req.socketAddress() is a loopback address and no X-Forwarded-* or Forwarded header is present), and shall otherwise answer 403 insecure_transport before reading any credential; public paths shall be exempt and handled as anonymous without reading a token.

#### Rationale

00 §6.3 R33 (editions 5, 8, 10, 21, 24, 26, 29) makes transport security a per-request decision instead of a bind-address decision (R21 withdrawn); §6.4 rows "R33 × 로그인", "R47 × 평문과 헤더 둘", "R29 × R33" and "R32 × R33" fix the outcomes.

#### Acceptance Criteria

- [ ] AC-1: PROD, plain-text request whose socket address is not loopback, POST /auth/login -> 403 with body error.code insecure_transport; the request body is not parsed and the login handler does not run.
- [ ] AC-2: PROD, plain-text non-local request to a protected path carrying two Authorization headers -> 403 insecure_transport, not 400 invalid_request, because the transport check runs before any credential is parsed.
- [ ] AC-3: PROD, socket address 127.0.0.1 or ::1, no X-Forwarded-* and no Forwarded header, plain text, POST /auth/login with valid credentials -> 200; the same request with an X-Forwarded-For or Forwarded header added -> 403 insecure_transport.
- [ ] AC-4: PROD, app.trustProxyHops(1) and the proxy sends X-Forwarded-Proto: https on a plain-text socket, POST /auth/login -> req.isSecure() is true and the request passes the transport check (200 for valid credentials).
- [ ] AC-5: PROD, .permit("/health"), plain-text non-local GET /health with an expired Bearer token -> 200 anonymous; auth.userOrNull(req) returns null and the token is not verified.
- [ ] AC-6: PROD, plain-text non-local request to each of POST /auth/login, /auth/refresh, /auth/logout, /auth/register, /auth/setup, /auth/password, POST /auth/me/apikeys and POST /auth/admin/apikeys -> 403 insecure_transport, also when the app configured .permitPrefix("/auth").
- [ ] AC-7: AuthMode.DEV, plain-text non-local POST /auth/login with valid credentials -> 200; the transport check is disabled.
- [ ] AC-8: The docs/api auth page and its docs/api/en mirror list the recommended reverse-proxy configuration (the proxy adds X-Forwarded-For and X-Forwarded-Proto, as in the nginx lines of IR-ENGINE-003 AC-7, 00 R32) as a mandatory deployment step, and state that Core does not read the Forwarded header (SEC-ENGINE-001 AC-5, SEC-ENGINE-002 AC-7), so a proxy that sends only Forwarded makes its requests non-local (AC-3) but leaves req.isSecure() false and every client on the proxy's address; they also state the residual risk that a same-host proxy adding none of these headers makes every request look local, so plain-text external requests pass the transport check and every client shares the proxy's address as its IP, so the login IP limit applies to all users as one key (/auth/setup stays protected by its one-time setup token); a docs test asserts the mandatory step, the X-Forwarded-For and X-Forwarded-Proto header names, and both residual-risk statements on both pages.

#### Research / Analysis

- Decisive facts: "local" means loopback socket address AND zero proxy headers (X-Forwarded-*, Forwarded); a TLS-terminating LB passes through C6b trust (trustProxyHops/trustProxyCidrs) alone. The check is the very first step, before multiple-credential parsing (26th ed.), so a plain-text request never gets 400 invalid_request. Credential endpoints are never public paths even if listed in .permit (8th ed., S-3). Pitfall: when v2 adds self password reset or email verification endpoints they must be added to the credential-endpoint list, otherwise reset tokens travel over plain text as anonymous public requests (10th ed.). Residual risk (K-12): a same-host proxy that adds no headers makes every request look local; docs make the recommended proxy config a mandatory step and /auth/setup independently requires the one-time setup token (AUTH scope). Rejected: R21 bind-address check - reopen only if C5 lands and a deployment cannot send proxy headers.

#### Implementation Notes

- First step of the global auth middleware (Auth.handle) in utils.auth, before credential extraction. Reads only Core public API: req.isSecure(), req.socketAddress() (C6a, HTTP scope), req.header/headers. Loopback test on the literal address (127.0.0.0/8 and ::1) without DNS lookups. Mode handling comes from AuthMode (AUTH scope). Tests use InMemoryHttpAdapter(remoteAddress, secure). API 21 / Core-public-API-only constraints are owned by the AUTH scope.
- [2026-10-30] Maintenance obligation (00 R33 edition 10; §6.4 "R33 × v2 재설정"): when v2 adds self-service password reset or email-verification endpoints (for example /auth/password/reset), they must join the eight-endpoint credential list checked here; otherwise they are handled as plain-text anonymous public requests and reset tokens can travel in plain text. No 0.11.0 behaviour.

#### Requirement

The builder method .allowInsecureTransport(String reason) shall disable the secure-transport check in PROD mode while forcing an access token TTL of 5 minutes and a refresh token TTL of 24 hours, warning when auth cookies are sent without the Secure attribute, and logging the reason as a WARN on every start.

#### Rationale

#### Acceptance Criteria

- [ ] AC-1: PROD with .allowInsecureTransport("TLS adapter pending"), plain-text non-local POST /auth/login with valid credentials -> 200, not 403 insecure_transport.
- [ ] AC-2: Same configuration with .accessTtl set to 15 minutes and .refreshTtl set to 14 days: the issued access token has exp - iat = 300 seconds and the refresh token expires 24 hours after issue.
- [ ] AC-3: Every start of an app whose Auth has the opt-in logs one WARN line that contains the reason string "TLS adapter pending"; two consecutive starts produce two such lines.
- [ ] AC-4: Same configuration in COOKIE transport over plain text: a token-issuing request with a same-origin Origin (for example POST /auth/login with valid credentials) whose response sets naru_at, naru_rt or naru_csrf without the Secure attribute logs a WARN stating that the auth cookies lack Secure.
- [ ] AC-5: Without the opt-in in PROD the same plain-text non-local request -> 403 insecure_transport (the opt-in is the only PROD switch).

#### Requirement

The auth module shall classify POST /auth/login, /auth/refresh, /auth/logout, /auth/register and /auth/setup as anonymous-entry credential endpoints that ignore invalid or expired JWT and cookie access tokens and never attach a principal (logout excepted for identity), and POST /auth/password, POST /auth/me/apikeys and POST /auth/admin/apikeys as subject-required credential endpoints judged exactly like protected paths, independent of any .permit configuration. The /auth prefix here is the default mount path; the account endpoints are classified under the configured mount path (.mountPath(String), FR-AUTH-005), and the admin endpoint is classified where auth.adminRoutes() is mounted (whether that follows a configured mount path is open).

#### Rationale

00 §6.3 R29 (editions 27–30) and R33 (29th edition list of eight credential endpoints); R47 (1). §6.4 rows "R29 × 자격 증명 엔드포인트의 만료 토큰", "R29 × 자격 증명 엔드포인트의 키와 헤더 둘", "R29 × 주체 필요 자격 증명 엔드포인트의 만료 토큰".

#### Acceptance Criteria

- [ ] AC-1: BOTH, POST /auth/refresh with an expired Authorization: Bearer token and a valid naru_rt cookie (matching X-CSRF-Token, same-origin Origin) -> 200; the expired JWT is read and ignored and no 401 invalid_token is sent. COOKIE, the same request with an expired naru_at cookie instead of the Bearer token -> 200.
- [ ] AC-2: POST /auth/login with an expired Bearer token and valid credentials -> 200 regular login; no 401 invalid_token.
- [ ] AC-3: POST /auth/login, /auth/register, /auth/setup and /auth/refresh carrying a valid access token -> the handler sees no principal (auth.userOrNull(req) returns null).
- [ ] AC-4: POST /auth/password with an expired Bearer token -> 401, code invalid_token, header WWW-Authenticate: Bearer error="invalid_token"; the handler does not run. With API keys enabled, POST /auth/me/apikeys with the same token and POST /auth/admin/apikeys with a bad-signature Bearer give the same 401 with ", ApiKey" appended to the challenge.
- [ ] AC-5: On an anonymous-entry endpoint, two Authorization headers -> 400 invalid_request, and with API keys enabled (.apiKeys(store)) a valid API-key Authorization header on POST /auth/refresh -> 403 api_key_not_allowed; multiple credentials (SEC-FLOW-004, except two or more naru_at cookies in COOKIE or BOTH mode, which count as no access cookie) and the key procedure are the only credential judgments on anonymous-entry endpoints that follow protected-path rules. - [ ] AC-7: With .mountPath("/api/auth") (FR-AUTH-005) the classes follow the configured mount path: (a) PROD with .permitPrefix("/api/auth"), a plain-text non-local POST /api/auth/login -> 403 insecure_transport and the login handler does not run (00 R33: credential endpoints are never public paths); (b) HEADER over a local connection, POST /api/auth/refresh with an expired Authorization: Bearer token and a valid JSON body refreshToken -> 200, with no 401 invalid_token; (c) HEADER over a local connection, POST /api/auth/password with an expired Bearer token -> 401 invalid_token with WWW-Authenticate: Bearer error="invalid_token", and the handler does not run.
- [ ] AC-8: Access cookie on a subject-required endpoint and a protected path (00 R29 29th edition: expired or invalid Bearer and cookie access tokens are 401 invalid_token there). #### Research / Analysis

- Ground truth: the credential-endpoint list in R33 is the single list (8 entries); R29 and R47 (1) refer to it. Anonymous-entry endpoints judge only two things like protected paths: multiple credentials (400 invalid_request) and the API-key procedure (401 invalid_api_key, 403 api_key_not_allowed); expired or invalid JWT and access cookies are ignored. The single exception is logout?all=true with tokens but no valid one (401 invalid_token; no tokens -> 401 unauthenticated). A valid access token is used as identity only by logout. Rejected alternatives: 27th ed. "credentials make anonymous-entry endpoints protected" - broke refresh for clients whose access token had expired; 28th ed. "subject-needing handlers answer 401 themselves" - clients got a handler 401 instead of invalid_token and could not tell that they should refresh; attaching a valid access cookie as principal on login - would make CSRF depend on access cookie state.

#### Implementation Notes

- Endpoint classification is a fixed table inside the auth middleware keyed by method + path under the mount path (utils.auth); it is consulted before the public-path matcher (AUTH scope) so .permit cannot reclassify. API-key handling inside the chain is APIKEY scope.

#### Requirement

The auth documentation in docs/api (Korean page and English mirror) shall instruct cross-origin clients to list in app.cors allowedHeaders every header they send (Authorization, Content-Type, X-CSRF-Token for cookie writes, Naru-Device when sending the device token by header), to register app.cors before auth.install(app), and to put BOTH-mode body-delivery origins such as Capacitor in allowedOrigins but not in trustedOrigins.

#### Rationale

00 §6.3 R29 (h) edition 33 (adds Naru-Device, which 05 §7 omitted) and R28 (CORS before install); §6.4 row "R29 × CORS 헤더"; CLAUDE.md API documentation rule (Express mapping, Java and Kotlin examples).

#### Acceptance Criteria

- [ ] AC-1: The docs/api auth page and its docs/api/en mirror list Authorization (Bearer and the key scheme), Content-Type, X-CSRF-Token and Naru-Device as allowedHeaders entries, each with the condition under which it is needed.
- [ ] AC-2: The page states that a cross-origin request carrying Naru-Device while allowedHeaders lacks it is blocked at preflight and never reaches the server.
- [ ] AC-3: The page states that other-site SPA origins receiving body delivery in BOTH mode belong in allowedOrigins only, that adding them to trustedOrigins switches them to cookie delivery even though SameSite=Strict cookies are not sent on cross-site requests, and that a non-http(s) origin such as Capacitor's capacitor://localhost cannot be listed in CorsOptions.allowedOrigins.
- [ ] AC-4: The page states that app.cors(...) is registered before auth.install(app).
- [ ] AC-5: The page shows the CORS configuration as a Java example and a Kotlin example next to the Express equivalent, following the docs/api conventions.
- [ ] AC-6: The page states that a BOTH-mode client checks the body of every token-issuing response: accessToken present -> body delivery (keep the tokens, send Bearer); only csrfToken present -> cookie delivery (send X-CSRF-Token); the same client may receive either shape depending on Origin and trustedOrigins, so it never assumes one.

#### Requirement

POST /auth/login shall read username and password from a JSON body, normalize the username, run the login throttle and device-trust checks (SEC-FLOW-012) and one constant-work password verification, and, only after the password verified for the found, enabled user, run beforeLogin with that user's AuthUser (00 R30 (7) and FR-AUTH-007 AC-5 give beforeLogin an AuthUser; the step after a successful verify is 05 §5.1 [INFERRED:med:advisory], 00 being silent on the exact step), and on success issue a new token pair on a new family plus a device token through the delivery rule, while every credential failure shall share one 401 response.

#### Rationale

00 §6.3 R45 (endpoint list), R34 (throttle and device trust), R38 (constant-work login, async handler), R30 (7) (beforeLogin), R47 (7) (service account with password gets the same 401 and timing as a wrong password), R2 (new pair = new family); 05 §4.1 #1 for the request body.

#### Acceptance Criteria

- [ ] AC-1: Valid {"username":"alice","password":"<correct>"} -> 200 with a token pair per the delivery rule; the access token's fam differs from every family alice held before.
- [ ] AC-2: Unknown username, wrong password, disabled user, and the name of a service account (AuthUser.isServiceAccount() true, passwordHash null) with any password all -> the same 401 status and the same body code invalid_credentials [INFERRED:med:advisory]
- [ ] AC-3: {"username":"ALICE"} with alice's password logs in the user stored as alice (NFKC plus Locale.ROOT lower-case normalization).
- [ ] AC-4: A successful login issues a device token: HEADER -> body deviceToken; COOKIE with a same-origin Origin -> naru_device cookie and no body deviceToken (FR-FLOW-002 AC-2); BOTH follows the delivery rule (cookie delivery -> naru_device and no body deviceToken, body delivery -> body deviceToken).
- [ ] AC-5: With alice's correct password (alice enabled, not throttled), a beforeLogin listener throwing new AuthRejection(403, "blocked") -> 403 JSON with code blocked and no tokens, and the listener received alice's AuthUser with passwordHash null (FR-AUTH-007 AC-5). The same listener, which records each call, is not called for a wrong password, an unknown username, a disabled user or a service-account name; each of those gets the AC-2 401 invalid_credentials, so a beforeLogin rejection never reveals that an account exists. The 403 is a failure response of an attempt that reached the hash step, so it is sent no earlier than the SEC-TOKEN-009 failure floor (SEC-TOKEN-009 statement: every failure response of an attempt).
- [ ] AC-6: Missing password field, "password": 7, or "password": "" (empty, 06 AUTH-T24 [INFERRED:med:advisory]) -> 400 BAD_REQUEST without hashing; such a request is not a login attempt under SEC-TOKEN-009, so it takes no hash slot and is not held to the 1.25T failure floor.
- [ ] AC-7: The login route is registered with methodAsync (the no-hash, no-floor 429 is owned by SEC-TOKEN-009 AC-3).

#### Requirement

POST /auth/refresh shall accept the refresh token from the JSON body in HEADER and BOTH modes or from the naru_rt cookie in COOKIE and BOTH modes (body first), rotate it within the same family, and return the new pair through the delivery rule; with API keys enabled (.apiKeys(store)), a request carrying an API-key scheme Authorization header shall be decided by the key procedure before the refresh cookie is read (a valid key -> 403 api_key_not_allowed, owned by SEC-FLOW-003 AC-5; a wrong key -> 401 invalid_api_key, owned by SEC-APIKEY-004 AC-2), and naru_rt shall be neither read nor rotated for it; without .apiKeys(store) such a header is no credential (IR-TOKEN-001 AC-5) and the request is decided by its refresh token alone.

### SEC-FLOW-011 — Login throttling keys, limits and enumeration-resistant 429

| Field | Value |
| --- | --- |
| Type | security |
| Target | 0.11.0 |
| Status | implemented |
| Priority | high |
| Tags | 0.11.0, auth-rbac, feasibility:high, abuse |
| Risk | medium |

#### Requirement

Password login shall be limited by three keys computed over the normalized login name, counted identically for unknown names: (user, IP) 5 failures per 15 minutes, IP 20 failures per 15 minutes with trusted-device requests exempt, and user-only 10 failures per 15 minutes for non-trusted-device requests only; exceeding a limit shall answer 429 too_many_attempts with Retry-After and shall never delay the response by sleeping.

#### Rationale

00 §6.3 R34 (1)(3)(5) editions 4–5 and 23 (password login only), §6.4 rows "R34 × 공격", "R34 × 기업 NAT", "R34 × 없는 이름", "R38 × R34"; §10 Q7 keeps 5/20/10 per 15 minutes as OWASP-range initial values.

#### Acceptance Criteria

- [ ] AC-1: 5 failed logins for alice from IP A within 15 minutes -> the 6th attempt from A, even with the correct password, -> 429 code too_many_attempts with a Retry-After header holding a positive number of seconds.
- [ ] AC-2: The same sequence for the unknown name nobody -> 429 at the same attempt number with the same status, code and header set.
- [ ] AC-3: 20 failures from IP A spread over different names (at most 4 per name) -> the next attempt from A without a trusted device -> 429; an attempt from A carrying a valid trusted-device token for a real user is not limited by the IP key.
- [ ] AC-4: 10 failures for admin from 10 distinct IPs within 15 minutes -> the 11th attempt from a new IP without a trusted device -> 429; the admin's trusted device from that IP is not limited by the user-only key.
- [ ] AC-5: A 429 response is written without sleeping: the handler never calls Thread.sleep (a TimeSource-driven test sees the 429 written without waiting); that a 429 runs no hash and is not held to the 1.25T floor is owned by SEC-TOKEN-009 AC-3.
- [ ] AC-6: The IP part of the key is req.remoteAddress() as resolved by C6b proxy trust, and IPv6 addresses in one /64 share a key: failures from 2001:db8::1 and 2001:db8::ffff count together.

#### Requirement

In-memory login-throttle and device-token failure counters shall be capped at a key count (JVM default 100,000, Android default 10,000) evicting the oldest key and logging one WARN when the cap is reached, file-backed deployments shall snapshot counters every 60 seconds rather than per failure while writing device-token invalidation immediately, the default storage shall follow the built-in user store type, and under MULTI_INSTANCE auth shall count every failure only through the configured app-provided LoginThrottle and DeviceTrust, keeping no node-local counter beside them, so that a store with atomic shared counting keeps N nodes from multiplying the limits.

#### Rationale

00 §6.3 R34 (6) edition 6 (P-11 memory cap), R42 editions 5–7 (K-13, P-1, Q-12: snapshot every 60 s, immediate device invalidation in file mode, atomic shared counting, which 00 sketches as a JDBC UPDATE ... SET count = count + 1 and which since the 2026-11-03 SPI-only decision is the app-provided store's job, defaults follow the user store); §6.4 row "R34 × 다중 노드".

#### Acceptance Criteria

- [ ] AC-1: With the key cap set to 3 for a test, failures for 4 distinct keys evict the oldest key and log exactly one WARN, and further evictions log no additional WARN.
- [ ] AC-2: Default cap: 100,000 keys on a JVM runtime and 10,000 keys when running on Android.
- [ ] AC-3: FileUserStore deployment: 10 failed logins within 60 seconds cause no throttle file write per failure; one snapshot is written at the next 60-second tick.
- [ ] AC-4: FileUserStore deployment: the 5th failure on one device token invalidates it and the invalidation is on disk before the next snapshot tick.
- [ ] AC-5: Default storage follows the user store: InMemoryUserStore -> in-memory counters, FileUserStore -> files in the same directory. A custom (app-provided) UserStore without an explicit throttle or device-trust store -> under SINGLE_INSTANCE in-memory counters, and this fallback contributes to the single OPS-AUTH-001 AC-6 custom-store doctor WARN that a restart logs every user out (exactly one such WARN line even when the refresh-store default also falls back); under MULTI_INSTANCE the same set-up makes build() throw AuthConfigException instead of falling back (FR-AUTH-003 AC-3; 00 R35 x R42).
- [ ] AC-6: Two Auth instances sharing one app-provided LoginThrottle (a test implementation with atomic counting over one shared backing store, standing in for the application's database; no JDBC driver): 3 failures on node A and 2 on node B for the same (user, IP) key -> the next attempt on either node -> 429.
- [ ] AC-7: Two Auth instances sharing one app-provided DeviceTrust (a test implementation over one shared backing store, standing in for the application's database; no JDBC driver): 3 failures with device token D on node A and 2 on node B -> D is invalidated, and the next attempt with D on either node is handled as a request without a device token.
- [ ] AC-8: FileUserStore deployment: the throttle snapshot file and the device-trust file each carry a format-version field, and starting with either file at an unknown version fails startup with a message naming the version and does not overwrite the file (the shared auth-file rule of REL-IAM-004 AC-7; 00 R42).

#### Research / Analysis
