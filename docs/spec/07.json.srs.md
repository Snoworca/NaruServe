## 1. Scope Overview

This scope covers JSON binding of NaruServe (issue #9, wave 5): `TypeRef` with its consumer R8/ProGuard rules, `app.jsonCodec(codec)`, `req.body(Class)` and `req.body(TypeRef)` with the media-type, syntax, size, depth, UTF-8 and polymorphism checks, the JSON `null` handling, `res.json(value)`, the Gson codec `GsonJsonCodec` in `NaruServe-gson` with its STRICT, Unsafe-free defaults and its nesting limit, and the JSON decisions recorded in `docs/api`. It holds T08 and T09.

## 2. Scope Boundaries

### In Scope

- `TypeRef`, the JSON methods of `RestApp`, `Request` and `Response` in `NaruServe-api` and their internal implementation.
- `GsonJsonCodec` in `NaruServe-gson` (`com.snoworca.naruserve.gson`).
- The (미확정) markers owned by #9 in `docs/api/json.md`, `docs/api/request.md`, `docs/api/kotlin.md` and `docs/api/defaults.md`, and the Kotlin `req.body(...)` examples of `docs/api`.

### Out of Scope

- `ws.sendJson` and `ws.onJson` themselves (wave 7); this scope only fixes that they use the configured codec.
- The Kotlin reified `Request.body()` extension of D-354 (wave 8); this scope only decides its JSON `null` handling in `docs/api`.
- Form and multipart bodies (wave 6).

## 3. Assumptions and Constraints

- Core code is engine-free code in `NaruServe-api`: it references no TinyHttpd, Servlet, Gson, SLF4J, `android.*` or Kotlin stdlib type, compiles to Java 8 bytecode and passes the wave 1 animal-sniffer API 21 checks.
- Public types follow the wave 1 conventions: nullability annotations on public signatures, `@FunctionalInterface` callbacks, Express-style short method names, getter/setter names on value objects, no Kotlin keywords as method names, and no removed or changed public signature of `RestApp`, `Request`, `Response` or the `HttpAdapter` SPI that an earlier wave added: those types gain new methods only, and new public types such as `Cookie`, `SameSite`, `TypeRef`, `ServerOptions`, `ServerSettings` and `ErrorRenderer` are additions (I-014).
- Where the design leaves a choice open, the wave decisions and the residual section of `docs/research/naruserve-v1/waves/wave-5/design.md` apply; otherwise the implementer decides under standing rule C-07, following RFC 9110 and, between equally valid options, Express behaviour.
- Source of the requirements: `docs/research/naruserve-v1/waves/wave-5/design.md`, `docs/research/naruserve-v1/waves/wave-5/excerpt.md`, `docs/research/naruserve-v1/waves/carried-into-wave-5.md` and `object.md`.

#### Requirement

The system shall provide in package `com.snoworca.naruserve` of `NaruServe-api` the public abstract class `TypeRef<T>` whose protected constructor captures the generic `java.lang.reflect.Type` argument of its anonymous subclass and exposes it through `Type getType()`, rejects a subclass without a concrete type argument, and ship consumer R8/ProGuard rules under `META-INF/proguard/` in the `NaruServe-api` jar that keep the generic signature of every `TypeRef` subclass in a minified Android build.

#### Rationale

Covers D-183, D-184 and D-421. Pitfall: R8 strips the `Signature` attribute by default, after which `getGenericSuperclass()` returns the raw class and `new TypeRef<List<User>>() {}` silently decodes into `List<Map>`; the consumer rules must keep `Signature`, `InnerClasses` and `EnclosingMethod`. The rules file is checked in the jar, not only in the source tree, because consumers see only the jar.

#### Acceptance Criteria

- [x] AC-1: `new TypeRef<List<User>>() {}.getType()` returns a `ParameterizedType` whose raw type is `java.util.List` and whose only argument is `User`, and `new TypeRef<String>() {}.getType()` returns `String.class`. [D-183; T08] Decision: `TypeRef` is a public abstract class with a protected no-argument constructor and the public method `Type getType()`.
- [x] AC-2: Constructing a raw subclass (`new TypeRef() {}`) or a subclass whose type argument is a type variable (inside `<X> TypeRef<X> make() { return new TypeRef<X>() {}; }`) throws `IllegalStateException` whose message says that a concrete type argument is required. [D-184] Decision: the exception type is `IllegalStateException`. Decision [SDS 2026-10-19.naruserve.naruserve-v1-wave-5-1 SDS-AC-1]: the message is `TypeRef needs a concrete type argument`.
- [x] AC-3: The `NaruServe-api` jar built by `./gradlew build` contains `META-INF/proguard/naruserve-api.pro` holding `-keepattributes Signature,InnerClasses,EnclosingMethod`, `-keep,allowobfuscation,allowshrinking class com.snoworca.naruserve.TypeRef` and `-keep,allowobfuscation,allowshrinking class * extends com.snoworca.naruserve.TypeRef`, which a test reads from the built jar. [D-421] Decision: the file name is `naruserve-api.pro`. Decision [SDS 2026-10-19.naruserve.naruserve-v1-wave-5-1 SDS-AC-2]: the file also holds one `-keepclassmembers` line for `com.snoworca.naruserve.Cookie` that keeps its package-private static factory `unvalidated(java.lang.String, java.lang.String)` of IR-COOKIE-001 AC-6.
- [x] AC-4: A Kotlin test compiles and runs `val t = object : TypeRef<List<String>>() {}` and finds `t.type` equal to the `List<String>` type of AC-1. [D-183; C-03; I-010]

### IR-JSON-002 — JSON API surface: app.jsonCodec, app.jsonLimit, req.body, res.json and the nullable JsonCodec.decode

#### Requirement

The system shall add to `RestApp` the methods `RestApp jsonCodec(JsonCodec codec)` and `RestApp jsonLimit(long bytes)`, to `Request` the methods `<T> @Nullable T body(Class<T> type)` and `<T> @Nullable T body(TypeRef<T> type)`, and to `Response` the method `void json(@Nullable Object value)`, and mark the return value of `JsonCodec.decode` `@Nullable`, so the codec held by the app is the single codec that `req.body`, `res.json` and the later `ws.sendJson` and `ws.onJson` use.

#### Rationale

Covers D-185, D-431, the configuration-API part of D-192 (size limit name, no `jsonTree()`/`jsonMap()`) and the wave decision "A JSON `null` decodes to `null`". Adding `@Nullable` to the return of `decode` keeps the erased signature that verified IR-APP-001 AC-4 fixes, so IR-APP-001 is not superseded (committee decision wave-5-srs-supersede). `jsonLimit` follows Express `express.json({ limit })`; rejected alternative: a limit option on `GsonJsonCodec` (the size limit is enforced on the byte stream by the core for every codec, D-088).

#### Acceptance Criteria

- [x] AC-1: `RestApp` declares `RestApp jsonCodec(JsonCodec)`; `jsonCodec(null)` throws `NullPointerException` and a call outside `NEW` throws `IllegalStateException` through the `NEW`-state guard of FR-APP-002; after `app.jsonCodec(c2)` on an app built with codec `c1`, `req.body` and `res.json` call only `c2`, and the app's internal codec accessor, which the wave 7 `ws.sendJson` and `ws.onJson` read, returns `c2`. [D-185] Decision: the app holds one codec in `DefaultRestApp`, read through an internal accessor by every JSON feature. Decision [SDS 2026-10-19.naruserve.naruserve-v1-wave-5-1 SDS-AC-3]: the codec that `req.body` and `res.json` use is read once from the internal accessor `DefaultRestApp.jsonCodec()` at the configuration freeze. User-approved revision: FR-DX-007 permits cached same-Type JSON reads, including cached null; mixed formats, mismatched types and retries after failed parsing remain rejected.
- [x] AC-2: `RestApp` declares `RestApp jsonLimit(long bytes)` under the same guard; the limit defaults to 1048576 bytes, and values below 1 or above 1073741824 throw `IllegalArgumentException`. [D-188; D-192; residual: Upper bounds on size settings] Decision: the size API is `app.jsonLimit(bytes)` with a 1 GiB maximum. Decision [SDS 2026-10-19.naruserve.naruserve-v1-wave-5-1 SDS-AC-4]: the `IllegalArgumentException` message names `jsonLimit` and the range `1..1073741824`.
- [x] AC-3: `Request` declares `<T> @Nullable T body(Class<T>)` and `<T> @Nullable T body(TypeRef<T>)`, and `Response` declares `void json(@Nullable Object)`; a reflection test checks the `@Nullable` type-use annotation on both `body` returns and on the `json` parameter. [D-431; D-193] Decision: `json` returns `void` like `send`.
- [x] AC-4: The return type of `JsonCodec.decode` carries the JSpecify `@Nullable` type-use annotation while the erased signature `<T> T decode(Reader, Type) throws IOException` and the `@Nullable` parameter of `encode` stay unchanged, and the copy of the interface shown in `docs/api/json.md` shows the same annotations. [D-431; FR-HTTP-019] User-approved revision: FR-DX-007 permits cached same-Type JSON reads, including cached null; mixed formats, mismatched types and retries after failed parsing remain rejected.

### FR-JSON-001 — req.body media-type, syntax, size, depth, UTF-8 and polymorphism checks

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-5 |
| Status | verified |
| Priority | high |
| Tags | wave-5, feasibility:high, json, security |
| Risk | high |

| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/9 |
| Related Docs | - |

#### Requirement

The system shall make `req.body(Class)` and `req.body(TypeRef)` accept only `application/json` and `application/*+json` bodies, read them as UTF-8 through the core's size-limited stream and the app codec, and raise `HttpException` with status `415` for another media type, `413` for a body over the JSON limit, and `400` with code `BAD_REQUEST` for an empty, syntactically invalid, too deeply nested, trailing-data or invalid-UTF-8 body, returning `null` for a JSON `null` body and never instantiating a class named inside the input.

#### Rationale

Covers D-186, D-187, D-188, D-189, D-190, D-191 and D-431 with the wave decision "A JSON `null` decodes to `null`" (empty body is `400`, not `null`) and the residual "Trailing JSON data" (T09 cases `{"a":1} x` and `{} {}`). Measured fact: Gson 2.14 returns `null` for empty input, so the core must detect an empty or whitespace-only body before calling the codec. Pitfall: an `IOException` from the codec means malformed input (`400`), but an `HttpException` thrown by the body stream (size `413`, adapter `408`) must pass through with its own status.

#### Acceptance Criteria

- [x] AC-1: Bodies with `Content-Type` `application/json`, `application/json; charset=utf-8`, `application/problem+json` and `APPLICATION/JSON` are decoded, while `text/plain`, `application/x-www-form-urlencoded`, `application/jsonx`, `application/json; charset=iso-8859-1` and a missing `Content-Type` make `req.body(...)` throw `UnsupportedMediaTypeException`, answered `415` with the standard error body (code `UNSUPPORTED_MEDIA_TYPE`) without calling the codec. [D-186; T09] Decision: an allowed type is `application/json` or `application/<subtype>+json`, compared case-insensitively, with no `charset` parameter or `charset=utf-8`. Decision [SDS 2026-10-19.naruserve.naruserve-v1-wave-5-1 SDS-AC-7]: the media type is checked before the codec is called or the body stream is read. Content-Type uses valid media-type token and quoted-parameter syntax; quoted delimiters in unrelated parameters are not charset declarations. Invalid syntax is rejected with415 before invoking the codec.
- [x] AC-2: The bodies `{"a":`, `[1,]`, an empty body and a body of only spaces and newlines are each answered `400` with code `BAD_REQUEST`; the empty and whitespace-only bodies never reach the codec, and an `IOException` thrown by `JsonCodec.decode` is turned into `HttpException` `400` with that exception as cause unless AC-9 applies. [D-187; T09; wave decision: A JSON `null` decodes to `null`] Decision: the core maps a codec `IOException` to `400` and lets an unchecked codec exception reach the error path as `500`.
- [x] AC-3: With the default codec, `{"a":1} x` and `{} {}` are answered `400` with code `BAD_REQUEST`. [residual: Trailing JSON data; D-187; T09]
- [x] AC-4: A body of 1048577 bytes with `Content-Length` is answered `413` with code `PAYLOAD_TOO_LARGE` before the codec reads it, and a chunked body without `Content-Length` larger than the limit, decoded through the default `GsonJsonCodec`, is answered `413` (not `400`) after at most limit + 1 bytes were taken from the exchange stream; with `app.jsonLimit(10)` an 11-byte body gives `413` and a 10-byte body is decoded. - [x] AC-5: With the default codec, an array nested 65 levels deep is answered `400` with code `BAD_REQUEST` and one nested 64 levels deep is decoded. [D-189; T09]
- [x] AC-6: A body holding the bytes `{"a":"` `0xC3 0x28` `"}` or a truncated UTF-8 sequence is answered `400` with code `BAD_REQUEST`, because the core decodes the body with a UTF-8 decoder whose malformed and unmappable actions are `REPORT`. [D-190]
- [x] AC-7: Decoding `{"@class":"<canary class>","class":"<canary class>","@type":"<canary class>"}` into `Object.class` with the default codec returns a `Map` and never initialises the canary class, whose static initializer records any loading. [D-191]

[D-186; D-187; D-188; D-219] Decision: the overrun is detected from the limited stream's state, not only from the exception the codec rethrows. Decision [SDS 2026-10-19.naruserve.naruserve-v1-wave-5-1 SDS-AC-11]: an `HttpException` found in the cause chain is rethrown unchanged (the same instance).

### FR-JSON-002 — res.json encodes through the app codec and round-trips JSON values

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-5 |
| Status | verified |
| Priority | high |
| Tags | wave-5, feasibility:high, json |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/9 |
| Related Docs | - |

#### Requirement

The system shall make `res.json(value)` encode `value` through the app codec into a buffer and then send it with `Content-Type: application/json; charset=UTF-8` and a matching `Content-Length`, so that POJOs, `List<User>`, strings, numbers, booleans and `null` round-trip unchanged through `req.body` and `res.json` and an encoding failure is handled before the response commits.

#### Rationale

Covers D-193, D-194, D-195 and the wave 4 carried case of D-136 and D-112 (`carried-into-wave-5.md`). Encoding into a buffer first means a serialisation exception always happens while the response is uncommitted, so the standard error response of FR-APP-006 replaces it and no partial JSON reaches the client; the committed case is a `res.json` call on a response that is already committed, which the error path of FR-APP-005 handles by the response state. Measured fact recorded in `docs/api/request.md`: the default Gson decodes untyped numbers as `Double`, so an untyped `Map` round-trips to JSON-value equality only.

#### Acceptance Criteria

- [x] AC-1: `res.json(value)` calls the app codec's `encode` once and sends status 200 (or the status set before) with `Content-Type: application/json; charset=UTF-8` and a `Content-Length` equal to the encoded byte count. [D-193]
- [x] AC-2: A T08 echo route `res.json(req.body(type))` returns values equal to the sent ones for a POJO `User`, a `List<User>` read through `TypeRef`, the string `"x"`, the numbers `42` and `1.5`, `true` and `null`, while `{"n":42}` read with `req.body(Map.class)` comes back as JSON equal to `{"n":42.0}`, which the test compares as JSON values. [D-194; T08]

### FR-JSON-003 — GsonJsonCodec with STRICT, Unsafe-free defaults, a nesting limit and end-of-document check

#### Requirement

The system shall provide in `NaruServe-gson` the public final class `com.snoworca.naruserve.gson.GsonJsonCodec` implementing `JsonCodec`, built with a default `Gson` configured with `Strictness.STRICT` and `disableJdkUnsafe()` or with a caller-built `Gson`, that decodes through a `JsonReader` with a nesting limit of 64 by default for every instance, requires the end of the document after the value, returns `null` for a JSON `null` document and reports malformed input as `IOException`.

#### Rationale

Covers D-196, D-197, D-198, D-199, the wave decision "The JSON depth limit lives in the Gson codec" and the residual "Trailing JSON data". Pitfalls: `Gson.fromJson(JsonReader, Type)` does not check for trailing input, so the codec must check `reader.peek() == END_DOCUMENT`; a caller-built `Gson` must not silently raise the nesting limit to Gson's 255; Gson's `JsonSyntaxException` is unchecked, so the codec converts malformed-input failures to `IOException` for the core's `400` mapping. Rejected alternative: a depth parameter on `JsonCodec.decode` (changes the frozen SPI signature of D-182).

#### Acceptance Criteria

- [x] AC-1: `GsonJsonCodec` is public, final and implements `JsonCodec` with the public constructors `GsonJsonCodec()`, `GsonJsonCodec(Gson)` and `GsonJsonCodec(Gson, int maxDepth)` and the public static method `Gson defaultGson()`; a `null` `Gson` throws `NullPointerException` and a `maxDepth` below 1 or above 255 throws `IllegalArgumentException`. [D-196; wave decision: The JSON depth limit lives in the Gson codec] Decision: the depth setting is the constructor argument `maxDepth`, and `GsonJsonCodec()` uses `defaultGson()`. Decision [SDS 2026-10-19.naruserve.naruserve-v1-wave-5-2 SDS-AC-1]: the `IllegalArgumentException` message names `maxDepth`, and both exceptions are thrown before the instance keeps any state.
- [x] AC-2: `defaultGson()` returns a `Gson` built with `Strictness.STRICT` and `disableJdkUnsafe()`: decoding `{a:1}`, `{'a':1}` and `{"a":1 /* c */}` with `new GsonJsonCodec()` throws `IOException`, and through `req.body` each is answered `400`. [D-197; D-198]
- [x] AC-3: Decoding `{}` with `new GsonJsonCodec()` into a class whose only constructor takes arguments throws an unchecked exception and creates no instance, and through `req.body` the request is answered `500`. [D-199] Decision: a codec failure that is not malformed input stays unchecked and gives `500`, because it is a server-side type error. Decision [SDS 2026-10-19.naruserve.naruserve-v1-wave-5-2 SDS-AC-3]: the unchecked exception is Gson's `JsonIOException`, propagated without wrapping.

#### Requirement

The system shall record in `docs/api/json.md`, `docs/api/request.md`, `docs/api/kotlin.md` and `docs/api/defaults.md` the wave 5 JSON decisions — the size and depth configuration API, the absence of `jsonTree()`/`jsonMap()`, the JSON `null` handling of `req.body` and of the Kotlin reified extension of D-354 — each with its reason, rewrite every Kotlin `req.body(...)` example of `docs/api` for the nullable return, and remove the (미확정) markers these decisions settle.

#### Rationale

Covers D-192 (documentation half), D-440, I-008, I-009 and I-013 for issue #9. Decision on the D-354 extension: it keeps its frozen non-null signature `inline fun <reified T : Any> Request.body(): T` and throws `HttpException` `400` for a JSON `null` body, because a caller who asks for a non-null value treats a `null` body as a client error; rejected alternative: changing the extension to return `T?` (contradicts frozen D-354; reopen only if wave 8 changes D-354).

#### Acceptance Criteria

- [x] AC-1: `docs/api/json.md` names `app.jsonLimit(bytes)` (default 1 MiB, at most 1 GiB) and `new GsonJsonCodec(gson, maxDepth)` (default 64, at most 255, kept also for a caller-built `Gson`), states that trailing data after the value and an empty body are answered `400`, and its limit section has no (미확정) marker; the JSON rows of `docs/api/defaults.md` name the same APIs without markers. [D-192; I-013]
- [x] AC-2: `docs/api/request.md` states that `req.body(...)` returns `null` for a JSON `null` body, that `415`, `400` and `413` are its failure statuses, and that v1 has no `jsonTree()`/`jsonMap()` (use `req.body(Map.class)`) with its reason, and the `jsonTree()`/`jsonMap()` marker is gone. [D-192; D-431]
- [x] AC-3: In `docs/api/kotlin.md` the nullability table row `req.body(type)` reads `T?` without a marker, the `val users: List<User>` example and the `val body = req.body(CreateUserRequest::class.java)` example followed by `body.name` use a nullable type with safe-call syntax or the reified extension, and the extension shown reads `inline fun <reified T : Any> Request.body(): T = body(T::class.java) ?: throw HttpException(400, "JSON body is null")` with a sentence on the JSON `null` decision. [D-440; D-192] Decision: the reified extension of D-354 throws `HttpException` `400` for a JSON `null` body.
- [x] AC-4: The `val user = req.body(User::class.java)` example of `docs/api/README.md` and the `val todo = req.body(Todo::class.java)` example of `docs/api/express-migration.md` no longer pass a possibly-null value to a non-null parameter: each uses safe-call or elvis syntax or the reified extension. [D-440]
- [x] AC-5: A Kotlin test in `NaruServe-api` compiles and runs each rewritten `req.body(...)` example of AC-3 and AC-4 against the wave 5 API, declaring the example types (`User`, `CreateUserRequest`, `Todo`) and, for examples that call `req.body<T>()`, a test-local copy of the extension shown in AC-3 (the module extension of D-354 arrives in wave 8). [D-440; D-349; D-351; I-009; OPS-APP-002] Decision: the docs compile test keeps its fixed imports, so Gson-using blocks stay skipped with the Gson reason; the root test classpath may gain `project(':NaruServe-gson')` for the defaults test of OPS-ENGINE-001 AC-6.
