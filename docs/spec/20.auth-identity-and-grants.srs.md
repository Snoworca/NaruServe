# Auth Identity and Grants

| Field | Value |
|---|---|
| Document Type | scope_srs |

## 1. Scope Overview

This scope covers who a user is and what a user may do inside the `com.snoworca.naruserve.utils.auth` package of `NaruServe-api` (target 0.11.0, auth/RBAC v1). It fixes the `AuthUser` value class, the `UserStore` SPI with its atomic partial-write contract, the built-in in-memory and file stores with the `AtomicFiles` protocol, the `ForwardingUserStore` decorator base, the app facade `AuthUsers` (`auth.users()`), the opaque login identifier, groups (`GroupStore`, `GroupAdminStore`, DAG expansion and limits), roles and scopes (`RoleStore`, `RolePolicy`, `Scopes`), the single grant rule "you can only grant what you have" with target protection and the recovery path, revocation by `ver`, and the store SPIs (user, group, refresh token, login throttle, device trust) that an application implements to connect its own database; no built-in database store is shipped (34판, 2026-11-03: built-in JDBC stores removed; persistence is SPI-only, CON-IAM-003). The source of truth is `docs/research/auth-rbac/00.overview.md` (edition 33).

## 2. Scope Boundaries

### In Scope

- `AuthUser`, `UserStore` (five required methods, five default field methods, the default listing method `list(offset, limit, search)` with `UserPage`, `supportsAtomicFieldWrites()`), `InMemoryUserStore`, `FileUserStore`, `ForwardingUserStore`, `DuplicateUserException`, `AuthTesting.verifyUserStore`.
- `AuthUsers` facade, `UserMutator`, `rename`, `checkPassword`, and username normalization (NFKC + `Locale.ROOT` lower-case) as the only login-identifier handling.
- `AtomicFiles` write and start-up recovery for auth's own files.
- `GroupStore`, `GroupAdminStore`, `InMemoryGroupStore`, `FileGroupStore`, `GroupLimits`, group expansion, user-delete ordering.
- Scope grammar and covering, `RolePolicy`, built-in `admin` role, `RoleStore`, effective role and scope resolution.
- Grant rule R31 (1)–(5), group-delete and edge-removal limits, the user-state outcome of recovery R31 (6), revocation by `ver` (R44).
- The admin endpoint table of `auth.adminRoutes()` (A1–A6, G1–G8 and the lockout endpoint) with its R39 scope guard and the A4 admin PATCH rules.
- The atomicity declarations an app-provided store makes for MULTI_INSTANCE (supportsAtomicFieldWrites, usesLimitArguments) and the docs/api guide for connecting an application database (34판, 2026-11-03: built-in JDBC stores removed; persistence is SPI-only, CON-IAM-003).
- Kotlin compile-and-run coverage of the public API in this scope.

### Out of Scope

- Group role assignment `PUT /auth/admin/groups/:id/roles` (05 G9) — v2.
- SCIM provisioning (`utils.auth.scim`) — v3.
- Personal-data export and deletion endpoints — v2.
- Any email, phone or alternate login-key API: the login identifier is one opaque `username` string and the store decides lookup and uniqueness (R37, edition 20).
- API keys, `ApiKeyStore` and its contract test (APIKEY scope).
- HTTP endpoint tables for `/auth/*` (account endpoints), CSRF, transport and abuse-protection policy (FLOW scope); tokens, hashers and `RefreshTokenStore` SPI (TOKEN scope); builder, install, events, principal cache, doctor and bootstrap seeding (AUTH scope).

## 3. Assumptions and Constraints

- Code lives in `NaruServe-api` under `com.snoworca.naruserve.utils.auth` and uses only Core public API, the JDK and API 21 `android.jar` classes; no new main dependency (cross-cutting rules owned by the AUTH scope).
- No `java.time`, `java.util.Base64`, `java.nio.file` or `java.util.function` in public signatures; callbacks are own `@FunctionalInterface` types.
- NaruServe-api ships no database store and references neither `java.sql` nor `javax.sql`; no JDBC driver is used in any configuration, tests included. Multi-instance store behaviour is checked with test stores that implement the SPIs the way an application would (34판, 2026-11-03: built-in JDBC stores removed; persistence is SPI-only, CON-IAM-003).
- All type and method names are proposals from 00 unless marked confirmed; names marked "(name not final)" are settled during implementation.
- Values taken from research files 01–07 that 00 does not restate are marked `[INFERRED:med:advisory]`.

#### Rationale

#### Acceptance Criteria

- [x] AC-1: AuthUser exposes getId() as String (null only before create), getUsername(), @Nullable getPasswordHash(), the ver getter (name not final), isEnabled(), getRoles(), getAttributes() and isServiceAccount(); collections returned are unmodifiable and a Kotlin test reads them as properties (user.username, user.isEnabled, user.isServiceAccount).
- [x] AC-2: AuthUser has no direct-scope field or accessor in v1; reflection over the class finds no scopes getter and scopes reach a user only through roles.
- [x] AC-3: The passwordHash field is declared transient: serializing an AuthUser with a non-null hash through new GsonJsonCodec() (default Gson) yields JSON without a passwordHash member.
- [x] AC-4: toBuilder() on an AuthUser returns a builder whose build() is equal to the original; changing one attribute through toBuilder() leaves the original instance unchanged.
- [x] AC-5: AuthUser.toString() does not contain the passwordHash value. [INFERRED:med:advisory]
- [x] AC-6: Building an AuthUser without a username throws IllegalStateException. [INFERRED:med:advisory]
- [x] AC-7: The AuthUser and auth.userStore() Javadoc and docs/api state that the transient passwordHash is omitted only by default-modifier Gson, and that with a Gson built with excludeFieldsWithModifiers(STATIC) or another JsonCodec the app must remove passwordHash itself (docs test asserts the sentence).
- [x] AC-8: utils.auth.user.AuthIds offers parseLong(String) and parseUuid(String) (00 §4.3) for mapping numeric and UUID store keys to and from AuthUser's String id: AuthIds.parseLong("7") returns 7, AuthIds.parseUuid of a lower-case canonical UUID string returns that UUID; a non-parsing id such as "abc" returns null (so a store adapter's findById answers null and the request gets 404, not 500), and "007", "+7" and " 7" are rejected with null; exact signatures and a parseInt variant not final. ### REL-IAM-001 — SINGLE_INSTANCE default field-method algorithm under a per-user lock

| Field | Value |
| --- | --- |
| Type | reliability |
| Target | 0.11.0 |
| Status | verified |
| Priority | high |
| Tags | 0.11.0, auth-rbac, feasibility:high, iam-user |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | docs/research/auth-rbac/00.overview.md |

#### Requirement

Under SINGLE_INSTANCE the default field methods and every auth-originated user write shall run inside one and the same per-user-id lock (00 R37: auth's user writes run in '같은 락', the lock of the default field methods), which a thread that already holds it can acquire again (re-entrant), so that a default field method that auth calls while holding that user's lock, for example inside the REL-APIKEY-003 key owner lock taken under it (00 R47 (2) one-way lock order), neither blocks nor takes a second user lock; each such write runs as lock, findById re-read, expectation compare, update of a copy with only that method's field changed (changePassword: the hash and ver together), and re-read to confirm, retrying unconfirmed setEnabled, bumpTokenVersion and setRoles writes up to 3 times before throwing an AuthUnavailableException with code security_write_conflict (IR-AUTH-003 AC-6), which the auth error layers answer as 503 security_write_conflict (FR-AUTH-006 AC-3, IR-AUTH-002 AC-1; the A4 handler answers it itself, FR-IAM-014), with one audit event that auth emits on its auth-router call path through the builder's AuditSink (the store default holds no AuditSink and emits none), while only the rehash write is silently skipped (the default updatePasswordHash never throws security_write_conflict); auth's rehash path shall compare the login-time passwordHash, ver, enabled and roles with the row re-read inside the lock before calling updatePasswordHash, whose default compares only expectedOldHash.

#### Rationale

00 R37 (SINGLE_INSTANCE junior default; 10판 default order; 5판 K-4 security writes are never skipped; 8판 S-6/9판 T-2 updatePasswordHash boolean rehash-only), §6.4 rows "R37 × 동시 비활성화", "R37 × 프로필 수정과 전체 로그아웃", "R37 × 관리자 비활성화", "R37 × 단일 노드 사용자 정의 store".

#### Acceptance Criteria

- [x] AC-1: With a store implementing only the five required methods, setEnabled(id, false) calls findById, then update with a copy whose only change is enabled, then findById again; the resulting row keeps the passwordHash, roles and attributes it had before.
- [x] AC-2: A test store whose update() silently does not apply the change makes setEnabled, bumpTokenVersion and setRoles call update exactly 4 times (first try plus 3 retries) and then throw an AuthUnavailableException whose code is security_write_conflict (IR-AUTH-003 AC-6). On the HTTP path through the auth routers (for example logout ?all=true and A4) the answer is 503 with body code security_write_conflict (FR-AUTH-006 AC-3; for A4 the A4 handler's own answer, FR-IAM-014 AC-6), and on that path auth emits exactly one audit event security_write_conflict to the builder's AuditSink (FR-AUTH-009 AC-2). - Ground truth: the admin scope prefix is auth-users / auth-groups / auth-apikeys (00 R46); 05's auth:users:read and adminScopePrefix option are superseded.
- Pitfall: a key actor's * scope never covers auth-* (SEC-APIKEY-009); the guard must use the same covering predicate (FR-IAM-009) so a * key gets 403 on every admin endpoint.
- Open: whether an R39 guard denial (as opposed to an R31 denial) emits an audit event is not stated in 00; left out of the ACs.
- Rejected: per-endpoint custom scopes (e.g. auth-users:delete); 00 keeps read/write only. Reopen only if a delegated role needs delete without modify.

#### Implementation Notes

- Guards are built into the adminRoutes() router (one guard per route, not a detachable app middleware) and reuse the IR-AUTH-004 guard path and the FR-IAM-009 covering predicate.
- Admin API-key routes use auth-apikeys:read / auth-apikeys:write under the same rule; their handler order is FR-APIKEY-004.
- Bound by CON-AUTH-001..004.
- [2026-10-31] For a key actor the step-10 endpoint restriction of SEC-APIKEY-008 (403 api_key_not_allowed) answers before this R39 guard (403 insufficient_scope): 00 R47 (2) 26th edition puts step 10 before step 11 and the earlier step answers (SEC-APIKEY-004 AC-10).

### SEC-IAM-008 — Secret values in auth files stored as enc(...) with AES-256-GCM under an app-supplied master key

#### Requirement

When an auth file store writes a secret value (the passwordHash of each FileUserStore users-file record and the signing key written by KeySources.fromFile) while a master key (AuthFileKey, name not final) is configured, the store shall write the value as enc(<payload>), where payload is unpadded base64url of a 1-byte format version (1), a random 96-bit IV, the AES-256-GCM ciphertext and its 128-bit tag, computed with javax.crypto only under a key derived per purpose from the master key by HMAC-SHA256 over a purpose label and with the purpose and record identity as additional authenticated data; and when a stored enc(...) value does not authenticate or decode (tampered, wrong key, unknown version, malformed), the store shall refuse to load the file instead of treating the value as a wrong password, and shall never log or write the master key or a derived key.

#### Rationale

#### Research / Analysis

- Inventory of auth file stores (code read 2026-11-03). Encrypted: FileUserStore users file field passwordHash (a credential hash: offline cracking target) and the KeySources.fromFile key file (raw HS256 signing key: token forgery). Left plain, by design: FileRefreshTokenStore tokenHash (SHA-256 of a 256-bit random refresh token; it can be neither reversed nor presented), FileLoginThrottle keys (SHA-256 identifiers of user and IP plus failure times; counters, not credentials), FileDeviceTrust tokenId and counters (identifiers of a signed device token; forging one needs the signing key), FileGroupStore (no secret), and the users-file fields id, username, ver, enabled, roles, serviceAccount (identifiers and state). attributes are application-defined (app semantics stay with the app); docs/api tells apps not to put secrets there.
- Design: per-purpose key = HMAC-SHA256(masterKey, "naru-auth-file/v1/" + purpose) (purpose labels such as users.passwordHash and signing-key, names not final); AAD = purpose plus record identity (user id for passwordHash, the file name for the key file) so values cannot be swapped between records or purposes. The version byte leaves room for a later rotation format; rotation itself is not part of this requirement (FR companion).
- Pitfall: an older NaruServe reading enc(...) as a hash would treat every login as a wrong password; the companion FR raises the users-file format version when enc values are written so older readers fail closed on the unknown version (REL-IAM-004 AC-7).

#### Implementation Notes

- Proposed: internal utils.auth.internal.SecretBox (name not final) for seal/open; public utils.auth.AuthFileKey. GCM with a random IV per write; never reuse an IV under one derived key (random 96-bit IVs keep the collision risk negligible at auth-file write volumes). Wipe derived key byte arrays after use where practical.

#### Requirement
