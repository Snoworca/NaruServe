## 1. Scope Overview

This scope covers the release preparation of NaruServe (epic #20, wave 8; issue #18 and the release items of the epic; issue #17 is closed by the user's decision): the CycloneDX SBOM, the dependency vulnerability scan and its release block, the license report and third-party license file, publishing to `mavenLocal`, the repository README, the cleanup of the `(미확정)` markers of `docs/api`, the release test results document and the release documentation (platform matrix, TinyHttpd for consumers, TLS/WSS post-v1, the Android scope statement and the recorded deviations).

## 2. Scope Boundaries

### In Scope

- The SBOM and vulnerability-scan Gradle wiring that is applied only for `-Prelease`, the release block rule and the license check (D-375, D-376, D-377, D-378).
- `maven-publish` for the published modules to `mavenLocal` (wave decision Publishing; D-383).
- The root `README.md`, the marker cleanup of `docs/api` and the release documents under `docs/release` (D-379, D-380, D-381, D-382, D-383, D-434).
- The listing of T01 to T50 with the status `out-of-v1-scope` for the Android tests (carried line, wave decisions r1 W1-001 and r2 W2-005).

### Out of Scope

- The Android sample build and the API 21 device or emulator verification, including T10, T12, T47 and the Android device parts of T26 and T49 (D-364 to D-374, D-412): out of v1 scope by user decision of 2026-10-20, so the release documents list them as `out-of-v1-scope`, not as manual-pending.
- Publishing to a remote repository: v1 publishes to `mavenLocal` only.
- Publishing TinyHttpd: its checkout is read-only (I-006) and has no publishing configuration here.
- A TLS listener on the TinyHttpd adapter: a post-v1 item (D-434).

## 3. Assumptions and Constraints

- A default `./gradlew build`, online or offline, never resolves the CycloneDX or vulnerability-scan plugins; they apply only when the Gradle property `-Prelease` is set and are not wired into `check` or `build` (wave decision r4 W2-004, I-019).
- Android 5.0 (API 21) compatibility rests on `--release 8` and the animal-sniffer `android-api-level-21` check of the seven API 21 modules, unchanged from wave 1, and on the rule that no module has a compile-time `android.*` reference (D-385).
- The type prefix `REL` (reliability) equals this scope's prefix, so this scope has no `reliability` requirement (the SRS rules exclude the pair).
- Source of the requirements: `docs/research/naruserve-v1/waves/wave-8/design.md` (frozen design items, wave decisions of loop W rounds 1 to 5, residual), `docs/research/naruserve-v1/waves/wave-8/excerpt.md`, `docs/research/naruserve-v1/waves/carried-into-wave-8.md` and `object.md`.

#### Requirement

The release build shall generate a CycloneDX SBOM for each of the nine published modules when run with `./gradlew -Prelease releaseSbom`, through the CycloneDX Gradle plugin that the root `build.gradle` applies only inside `if (project.hasProperty('release'))` by `apply from: 'gradle/release.gradle'`, so that a default `./gradlew build`, online or offline, never resolves the plugin and no release task is wired into `check` or `build`.

#### Rationale

Covers D-375, wave decision Release plugins (r4 W2-004), I-019 and T50. Measured (2026-10-20): the nine published modules are the entries of `naruModules` in `build.gradle:11-12`; the Gradle plugin portal metadata lists `org.cyclonedx:cyclonedx-gradle-plugin` up to 3.5.1 and the network was reachable; `build.gradle` has a `plugins {}` block with `ru.vyarus.animalsniffer` and the Kotlin plugin `apply false`. Decision: the plugin is applied from `gradle/release.gradle`, a script plugin with its own `buildscript {}` block, because a `plugins {}` block cannot be conditional and resolves its plugin even with `apply false`; `gradle/release.gradle` is not a module build file, so CON-BUILD-017 AC-2 (no `build.gradle` in a module directory) holds; CON-BUILD-003 AC-1 (the root `build.gradle` holds every module's configuration) would read false once release tasks live in the applied script, so wave 8 supersedes CON-BUILD-003 with CON-BUILD-017, whose AC-1 states the one exception, and the line of `CLAUDE.md` that says the root `build.gradle` configures all modules gets the same exception sentence. The plugin version is an exact literal pinned when the file is written (not a dynamic range); the SBOM files go to `build/reports/naruserve/sbom/<module>.cdx.json`; the lifecycle task names are `releaseSbom`, `releaseScan`, `releaseLicenses` and `releaseCheck`. Pitfall: `BuildLayoutTest` reads `build.gradle` for pinned strings (`'java-library'`, `options.release = 8`, the class-reference prefixes), so the conditional apply is added without touching them. Measured by prototype (2026-10-20, feasibility run): applying the CycloneDX plugin by id from a subproject failed while applying it by class (`org.cyclonedx.gradle.CyclonedxPlugin`) from the script plugin wrote nine SBOMs including the TinyHttpd components. Rejected alternative: a `buildscript { classpath }` in the root file; it resolves the plugin on every build, including offline.

### FR-REL-002 — Dependency vulnerability scan with a pending record that keeps the full dependency list

| Field | Value |
| --- | --- |
| Type | functional |

| Tags | wave-8, feasibility:high, release, vulnerability, T50 |

#### Requirement

The release build shall run `./gradlew -Prelease releaseScan`, an OWASP Dependency-Check scan, run in a child Gradle invocation whose exit value is ignored, of the runtime dependencies of the published modules, and write `build/reports/naruserve/vulnerability-scan.md` with the status `completed` and the findings, or, whenever the scanner cannot finish — no network, a missing NVD API key, a rate limit or a tool error — with the status `pending`, the failure reason and the full dependency list (`group:name:version`, one line each, sorted, without duplicates), without failing the build for that reason.

#### Rationale

Covers D-376, wave decision Release scan and result rows (r3 W2-005: pending for any reason the scanner cannot finish) and T50; the block on findings is FR-REL-003. Measured (2026-10-20): the Gradle plugin portal lists `org.owasp:dependency-check-gradle` up to 13.0.0; the network was reachable but a scan without an NVD API key is rate-limited and can fail partway; the shipped runtime dependencies are Gson 2.14.0 with `com.google.errorprone:error_prone_annotations:2.48.0`, `kotlin-stdlib` 2.2.0 with `org.jetbrains:annotations:13.0`, `slf4j-api` 1.7.36 and the TinyHttpd components, as `build/reports/naruserve/dependency-graphs.txt` lists them per module and configuration. Decision: the pure parts — the report writer, the pending decision and the dependency-list derivation — are plain Java 8 sources in `gradle/release-tools` (package `com.snoworca.naruserve.release`), which the root `test` source set adds as a source directory (so the unit tests compile in the default build) and which `gradle/release.gradle` compiles with its own `JavaCompile` task and runs with `JavaExec` tasks, so the script never needs compiled classes at configuration time, so the default build can test them without any plugin or network. Decision: the committed record of the release run is `docs/release/vulnerability-scan.md`, copied from the build report; the scan covers the `runtimeClasspath` of the nine published modules and excludes test scope (Jetty 9.4 of the Servlet tests); the scanner's own failure is caught by a wrapper task that writes the pending report. Measured by prototype (2026-10-20, feasibility run): Dependency-Check 13.0.0 aborts with "Analysis failed" even with `failOnError=false`, so a failure inside the same build cannot be turned into a record; `releaseScan` therefore runs the scan in a child Gradle invocation with `ignoreExitValue` and writes `pending` on a non-zero exit or a missing report. Pitfall: Dependency-Check fails the build on an update error by default; the wrapper converts that into `pending`, otherwise an offline release machine could not record anything. Rejected alternative: treating a pending scan as a pass; the record says `pending`, T50 stays `manual-pending` for this part and I-020 forbids promoting a requirement on a pending check.

#### Acceptance Criteria

- [ ] AC-1: With the scanner stubbed to fail for each of four causes — no network, a missing NVD API key, a rate limit and a tool error — the report writer in `gradle/release-tools` produces a report whose status line is `pending`, whose reason line names the cause, and whose dependency list equals the sorted union of the `group:name:version` of the `runtimeClasspath` entries of the nine published modules in `dependency-graphs.txt` without the project's own `com.snoworca.naruserve:*` components and with the `com.snoworca.tinyhttpd` components kept, which a default-build test over the writer asserts without network. - [ ] AC-3: `docs/release/vulnerability-scan.md` exists and holds the report of the release run (`pending` with the reason, or `completed`), and the T50 vulnerability line of `docs/release/test-results.md` is `manual-pending` when the report is `pending` and `verified` when it is `completed` on the release machine, which a docs test compares. [D-376; D-381]
- [ ] AC-4: The report's dependency list excludes `compileOnly` and test-scope artifacts (the Servlet API, JSpecify, JUnit, Jetty) and includes the TinyHttpd components. [D-376]
- [ ] AC-5: `releaseScan` runs the scanner in a child Gradle invocation with `ignoreExitValue` and writes the `pending` report when that invocation exits non-zero or leaves no report file, which the report writer's test covers with a stub exit code. [D-376; r3 W2-005]

### FR-REL-003 — Release is blocked by an unexcepted High or Critical dependency vulnerability

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-8 |
| Status | verified |
| Priority | medium |
| Tags | wave-8, feasibility:high, release, vulnerability, T50 |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/18 |
| Related Docs | - |

#### Requirement

The release build shall define `releaseCheck` as a task that depends on `releaseScan` and `releaseLicenses` and reads the report that run wrote (`releaseSbom` runs separately), and shall fail `./gradlew -Prelease releaseCheck` while the vulnerability report shows a High or Critical finding (CVSS 7.0 or higher) for a runtime dependency of a published module that has no recorded exception in `docs/release/vulnerability-exceptions.md`, where an exception names the vulnerability id, the dependency, the reason, the approver and the date; a `pending` scan does not block the build but is shown as pending, never as passed.

#### Rationale

#### Requirement

The release build shall run `./gradlew -Prelease releaseLicenses`, which resolves the license of every dependency on the `runtimeClasspath` of the published modules, fails when any has a GPL-family license (GPL, LGPL or AGPL) or none that can be determined, and writes `THIRD-PARTY-LICENSES.md` at the repository root listing each shipped dependency as `group:name:version` with its license name and URL, and a default-build test shall fail when that file does not list exactly those dependencies.

#### Rationale

Covers D-378 and T50. Measured (2026-10-20): the root `LICENSE` and `/Users/beom/work/git/TinyHttpd/LICENSE` both open "BSD 3-Clause License"; Gson, `com.google.errorprone:error_prone_annotations:2.48.0` (Gson's transitive dependency), `kotlin-stdlib` and `org.jetbrains:annotations:13.0` are Apache-2.0 and `slf4j-api` 1.7.36 is MIT by their POMs; `javax.servlet-api` 3.1.0 (CDDL with GPLv2 classpath exception) is `compileOnly` and therefore provided by the container, not shipped; `build.gradle` already writes the resolved graphs to `build/reports/naruserve/dependency-graphs.txt` (`checkDependencyRules`). Decision: licenses come from the POMs through an artifact resolution query; the TinyHttpd components come from an override table in `gradle/release.gradle` with the source `TinyHttpd/LICENSE` (the included build has no POM); a component with no license information and no override fails the task; the file also lists the compile-only artifacts under "provided by the container or the build, not shipped" with their licenses so the CDDL/GPL entry is explicit. Pitfall: the `slf4j-api` 1.7.36 POM has no `<licenses>` element; its MIT license is declared in the parent POM, so the resolution walks the parent POM chain before it reports a missing license. Pitfall: a dependency whose POM states two licenses (dual license) passes when at least one is non-GPL and the file lists both. Rejected alternative: a name-based allowlist of group ids; a new transitive dependency would pass unseen.

#### Rationale

#### Requirement

The release documentation and `docs/api/lifecycle.md` shall state that the Android sample build and the API 21 device or emulator verification are not part of v1 (user decision of 2026-10-20; issue #17 is closed by it and has no remaining deliverable), that the Android-only `ServerService` example is documented but not compiled in the v1 build, and shall list the recorded deviations from frozen design wording — D-408 over TinyHttpd, D-416 thread total 452, D-406 handler-thread writes, D-323 handshake bound, D-340 late-session abort, D-106 add-only SPI, the Servlet SSE blocked-write bound and the D-380 three-row exception — each with the requirement that records it.

#### Rationale

Covers the carried lines of `waves/carried-into-wave-8.md`, wave decisions Examples and Gson without the sample (r1 W1-002, W2-002: the `ServerService` example stays documented and the root docs test skips it with the reason "absent type `android.app.Service`"), Release documentation statement (r1 W1-005), Blocked writes of a Servlet SSE stream (r5 W2-001), D-364 to D-374 and D-412 (not authored), I-001, I-005, I-009 and I-020. Measured (2026-10-20): `DocsExamplesCompileTest.java:98` already skips `lifecycle.md` "public class ServerService extends Service {" with the reason "absent type `android.app.Service`"; `lifecycle.md:191` holds the example. Recorded deviations and their records: D-408 (`Connection: Upgrade` not asserted over TinyHttpd, FR-WS-004 AC-2); D-416 (452 threads because of the non-daemon `naruserve-keeper`, PERF-APP-001 AC-2); D-406 (handler-thread sends are written directly before the drain starts, FR-SSE-002 AC-5); D-323 (the handshake is bounded only by `headerTimeout` and `bodyReadTimeout`, FR-WS-008 AC-7); D-340 (a session opening after the close wait is aborted without a close frame, FR-WS-010 AC-7); D-106 (the SPI gained add-only types and default methods, IR-HTTP-007 AC-4); the Servlet SSE bound (FR-SVL-006 AC-3); D-380 (OPS-REL-002 AC-1). Wave 8 authors no requirement for the Android sample items, so no requirement covers or may call verified T10, T12 or T47. Rejected alternative: leaving the deviations in the requirement blocks only; the release reader would not find them.
