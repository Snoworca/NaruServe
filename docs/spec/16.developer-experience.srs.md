### FR-DX-012 — RestApp.start 정적 진입점: create, 설정 람다, listen을 한 호출로

| Field | Value |
| --- | --- |
| Type | functional |
| Target | start-api |
| Status | verified |
| Priority | high |
| Tags | - |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | docs/research/start-api/00-recommendation.md |

#### Requirement

The system shall provide the static interface method `ServerHandle start(int port, Configurer<RestApp> routes)` on `RestApp` that calls `RestApp.create()`, runs `routes` with the new app while it is still `NEW`, calls `app.listen(port)` and returns the resulting `ServerHandle` without blocking, so that `RestApp.start(3000, app -> app.get("/hello", (req, res) -> res.send("Hello World")))` is a complete server in one statement, and shall leave every rule of `listen` (default bind `127.0.0.1`, non-loopback warning, Host allowlist and the exception types) unchanged.

#### Rationale

Spring Boot's SpringApplication.run(Class) scans classes, which NaruServe rejects (no auto scan, Android). Only the shape "one static call" is adopted. Rejected alternatives (docs/research/start-api/00-recommendation.md): a port-less overload, a PORT environment variable or system property (hidden input sources; the default port is 3000 in README but 8080 in object.md), the start(Class) scan form, an instance app.start (two names beside listen), a blocking run (no handle, ANR on Android; the non-daemon keeper thread of FR-ENGINE-006 already holds the JVM), startAsync, AutoCloseable and await() (out of v1 scope). LAN exposure stays explicit inside the lambda: app.server(o -> o.bindAddress("0.0.0.0")). The method lives in the Core RestApp interface because create() already crosses the engine boundary through ServiceLoader, so no engine, Gson, android or servlet type is referenced.

#### Acceptance Criteria

#### Requirement

The system shall extend the interface `ServerHandle` with `String url()` and `void shutdown(long timeout, TimeUnit unit)`, so that the caller of `RestApp.start`, who never sees the `RestApp`, can read the address to open and stop the server; `url()` shall be `http://<address>:<port>` with the actual bound port, `localhost` in place of a wildcard bind address and brackets around an IPv6 literal, and `shutdown` shall follow the contract of `RestApp.shutdown(long, TimeUnit)` by delegating to the handle's own app.

#### Rationale

Names are decided during implementation (they were absent from object.md): url() and shutdown(long, TimeUnit), the latter named like RestApp.shutdown so one contract serves both. A 5-second default shutdown, close() and AutoCloseable are not added: try (ServerHandle h = start(...)) on a long-lived server would stop it at the end of the block. Returning RestApp from start was rejected because the app is already RUNNING and every setter would throw IllegalStateException, and it would break FR-APP-002 AC-5 and FR-HTTP-008 AC-6. This requirement changes IR-APP-005 AC-3 (ServerHandle declared exactly port(), address() and state()).

#### Acceptance Criteria

- [x] AC-1: Reflection finds `ServerHandle` declaring exactly `int port()`, `String address()`, `AppState state()`, `String url()` and `void shutdown(long, TimeUnit)`, no other public method, and no `@Nullable` position; the handle of `listen` and the handle of `start` both implement all five.
- [x] AC-2: `url()` returns `http://127.0.0.1:<port>` for the default bind, with `<port>` the bound port also after `listen(0)`; `http://localhost:<port>` when the bind address is `0.0.0.0`, `::`, `::0` or `0:0:0:0:0:0:0:0`; `http://<address>:<port>` for another IPv4 address or host name; and `http://[<address>]:<port>` for an IPv6 literal, with a zone id written `%25<zone>` as RFC 6874 requires (`fe80::1%en0` gives `http://[fe80::1%25en0]:<port>`), asserted for each form.
- [x] AC-3: `handle.shutdown(timeout, unit)` on a `RUNNING` app runs the `onStop` callbacks once and leaves `state()` as `TERMINATED` with the port closed; calling it again, after `RestApp.shutdown`, or from several threads returns without error; a negative timeout throws `IllegalArgumentException` and a `null` unit throws `NullPointerException`, as `RestApp.shutdown` does.

### FR-DX-014 — start의 시작 로그 한 줄과 JVM 한정 shutdown hook 등록·제거

| Field | Value |
| --- | --- |
| Type | functional |
| Target | start-api |
| Status | verified |
| Priority | high |
| Tags | - |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | docs/research/start-api/00-recommendation.md |

#### Requirement

The system shall make `RestApp.start`, and only `start`, write one INFO line `Listening on <url>` through the app logger after `listen` succeeded and, on a JVM but not on Android, register one JVM shutdown hook that stops the app with `app.shutdown(5, TimeUnit.SECONDS)` and remove that hook again on every path that ends the app, so that Ctrl+C or SIGTERM ends the server gracefully with `onStop` run and repeated starts in one JVM do not accumulate hooks, while `listen` itself neither logs a start line nor registers a hook.

#### Rationale

Measured before this work (docs/research/start-api/03-tinyhttpd-and-junior-dx.md scenarios 2 and 5): a plain listen prints nothing, so the terminal looks stuck, and SIGTERM cuts an in-flight request (curl exit 52) and never runs onStop. start is the convenience path and listen stays pure; the difference is a table in docs/api/app.md. The hook is not registered on Android because the OS ends the process without the JVM shutdown path (docs/api/lifecycle.md); the Android check is reflective, `Class.forName("android.util.Log")` like DefaultAppFactory.defaultLogger, because android.* may not be referenced at compile time. The hook is registered after listen succeeded, so a failed start leaves nothing to remove. Out of scope and left to follow-ups: better port-conflict message, a WARN for 421-rejected hosts, a NaruServe-kotlin extension and device verification.

#### Acceptance Criteria

- [x] AC-1: After a successful `start` the app logger receives exactly one start line at INFO that begins with `Listening on http://` followed by the real bound port (also for port `0`); for a loopback bind it is `Listening on http://127.0.0.1:<port> (this device only)`, for a wildcard bind `Listening on http://0.0.0.0:<port> - open http://localhost:<port> or http://<this-device-ip>:<port>`, for another address `Listening on http://<address>:<port>`; on a JVM the line ends with ` Press Ctrl+C to stop.` and on Android it does not.
- [x] AC-2: `listen` logs no start line: the log lines recorded for `RestApp.builder()` apps that call `listen` are the same as before this requirement (the existing log-count tests pass unchanged), and `listen` registers no shutdown hook.
- [x] AC-3: On a JVM `start` registers exactly one hook thread after `listen` returned (not before `listen`, so a failed start registers none); when the hook runs it logs one INFO line starting with `Stopping` and calls `app.shutdown(5, TimeUnit.SECONDS)`, which a recording hook registry and a child JVM that receives SIGTERM both show (`onStop` runs, the line `Stopping` is printed).
- [x] AC-4: When `android.util.Log` is visible to the class loader of `RestApp`, detected only by reflection (no class of `NaruServe-api` main references `android.*`, the CON-BUILD-013 check stays green), `start` registers no hook and the start line has no `Press Ctrl+C` text; the detection is separated so a test with a class loader that exposes a fake `android.util.Log` shows both outcomes.
- [x] AC-5: The registered hook is removed with `Runtime.removeShutdownHook` after `handle.shutdown(...)`, after `RestApp.shutdown(...)` called on the app captured in the lambda, and when the hook itself ran the shutdown (an `IllegalStateException` of the removal during JVM shutdown is swallowed); after a start whose lambda threw or whose `listen` failed no hook is registered; ten successive start and shutdown cycles through a recording registry leave zero registered hooks.
- [x] AC-6: A hook that runs for an app that is already `TERMINATED` does nothing and does not throw, and removing a hook twice is harmless.
- [x] AC-7: When the hook registry refuses the registration after `listen` returned (the JVM is already shutting down, or a security manager denies it), `start` shuts the app down (state `TERMINATED`, port closed) and rethrows the refusal exception instance unchanged, so no server is left running without a handle; asserted with a recording registry whose `add` throws.

#### Requirement

A GitHub Actions workflow shall build a MkDocs Material site from docs/api (Korean, at the site root) and docs/api/en (English, under /en/) only, with a language switch, per-language navigation and search and a link to the API reference on javadoc.io, and deploy it to GitHub Pages on pushes to main, without changing the Gradle build and without editing the guides.

#### Rationale

User-directed on 2026-11-09: publish the user guides at https://snoworca.github.io/NaruServe/ with MkDocs Material and actions/deploy-pages, pinned actions and Python packages, Javadoc linked on javadoc.io instead of hosted, and nothing else under docs/ (spec, research, release evidence, plans) on the site. The guides are owned by other sessions, so links that leave docs/api are rewritten at build time by a hook instead of edited.

#### Acceptance Criteria

- [x] AC-1: With the toolchain pinned in tools/docs-site/requirements.txt on Python 3.11, `mkdocs build --strict` run from the repository root exits 0 with link, anchor and nav-omission validation set to warn, and no file under docs/api is edited for it.
- [x] AC-2: The built site holds exactly one HTML page per guide: docs/api/<name>.md at /<name>/ (README.md at /) in Korean and docs/api/en/<name>.md at /en/<name>/ (README.md at /en/) in English, and no page from any other folder; `tools/docs-site/check_site.py` fails on any extra or missing page.
- [x] AC-3: Every page's language selector links to the same page in the other language; each language has its own navigation listing every guide plus an external entry to https://javadoc.io/doc/com.snoworca.naruserve/naruserve-api, and its own search index (search/search_index.json and en/search/search_index.json) holding only that language's pages; check_site.py asserts these.
- [x] AC-4: Guide links to repository files outside docs/api (README.md, README.ko.md, examples/) become https://github.com/Snoworca/NaruServe/blob/main/... or tree/main/... URLs and Korean links to docs/api/en pages become links to the English pages; check_site.py fails when a built page holds a relative link that leaves the site or ends in .md.
- [x] AC-5: .github/workflows/docs-pages.yml installs the pinned requirements, runs the strict build and check_site.py, and deploys with actions/upload-pages-artifact and actions/deploy-pages only on pushes to main and manual dispatch; every `uses:` is pinned to a 40-character commit SHA, the workflow runs no Gradle task, and no Gradle build file changes; check_site.py asserts the pinning and the absence of Gradle.
- [x] AC-6: English first for every visitor: the Korean home page (/) and only that page sends the visitor to /en/ with location.replace, keeping the query and hash, whatever the browser languages are, unless the visitor chose 한국어 in the language selector; the choice made in the selector is remembered in localStorage (`naruserve.lang`) on every page of both sites, and a remembered `ko` keeps the Korean home page; when storage throws the visitor goes to /en/, and without script the Korean page still works; every page carries `<link rel="alternate" hreflang>` entries for ko, en and x-default (= en) with absolute URLs; `tools/docs-site/test_language_redirect.mjs` runs the shipped script against en-US, ko-KR, ja-JP, stored ko and en, unknown stored values and throwing storage, and check_site.py asserts the script is on the Korean home page only and the alternate links on every page.
