## 1. Scope Overview

This scope covers the TinyHttpd engine adapter, the server settings that reach it and the `RestApp.create()` bootstrap of NaruServe (issue #8, wave 5): the `HttpAdapter` implementation in `NaruServe-tinyhttpd` with its per-feature classes, the loopback default bind and the LAN binding API with the Host allowlist, the request size, header, timeout, slow-body and connection limits mapped onto TinyHttpd's builder, the TinyHttpd `ErrorHandler`, the transport-level rejections that bypass the core, the bind, ephemeral-port, stop and release behaviour, the proxy trust API, the `AppFactory` provider in the bootstrap module `NaruServe` with its keep rules and default logger, and the TinyHttpd halves carried from waves 3 and 4. It holds T07 over sockets, T44, T48 and T49.

## 2. Scope Boundaries

### In Scope

- Public settings types of wave 5 in `NaruServe-api` under `com.snoworca.naruserve` and `com.snoworca.naruserve.spi`, and their internal implementation in `com.snoworca.naruserve.internal`.
- The TinyHttpd adapter in `NaruServe-tinyhttpd` (`com.snoworca.naruserve.tinyhttpd`) and the bootstrap factory in `NaruServe` (`com.snoworca.naruserve.bootstrap`).
- The (미확정) markers owned by #8 in `docs/api/app.md`, `docs/api/defaults.md`, `docs/api/request.md`, `docs/api/express-migration.md` and `docs/api/README.md`.

### Out of Scope

- Any change inside the TinyHttpd checkout (`/Users/beom/work/git/TinyHttpd` stays read-only; gaps become deferred issues under D-020).
- A TLS listener on the TinyHttpd adapter (post-v1 under D-434).
- File transfer, event streams and protocol upgrades through the adapter (waves 6 and 7), including D-408 over TinyHttpd (`docs/research/naruserve-v1/waves/carried-into-wave-7.md`).
- The Android sample app and the Android halves of T10 and T12 (wave 8).

## 3. Assumptions and Constraints

- Core code is engine-free code in `NaruServe-api`: it references no TinyHttpd, Servlet, Gson, SLF4J, `android.*` or Kotlin stdlib type, compiles to Java 8 bytecode and passes the wave 1 animal-sniffer API 21 checks.
- Public types follow the wave 1 conventions: nullability annotations on public signatures, `@FunctionalInterface` callbacks, Express-style short method names, getter/setter names on value objects, no Kotlin keywords as method names, and no removed or changed public signature of `RestApp`, `Request`, `Response` or the `HttpAdapter` SPI that an earlier wave added: those types gain new methods only, and new public types such as `Cookie`, `SameSite`, `TypeRef`, `ServerOptions`, `ServerSettings` and `ErrorRenderer` are additions (I-014).
- Where the design leaves a choice open, the wave decisions and the residual section of `docs/research/naruserve-v1/waves/wave-5/design.md` apply; otherwise the implementer decides under standing rule C-07, following RFC 9110 and, between equally valid options, Express behaviour.
- Source of the requirements: `docs/research/naruserve-v1/waves/wave-5/design.md`, `docs/research/naruserve-v1/waves/wave-5/excerpt.md`, `docs/research/naruserve-v1/waves/carried-into-wave-5.md` and `object.md`.

### IR-ENGINE-001 — Server settings API: app.server(Configurer<ServerOptions>) and app.trustProxy

| --- | --- |

#### Requirement

The system shall add to `RestApp` the methods `RestApp server(Configurer<ServerOptions> configurer)` and `RestApp trustProxy(boolean trust)`, both under the `NEW`-state guard, with the public interface `com.snoworca.naruserve.ServerOptions` whose fluent setters configure the bind address, allowed host names, header size, header count, request-line length, header and body-read timeouts, minimum request body rate and connection limits, each with a bounded default, a minimum of 1 and a fixed maximum, and no value meaning unlimited.

#### Rationale

Covers D-225 (API names, decided under C-07 with the Express-first rule), D-212 (the explicit call is `bindAddress`), the request-line API of D-414, the header-size API statement of D-437, the configuration half of D-404 and D-413, the wave decision "Server settings reach the adapter" (settings live on `RestApp`, so `RestApp.create()` users reach them) and the residual "Upper bounds on size settings" (the request-line maximum 65534 keeps `inputBufferBytes` at most 65536). The `Configurer` callback follows the existing `app.accessLog(options -> ...)` pattern; rejected alternative: Express-style `app.listen(port, host)` (splits the LAN binding API from its allowed host names; reopen if users ask for it, as an overload that sets `bindAddress`).

#### Acceptance Criteria

- [x] AC-1: `RestApp` declares `RestApp server(Configurer<ServerOptions>)` and `RestApp trustProxy(boolean)`; `server(null)` throws `NullPointerException`, both methods throw `IllegalStateException` outside `NEW` through the guard of FR-APP-002, and several `server(...)` calls apply in call order to one options object. [D-225; wave decision: Server settings reach the adapter] Decision: the settings entry point is `app.server(options -> ...)` and proxy trust is `app.trustProxy(boolean)` (Express `app.set('trust proxy', true)`).
- [x] AC-2: `ServerOptions` declares exactly these setters, each returning `ServerOptions`, with these defaults and inclusive ranges: `bindAddress(String)` `127.0.0.1`; `allowedHosts(String...)` none; `maxHeaderSize(int bytes)` 16384, 1..1048576; `maxHeaderCount(int)` 100, 1..10000; `maxRequestLineLength(int bytes)` 8190, 1..65534; `headerTimeout(long, TimeUnit)` 10 s, `bodyReadTimeout(long, TimeUnit)` 30 s and `writeTimeout(long, TimeUnit)` 30 s, each 1 ms..1 h; `minBodyRate(int bytesPerSecond)` 240, 1..104857600; `maxWorkers(int)` 64, 1..1024; `maxSseStreams(int)` 128, 1..1024; `maxConnections(int)` 512, 1..65536; `maxUpgradedConnections(int)` 128, 1..65536; `maxConnectionsPerAddress(int)` 256, 1..65536. [D-225; D-215; D-216; D-404; D-413; D-414; residual: Upper bounds on size settings] Decision: these names and maxima; `maxWorkers` is the HTTP worker budget of D-404, and `writeTimeout` maps TinyHttpd's socket write timeout (default 30000 ms) so the socket write timeout that `docs/api/defaults.md` names is configurable.
- [x] AC-3: A value below the minimum or above the maximum of AC-2 makes its setter throw `IllegalArgumentException` naming the setting and the allowed range, and `bindAddress(null)`, `bindAddress("")`, `allowedHosts((String[]) null)`, a `null` or empty host name and a `null` `TimeUnit` throw `NullPointerException` or `IllegalArgumentException`; no setter accepts `0`, a negative value or another value meaning unlimited. [residual: Upper bounds on size settings; I-012]
- [x] AC-4: `maxHeaderSize` changes only the total header size of D-215 and leaves the per-line header limit of D-437 unchanged, and `maxRequestLineLength(n)` is the request-line limit that D-414 turns into TinyHttpd's `inputBufferBytes = max(8192, n + 2)`. [D-437; D-414]
- [x] AC-5: `listen(port)` keeps the loopback default: an app that never calls `server(...)` binds `127.0.0.1`. [wave decision: Server settings reach the adapter; D-211]
- [x] AC-6: A Kotlin test compiles and runs `app.server { o -> o.bindAddress("0.0.0.0").allowedHosts("myphone.local").maxHeaderSize(32768) }` and `app.trustProxy(true)`. [D-225; C-03; I-010]
- [x] AC-7: The `RestApp` surface test of IR-APP-002 AC-2 (`HttpApiSurfaceTest`, the wave 4 method set) is re-pointed to the wave 5 set: the wave 4 methods plus `server`, `trustProxy`, `jsonCodec` and `jsonLimit`, every wave 4 signature unchanged, `create()` and `builder()` still the only static methods and no `@Nullable` position on `RestApp`. [I-014; D-225; D-185]

### IR-ENGINE-002 — HttpAdapter settings bind: ServerSettings value, ErrorRenderer and safe logger

| Field | Value |
| --- | --- |
| Type | interface |
| Target | wave-5 |

| Priority | high |
| Tags | wave-5, feasibility:high, engine, spi |

#### Requirement

The system shall add to the `HttpAdapter` SPI the default method `void bind(ServerSettings settings, ExchangeHandler handler) throws IOException`, which delegates to the existing `bind(host, port, handler)`, and the engine-free SPI types `com.snoworca.naruserve.spi.ServerSettings` (an immutable value carrying the port and every frozen `ServerOptions` value, the exception-safe app logger and an error renderer) and `com.snoworca.naruserve.spi.ErrorRenderer` (renders the standard error body with a fresh request id), and make `listen()` hand the frozen settings to the adapter through the new method.

#### Rationale

Covers the wave decision "Server settings reach the adapter" (one immutable settings value given to a new bind method whose default delegates to the old one, so the in-memory and third-party adapters keep compiling), the wave decision "The adapter gets the safe logger" (D-220), D-104 and the renderer that lets the TinyHttpd module produce the D-405/D-418 bodies without calling `internal` classes. I-014 holds because the existing `bind(String, int, ExchangeHandler)` stays unchanged.

#### Acceptance Criteria

- [x] AC-1: `HttpAdapter` keeps `void bind(String, int, ExchangeHandler) throws IOException` unchanged and gains the `default` method `void bind(ServerSettings, ExchangeHandler) throws IOException` whose body calls `bind(settings.bindAddress(), settings.port(), handler)`; the test-fixtures `InMemoryHttpAdapter` and a minimal adapter that implements only the four wave 3 methods compile and bind unchanged. [wave decision: Server settings reach the adapter; I-014; D-107]
- [x] AC-2: `DefaultRestApp.listen(port)` calls `bind(ServerSettings, ExchangeHandler)` exactly once with a settings value whose `port()` is the `listen` argument and whose other values equal the frozen `ServerOptions` (defaults when `server(...)` was never called), so a recording adapter sees `127.0.0.1` by default and `0.0.0.0` after `server(o -> o.bindAddress("0.0.0.0"))`. [wave decision: Server settings reach the adapter; D-225]
- [x] AC-3: `ServerSettings` is a public final class with a getter for every setting of IR-ENGINE-001 AC-2, the port, `Logger logger()` and `ErrorRenderer errorRenderer()`; it has no setter, `allowedHosts()` returns an unmodifiable list, and no parameter, return or field type of `ServerSettings` or `ErrorRenderer` lies outside `java.*` and `com.snoworca.naruserve` packages. [D-104; wave decision: Server settings reach the adapter]
- [x] AC-4: The `logger()` of the settings value is the core's exception-safe wrapper of the app logger, so a test app logger that throws on every call, used by an adapter through `settings.logger().warn(...)`, never lets an exception reach the adapter. [wave decision: The adapter gets the safe logger; D-220]
- [x] AC-5: `ErrorRenderer` is a `@FunctionalInterface` with `String render(int status)`; the renderer in the settings returns the standard error body of FR-APP-006 for that status with the `code` of its status and a fresh 16-hex-digit request id on every call, identical in format to the body the dispatcher writes. [D-405; D-132; wave decision: Server settings reach the adapter] Decision: the renderer returns the JSON text, which the adapter sends as `application/json; charset=UTF-8`.

#### Requirement

The system shall make the TinyHttpd adapter bind the IPv4 loopback `127.0.0.1` explicitly by default, bind another address only after `server(o -> o.bindAddress(...))`, log a security warning through the app logger whenever `listen()` binds a non-loopback address, configure TinyHttpd's Host allowlist so requests addressed to the bind address or an allowed host name are accepted and others get `421` with the standard error body, bind an ephemeral port for `listen(0)` that `ServerHandle` reports, report the address actually bound through `ServerHandle.address()`, and leave no socket open when binding fails.

#### Rationale

Covers D-211 under the wave decision "The default bind address is IPv4 `127.0.0.1`" and the residual "D-211 wording" (the loopback-only intent of D-211 is unchanged; the adapter never calls `InetAddress.getLoopbackAddress()`, which can return `::1` on Android), D-212, D-213 with the wave decision "The LAN warning is unconditional", D-214, D-418, D-221 and D-222 (T49). Measured fact: TinyHttpd binds every interface when no bind address is given (`TinyHttpd.Builder.bindAddress` default `null`), and its `HostAllowlistFilter` always accepts `localhost` and IP literals and throws `HttpException(421)` otherwise. IR-APP-005 AC-3 stays true because it describes the default configuration (committee decision wave-5-srs-supersede).

#### Acceptance Criteria

#### Requirement

The system shall implement the adapter stop of D-107 with TinyHttpd's `stop(grace)`, passing the time left until the shared shutdown deadline as grace, and the adapter release with `awaitTermination` bounded by a fixed margin of 1 second, close idle keep-alive connections and commit in-flight responses with `Connection: close` once the stop begins, and hold one non-daemon keeper thread from a successful bind until the stop, so the JVM stays alive after `main` returns while TinyHttpd's own threads stay daemon.

#### Rationale

Covers D-223, the TinyHttpd keep-alive socket case of D-166 with T44 and D-167 with the wave decision "Thread wording" (carried from wave 4, `carried-into-wave-5.md`). Measured fact: TinyHttpd's `daemon(boolean)` defaults to `true` for acceptor and workers and its watchdog is always daemon, so without a keeper thread a `main` that only calls `listen` exits at once. The 1 second margin matches the in-memory adapter release of IR-HTTP-004 AC-6.

#### Acceptance Criteria

- [x] AC-1: `app.shutdown(t, unit)` calls the adapter's `stop` once, which calls TinyHttpd's `stop(graceMillis)` with the milliseconds left until the deadline of D-162 (at most `t` converted, never negative), so in-flight requests may complete until the deadline and are force-closed only there; because `stop` closes the listening sockets before it waits, TinyHttpd's join tail after the deadline stays small, and a test asserts that `stop` returns within the deadline plus 1500 ms; the final `release` calls `awaitTermination` with at most 1000 ms. [D-223; D-107; D-162; FR-APP-011] Decision: the adapter passes the full time left as grace, as D-223 states, and its fixed release margin is 1 second.
- [x] AC-2: After shutdown returns, no thread of that app is alive: TinyHttpd's worker threads come from a `ThreadFactory` the adapter passes to the builder, which keeps TinyHttpd's default worker properties (daemon, the configured worker stack size of 256 KiB, an uncaught-exception handler that logs through `ServerSettings.logger().error(String, Throwable)`), names each thread `naruserve-<port>-worker-<n>` and reads the bound port when it creates the thread (so `listen(0)` names the real port); the acceptor is identified by TinyHttpd's own name `tinyhttpd-acceptor-<port>`, the keeper thread by `naruserve-keeper-<port>`, and a test that starts one app at a time also finds no `tinyhttpd-watchdog` thread alive after `release`; tests use handlers that end when interrupted, and a worker that TinyHttpd reports as left after stop is logged as a warning by `release`. [D-223; I-015] Decision: worker names come from the adapter's thread factory; acceptor and watchdog names are TinyHttpd's fixed names.
- [x] AC-3: A request sent on an idle keep-alive connection after `STOPPING` began receives either `503` with `Connection: close` or a connection closed without a response, and a response in flight when the stop begins is committed with `Connection: close`. [D-166; T44; wave-4 carried: TinyHttpd keep-alive socket case]
- [x] AC-4: After a successful bind exactly one non-daemon thread named `naruserve-keeper-<port>` is alive and TinyHttpd's acceptor and worker threads are daemon; the keeper thread ends when the adapter stop begins and no keeper thread exists after a failed bind. [D-167; T44]

### FR-ENGINE-008 — Proxy trust through app.trustProxy applied by the core on every adapter

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-5 |
| Status | verified |
| Priority | medium |
| Tags | wave-5, feasibility:high, engine, security |

#### Requirement

The system shall make `req.remoteAddress()` and `req.isSecure()` ignore `X-Forwarded-*` and `Forwarded` headers by default and, after `app.trustProxy(true)`, return the left-most address of the first `X-Forwarded-For` header and report a secure request when the first `X-Forwarded-Proto` value is `https`, applied in the core's request object for every adapter.

#### Rationale

Covers the proxy-trust API of D-225 for D-080 under the wave decision "Server settings reach the adapter" (proxy trust is not an adapter setting; the core applies it in `DefaultRequest` on every adapter, the in-memory one included). The trusted behaviour follows Express `app.set('trust proxy', true)`, which uses the left-most `X-Forwarded-For` entry and `X-Forwarded-Proto`; rejected alternative: a list of trusted proxy addresses (not in object.md; reopen if a deployment needs hop counting). The `Forwarded` header stays ignored even when trusted, as in Express.

#### Acceptance Criteria

- [x] AC-1: Without `trustProxy(true)`, a request with `X-Forwarded-For: 203.0.113.7`, `X-Forwarded-Proto: https` and `Forwarded: for=198.51.100.1;proto=https` from `127.0.0.1` has `req.remoteAddress()` `127.0.0.1` and `req.isSecure()` `false` on both the in-memory and the TinyHttpd adapter, so FR-HTTP-011 AC-2 (the default configuration) stays true. [D-080; FR-HTTP-011]
- [x] AC-2: After `app.trustProxy(true)`, `X-Forwarded-For: 203.0.113.7, 10.0.0.1` gives `req.remoteAddress()` `203.0.113.7`, `X-Forwarded-Proto: https` gives `req.isSecure()` `true`, `X-Forwarded-Proto: http` gives `false`, and a request without these headers keeps the adapter's values. [D-080; D-225] Decision: trusted mode uses the left-most `X-Forwarded-For` entry and the first `X-Forwarded-Proto` value, compared case-insensitively. Decision [SDS 2026-10-19.naruserve.naruserve-v1-wave-5-4 SDS-AC-8]: the left-most `X-Forwarded-For` entry is trimmed of surrounding whitespace.
- [x] AC-3: After `app.trustProxy(true)` the `Forwarded` header alone changes neither `remoteAddress()` nor `isSecure()`, and an empty or blank `X-Forwarded-For` entry keeps the adapter's remote address. [D-080] Decision: `Forwarded` is not interpreted in v1.
- [x] AC-4: The trust decision is made in `DefaultRequest` from the app setting, so the in-memory adapter and the TinyHttpd adapter give identical `remoteAddress()` and `isSecure()` results for the same headers, and no adapter class reads `X-Forwarded-*` itself. [D-080; wave decision: Server settings reach the adapter]

#### Requirement

The system shall provide the TinyHttpd adapter as a public final `HttpAdapter` implementation whose public signatures expose no TinyHttpd type, whose exchange bridge and file-transfer, event-stream and upgrade paths are separate module classes receiving the exchange, whose file-transfer hook writes the requested byte range of a file through a plain buffered copy, whose event-stream path and `webSocket` path from wave 7 write a chunked event stream and run the TinyHttpd WebSocket handshake instead of throwing `UnsupportedOperationException`, holding the exchange lock only to check abort and mark the response started, and whose raw `upgrade(headers, UpgradeHandler)` path stays unsupported in v1 with a message that names no wave.

#### Rationale

Covers D-209, D-210, D-404, D-106, D-291, D-433, D-080, D-399 and D-107 as restated from FR-ENGINE-010, with AC-2 changed by wave 7 (the event-stream and `webSocket` paths are filled; raw `upgrade` stays unsupported) and new AC-3 and AC-4 from wave decisions TinyHttpd feature hooks (W2-003; D-210) and maxEventStreams (W2-009; D-336). Measured: `tinyhttpd/TinyHttpdFeatures.java:51-57` throws `UnsupportedOperationException` "arrive in wave 7" for `eventStream` and `upgrade`; `TinyHttpdExchange.java:229-240` declares `upgrade` and `eventStream` as `synchronized` methods that take the lock, abort check and single-start bookkeeping of `commit()` (wave 5 commit 387db8c, w5-P2-002), and drain writes made later from another thread must also synchronize on the exchange (FR-SSE-003). Carried note (r2 W1-002 / W1-001, D-408): TinyHttpd at 46b973e keeps only `Connection: close`/`keep-alive` on a non-`101` response (`ExchangeResponse.java:172-177`, `:466-470`), so the `426` answer's `Connection: Upgrade` cannot pass through this adapter; the D-020 TinyHttpd-gap issue is opened in the wave 7 ledger and D-408 stays below `verified` (FR-WS-004); this requirement does not patch TinyHttpd. Pitfall: holding the exchange lock for the whole WebSocket read loop or SSE drain would block every other call that synchronizes on the exchange for the life of the connection. Rejected alternative: TinyHttpd's `startEventStream()` (D-335: fixed `Cache-Control: no-cache` and a separate `retry` block). Tests to re-point to FR-ENGINE-011: every `FR_ENGINE_010_*` method of `AdapterSurfaceTest`, `RawTargetSocketTest`, `AbortSocketTest` and `SendFileSocketTest` in `NaruServe-tinyhttpd/src/test/java/com/snoworca/naruserve/tinyhttpd/`; `AdapterSurfaceTest#FR_ENGINE_010_AC2_sendFileIsFilledAndTheOtherHooksThrowNamingWave7` is replaced by a test that asserts the event-stream and `webSocket` paths no longer throw and that raw `upgrade` throws with a message naming no wave; the `@req FR-ENGINE-001` (discarded id) and `@req FR-ENGINE-010` comments of `TinyHttpdExchange.java` and `TinyHttpdFeatures.java` move to FR-ENGINE-011.
