## 1. Scope Overview

This scope covers the NaruServe build foundation (issue #1, wave 1): the Gradle 8.14.3 wrapper build, the root `settings.gradle` / `build.gradle` / `gradle.properties` that configure every module, the module layout and names, the main dependency declarations of each module, the TinyHttpd composite build, the test tooling (JUnit 4.13.2, Kotlin Gradle Plugin 2.x, Java and Kotlin smoke tests), the build checks (animal-sniffer API 21, kotlin-stdlib confinement, Core dependency isolation, single Gson version), and the module naming recorded in `docs/api/` and `CLAUDE.md`.

## 2. Scope Boundaries

### In Scope

- Gradle wrapper, root project name, module includes and the single root build file.
- Java and Kotlin bytecode targets, Maven group and Java package root.
- Main and compileOnly dependency declarations of every module, declared up front in wave 1.
- TinyHttpd `includeBuild` wiring through a Gradle property, its dependency boundaries and its read-only status.
- Test tooling and the root `./gradlew build` gate on JDK 17 without an Android SDK.
- Build checks: animal-sniffer `android-api-level-21`, kotlin-stdlib on `runtimeClasspath`, forbidden package references in `NaruServe-api` classes, single Gson 2.14.0 resolution.
- Module names and dependency coordinates in `docs/api/README.md`, `app.md`, `json.md`, `kotlin.md`, `logging.md` and the module line of `CLAUDE.md`.

### Out of Scope

- Runtime behaviour of any module (routing, JSON, logging, adapters); later waves own it.
- Release and publishing plugins (issue #18).
- The `jakarta` module marker in `docs/api/servlet.md` (wave 8, D-358).
- Any change inside the TinyHttpd checkout.
- The Android sample application build.

## 3. Assumptions and Constraints

- The TinyHttpd checkout exists at the configured Gradle property path (default `/Users/beom/work/git/TinyHttpd`, commit 46b973e) and exposes the coordinates `com.snoworca.tinyhttpd:tinyhttpd-core` and `com.snoworca.tinyhttpd:tinyhttpd-websocket`.
- The local JDK is 17; no Android SDK is installed on the build machine.
- Waves run serially, so at most one worker builds the shared TinyHttpd checkout at a time.
- Names and library choices the design leaves open (exact logger module suffixes, the nullability annotation library) are decided by the implementer under standing rule C-07, within the constraints the requirements state.
- Source of the requirements: `docs/research/naruserve-v1/waves/wave-1/design.md` (frozen design items and wave decisions) and `object.md`.

#### Requirement

The system shall provide the module `NaruServe-android`, built by the root `build.gradle` with the Android Gradle Plugin as an Android library (AAR) whenever an Android SDK location resolves, whose manifest declares only the `android.permission.INTERNET` permission and whose `api` dependencies are exactly `NaruServe` and `NaruServe-logcat`, so one dependency line gives an Android app the default app with the Logcat logger.

#### Rationale

User decision (2026-10-26): `NaruServe` stays usable on any JDK, so the Logcat logger leaves it and moves to a dedicated Android module; the minimal Android module holds the Logcat logger and the INTERNET permission only, and further Android features (assets serving, lifecycle) are later work. A JAR cannot merge a manifest permission, so the module is an AAR. The Android Gradle Plugin needs an Android SDK, so the module is included only when one resolves and every other module keeps building without an SDK. AGP 8.13.2 is the first line that supports compileSdk 36 (the installed platform) on Gradle 8.14.3 without a suppression flag; the module holds no main Java or Kotlin source, so it adds no class of its own to check against API 21.
