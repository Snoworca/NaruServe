## 1. Scope Overview

This scope covers the HTTP core of NaruServe (issue #4 plus route registration and dispatch from #2 and #3, wave 3): the public `Request`, `Response`, `RouteHandler`, `RouteBuilder` and `RestApp` interfaces with the methods whose types exist by the end of wave 3, the engine-free dispatcher that maps router lookup results to handler calls or automatic responses, request accessors (path, raw path, parameters, query, headers, attributes), request body ownership (`BodyState`, `BodyAlreadyConsumedException`, limit-enforcing input stream), the response API and its state machine, the `HttpAdapter` SPI with an in-memory adapter in the `NaruServe-api` test fixtures, and the `docs/api` markers decided in wave 3. It holds the HTTP-level assertions of T01, T02, T03, T05 and T06 and the in-memory part of T07.

## 2. Scope Boundaries

### In Scope

- `Request`, `Response`, `RouteHandler`, `RouteBuilder`, `RestApp` and `BodyAlreadyConsumedException` in `NaruServe-api` under package `com.snoworca.naruserve`, and the internal `RestApp` implementation, dispatcher, `BodyState` and limit-enforcing stream in an internal package.
- The `HttpAdapter` SPI and its extension points, and the in-memory adapter plus test harness in the `NaruServe-api` test fixtures source set.
- The (미확정) markers owned by #4 and D-398 in `docs/api/request.md`, `docs/api/response.md`, `docs/api/routing.md`, `docs/api/app.md`, `docs/api/defaults.md` and `docs/api/express-migration.md`.

### Out of Scope

- `req.service`, `req.application` (wave 4); `req.body`, `res.json` and the cookie methods (wave 5); `req.form`, `req.file`, `req.files`, `req.parts`, `res.file`, `res.download`, `res.cache` (wave 6); `res.sse` (wave 7) (D-392).
- `listen()`, the lifecycle states, the public entry point `RestApp.create()` and the standard error body and error path (wave 4).
- The TinyHttpd halves of D-399, D-442 and I-021 (wave 5, `docs/research/naruserve-v1/waves/carried-into-wave-5.md`) and `426` over TinyHttpd (wave 7, `docs/research/naruserve-v1/waves/carried-into-wave-7.md`).
- HTTP-level `413` checks through body readers (waves 5 and 6).
- Any change inside the TinyHttpd checkout.

## 3. Assumptions and Constraints

- Core code is engine-free code in `NaruServe-api`: it references no TinyHttpd, Servlet, Gson, `android.*` or Kotlin stdlib type, compiles to Java 8 bytecode and passes the wave 1 animal-sniffer API 21 and class-reference checks.
- Public types follow the wave 1 conventions: nullability annotations on public signatures, `@FunctionalInterface` callbacks, Express-style short method names and no Kotlin keywords as method names.
- Where the design leaves a choice open, the wave decisions of `docs/research/naruserve-v1/waves/wave-3/design.md` apply; otherwise the implementer decides under standing rule C-07, following RFC 9110 and, between equally valid options, Express behaviour.
- Source of the requirements: `docs/research/naruserve-v1/waves/wave-3/design.md` (frozen design items, wave decisions, residual), `docs/research/naruserve-v1/waves/wave-3/excerpt.md` and `object.md`.

#### Requirement

The system shall define an `HttpAdapter` SPI in `NaruServe-api` through which an adapter gives the core the method token, the raw request-target path, the raw query string, the headers, a streaming body `InputStream`, the remote address and the secure flag of each request, and through which the core sends status, headers and a streaming body `OutputStream`. The core decodes the raw path and raw query once; adapters never pass decoded values.

#### Rationale

Covers D-105, the SPI half of D-399 and the wave decision on adapter halves. The TinyHttpd half of D-399 (reading `getRequestURI()` and `getQueryString()`, never `getPath()`) and the adapter value comparison of the residual (`/a//b` under `mergeSlashes(true)`, `/a%20b` to `/:x`, compared by `rawPath()` and decoded values) are deferred to wave 5 (`docs/research/naruserve-v1/waves/carried-into-wave-5.md`).

#### Acceptance Criteria

- [ ] AC-1: The SPI exposes, per request, the request line as the method token, the raw request-target path, the raw query string (or its absence) and the HTTP version, plus the header names and values in received order, a body `InputStream`, the remote address and the secure flag. [D-105]
- [ ] AC-2: The SPI accepts from the core a status code, response headers and a body `OutputStream`, and the core writes status and headers before the first body byte. [D-105]
- [ ] AC-3: The raw request-target path and the raw query string travel through the SPI as separate undecoded fields: an exchange with target `/a%20b?x=%41` reaches the core with raw path `/a%20b` and raw query `x=%41`, and the core alone yields `req.path()` = `/a b` and `req.query("x")` = `A`. [D-399; wave decision: Adapter halves]

#### Requirement

The system shall include in the `HttpAdapter` SPI extension points for file transfer, event streams and protocol upgrade, and lifecycle calls that bind synchronously to an address and port, report the actual bound port, and stop in two calls: a blocking stop bounded by a core-supplied deadline and a final release bounded by a fixed margin.

#### Rationale

Covers D-106 and D-107. Waves 6, 7 and 8 add adapter classes against these points without changing the SPI. No concrete deadline or margin value is set here.

#### Acceptance Criteria

- [ ] AC-1: Through the file-transfer extension point the core hands the adapter a `java.io.File` with an offset and a length, and the adapter writes exactly those bytes of the file as the response body; an in-memory test hands over a file with a non-zero offset and a length shorter than the rest of the file and reads back exactly that byte range from the client body. [D-106]
- [ ] AC-2: Through the protocol-upgrade extension point the core hands the adapter an upgrade callback with a `101` response, and the adapter invokes that callback with the exchange's raw input and output streams after writing the `101` response; an in-memory test observes that the callback ran with the exchange's streams (or that the in-memory adapter recorded the hand-over). [D-106]
- [ ] AC-3: The event-stream point hands the adapter a core-owned drain loop that keeps writing after the handler returned until the core reports the stream ended, and the adapter chooses the thread that runs it; in wave 3 (before `res.sse` exists) an in-memory test supplies a drain loop through the SPI type, runs it on an adapter-chosen thread after the handler returned and sees it end only when the end is reported. [D-106]
- [ ] AC-4: The three extension points are SPI types in `NaruServe-api`, usable by an adapter without any NaruServe class outside `NaruServe-api`, so waves 6, 7 and 8 add adapter classes against them without changing the SPI. [D-106]
- [ ] AC-5: The SPI declares a bind to an address and port that returns only after binding completed, and a separate call through which the core reads the actual bound port; with the in-memory adapter, a bind with port `0` reports a positive bound port that the core reads back through the SPI and that stays the same on every read until stop, and a bind with a positive port reports that port. [D-107]
- [ ] AC-6: The SPI declares a blocking stop that stops accepting, waits for in-flight exchanges until a deadline passed by the core and then force-closes the remaining connections, and a separate final release that waits at most a fixed margin for the adapter's threads to end; the in-memory adapter implements both and a test shows an in-flight exchange still running at the deadline is force-closed. [D-107]

### FR-HTTP-002 — Dispatcher pipeline and pre-request checks before route lookup

| Field | Value |
| --- | --- |
| Type | functional |

| Status | planned |
| Priority | high |
| Tags | wave-3, feasibility:high, dispatcher |

#### Requirement

The system shall provide a dispatcher that takes each exchange from an `HttpAdapter`, checks the asterisk-form `OPTIONS *` first, then rejects a raw path not starting with `/` with `400`, then rejects a raw path refused by the wave 2 path validator with `400`, and only then calls the router lookup and either invokes the matched `RouteHandler` with a `Request` and a `Response` or writes the automatic response. The pre-request rejections are answered before any `Request` is built.

#### Rationale

Covers D-394, D-397, the wave decision on order before lookup, the carried rule that the dispatcher runs the path validator before lookup (400, no decoding), and the residual on pre-request rejections (D-422, D-442, D-052, D-117, D-129, I-014). T01, T02, T03, T05 and T06 run their HTTP-level assertions through the in-memory adapter.

#### Acceptance Criteria

- [ ] AC-1: Through the harness, a `GET /users/7` request with `app.get("/users/:id", h)` registered reaches `h` once with a `Request` and a `Response`, and the status, headers and body `h` wrote come back through the in-memory adapter. [D-394; D-397]
- [ ] AC-2: With a recording handler registered through `app.route(Method.any(), "/", h)` and `app.route(Method.any(), "/:x", h)`, `OPTIONS *` is answered `204` before path validation (so `*` is not rejected with `400`), and a validator rejection happens before the router lookup: `GET /%2e%2e` and `GET /a%2Fb` (both rejected by the `PathValidator`) are answered `400`, no lookup exception escapes, and `h` registered on the matching pattern `/:x` records no call. [wave decision: Order before lookup; D-442; D-052]
- [ ] AC-3: A raw path that the wave 2 `PathValidator` rejects is answered `400` with `Content-Length: 0` and an empty body without a router lookup, and the validator sees the raw form with a single decoding: `/%2e%2e` and `/a%2Fb` are answered `400`, while `/%252e%252e` reaches a `/:x` route with `req.param("x")` = `%2e%2e`. [wave-3 carried: path validator before lookup; D-052; wave decision: Automatic response bodies]
- [ ] AC-4: An unrecognised method token is answered `501`, a raw path not starting with `/` `400`, a validator rejection `400` and `OPTIONS *` `204`, each before a `Request` is built, so no handler sees them; a recording handler registered through `app.route(Method.any(), "/", h)` and `app.route(Method.any(), "/:x", h)` records that it was never called. [wave-3 residual: pre-request rejections; D-422]
- [ ] AC-5: In every handler call `req.method()` returns a non-null `Method` and `req.path()` a non-null decoded path. [wave-3 residual: pre-request rejections]
- [ ] AC-6: The HTTP-level assertions of T01, T02, T03, T05 and T06 run as tests through the in-memory adapter and the harness in `./gradlew build`. [D-397]
