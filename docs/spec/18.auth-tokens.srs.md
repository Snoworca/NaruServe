## 1. Scope Overview

Tokens, keys and passwords of the 0.11.0 auth module (`com.snoworca.naruserve.utils.auth` inside `NaruServe-api`). This scope covers the hand-written HS256 JWT (`Jwt`, `JwtKeys`, `JwtClaims`, `JwtException`), the access/refresh token pair issued by `TokenService`, key sources with `kid` key sets, the strict internal `MiniJson` parser/writer (R43), the `RefreshTokenStore` family store with rotation and reuse detection, the PBKDF2 hasher with `HashCost` calibration (R27, R38), the `PasswordHashers` chain with legacy verifiers (bcrypt, MD5, SHA digests), hash concurrency slots, constant-work login timing, the rehash queue, `PasswordPolicy`/`BreachedPasswordChecker`, the `Authenticator` SPI and the internal primitives `Base64Url`, `HmacSigner` and `ConstantTime`. Every behavior here is testable without an HTTP server. Source of truth: `docs/research/auth-rbac/00.overview.md` (edition 33).

## 2. Scope Boundaries

### In Scope

- HS256 JWT encode and verify, header `{alg, typ, kid}`, access claims `{sub, ver, fam, iat, exp, jti}`, `typ` `at+jwt`/`rt+jwt` with distinct derived keys (R2, R8).
- `KeySource`/`KeySources` factories, `kid` key sets with one signing key and n verification keys, purpose-specific derived keys.
- `MiniJson` `CLAIMS` and `FILE` profiles and their rejection rules (R43).
- `TokenService`/`TokenPair` issue and refresh rotation within a family, per-family reuse detection (R1, R2, R10), `RefreshTokenStore` SPI and its default selection and cleanup (R42).
- `PasswordHasher` SPI, `Pbkdf2PasswordHasher`, `HashCost` calibration and fixed cost, rehash thresholds (R5, R27, R38).
- `PasswordHashers.chain`, `BcryptPasswordHasher`, unsalted and salted digest legacy verifiers (R37 rehash path).
- Hash concurrency slots and 503 backpressure, constant-work login with the 1.25T failure floor, the low-priority rehash queue (R38).
- `PasswordPolicy`, `BreachedPasswordChecker`, the `Authenticator` SPI and built-in authenticators.
- Internal primitives `Base64Url`, `HmacSigner`, `ConstantTime`.

### Out of Scope

- RS256, ES256 and JWKS (v2).
- Opaque token introspection, RFC 7662 (v2).
- `EXTERNAL_CLAIMS` profile and OIDC token acceptance (v2).
- One-time tokens for self-service password reset and email verification (v2).
- `AndroidKeystoreKeySource` (v2, `NaruServe-android`).
- Endpoint HTTP contracts, token delivery, cookies and CSRF (FLOW scope); pipeline, doctor, modes and cross-cutting build constraints (AUTH scope); user/group/role stores, `AtomicFiles` and the app-provided store contracts (IAM scope); API key verification (APIKEY scope).

## 3. Assumptions and Constraints

- Cross-cutting rules (no new dependency, Core public API only, API 21 animal-sniffer check, no `java.time`, no `java.util.Base64`, no `java.nio.file`) are owned by the AUTH scope and apply to every requirement here.
- Only JDK and Android-common APIs are used: `javax.crypto.Mac`, `java.security` (`SecureRandom`, `MessageDigest`), `java.util.concurrent` (00 §2).
- Time is read through `com.snoworca.naruserve.utils.TimeSource` so tests can fix the clock (00 §2).
- All type and method names in the research are proposals; names marked "(name not final)" are decided during implementation (CLAUDE.md).
- Android hash timing numbers in 06 (9–21 s) are estimates; device measurement is out of scope (00 §10 Q6, §12).

#### Requirement

The auth module shall provide the internal primitives Base64Url, HmacSigner and ConstantTime in utils.auth.internal, which encode and strictly decode unpadded base64url, compute HMAC-SHA256 safely from concurrent threads, and compare byte arrays in time independent of where they differ.

#### Rationale

00 §2 lists Base64Url, HmacSigner and ConstantTime as internal (non-public, not contract-stable) building blocks for JWT, CSRF, device tokens and API key comparison; R8 (kid, derived keys) and R47 (constant-time SHA-256 compare) depend on them. java.util.Base64 is API 26 and cannot be used on API 21.

#### Acceptance Criteria

- [ ] AC-1: Base64Url.encode of any byte array emits only the characters A-Z, a-z, 0-9, '-' and '_' and never emits '=' padding [INFERRED:med:advisory]
- [ ] AC-2: Base64Url.decode rejects input containing '=', '+', '/', whitespace, or a final character whose unused low bits are non-zero (a non-canonical encoding of the same bytes), and decode(encode(b)) equals b for random arrays of length 0 to 64 [INFERRED:med:advisory]
- [ ] AC-3: HmacSigner computing HMAC-SHA256 from 16 threads at once over the same key yields, for every call, the same output as a single-threaded javax.crypto.Mac computation (no shared Mac state) [INFERRED:med:advisory]
- [ ] AC-4: ConstantTime.equals(a, b) returns true only for arrays of equal length and content, returns false for arrays of different length, and does not call MessageDigest.isEqual [INFERRED:med:advisory]
- [ ] AC-5: The three classes are in package com.snoworca.naruserve.utils.auth.internal and are excluded from the public API package list checked by ApiJarClasses.PUBLIC_PACKAGES

#### Research / Analysis

- Decisive facts: java.util.Base64 is API 26+, so base64url is hand-written (01 §2.1). javax.crypto.Mac is not thread-safe: use Mac.getInstance per call or a ThreadLocal (01 §2.1).
- Ground truth: strict decode rejects padding, whitespace and the standard alphabet so one token has exactly one valid encoding (06 AUTH-T03, T04: a signature whose last character is swapped for one decoding to the same bytes must be rejected).
- Pitfall: do not rely on MessageDigest.isEqual; older Android implementations were not constant time. Use an XOR-accumulate loop over the full length (01 §2.1). 04 §2.4.1 still says MessageDigest.isEqual for bcrypt; 00 lists ConstantTime as the primitive, so ConstantTime wins.
- Rejected: exposing these as public API (00 §2 marks internal as no compatibility promise). Reopen only if an app-facing SPI needs them.

Consumers: Jwt (TOKEN), CSRF and device tokens (FLOW), API key hash comparison (APIKEY).

### SEC-TOKEN-002 — MiniJson strict parser and writer with CLAIMS and FILE profiles

| Field | Value |
| --- | --- |
| Type | security |
| Target | 0.11.0 |
| Status | implemented |
| Priority | high |
| Tags | 0.11.0, auth-rbac, feasibility:high, minijson |
| Risk | medium |

| GitHub Issue | - |
| Related Docs | docs/research/auth-rbac/00.overview.md, docs/research/auth-rbac/06.threat-model-and-verification.md |

#### Requirement

The auth module shall read and write JWT headers, JWT claims and auth-owned files only through the internal MiniJson parser and writer, which enforces the CLAIMS profile (depth 2, total 8 KB, string 1 KB) for JWT input and the FILE profile (depth 8, default total 8 MB raisable by the builder, string 64 KB) for auth files, and rejects duplicate keys, NaN, invalid escapes and trailing characters in both profiles.

#### Rationale

00 §6.3 R43 (edition 5 onward) fixes the two profiles and their limits; 00 §2 splits JSON into MiniJson for untrusted JWT input and auth files versus the app codec for HTTP bodies. CON-BUILD-013 forbids Gson types in NaruServe-api.

#### Acceptance Criteria

- [ ] AC-1: Under CLAIMS, a document nested 3 levels deep is rejected and a document nested 2 levels deep is accepted; under FILE, depth 8 is accepted and depth 9 is rejected
- [ ] AC-2: Under CLAIMS, input larger than 8 KB or containing a string longer than 1 KB is rejected before any value is returned; under FILE, input larger than the configured total (default 8 MB) or a string longer than 64 KB is rejected
- [ ] AC-3: In both profiles {"alg":"HS256","alg":"none"} (duplicate key) is rejected, NaN and Infinity literals are rejected, an invalid escape such as \x41 is rejected, and any non-whitespace character after the top-level value is rejected
- [ ] AC-4: A JWT header or payload containing a 100-level nested array is rejected by the CLAIMS limit with no further parsing of the nested content (06 AUTH-T07)
- [ ] AC-5: A FILE-profile document of depth 3 or more written by MiniJson and read back yields the same values (00 §6.4 R43 x R42)
- [ ] AC-6: An auth file store's file larger than the configured FILE total (for example a 9 MB users.json under the default 8 MB) is not loaded: because the reader rejects it (AC-2), the file is unreadable and start stops with the R42 FAIL of REL-IAM-004 (nothing is overwritten), and that FAIL's message names the limit, the store constructor argument that raises it (new FileUserStore(file, maxFileBytes, logger)) and advises moving to an app-provided UserStore implementation backed by the application's database (R43; no built-in JDBC store exists since 2026-11-03). Whether R43's 'doctor WARN' level also applies to a file near the limit or to a write that would exceed it is an open question, so no WARN is asserted here
- [ ] AC-7: No class under com.snoworca.naruserve.utils.auth references Gson or the app JsonCodec to parse JWT headers, JWT claims or auth files

#### Research / Analysis

- Decisive facts: CLAIMS is only for HS256 tokens auth issued itself. v2 external IdP tokens need EXTERNAL_CLAIMS (depth 4, 16 KB) because Keycloak realm_access.roles is depth 3 and Entra group claims approach 8 KB (R43, edition 5); that profile is out of scope for 0.11.0.

#### Requirement

The public jwt package shall provide Jwt, JwtKeys, JwtClaims and JwtException so that an application can sign and verify HS256 JWS compact tokens without an Auth instance, where the algorithm is fixed by the key set rather than read from the header, the key is selected by the header kid, the signature is checked in constant time before any claim is trusted, and every malformed or invalid token raises JwtException.

#### Rationale

00 §2 (no external JWT library, jwt package usable standalone), §9 v1 row (HS256 Jwt), R8 (always kid). Algorithm confusion and alg=none are removed structurally by never choosing the algorithm from the header (01 §2.1, 06 F1-F7).

#### Acceptance Criteria

- [ ] AC-1: Jwt.sign produces a token whose header is exactly the members alg, typ and kid with alg "HS256" and kid equal to the key set's signing kid, and Jwt.verify of that token returns JwtClaims with the same subject, expiry and custom claims
- [ ] AC-2: A valid token whose header alg is changed to "none" with an empty signature, or to "HS512" or "hs256", raises JwtException (06 AUTH-T01, T02)
- [ ] AC-3: A token with one or three dots, with '=' padding, or with '+' or '/' in any part raises JwtException; a token whose last signature character is replaced by a non-canonical character decoding to the same bytes raises JwtException (06 AUTH-T03, T04)
- [ ] AC-4: A token whose payload lacks exp, has exp as a string ("1761700900"), a fraction (1761700900.5) or 1e300 raises JwtException and never an unchecked exception other than JwtException (06 AUTH-T05)
- [ ] AC-5: A token whose header contains crit raises JwtException; a header containing jku is ignored and verification makes zero network calls (06 AUTH-T10) [INFERRED:med:advisory]
- [ ] AC-6: A token whose kid is not in the key set raises JwtException, and a token larger than the maximum token size (default 8 KiB) raises JwtException before its signature is computed [INFERRED:med:advisory]
- [ ] AC-7: With TimeSource set to exp + leeway - 1 ms verification passes and at exp + leeway + 1 ms it raises JwtException; the default leeway is 60 seconds and a leeway above 5 minutes is refused by the builder (06 AUTH-T11) [INFERRED:med:advisory]
- [ ] AC-8: JwtException reports a reason distinguishing at least malformed, bad algorithm, unknown key, bad signature, expired, not yet valid, wrong type and too large (name not final) [INFERRED:med:advisory]

| Field | Value |

| Priority | high |
| Tags | 0.11.0, auth-rbac, feasibility:high, keys |

#### Requirement

The auth module shall obtain signing material through the KeySource SPI and the KeySources factories of, fromEnv, fromFile, fromBytes and rotating, each yielding a key set of exactly one signing key and zero or more verification keys addressed by kid, and shall refuse short or example secrets when the configuration is built in PROD (in DEV they produce a WARN instead, per SEC-AUTH-001).

#### Rationale

00 §4.4 and §7 name KeySource and KeySources.of/fromEnv/fromFile/fromBytes/rotating and fix the kid set as one signing key plus n verification keys; R8 requires kid on every token; 00 §4.4 says short or example keys are refused by build().

#### Acceptance Criteria

- [ ] AC-1: A key set built with KeySources.rotating(signing k2, verification k1) (signature name not final) signs new tokens with kid k2 and still verifies a token signed earlier with k1; after k1 is removed from the verification list the k1 token is rejected
- [ ] AC-2: A key set has exactly one signing key; building a set with zero or two signing keys fails with an exception at build time
- [ ] AC-3: In PROD, Auth.builder(KeySources.of(secret)) with a secret that SEC-AUTH-001 AC-2 or AC-3 rejects is refused at build() with a message that contains the text "openssl rand -base64 32"; the rejection cases and the DEV behaviour are owned by SEC-AUTH-001 (AC-2 to AC-4, AC-8) [INFERRED:med:advisory]
- [ ] AC-4: KeySources.fromEnv(name) with the variable unset or empty fails at build() with a message that contains the variable name [INFERRED:med:advisory]
- [ ] AC-5: KeySources.fromFile(file) on a missing file creates it with 32 random bytes from SecureRandom readable only by the owner, returns the same key on the next start, and never overwrites an existing file [INFERRED:med:advisory]
- [ ] AC-6: KeySources.fromBytes(bytes) and KeySources.of(secret) with the same key material produce tokens that verify against each other's key set
- [ ] AC-7: The equivalence of Auth.builder(secret) and Auth.builder(KeySources.of(secret)) is owned by SEC-AUTH-001 AC-6 (name not final for the KeySource overload)
- [ ] AC-8: NaruServe-api contains the public interface com.snoworca.naruserve.utils.auth.spi.KeySource (method set not final; 00 §2 spi, §4.1 row 3). A KeySource written by the test, not produced by KeySources, that returns one fixed 32-byte signing key under kid "vault-1", passed to Auth.builder(KeySource) (name not final; the overload of AC-7), is the source auth signs with under the default TokenCodec: the access token a login issues carries kid "vault-1" in its header and authenticates a protected request, and a token signed with any other key gets 401 invalid_token. A Kotlin source test implements KeySource in Kotlin and passes it to the builder, and it compiles and runs (CLAUDE.md T11).

#### Requirement

Under the default HS256 TokenCodec (IR-TOKEN-002), auth-issued access tokens shall carry the header {alg, typ, kid} with typ at+jwt and exactly the claims {sub, ver, fam, iat, exp, jti} and refresh tokens shall carry typ rt+jwt; each purpose (access, refresh, device token) shall be signed with its own key, and the device fingerprint computed with its own key, each derived per kid from the key set's secret, so that a token of one purpose never verifies as another. #### Rationale

#### Acceptance Criteria

- [ ] AC-2: A refresh token header has typ "rt+jwt" and its payload carries sub, ver, fam, jti, iat and exp [INFERRED:med:advisory]
- [ ] AC-3: Verifying a refresh token as an access token is rejected and verifying an access token as a refresh token is rejected, both because of typ and because the derived signing keys differ (06 AUTH-T09)
- [ ] AC-4: A token re-signed with the access-derived key but carrying typ rt+jwt fails refresh verification, proving the refresh key differs from the access key
- [ ] AC-5: The device-token key equals HMAC(secret, "naru-device") and the fingerprint key equals HMAC(secret, "naru-device-fp") for the kid named in the token header, and both differ from the access and refresh keys

#### Requirement

The spi package shall define the Authenticator SPI as a @FunctionalInterface for password credential verification (the password seam of 05 §3.9, @Nullable AuthUser authenticate(String username, char[] password, AuthEventContext ctx) throws Exception, names not final [INFERRED:med:advisory]), and the auth module shall ship three built-in authenticators - password (store plus PasswordHasher chain, replaceable through that SPI), Bearer JWT (TokenService access verification) and API key (the R47 scheme path, active only when API keys are enabled) - where the Bearer and API key authenticators are internal and not replaceable in 0.11.0 (open question Q35, decided 2026-11-02), and the password authenticator never distinguishes an unknown user from a wrong password or a disabled user.

#### Rationale

00 §9 v1 row (Authenticator: password, Bearer, API key), §7 (Authenticator replaces CredentialAuthenticator, spi package), §2 (LDAP is not a module but an Authenticator example), R47 (API key is the "ApiKey" scheme path, off by default), R30 (store/listener errors become 503 JSON).

#### Acceptance Criteria

- [ ] AC-1: A Kotlin lambda and a Java lambda each compile as an Authenticator and can replace the built-in password authenticator through the builder (name not final)
- [ ] AC-2: The built-in password authenticator returns no user for an unknown username, a wrong password, a disabled user and a service account, and (for the wrong-password and disabled users, each with a stored iteration count equal to the current target) all four cases each run exactly one target-cost PBKDF2 computation inside one slot (SEC-TOKEN-009 AC-1)
- [ ] AC-3: The built-in password authenticator returns the user for the correct password and passes a needed rehash to the rehash queue
- [ ] AC-4: The built-in Bearer authenticator accepts only access tokens (typ at+jwt under the default HS256 codec) and yields a principal id equal to the token sub; a refresh token, or a token that the configured TokenCodec (IR-TOKEN-002) fails to decode as an access token, yields no principal
- [ ] AC-5: Without .apiKeys(store) the API key authenticator is not installed and an Authorization: ApiKey header is treated as no credentials; with it, ApiKey-scheme requests are routed to the API key verification path
- [ ] AC-6: An exception thrown by a custom Authenticator is reported as 503 JSON, not as a stack trace and not as a successful login
- [ ] AC-7: The public API surface holds one authenticator seam (open question Q35, decided 2026-11-02): a reflection test over the public types of com.snoworca.naruserve.utils.auth.spi finds exactly one authenticator interface, Authenticator, whose single abstract method takes a username String and a char[] password, and no public type or Auth builder option accepts a replacement for the Bearer or the API key authenticator.

#### Requirement

The spi package shall define TokenCodec, the token-format replacement seam that 00 §2 lists as a v1 spi member, and the auth module shall encode and decode its access and refresh tokens only through the configured TokenCodec, whose default is the HS256 codec built on the KeySource keys (SEC-TOKEN-003, SEC-TOKEN-005); 0.11.0 ships no other codec (RS256, ES256, JWKS and introspection codecs are v2).

#### Rationale

00 §2 package tree puts TokenCodec in spi without a (v2) mark, unlike ClaimMapping, TenantResolver and CacheInvalidation; 00 §4.1 row 3 (SPI replacement: token format, written as .tokens(TokenCodecs...)) and §9 v1 row (HS256 Jwt and TokenService). Method shape comes from 05 §3.8 and is advisory; the builder option name is not final (00 §4.1 .tokens(...), 05 §3.8 .tokenCodec(...)).

#### Acceptance Criteria

- [ ] AC-1: NaruServe-api contains the public interface com.snoworca.naruserve.utils.auth.spi.TokenCodec; with no codec configured, the effective codec is the default HS256 codec and the tokens a login issues have the SEC-TOKEN-005 format (HS256 header with kid, typ at+jwt / rt+jwt, purpose-derived keys).
- [ ] AC-2: With a custom TokenCodec configured on the builder (option name not final; 00 §4.1 row 3 writes .tokens(TokenCodecs...), 05 §3.8 proposes .tokenCodec(codec)), a login issues the access and refresh tokens that the custom codec's encode returns, and a protected request is authenticated from the claims its decode returns; when decode throws, the request gets the same 401 invalid_token as for a bad signature (the failure reason is logged only, never in the response).
- [ ] AC-3: TokenCodec methods follow 05 §3.8 [INFERRED:med:advisory]: encode(claims) and decode(token, expectedType), both with non-null parameters and returns through the utils.auth.spi package's @NullMarked default (no @Nullable, and no @NonNull annotation, FR-KT-001 AC-3) and allowed to throw Exception (names and the claims type not final); the default codec's decode with expectedType access rejects a refresh token and vice versa (SEC-TOKEN-005 typ separation).
