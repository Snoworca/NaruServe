## 1. Scope Overview

This scope covers WebSocket support of NaruServe (issue #13, wave 7): `app.ws(path, handler)` and `app.webSocket(...)` settings, the upgrade dispatch after the global and prefix middleware, the core `Origin` check, the RFC 6455 handshake and protocol enforcement taken from TinyHttpd's websocket module through the add-only WebSocket SPI types and the TinyHttpd upgrade class, `WebSocketSession` with its listeners and attributes, the bounded per-session send queues drained by one app-wide sender executor, ping, pong and idle timeouts, the WebSocket connection limit, and the closing of open sessions with `1001` at shutdown. It holds T19, T20, T21, T22, T23 and the WebSocket parts of T35, T38 and T44.

## 2. Scope Boundaries

### In Scope

- WebSocket types and methods of wave 7 in `NaruServe-api` under `com.snoworca.naruserve` and `com.snoworca.naruserve.spi`, and their internal implementation in `com.snoworca.naruserve.internal`.
- The TinyHttpd upgrade class of `NaruServe-tinyhttpd` built on TinyHttpd's `WebSocketHandler`.
- The (미확정) markers owned by #13 in `docs/api/websocket.md`, `docs/api/app.md`, `docs/api/defaults.md` and `docs/api/express-migration.md`.

### Out of Scope

- A NaruServe frame codec (D-302: framing comes from TinyHttpd).
- WebSocket subprotocol negotiation, per-message compression and large binary streaming (not in v1).
- Server-Sent Events (scope SSE) and the shutdown coordination shared with SSE (scope APP).
- Kotlin, Servlet and Android sample-app items (wave 8).

## 3. Assumptions and Constraints

- Core code is engine-free code in `NaruServe-api`: it references no TinyHttpd, Servlet, Gson, SLF4J, `android.*` or Kotlin stdlib type, uses `java.io` and `java.util.concurrent` and never `java.nio.file` or `CompletableFuture`, compiles to Java 8 bytecode and passes the wave 1 animal-sniffer API 21 checks.
- Public types follow the wave 1 conventions: nullability annotations on public signatures, `@FunctionalInterface` callbacks, Express-style short method names, no Kotlin keywords as method names, and no removed or changed public signature of `RestApp`, `Request`, `Response` or the `HttpAdapter` SPI: those types gain new methods and types only (I-014, D-106 read as "without breaking the SPI").
- Where the design leaves a choice open, the wave decisions and the residual section of `docs/research/naruserve-v1/waves/wave-7/design.md` apply; otherwise the implementer decides under standing rule C-07, choosing what is most natural to an Express user without contradicting `object.md`.
- Source of the requirements: `docs/research/naruserve-v1/waves/wave-7/design.md`, `docs/research/naruserve-v1/waves/wave-7/excerpt.md` and `object.md`.
- TinyHttpd at `/Users/beom/work/git/TinyHttpd` (commit `46b973e`) stays read-only; gaps become deferred TinyHttpd-gap issues under D-020.

#### Requirement

The system shall provide `RestApp ws(String path, WebSocketHandler handler)`, the `@FunctionalInterface` `WebSocketHandler` taking `(Request req, WebSocketSession ws)`, the `WebSocketSession` interface with its nested `@FunctionalInterface` listeners, and `RestApp webSocket(Configurer<WebSocketOptions> configurer)` with the settings `allowedOrigins`, `maxMessageSize`, `sendQueueSize`, `pingInterval` and `idleTimeout`, each bounded and defaulted as the acceptance criteria state.

#### Rationale

Covers D-294, D-311, D-303 (API and default part), D-419 (WebSocket setting names), D-323 (configuration API part), D-317 (API part), wave decision Handler timing (W2-004, API part) and the C-07 choices of the authoring plan; T11/C-03 for Kotlin. Registration goes through the existing internal `Router.addWebSocket` path: `ws` registers through the internal `DefaultRestApp.webSocketRoute(String, RouteHandler)` hook, which keeps its signature so the verified FR-HTTP-008 AC-5 and AC-7 tests and the `TestApp.webSocketRoute` fixture stay unchanged (FR-WS-001 AC-7), so the pattern syntax and the freeze and conflict rules are the HTTP route rules of FR-ROUTE-003 and FR-ROUTE-015 (measured: `DefaultRestApp.java:828` records a `webSocketRoute` with `MethodSet.of(GET)` and `:859` calls `router.addWebSocket`). The configurer follows IR-APP-007 and IR-MULTIPART-001 (copy swapped in after it returned); range messages follow the existing forms `<name> must be in 1..<max>: <value>` (`DefaultServerOptions.java:23`) and `<name> must be in 1 ms..1 h: <time> <unit>` (`DefaultServerOptions.java:35`), with the 1 s lower bound for WebSocket durations. Pitfall: an unlimited value would contradict I-012, so no setting accepts a value meaning unlimited and every setting has a bounded range and a finite default. Decision: each `allowedOrigins` call replaces the allowlist (Express `cors` `origin` style), although TinyHttpd's own `allowedOrigins` appends; the core does the Origin check (FR-WS-003). No handshake-timeout setting exists (residual r5 W2-002: TinyHttpd at 46b973e has no upgrade deadline, so a setting would have no effect) and no pong-timeout setting exists (D-424: pong timeout equals the ping interval). Test to re-point: the RestApp signature set of `HttpApiSurfaceTest` gains `ws` and `webSocket` (AC-1, AC-6). Rejected alternative: `ws` returning a route builder like `route()`; reopen if per-route WebSocket middleware is requested. Rejected alternative: a listener interface with all callbacks (express-ws style `ws.on(...)`); Java SAM per event keeps Kotlin lambdas without a DSL. Express mapping: express-ws `app.ws(path, (ws, req) => ...)` with argument order reversed.

#### Acceptance Criteria

- [x] AC-1: `RestApp` declares `ws(String path, WebSocketHandler handler)` returning the same `RestApp`, and `com.snoworca.naruserve.WebSocketHandler` is a `@FunctionalInterface` with the single abstract method `void handle(Request req, WebSocketSession ws) throws Exception`; a Java test registers `app.ws("/ws/rooms/:room", (req, ws) -> ...)` and reflection confirms both signatures, and the RestApp signature set of `HttpApiSurfaceTest` gains `ws(String,WebSocketHandler)->RestApp`. Decision: `ws` returns `RestApp` like `get`, and the callback interface is named `WebSocketHandler`. [D-294]
- [x] AC-2: A path passed to `ws` follows the HTTP route pattern syntax and its registration-time validation: `app.ws("/a/:id", h)` registers and resolves `req.param("id")` in the handler, an invalid pattern throws the same exception type as `app.get` with that pattern, and `ws(null, h)` or `ws("/a", null)` throws `NullPointerException`. Decision: registration goes through the internal `Router.addWebSocket` path, which the internal `DefaultRestApp.webSocketRoute` hook already uses. [D-294]
- [x] AC-3: `ws(...)` and `webSocket(...)` called after `listen()` throw `IllegalStateException` from the `NEW`-state guard of FR-APP-002 before the handler is recorded or the configurer runs, leaving routes and settings unchanged. [D-294; D-323] Decision: `requireConfigurable("ws")` or `requireConfigurable("webSocket")` runs first and the null checks after it, so the `IllegalStateException` wins over a null argument after `listen()`. [SDS 2026-10-19.naruserve.naruserve-v1-wave-7-2 SDS-AC-2]
- [x] AC-4: `com.snoworca.naruserve.WebSocketSession` declares `String id()`, `void sendText(String)`, `void sendBinary(byte[])`, `void sendJson(@Nullable Object)`, `void ping()`, `void close()`, `void close(int code, String reason)`, `boolean isOpen()`, `void onText(TextListener)`, `void onBinary(BinaryListener)`, `<T> void onJson(Class<T> type, JsonListener<T>)`, `void onClose(CloseListener)`, `void onError(ErrorListener)`, `void attribute(String key, @Nullable Object value)` and `<T> @Nullable T attribute(String key, Class<T> type)`, which a reflection test lists. Decision: `close()` equals `close(1000, "")`, and the attribute overloads follow the `Request.attribute` overload rule. [D-311]
- [x] AC-5: The nested types `WebSocketSession.TextListener.onText(String)`, `BinaryListener.onBinary(byte[])`, `JsonListener<T>.onJson(@Nullable T value)`, `CloseListener.onClose(int code, String reason)` and `ErrorListener.onError(Throwable error)` are each annotated `@FunctionalInterface` and declare `throws Exception`, which a reflection test asserts; two listeners of one kind registered on one session both run, in registration order. [D-311]
- [x] AC-6: `RestApp` declares `webSocket(Configurer<WebSocketOptions> configurer)` returning the same `RestApp`, and the public interface `com.snoworca.naruserve.WebSocketOptions` declares the fluent setters `allowedOrigins(String... origins)`, `maxMessageSize(int bytes)`, `sendQueueSize(int bytes)`, `pingInterval(long time, TimeUnit unit)` and `idleTimeout(long time, TimeUnit unit)`, each returning `WebSocketOptions`; a configurer setting all five is applied, which a test reads back through the internal settings, and the RestApp signature set of `HttpApiSurfaceTest` gains `webSocket(Configurer)->RestApp`. Decision: the configurer runs on a copy that is swapped in only after it returned, so a throwing configurer leaves every earlier setting unchanged. [D-419; D-323; D-303]
- [x] AC-7: An app that never calls `webSocket` uses no configured origin allowlist, `maxMessageSize` 1048576, `sendQueueSize` 1048576, `pingInterval` 30 s and `idleTimeout` 300 s; `allowedOrigins()` with no argument resets the allowlist to that default, and a second `allowedOrigins("https://b.example")` after `allowedOrigins("https://a.example")` leaves only `https://b.example` allowed, which a test asserts. Decision: ping interval default 30 s and idle timeout default 5 min; each `allowedOrigins` call replaces the allowlist (like the `origin` option of Express `cors`). [D-303; D-323; D-419] Decision: `allowedOrigins` with a null array or a null entry throws `NullPointerException` and keeps the previous list; otherwise it stores a defensive copy in the given order. [SDS 2026-10-19.naruserve.naruserve-v1-wave-7-2 SDS-AC-5]
- [x] AC-8: `maxMessageSize` accepts 1 to 16777216, `sendQueueSize` accepts 1 to 67108864, `pingInterval` accepts 1 s to 1 h and `idleTimeout` accepts 1 s to 24 h, all inclusive; `0`, a negative value or a value above the bound throws `IllegalArgumentException` whose message has the form `<setting> must be in 1..<max>: <value>` for a size (for example `maxMessageSize must be in 1..16777216: 0`) and `<setting> must be in 1 s..<max>: <time> <unit>` for a duration (for example `pingInterval must be in 1 s..1 h: 0 SECONDS`), a `null` unit or origin entry throws `NullPointerException`, and no setting accepts a value meaning unlimited: every setting has a bounded range and a finite default (I-012). [D-419; D-323] Decision: a duration is converted with `unit.toMillis` (saturating) and compared against 1000..3600000 ms or 1000..86400000 ms, so `999 MILLISECONDS` and `Long.MAX_VALUE DAYS` are refused with the caller's own time and unit in the message. [SDS 2026-10-19.naruserve.naruserve-v1-wave-7-2 SDS-AC-4]
- [x] AC-9: Reflection finds no handshake-timeout setter and no pong-timeout setter on `WebSocketOptions` or `RestApp`. Decision: the handshake is bounded by the server-wide `headerTimeout` and `bodyReadTimeout`, and the pong timeout equals the ping interval. [residual: WebSocket handshake timeout (r5 W2-002)] [D-424]
- [x] AC-10: A Kotlin test compiles and runs `app.ws("/ws") { req, ws -> ws.onText { m -> ws.sendText(m) }; ws.onClose { code, reason -> } }` and `app.webSocket { o -> o.maxMessageSize(1024).pingInterval(5, TimeUnit.SECONDS) }` as SAM lambdas without a DSL, and the returned `RestApp`, `WebSocketOptions` and `ws.id()` are non-platform types (`@NonNull`). [D-294; D-311; C-03; T11]

#### Requirement

The system shall extend the `com.snoworca.naruserve.spi` package for WebSocket only by adding the types `WebSocketEndpoint`, `WebSocketChannel` and `WebSocketSettings` and the `default` method `HttpExchange.webSocket(WebSocketSettings, WebSocketEndpoint)`, which throws `UnsupportedOperationException` unless an adapter overrides it, beside which wave 7 adds only the SSE `default` method `StreamDrain.attach(OutputStream)` of IR-HTTP-007, so that an adapter supplies RFC 6455 framing and the core owns every WebSocket callback without any existing SPI signature changing.

#### Rationale

Covers wave decision WebSocket upgrade SPI (W2-001; D-106, D-302, D-429, D-435, D-444, D-419, D-423), Ping (r2 W2-001; D-309, D-311), Start state on a refused handshake (r2 W2-002, SPI part) and D-302 (no NaruServe frame codec). Deviation note: D-106 says the upgrade extension point works "without changing the SPI"; the wave reads it as "without breaking it" (add-only types and one default method), which `docs/api` records; IR-HTTP-007 (the successor of IR-HTTP-004 in the HTTP scope) restates the SPI-surface AC accordingly. Measured: `spi/HttpExchange.java:85` declares `upgrade(List<Map.Entry<String,String>>, UpgradeHandler)` and `:89` `eventStream(...)`; the existing raw `upgrade` stays for raw upgrades and keeps its signature. Pitfall: putting TinyHttpd's `WebSocket`/`WebSocketListener` types on the SPI would leak an engine type into the core (CON constraints of wave 1); rejected. Rejected alternative: driving WebSocket through the raw `UpgradeHandler` and a NaruServe frame codec; contradicts D-302, reopen never in v1. The in-memory test adapter implements `webSocket` so core-level tests of FR-WS-001, FR-WS-003, FR-WS-006, FR-WS-007 and FR-WS-009 run without sockets.
- [2026-10-20] Correction (feasibility F-03/F-05): the SPI now gains two default methods, HttpExchange.webSocket and StreamDrain.attach (committee decision B-1), replacing the earlier "one default method" wording. AC-5's signature test names StreamDrain.attach, which IR-HTTP-007 AC-4 owns; IR-HTTP-007 depends_on this requirement, so the two are built and verified together as one group (no reverse edge, to keep the graph acyclic).

#### Requirement

### FR-WS-002 — TinyHttpd upgrade class: RFC 6455 handshake through WebSocketHandler and pre-101 rejections through the dispatcher's error path

#### Requirement

The system shall implement `HttpExchange.webSocket` on the TinyHttpd adapter with a TinyHttpd `WebSocketHandler` built with `allowAnyOrigin()`, the configured message limit and ping interval, called on the request worker through a `ResponseWrapper` that keeps the returned `UpgradedConnection`, answering a valid RFC 6455 handshake with `101` and the correct `Sec-WebSocket-Accept`, and turning every rejection raised before `101` into a NaruServe `HttpException` that carries its status and headers and leaves the exchange unstarted for the dispatcher's error path.

#### Rationale

Covers D-298, D-299, D-302, D-444, D-429 (TinyHttpd part), wave decisions WebSocket upgrade SPI (W2-001, TinyHttpd part), Handshake headers on rejections (W2-008), Start state on a refused handshake (r2 W2-002) and User exceptions after 101 (r2 W2-005, adapter part); carried loop-D fix V2-001; tests T19 and the upgrade part of T35. Measured: `tinyhttpd/TinyHttpdFeatures.java:56` `upgrade(Response, ...)` and `:51` `eventStream(...)` throw `UnsupportedOperationException` naming wave 7; the feature hooks are package-private and may change to receive the exchange (W2-003, D-210 protects only the adapter core limit mapping). TinyHttpd's `WebSocketHandler` (read-only checkout at 46b973e) offers `allowAnyOrigin()`, `maxFramePayloadBytes(int)`, `maxMessageBytes(int)`, `pingInterval(int millis)` and `handle(Request, Response)`; its listener has `onOpen/onText/onBinary/onClose` and no `onError`. `allowAnyOrigin()` is used because the core checks `Origin` itself (FR-WS-003, W2-005). Pitfall: TinyHttpd's handshake may set `Sec-WebSocket-Accept` before it throws; W2-008 requires dropping it before the error path renders, through whatever mechanism the TinyHttpd `Response` API allows (SDS decides). Pitfall: marking the exchange started before `101` would make the error path's commit throw (r2 W2-002). Rejected alternative: answering rejections inside the TinyHttpd class with TinyHttpd's own error page; it would bypass the D-132 standard body and the request id, reopen never. The access log records the rejection status on the request's ordinary line (FR-APP-019, APP scope). Header carriage uses `HttpException.withHeader` (IR-HTTP-008, HTTP scope).

#### Requirement

The system shall check the `Origin` header of every upgrade request in the core after the middleware chain and before `HttpExchange.webSocket`, admitting a request with no `Origin`, a same-origin `Origin` and, when an allowlist is configured, each listed origin or any origin for the entry `*`, and answering every other `Origin` with `403` without upgrading.

#### Rationale

Covers D-300, wave decision Origin check (W2-005; D-300, D-303) and the default part of D-303; test T22. Reason the check sits in the core: TinyHttpd's own check always admits a missing or same-origin `Origin`, so its allowlist cannot express the NaruServe default; the adapter therefore uses `allowAnyOrigin()` (FR-WS-002). Decision (C-07): same-origin means scheme, host and port equal to the request's own, with scheme `https` when `req.isSecure()` and `http` otherwise, host and port from `Host`, default ports 80/443 normalised and host compared case-insensitively; the literal `Origin: null` (sandboxed iframes, file URLs) is rejected unless `*` is listed. Pitfall: browsers do not apply CORS to WebSocket, so a cross-site page can open an authenticated socket with cookies (cross-site WebSocket hijacking); the same-origin default blocks it. Rejected alternative: admit-all when unset (the `ws` library default); reopen if non-browser-only deployments find the default too strict, since `*` exists. Rejected alternative: reject-all when unset; it breaks the same-origin browser case that works in Express with `express-ws`. The 403 body is the standard error body of FR-APP-006 (HTTP_403 via its fallback rule).

#### Acceptance Criteria

- [x] AC-1: With no allowlist configured, an upgrade request without an `Origin` header and one with `Origin: http://example.test:8080` and `Host: example.test:8080` both reach `HttpExchange.webSocket`. Decision: the default admits no-`Origin` and same-origin requests. [D-303; wave decision: Origin check (W2-005)]
- [x] AC-2: With no allowlist configured, an upgrade request with `Origin: http://evil.test` and `Host: example.test` receives `403` with the standard JSON error body carrying the request id, `HttpExchange.webSocket` is never called and the `ws` handler never runs (T22). [D-300; wave decision: Origin check (W2-005)]
- [x] AC-3: Same-origin comparison uses scheme `https` when `req.isSecure()` is true and `http` otherwise, normalises default port 80 for `http` and 443 for `https`, and compares hosts case-insensitively: `Origin: HTTP://Example.Test` with `Host: example.test:80` is admitted, `Origin: https://example.test` on a non-secure request is rejected with `403`, and `Origin: http://example.test:8081` with `Host: example.test:8080` is rejected with `403`. Decision: scheme from `isSecure()`, host and port from `Host`. [wave decision: Origin check (W2-005)] Decision: scheme and host of the `Origin` are lowercased, port 80 or 443 is taken by scheme when absent, `Host` is read as `host[:port]` with a bracketed IPv6 form, and an unparseable `Origin`, or a present `Origin` with no `Host`, is not same-origin. [SDS 2026-10-19.naruserve.naruserve-v1-wave-7-3 SDS-AC-7]
- [x] AC-4: `Origin: null` is rejected with `403` when no allowlist is configured and when the allowlist holds only named origins. [D-300; wave decision: Origin check (W2-005)]

[D-300; D-429]

#### Requirement

The system shall answer a request without `Upgrade: websocket` to a path that has only an `app.ws` route with `426 Upgrade Required` carrying `Upgrade: websocket` and `Connection: Upgrade` from the core, and over the TinyHttpd adapter shall deliver `426` with `Upgrade: websocket`, recording the missing `Connection: Upgrade` as a deferred TinyHttpd gap.

#### Rationale

Covers D-408 and the carried line "D-408 over TinyHttpd" (from earlier waves), plus wave decisions 426 over TinyHttpd (W1-001) and (r2 W1-002). Measured: TinyHttpd at 46b973e keeps only `Connection: close`/`keep-alive` on a non-`101` response (`ExchangeResponse.java:172-177` and `:466-470` in the read-only checkout), so `Connection: Upgrade` cannot pass through the TinyHttpd adapter; the core already sets both headers (`internal/Dispatcher.java:357-360`, WEBSOCKET_ONLY case of FR-ROUTE-016 / FR-HTTP-022). Deviation (recorded): the frozen wording asks for both headers in an end-to-end test over the TinyHttpd adapter; wave 7 asserts both headers through the in-memory adapter and `426` + `Upgrade: websocket` over TinyHttpd, opens the D-020 TinyHttpd-gap issue in the wave 7 issue ledger at triage, defers it, and keeps this requirement below `verified` until that gap closes. Rejected alternative: patching TinyHttpd; TinyHttpd is read-only for NaruServe (D-020), reopen when TinyHttpd ships the fix. Rejected alternative: writing the `Connection` header through a raw socket hack in the adapter; it would bypass TinyHttpd's connection management.
- [2026-10-20] D-020 deferred issue: `ExchangeResponse` dropping `Connection: Upgrade` on non-`101` responses is a TinyHttpd gap that the orchestrator records as a deferred D-020 issue in the run's issue ledger at triage; while it is open this requirement is not promoted to `verified` on the TinyHttpd test alone (D-408). ### FR-WS-005 — RFC 6455 protocol enforcement from TinyHttpd: masking, UTF-8, message limit, reassembly, control frames, ping and close handshake

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-7 |
| Status | verified |
| Priority | high |
| Tags | wave-7, feasibility:high, websocket, protocol |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/13 |
| Related Docs | - |

#### Requirement

The system shall enforce RFC 6455 on accepted WebSocket connections through TinyHttpd's websocket module, closing with `1002` for an unmasked client frame or an oversized or fragmented control frame, `1007` for invalid UTF-8 text and `1009` for a message above the configured limit whether sent as one frame or fragmented, delivering fragmented messages reassembled, answering Ping with Pong, sending Ping on `ws.ping()`, and completing the close handshake on `ws.close(code, reason)` after which `isOpen()` returns `false`.

#### Rationale

Covers D-302, D-304, D-305, D-306, D-307, D-308, D-309, D-310, D-419 (limit mapping part), wave decision Ping (r2 W2-001) and carried loop-D fixes V1-004 and V2-003 (both: the configured message limit goes to both `maxFramePayloadBytes` and `maxMessageBytes`, tested at a non-default limit as one frame and fragmented); tests T20 and T21. Measured: TinyHttpd's `WebSocket` offers `sendText`, `sendBinary`, `ping(byte[] <= 125)`, `close(code, reason)` and `isOpen`; NaruServe adds no frame codec (D-302), so these ACs are end-to-end tests over the TinyHttpd adapter with a raw-socket client that writes frames by hand. Pitfall: passing the limit only to `maxMessageBytes` lets one unfragmented frame above the limit through until reassembly, and only to `maxFramePayloadBytes` lets a fragmented message grow without bound (V1-004). Decision: `ws.ping()` sends an empty-payload Ping through the session's sender slot (FR-WS-007), calling `WebSocketChannel.ping(new byte[0])`, so it never interleaves with a data frame being written. Rejected alternative: a NaruServe-side UTF-8 or size check before TinyHttpd; duplicate logic, reopen only if TinyHttpd lacks a check.

#### Acceptance Criteria

- [x] AC-1: Over TinyHttpd, a raw-socket client that sends an unmasked text frame after `101` receives a close frame with code `1002` and the session's `onClose` listener receives `1002` (T20). [D-304]
- [x] AC-2: A text frame whose payload is the invalid UTF-8 byte sequence `0xC3 0x28` makes the server send close `1007`, and `onText` is not called (T20). [D-305]
- [x] AC-3: With the default limit, a 1048577-byte text message sent as one frame makes the server send close `1009`, while a 1048576-byte message reaches `onText` whole (T20). [D-306]
- [x] AC-4: With `maxMessageSize(4096)`, a 4097-byte binary message sent once as a single frame and once as three continuation fragments of 2048, 2048 and 1 bytes makes the server send close `1009` both times, and a 4096-byte message sent in four fragments reaches `onBinary` once with all 4096 bytes in order (T20). [D-419; D-307] [carried: V1-004] [carried: V2-003]
- [x] AC-5: A text message sent as fragments `"Hel"`, `"lo"` reaches `onText` once as `"Hello"`, and a Ping frame interleaved between the two fragments is answered with a Pong without breaking the reassembly (T20). [D-307; D-309]

### FR-WS-006 — WebSocketSession semantics: unique ids, per-connection attributes, onClose once, JSON through JsonCodec, onJson failure and listener exceptions

#### Requirement

The system shall give each WebSocket session an id unique within its app, a per-connection concurrent attribute map separate from request attributes and released at close, `onClose` listeners run exactly once with the close code and reason, `sendJson` and `onJson` through the app's `JsonCodec`, `onJson` decode failures reported to `onError` with the session left open, and user listener exceptions caught, logged and answered by close `1011`.

#### Rationale

Covers D-312, D-313, D-314, D-315, D-317 (decision part), wave decision User exceptions after 101 (r2 W2-005, core endpoint part) and the C-07 send/close choices; test T21. Decisions (C-07): session id = 16 lowercase hex digits of an app-wide counter starting at 1; sends on a closed session are dropped without exception, like the `ws` library's send on a closed socket, with `isOpen()` reporting the state; `close(code, reason)` accepts only the codes an endpoint may send per RFC 6455 section 7.4 (1000-1003, 1007-1014 and 3000-4999; 1004-1006, 1015 and the unassigned 1016-2999 are rejected, matching TinyHttpd's `WebSocket` receive check so a NaruServe close is never failed as a protocol error by a strict peer) and rejects a reason over 123 UTF-8 bytes instead of truncating. Decision (close codes on TinyHttpd, AC-9): measured `WebSocket.java:261-405` at 46b973e reports to `WebSocketListener.onClose` the code of the peer's close frame, its own code for a close it starts itself (ping timeout `1001`, protocol failure), and `1006` when the socket ends without a close frame, so a close the core started and the peer never answered would surface as `1006`; the core therefore records the code and reason of every close it starts and reports those to `onClose` and to the FR-APP-019 close line. This decision applies to FR-WS-005 AC-8, FR-WS-007 AC-6, FR-WS-008 AC-4, FR-WS-010 AC-2/AC-7 and FR-APP-019 AC-9. Decision for D-317: an `onJson` parse failure goes to the `onError` listeners and the session stays open; with no `onError` listener it is logged at WARN with the request id. Rejected alternative: closing 1007 on a JSON parse failure; a malformed application message is not a protocol error, reopen if users ask for strict mode. Decision for r2 W2-005: an exception from any user listener is caught, passed to the `onError` listeners, logged at ERROR with the request id, and the session is closed with `1011`; nothing reaches TinyHttpd's callbacks. Pitfall: an `onError` listener that itself throws must not recurse; it is logged and ignored. Rejected alternative: random UUID ids; the counter is cheaper on API 21 and unique per app as D-312 requires.
- [2026-10-20] Handler exceptions (AC-10, r2 W2-005): the `ws` handler runs from the core endpoint's `onOpen` after `101`, and TinyHttpd's `WebSocketListener.onOpen` declares no checked exception and answers a RuntimeException with close 1011 plus a rethrow out of `handle`, so the core catches every handler exception itself, reports it to the onError listeners registered so far, logs it at ERROR and closes 1011; no HTTP answer is possible after the upgrade.

Decision: an exception from the `ws` handler is handled like a listener exception after `101`. ### FR-WS-007 — Bounded per-session send queue drained by one app-wide sender executor, whole ordered messages and the 1008 overflow policy

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-7 |
| Status | verified |
| Priority | high |
| Tags | wave-7, feasibility:high, websocket, concurrency |
| Risk | high |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/13 |

#### Requirement

The system shall queue every WebSocket send in a per-session outbound queue bounded by `sendQueueSize` and drain the queues with one app-wide sender executor whose thread limit equals `maxUpgradedConnections`, running at most one write task per session at a time so that messages go out whole in queue-entry order and a stalled session never delays another session, closing a session whose queue would overflow with `1008`, and leaving no queue, thread or attribute of a closed session behind.

#### Rationale

Covers D-318, D-417, D-319, D-320, D-321 (decision), D-322, wave decisions Sender slot release (W2-007) and Sender-slot wait (r2 W2-004, which moves the W2-007 wait into the core after `HttpExchange.webSocket` returns and before the exchange finishes, behaviour unchanged); test T23. Reason: TinyHttpd's `WebSocket` send is synchronous, so a direct send from a broadcaster would block on a slow peer. Measured: `ServerOptions.java:41-54` already defines `maxUpgradedConnections` (default 128, FR-ENGINE-004); TinyHttpd's write timeout defaults to 30 s. Decision for D-321 (C-07): when queuing a message would make the session's queued bytes exceed `sendQueueSize`, the message is dropped, the queue is discarded, close `1008` with reason `send queue overflow` is handed to the sender slot as the last task, `onClose` receives `1008`, and the overflowing send returns normally. Rejected alternative: throwing from `send` on overflow; it forces every broadcaster to catch per peer, reopen if users need synchronous backpressure. Pitfall: a fixed pool of 16 threads would let 16 stalled peers block every other session (D-320 asks for at least 20 stalled sessions in the test). Pitfall: reusing a sender thread for another session's task while one write is in flight would interleave frames (D-319). Thread total and stack figures belong to PERF-APP-001 in the APP scope.

#### Acceptance Criteria

- [x] AC-1: With `sendQueueSize(1000)`, a session whose client does not read accepts queued sends up to 1000 bytes of payload without closing, and the in-memory test observes the queued byte count never exceed 1000; a test with non-ASCII text (`"é"` counts 2 bytes) asserts the count. Decision: queued bytes count the UTF-8 encoded length of a text message's payload and the array length of a binary message's payload; ping and close frames are not counted. [D-318] Decision: `sendJson` counts its encoded text, and the bytes are released when that write returns, so the in-flight message stays counted. [SDS 2026-10-19.naruserve.naruserve-v1-wave-7-6 SDS-AC-1]
- [x] AC-2: All sessions of an app share one sender executor whose maximum thread count equals `maxUpgradedConnections` (default 128), which a test reads from the internal executor; its threads are named `naruserve-<port>-ws-sender-<n>`, with `<port>` the app's bound port read when the thread is created, so two apps in one JVM own distinct thread names, which a test with two bound apps asserts; an idle thread ends after the executor's keep-alive time, which a test that sets the internal keep-alive to 200 ms asserts by observing the thread count fall to 0 within 1 s after the last send. Decision: the keep-alive time is 60 s, overridable only through an internal test hook. Decision: sender threads are named `naruserve-<port>-ws-sender-<n>` like the adapter's `naruserve-<port>-worker-<n>`, so thread-count tests attribute them per app. [D-417] Decision: the sender is a `ThreadPoolExecutor(max, max, keep-alive, LinkedBlockingQueue)` with `allowCoreThreadTimeOut(true)` and daemon threads with a 256 KiB requested stack, with `port.getAsInt()` read in `newThread`. ### FR-WS-008 — Ping interval, pong timeout, idle timeout scheduler and the handshake bound on TinyHttpd

| Field | Value |

#### Requirement

The system shall pass the WebSocket ping interval to TinyHttpd's `WebSocketHandler.pingInterval` so that a silent peer is closed with `1001` after two intervals, fix the pong timeout to the ping interval, enforce the idle timeout with one NaruServe scheduler thread that hands close `1001` to an idle session's sender slot and aborts the session's socket 1 s later when that close task has not returned, and bound the handshake on TinyHttpd by the server-wide `headerTimeout` and `bodyReadTimeout`.

#### Rationale

Covers D-323, D-423, D-424, D-425 and residual WebSocket handshake timeout (r5 W2-002); test T21. Measured: TinyHttpd's read loop sends a Ping after one interval without an inbound frame and closes with 1001 after a second such interval, treats any inbound frame as the answer, and its `WebSocketListener` has no Pong callback, so NaruServe runs no ping scheduler (D-423) and cannot measure a separate pong timeout (D-424). TinyHttpd counts Ping and Pong as activity, so a peer that answers pings never idles out there; the idle timeout counts only text and binary messages received or sent (D-425). TinyHttpd at 46b973e has no upgrade-specific deadline; `ServerOptions.headerTimeout` and `bodyReadTimeout` (`ServerOptions.java:29,32`, mapped in the adapter core under D-210) bound the handshake. Deviation (recorded): D-323 asks for a configurable handshake timeout; on TinyHttpd it is satisfied only through these existing server-wide timeouts, and no separate setting is added because it would have no effect. Deferred D-020 TinyHttpd-gap issues (opened by the orchestrator in the run's issue ledger at triage, not patched in TinyHttpd by wave 7): (1) the missing Pong callback of `WebSocketListener`, which blocks a separate pong timeout (D-424); (2) a dedicated upgrade (handshake) deadline (r5 W2-002). AC-3 and AC-7 check the user-facing statement of both gaps in `docs/api/`. Pitfall: a scheduler thread that writes the close frame itself would block on a stalled peer and delay every other session's idle check; it only enqueues and aborts. Rejected alternative: one timer per session; it multiplies threads on API 21. Defaults (30 s ping, 5 min idle) are settled in IR-WS-001.
- [2026-10-20] AC-4 has the client answer the server's close frame. A peer that never answers the close and keeps sending frames keeps the session open: TinyHttpd's closing read timeout restarts on every inbound frame, so such a peer is ended only by its own close, the shutdown abort or `writeTimeout`. This is a TinyHttpd gap under D-020, deferred and not patched by wave 7.

### FR-WS-009 — WebSocket connection limit and session registration: 503 beyond maxUpgradedConnections, reservation before the upgrade, refusal after the closed flag and after STOPPING

| Field | Value |
| --- | --- |
| Type | functional |

#### Requirement

The system shall count WebSocket upgrades against `maxUpgradedConnections` and answer an upgrade beyond it with `503`, reserve each session in the WebSocket session registry under its lock before calling `HttpExchange.webSocket`, refuse the reservation with `503` and `Connection: close` once the registry's closed flag is set, remove the reservation when the handshake is refused, send close `1001` without running the handler for a reserved session whose `onOpen` comes after the flag, and reject upgrade requests arriving after `STOPPING` began without upgrading.

#### Rationale

Covers D-301, D-324, D-445 (WebSocket part: closed flag before snapshot, upgrade answered `503` + `Connection: close` before any `101`) and wave decision Session registration (r2 W2-003). Measured: `ServerOptions.java:41-54` defines `maxUpgradedConnections` (default 128, range up to 65536) and `TinyHttpdAdapter.java:105-116` maps it onto TinyHttpd's `maxUpgradedConnections` (wave 5, FR-ENGINE-004), so TinyHttpd answers `503` + `Retry-After` beyond the limit and FR-WS-002 maps that rejection. D-301 is satisfied by FR-APP-013's stopping gate (requests reaching the dispatcher during `STOPPING` get `503` + `Connection: close`). The closing participant that sets the flag and takes the snapshot is FR-WS-010; the shared coordination across WebSocket and SSE belongs to FR-APP-020 in the APP scope. Pitfall: registering only in `onOpen` would let a session open between the closing participant's snapshot and the flag and escape the 1001 close; the reservation before `webSocket` closes that window. Rejected alternative: a NaruServe-side counter in addition to TinyHttpd's; two counters drift, reopen if a non-TinyHttpd adapter lacks a limit.

### FR-WS-010 — Shutdown of WebSocket sessions: before-wait participant closes with 1001, bounded close wait and abort through UpgradedConnection

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-7 |

| Risk | high |

| Related Docs | - |

#### Requirement

The system shall register a before-wait shutdown participant that sets the WebSocket registry's closed flag, snapshots every reserved and open session, stops the sender executor from taking new messages, discards every session's queued messages, hands close `1001` to each session's sender slot as its last task, waits until every close task returned or until the earlier of 1 s and the time left to the shutdown deadline, and then aborts through `UpgradedConnection.close()` the socket of every session whose close task has not returned.

#### Rationale

Covers D-340, D-343 (WebSocket part), D-435, wave decisions Reserved session at shutdown (r3 W2-003, which replaces the round-2 "abort as soon as its channel is set"), Session opening after the close wait (r4 W2-002) and residual Deadline for shutdown participants (r5 W2-003, WebSocket use of the deadline; the add-only `ShutdownParticipants` overload itself is FR-APP-020 in the APP scope); tests T21 and T44. Measured: `internal/ShutdownParticipants.java:10-50` has a `Phase` enum and `add(Phase, Runnable)` without a deadline; `internal/DefaultRestApp.java:114-127,539-636` holds the shutdown deadline and `runShutdownSequence` (FR-APP-011). The bound rests on the abort alone with no write tracking: closing the socket makes a blocked write throw, including TinyHttpd's read-loop Ping/Pong writes and a close frame blocked on a full receive window, which share one write lock, so TinyHttpd's later stop callback `close(1001)` finds `closeSent` set or the socket closed and returns at once. Deviation (recorded): D-340 says shutdown closes every open session with 1001; a reserved session whose `onOpen` runs after the close wait ended is aborted at once with no close frame (r4 W2-002), which `docs/api/websocket.md` records, so TinyHttpd's stop callback never waits on a blocked close write and D-344's bound holds. Pitfall: waiting the full TinyHttpd write timeout (30 s) on a stalled peer would break the D-344 bound. Rejected alternative: tracking per-write ages to decide what to abort; the abort-all-unreturned rule is simpler and bounded. The closed-flag ordering shared with SSE, the D-344 margin and T44 as a whole are FR-APP-020.
- [2026-10-20] Verification coupling (wave-7 feasibility): AC-5 uses the `ShutdownParticipants` deadline overload owned by FR-APP-020 AC-1. No depends_on FR-APP-020 is declared because FR-APP-020 already depends_on this requirement for its T44 ACs and the reverse edge would form a cycle; implement FR-APP-020 AC-1 first and verify FR-WS-010 and FR-APP-020 in one group.

#### Requirement

The system shall document the wave 7 WebSocket API and decisions in `docs/api/websocket.md`, `docs/api/app.md`, `docs/api/defaults.md` and `docs/api/express-migration.md` with every (미확정) marker owned by issue #13 removed, Express counterparts and Java and Kotlin examples for each API, Java examples that compile and a Kotlin test that compiles and runs the documented usage.

#### Rationale

Covers the documentation parts of D-303 (Origin API and default, handler timing), D-317 (onJson failure), D-321 (overflow policy), D-323 (idle, ping, handshake), D-419 (setting names), D-424 (pong timeout equals ping interval), wave decision Session opening after the close wait (r4 W2-002, docs/api/websocket.md note) and residual WebSocket handshake timeout (r5 W2-002, websocket.md and defaults.md say the handshake is bounded by headerTimeout and bodyReadTimeout); project rule (CLAUDE.md): every public API in `docs/api/` with Express counterpart and Java and Kotlin examples, (미확정) items settled during implementation and their marks removed. Measured (grep on 2026-10-20): `docs/api/websocket.md` lines 34, 54, 74, 97 and 117, `docs/api/app.md` lines 67 and 187, and `docs/api/defaults.md` lines 25, 26 and 89 hold the #13 markers; `docs/api/express-migration.md:101` holds the `app.ws` row. Pitfall: the WaveFiveDocsTest first-match `lineWith(d, "무제한")` on defaults.md must keep finding the same line when WebSocket rows change. The kept-marker lists of the docs tests owned by superseded requirements (OPS-ENGINE-001, OPS-APP-004, OPS-HTTP-006) move to their wave 7 successors in the ENGINE, APP and HTTP scopes; this requirement owns only the WebSocket lines. Rejected alternative: leaving decisions only in the SRS; users read `docs/api/`.
