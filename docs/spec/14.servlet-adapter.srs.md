## 1. Scope Overview

This scope covers the Servlet adapter of NaruServe (issue #19, wave 8): the `NaruServe-servlet` module that implements the `HttpAdapter` SPI on `javax.servlet` 3.1, its container integration (class names, registration, configurer interface and init-parameters), request mapping with the context-path and servlet-mapping stripping, response and exchange semantics, multipart over the core parser, Server-Sent Events under `AsyncContext` with an adapter-owned bounded executor, the `501` answer for WebSocket, stop and release, the ignored server options, the test-scope embedded container, and `docs/api/servlet.md`.

## 2. Scope Boundaries

### In Scope

- `NaruServe-servlet` classes in package `com.snoworca.naruserve.servlet`: the `HttpAdapter` implementation, the `HttpExchange` implementation, the event-stream class, the container integration and the configurer interface (D-358, D-359, D-363).
- Same application types on the Servlet adapter as on the embedded engine, verified by an embedded javax Servlet 3.1 container in test scope only (D-360, D-362).
- SSE under `AsyncContext` (D-361), WebSocket `501`, multipart over the core parser, path handling, stop and release, ignored `ServerOptions` (wave decisions of loop W rounds 1 to 5).
- The `NaruServe-servlet` build placement and `docs/api/servlet.md` (D-358, D-363).

### Out of Scope

- A `jakarta.servlet` module: none exists in v1 (D-358, Q-4).
- Servlet WebSocket support: Servlet 3.1 has no WebSocket API, so `app.ws` answers `501` on this adapter.
- TLS, container pool and port configuration: the container owns them.
- Any change to the `HttpAdapter` or `HttpExchange` SPI: the adapter uses the add-only SPI of waves 5 to 7 (D-106) unchanged (I-014).
- The Android sample build and the Android device verification are out of v1 scope by user decision of 2026-10-20 (D-364 to D-374 and D-412): no requirement of this scope covers them, and no requirement in this scope may call T10, T12 or T47 verified.

## 3. Assumptions and Constraints

- `NaruServe-servlet` is JVM-only: `javax.servlet-api:3.1.0` and `javax.websocket-api:1.1` are `compileOnly` and its `runtimeClasspath` holds `NaruServe-api` only (CON-BUILD-006 AC-5), so the Gson codec is found by reflection (wave decision r5 W2-002).
- The module is not an API 21 module: no animal-sniffer check applies to it, and the seven API 21 modules stay free of `javax.servlet` (CON-BUILD-013, I-004).
- The `HttpAdapter` SPI of waves 5 to 7 is add-only; the Servlet adapter overrides `bind(ServerSettings, ExchangeHandler)` and implements `eventStream`, `sendFile` and `upgrade` as the SPI requires.
- Where the design leaves a choice open, the wave decisions of `docs/research/naruserve-v1/waves/wave-8/design.md` apply; otherwise the implementer decides under standing rule C-07 and `docs/api/servlet.md` records it.
- Source of the requirements: `docs/research/naruserve-v1/waves/wave-8/design.md` (frozen design items, wave decisions of loop W rounds 1 to 5, residual), `docs/research/naruserve-v1/waves/wave-8/excerpt.md`, `docs/research/naruserve-v1/waves/carried-into-wave-8.md` and `object.md`.

#### Requirement

The system shall provide in `NaruServe-servlet`, package `com.snoworca.naruserve.servlet`, the public final class `ServletAdapter` implementing `HttpAdapter`, the public `@FunctionalInterface ServletConfigurer` with `RestApp configure(RestApp.Builder builder) throws Exception`, and the public `NaruServeInitializer` implementing `javax.servlet.ServletContainerInitializer`, registered in `META-INF/services/javax.servlet.ServletContainerInitializer`, which reads the context init-parameters `naruserve.configurer`, `naruserve.urlPattern` and `naruserve.shutdownTimeoutSeconds`; the module has no `jakarta.servlet` counterpart in v1.

#### Rationale

Covers D-358, D-363 (container registration and class names), wave decisions Servlet adapter decisions (r1 W2-007), Who builds the app on the Servlet adapter (r4 W2-003) and Servlet SSE registration (r4 W2-005); answers Q-4. Measured (2026-10-20): `NaruServe-servlet/src/main` holds only `package-info.java`; `build.gradle` declares `javax.servlet:javax.servlet-api:3.1.0` and `javax.websocket:javax.websocket-api:1.1` `compileOnly` for the module; a built `RestApp` has no adapter setter and `RestApp.Builder` takes `httpAdapter`, `jsonCodec` and `logger` (`RestApp.java:226-267`). Decision (C-07): the names are `ServletAdapter`, `ServletConfigurer`, `NaruServeInitializer` and the package-private `NaruServeServlet`; the initializer is discovered through the Servlet 3.0 service file, so an application only sets the init-parameter; `naruserve.urlPattern` defaults to `/*` and accepts `/*`, `/` or `/prefix/*`; the servlet is named `naruserve` and registered with `asyncSupported=true` and no `MultipartConfig`. Decision (C-07): the container's destroy callback calls `app.shutdown(timeout, SECONDS)` because `RestApp` has only `shutdown(long, TimeUnit)`; the timeout is `naruserve.shutdownTimeoutSeconds`, an integer from 1 to 300 with default 10 (the value `docs/api/app.md` uses; a bound exists because no limit may default to unlimited, I-012). When `naruserve.configurer` is absent the initializer does nothing, because the jar may sit in `WEB-INF/lib` of an application that does not use NaruServe. Pitfall: `@HandlesTypes` is not used, so no classpath scan runs at container start. Pitfall: `jetty-servlet` alone does not run `ServletContainerInitializer`s; the tests use a Jetty `WebAppContext` with the annotation configuration so that the services file is discovered, and containers other than Jetty 9.4 are not exercised (recorded in `docs/api/servlet.md`). Rejected alternative: a `ServletContextListener` declared in `web.xml` or by `@WebListener`; it needs the application to list it and `@WebListener` needs annotation scanning, which a jar in `WEB-INF/lib` loses when `metadata-complete=true`.

### FR-SVL-001 — Servlet adapter lifecycle: the container initialises the app with onStart and destroys it with shutdown, binds no socket and reports port 0

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-8 |
| Status | verified |
| Priority | high |
| Tags | wave-8, feasibility:high, servlet, lifecycle |
| Risk | high |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/19 |
| Related Docs | - |

#### Requirement

The system shall start the app on the Servlet adapter when the container initialises the web application — the initializer installs the `ServletAdapter`, finds the Gson codec by reflection, calls the configurer and then `app.listen(0)`, so `onStart` runs and the state becomes `RUNNING` exactly as on the embedded engine — and shall run `app.shutdown(timeout, SECONDS)` with the timeout of `naruserve.shutdownTimeoutSeconds` (default 10) when the container destroys the web application; `ServletAdapter.bind` stores the handler and opens no socket, and `boundPort()` and `ServerHandle.port()` are `0`.

#### Rationale

Covers D-359, wave decisions Servlet start path (r2 W2-001), Port on the Servlet adapter (r3 W2-001, which supersedes the first-request port of round 2), Servlet bind (r4 W2-006), Gson on the Servlet adapter (r5 W2-002) and the D-107 bind contract. Measured (2026-10-20): `HttpAdapter.bind(ServerSettings, ExchangeHandler)` defaults to `bind(host, port, handler)` (`spi/HttpAdapter.java:20-29`); `DefaultRestApp.start` reads `a.boundPort()` once right after bind (`internal/DefaultRestApp.java:506-507`) and `ServerHandle.port()` returns that captured value; `RestApp.Builder.build()` throws `IllegalStateException` without `httpAdapter` or `jsonCodec`; the module `runtimeClasspath` is `NaruServe-api` only (CON-BUILD-006 AC-5). Decision: the destroy callback is a `ServletContextListener` that the initializer adds with `addListener`; a user call of `listen(int)` on an app holding the Servlet adapter takes the same path and binds nothing; `docs/api/servlet.md` tells the reader to take the port from the container. The logger is the one the configurer sets, otherwise the Builder default `ConsoleLogger`, which is also what `RestApp.create()` picks on a JVM without `android.util.Log` (FR-ENGINE-009). Pitfall: because `boundPort()` is read once, a port learned from the first request would never reach `ServerHandle`; round 3 therefore fixed `0`. Pitfall: `Class.forName("com.snoworca.naruserve.gson.GsonJsonCodec")` must use the web application's class loader, not the module's, when the container isolates them. Rejected alternative: a `compileOnly` or `runtimeOnly` dependency on `NaruServe-gson` so the codec is a normal import; it would break the `runtimeClasspath` pin of CON-BUILD-006 AC-5 and I-005.

#### Acceptance Criteria

- [x] AC-1: On the embedded container, context startup builds the app through the configurer and calls `app.listen(0)` before the first request: `onStart` callbacks have run once, `app.state()` is `RUNNING` and a request is served. [D-359]
- [x] AC-2: Context destruction runs `app.shutdown(10, SECONDS)` (or the `naruserve.shutdownTimeoutSeconds` value): `onStop` callbacks run, the state is `TERMINATED`, `ServletAdapter.stop` and `release` have been called, `shutdown` returns within that timeout plus the margin of `docs/api/lifecycle.md`, and a second destruction is harmless. [D-359]

### FR-SVL-002 — Servlet request mapping: raw path minus context path and servlet mapping, raw query, headers, and the same application types as on the embedded engine

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-8 |
| Status | verified |
| Priority | high |
| Tags | wave-8, feasibility:high, servlet, request, paths |
| Risk | high |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/19 |
| Related Docs | - |

#### Requirement

The system shall map each servlet request to the `HttpExchange` values the core expects — `methodToken`, the raw `getRequestURI()` with the context path and the url-pattern prefix the initializer registered stripped at a segment boundary and kept percent-encoded, the raw `getQueryString()`, `getProtocol()`, every header value with duplicates kept and per-name order preserved, `getRemoteAddr()`, `isSecure()` and `getInputStream()` — so that routes, middleware, `Request`, `Response` and `Cookie` behave as on the embedded engine.

#### Rationale

Covers D-360, D-363 (path handling), D-399, D-052, wave decisions Servlet path edge cases (r2 W2-003) and Servlet path and WebSocket answer (r3 W2-004: the remainder is the request URI minus the context path minus the url-pattern prefix, not `getServletPath()`), and I-021. Measured: `HttpExchange.rawPath()` is "the raw request-target path, undecoded" and `httpVersion()` is the request-line version such as `HTTP/1.1` (`spi/HttpExchange.java:27-37`). Decision: context path `/app`, pattern `/api/*` and URI `/app/api/users/%41;v=1` give the path `/users/%41;v=1`; patterns `/*` and `/` strip nothing after the context path; an empty remainder is the path `/`; path parameters (`;name=value`) stay in the path as in Express; when the raw URI does not start with the context path plus the prefix at a segment boundary (the remainder must be empty or start with `/`) the adapter answers `404` with the standard error body through the `ErrorRenderer` of the settings. Pitfall: containers match servlet mappings on the decoded path, so `/app/%61pi/x` can reach the servlet while the raw prefix `/api` does not match; `getServletPath()` and `getPathInfo()` are decoded and normalised and must not be used (D-399). Pitfall: `getParameter*` would consume a form body (FR-SVL-004). Rejected alternative: matching the prefix on the decoded path; it would let an encoded segment change which handler runs.

#### Acceptance Criteria

- [x] AC-1: With context path `/app` and pattern `/api/*`, a request to `/app/api/users/%41;v=1?x=%20` reaches a route `/users/:id` with `req.rawPath()` equal to `/users/%41;v=1`, `req.param("id")` equal to `A;v=1` and `req.query("x")` equal to a space; with pattern `/*` or `/` the same request without `/api` reaches the same route, and a request to the bare servlet root reaches the route `/` (empty remainder is `/`). [D-363; D-399]
- [x] AC-2: A request whose raw URI does not start with the context path plus the registered prefix at a segment boundary (a test sends `/app/%61pi/users` to pattern `/api/*`) is answered `404` with the standard error body and a request id, and `getServletPath()`, `getPathInfo()` and `getParameter*` are never read, which a recording `HttpServletRequest` proxy asserts. [D-363; r3 W2-004]
- [x] AC-3: Headers reach `req.header(name)` and `req.headers(name)` with repeated names kept in their per-name order (the Servlet API gives no cross-name order), `Cookie` request headers reach the core cookie parser unchanged (`req.cookie("s")` returns a NaruServe `Cookie`, never `javax.servlet.http.Cookie`), `req.remoteAddress()` is `getRemoteAddr()` and `req.isSecure()` is `isSecure()`; `app.trustProxy(true)` takes effect in the core (FR-ENGINE-008). [D-360]
- [x] AC-4: A shared case suite — route parameters, query decoding, JSON body and `res.json`, cookies read and written, `404`, `405` with `Allow`, automatic `HEAD` and `OPTIONS`, middleware order, `onError` and the standard error body, `res.file` — runs on the Servlet adapter and on the in-memory adapter with identical statuses and bodies, using the same app definition code, so application code needs no change between engines. [D-360; I-021]
- [x] AC-5: The path-rejection cases of D-052 (malformed percent-encoding, invalid UTF-8, an encoded `/`, an encoded or raw `NUL`, `.` and `..` segments raw and encoded) sent as raw request lines to the embedded container are answered `400`, or `404` when the container normalises the path and never reaches the servlet, and never `2xx`; the `OPTIONS *` request is sent too, and the observed status of every case is recorded in `docs/api/servlet.md`. [D-052; I-021]
- [x] AC-6: Header values the framework writes never contain CR or LF on this adapter, and security-related log lines of the adapter carry no token, session id or file content. [I-016; I-017]

### FR-SVL-003 — Servlet response writing: commit, finish, abort, sendFile and a single start per exchange

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-8 |
| Status | verified |
| Priority | high |
| Tags | wave-8, feasibility:high, servlet, response |
| Risk | high |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/19 |
| Related Docs | - |

#### Requirement

The system shall write each response through the container's `HttpServletResponse` — `commit` sets the status with `setStatus` and writes each header with `addHeader` in the given order, and `Content-Length` with `setHeader` exactly as the core gave it, without `sendError`, never itself adds, removes or changes `Content-Length` (its own code never calls `setContentLength`; a container may still frame a small buffered body with a length), and returns the container's output stream; `finish` completes the response; `abort` marks the exchange aborted so that every later write, `commit` or `finish` throws `IOException`; `sendFile` writes exactly `length` bytes of the file from `offset` in bounded chunks; and a second start of the same exchange throws `IllegalStateException`.

#### Rationale

Covers D-360 (the `Response` behaviour is the core's; the adapter must not alter it), wave decision Servlet adapter semantics left open (r2 W2-006: `abort()` marks the exchange aborted and later writes throw `IOException` because the container owns the socket; response header order is the container's) and the SPI contract of `HttpExchange.commit`, `abort` (idempotent, thread-safe) and `sendFile`. Measured: `spi/HttpExchange.java:55-75` states that the adapter never adds, removes or changes `Content-Length`, that header chars are at most U+00FF and never CR or LF, and that `abort()` may run on any thread while another thread is writing. Decision: header values are written with `addHeader` as given and the `Content-Length` header the core provides with `setHeader` (one rule, no `setContentLength`); the status is set with `setStatus` so the container renders no error page; `abort` does not close the container's socket (the container owns it) and does not call `sendError`; `sendFile` uses `java.io` only (no `java.nio.file`, CON-HTTP-002) and a buffer of at most 64 KiB. Pitfall: `HttpServletResponse.setContentLength` and containers that compute a length for small bodies can change `Content-Length`; the core's header is passed through `setHeader`, and a HEAD response keeps the length the GET body would have had (FR-HTTP-017). Rejected alternative: closing the connection from `abort` through container-specific APIs; it is not portable across containers.

#### Acceptance Criteria

- [x] AC-1: A handler's `res.status(201).header("X-A", "1").send("ok")` reaches the client as status `201`, header `X-A: 1` and body `ok` with the `Content-Length` the core set; a `res.stream` response of unknown length arrives with an intact body and without a `Content-Length` and `Transfer-Encoding` conflict (chunked framing is asserted only for a body larger than the container's output buffer or after a flush, because a container may buffer a small body and frame it with a length); and no error page of the container appears for a `404` or `500` the core produced, because `sendError` is never called. [D-360]
- [x] AC-2: A HEAD request to a GET route returns the `Content-Length` of the GET body and no body bytes, and a `204` and a `304` carry no body, on the embedded container. [D-360; FR-HTTP-017]
- [x] AC-3: After `abort()` the next body write, `commit` or `finish` throws `IOException` (a write already blocked inside the container ends only by the container's write timeout, FR-SVL-006 AC-3), `abort()` called twice is harmless and `abort()` may run on another thread than the writer; a second `commit`, `sendFile` or `eventStream` on one exchange throws `IllegalStateException`. [r2 W2-006]
- [x] AC-4: `res.file` and `res.download` on a file serve the whole file, a single `Range` (`206` with `Content-Range`) and a `416`, byte for byte equal to the in-memory adapter, with `sendFile` copying in chunks of at most 64 KiB, which a spy output stream records, and never reading the file into memory; the class references no `java.nio.file` type. [D-360; FR-STATIC-010]
- [x] AC-5: Response header order on the wire is the container's, `docs/api/servlet.md` says so, and no test of the shared case suite depends on header order. [r2 W2-006]

### FR-SVL-004 — Servlet multipart and form bodies go through the core parser over the request input stream

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-8 |
| Status | verified |
| Priority | high |
| Tags | wave-8, feasibility:high, servlet, multipart |
| Risk | high |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/19 |
| Related Docs | - |

#### Requirement

The system shall serve multipart and urlencoded request bodies on the Servlet adapter through the core parser reading `requestBody()`, the container's input stream, and shall never call `getParts()`, `getPart(...)`, `getParameter*`, or register the servlet with a `MultipartConfig`, so the `app.multipart`, `formLimit` and `jsonLimit` limits of the core apply as on the embedded engine.

#### Rationale

Covers D-363 (multipart support) and wave decision Servlet adapter decisions (r1 W2-007: multipart uses the core parser over the request input stream, not the Servlet `Part` API; `jsonLimit`, `formLimit` and the multipart limits still apply in the core (the wave decision's "body limit"; `RestApp` has no other body limit setting)), r4 W2-005 (no multipart configuration) and I-015. Measured: `internal/MultipartParser.java` is the engine-free parser shared by every adapter (FR-MULTIPART-001). Pitfall: on a POST with `application/x-www-form-urlencoded`, `getParameter*` makes the container read and consume the body, leaving the core an empty stream; the adapter must not touch it. Pitfall: a servlet registered with a `MultipartConfig` makes some containers parse multipart before the servlet and write temp files the core cannot clean. Rejected alternative: `getParts()` with `MultipartConfig` limits; it would duplicate the limits (container versus `app.multipart`) and break the one-parser rule of FR-MULTIPART-001.

#### Acceptance Criteria

- [x] AC-1: On the embedded container, a multipart request with two files and a text field returns the same `req.file`, `req.files`, `req.form` and `req.parts` values as on the in-memory adapter, and a urlencoded form returns its fields, using the shared case suite of FR-SVL-002. [D-363; FR-MULTIPART-003]
- [x] AC-2: A recording `HttpServletRequest` proxy shows that during these requests the adapter reads `getInputStream()` and never calls `getParts`, `getPart`, `getParameter`, `getParameterMap`, `getParameterNames` or `getParameterValues`, and the registered servlet has no multipart configuration. [r1 W2-007; r4 W2-005]
- [x] AC-3: A multipart body above the `app.multipart` file size, part count or total limit is answered `413`, a urlencoded form above `app.formLimit` is answered `413` and a JSON body above `app.jsonLimit` is answered `413`, each with the standard error body, and after the response no upload temporary file of the app remains in `tempDirectory`. [D-363; FR-MULTIPART-002; I-015]
- [x] AC-4: A client that closes the connection in the middle of a multipart upload leaves no upload temporary file after the request ends (T17 on this adapter), which a test asserts by listing `tempDirectory` after the container's request thread returned. [FR-MULTIPART-006; I-015]

### FR-SVL-005 — Servlet SSE under AsyncContext: bounded stream counter, dedicated executor and no async timeout

| Field | Value |
| --- | --- |
| Type | functional |
| Target | wave-8 |
| Status | verified |
| Priority | high |
| Tags | wave-8, feasibility:high, servlet, sse, async |
| Risk | high |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | https://github.com/Snoworca/NaruServe/issues/19 |
| Related Docs | - |

#### Requirement

The system shall implement `HttpExchange.eventStream` on the Servlet adapter so that the exchange counts open streams against `maxSseStreams` (default 128) and answers `503` before the exchange is marked started when the bound is reached, otherwise calls `startAsync()` and `AsyncContext.setTimeout(0)`, commits status and headers, hands the container's output stream to `StreamDrain.attach`, runs the core drain loop on a dedicated bounded executor owned by the adapter — daemon threads named `naruserve-servlet-sse-<n>`, at most `maxSseStreams`, never the container's pool threads — returns at once so the container's request thread is released after the handler returned, and completes the `AsyncContext` when the drain ends.

#### Rationale

Covers D-361, D-106 (the event-stream point), wave decisions SSE bound and thread owner on the Servlet adapter (r3 W2-002) and Servlet SSE registration (r4 W2-005: `asyncSupported=true` and `AsyncContext.setTimeout(0)` per stream), and I-012 and I-015. Measured: `spi/StreamDrain.java` is the core-owned drain loop type with `attach(OutputStream)`; FR-SSE-003 fixes the TinyHttpd mirror (counter that throws a `503` `HttpException` before the exchange is marked started, drain on the request worker). Decision: the Servlet counter is the adapter's own, with the same `maxSseStreams` of the frozen `ServerSettings`; the executor is created at `bind(ServerSettings, handler)`; heartbeat and event writes are flushed after each write so the container does not buffer them. Frozen: D-106 says the adapter chooses the thread that runs the loop ("an `AsyncContext` on the Servlet adapter"). Deviation (recorded): the loop runs on an adapter-owned executor thread, not on the container's request thread; a container pool thread blocked for the life of a stream would exhaust the pool, and the 128-thread bound keeps I-012 (no unbounded default). Deviation (recorded, inherited from FR-SSE-002 for D-406): sends made inside the handler before the drain starts are written directly on the handler thread, synchronised on the exchange, as on TinyHttpd. Pitfall: the default async timeout of a container (30 s on Jetty 9.4) would end a long stream with a `500`, hence `setTimeout(0)`. Pitfall: checking the counter after the exchange is marked started leaves the dispatcher unable to commit the `503` (r3 W2-001 of wave 7). Rejected alternative: running the drain on the container thread with a blocking loop; it holds one container thread per stream.

#### Acceptance Criteria

- [x] AC-1: With `maxSseStreams(2)` and two open streams, a third request whose handler calls `res.sse()` receives `503` with the standard error body and its request id, because the adapter's counter throws a `503` `HttpException` before the exchange is marked started; after one stream ends a new `res.sse()` is accepted, and the counter is released also when the drain fails with `IOException` and when the exchange is aborted. [D-361; r3 W2-002]
- [x] AC-2: The drain runs on a thread named `naruserve-servlet-sse-<n>` that is a daemon and not a container pool thread, the container request thread has returned from `service()` while the stream is open (a test records both thread ids and the return), and the executor never holds more than `maxSseStreams` threads. [D-361; D-106]
- [x] AC-3: The servlet is registered with `asyncSupported=true`; a test filter in front of the servlet records, after the handler called `res.sse()`, that `request.getAsyncContext().getTimeout()` is `0` for every stream; and a stream kept open longer than the container's default async timeout (the test lowers it to 1 s) still receives a heartbeat after 2.5 s and is not ended by the container. [r4 W2-005]
- [x] AC-4: An event sent from another thread after the handler returned reaches the client within 500 ms of the `send`, a `: ping` heartbeat reaches an idle client within `heartbeatInterval` plus 500 ms, and an event sent by the handler thread before the drain starts reaches the client while the handler still runs, each flushed without further writes behind it. [D-361; D-406; FR-SSE-002]
- [x] AC-5: When the drain ends (client close, `close()` or the core's end report) `AsyncContext.complete()` is called, the stream's `onClose` listeners run once, and `abort()` on an SSE exchange also calls `AsyncContext.complete()`. [D-361; r5 W2-001] Abort, timeout or rejected drain submission before the SSE drain starts must still close the core client exactly once, free its registry entry and invoke close listeners.
- [x] AC-6: A stream whose client closed its socket is detected by the next write or heartbeat failing with `IOException`, ends with the access-log cause `client` and returns its executor thread within two heartbeat intervals plus 1 s. [D-361; FR-SSE-004]

#### Requirement

The system shall implement `HttpAdapter.stop(timeout, unit)` on the Servlet adapter so that it first refuses new requests with `503` and `Connection: close`, then waits for the in-flight exchanges until the deadline, and at the deadline calls `shutdownNow()` on the SSE executor and `AsyncContext.complete()` on every stream still open; and `release()` detaches the handler, so that after shutdown no `naruserve-servlet-sse-*` thread and no upload temporary file of the app remains.

#### Rationale

Covers D-359 (shutdown on container destroy), D-107 (two-call stop), wave decisions Servlet stop (r3 W2-003) and Blocked writes of a Servlet SSE stream (r5 W2-001), and I-012, I-015. Measured: the core shutdown sequence runs the before-wait participants (the SSE and WebSocket closing participants, FR-SSE-005) and then `adapter.stop(left(deadline))` (`internal/DefaultRestApp.java:682` `a.stop`, `:705` `a.release`, FR-APP-011). Deviation (recorded under I-012): a drain thread stuck in a socket write to a client that stopped reading is bounded only by the container's own write timeout, which the adapter does not control; the "cut at timeout" promise of `docs/api/sse.md` therefore holds on the Servlet adapter up to that container bound, and the release documentation lists the deviation (OPS-REL-007). Decision: the adapter counts in-flight `service()` calls and open streams under one lock and waits on its condition; refusing by `503` happens before the core handler runs, using the `ErrorRenderer` of the settings. Pitfall: `stop` called from the container's destroy callback may run on a container thread, so it must not wait for container-owned work beyond the deadline. Rejected alternative: interrupting container request threads at the deadline; interrupting a thread the container owns is unsafe.

#### Acceptance Criteria

- [x] AC-1: With one slow plain request in flight, `stop(2, SECONDS)` makes a new request answer `503` with `Connection: close` and the standard error body at once, returns as soon as the slow request finishes (before the deadline), and a request that outlasts the deadline does not make `stop` return later than the deadline plus 1 s. [D-359; r3 W2-003]
- [x] AC-2: With open SSE streams, `shutdown` delivers the closing notice of FR-SSE-005 through the core, each stream's client sees the end of the chunked body within the shutdown timeout plus the D-344 margin, the `AsyncContext` of each stream is completed, and the executor is shut down. [D-359; FR-SSE-005]
- [x] AC-3: A stream whose client stopped reading is cut at the deadline: `stop` returns within the deadline plus 1 s and the stream's `AsyncContext` is completed, so the container closes the output (Jetty frees a blocked writer at once, another container at its own write timeout, which the test does not wait for); the deviation sentence is present in `docs/api/servlet.md` and `docs/api/sse.md` gains a pointer to it. #### Requirement

The system shall answer a real WebSocket upgrade request to a route registered with `app.ws` on the Servlet adapter with status `501` and the standard JSON error body, because `ServletExchange.webSocket` (and `upgrade`) throw `HttpException(501)` instead of the SPI default that leads to `500`, while a request without an upgrade to a path that has only an `app.ws` route keeps the core's `426`.

#### Rationale

Covers D-363 (WebSocket support) and wave decisions Servlet adapter decisions (r1 W2-007: Servlet 3.1 has no WebSocket API, so a route registered with `app.ws` answers `501` with the standard JSON error body and `docs/api/servlet.md` says it is not supported in v1) and Servlet path and WebSocket answer (r3 W2-004: `HttpException(501)` because the SPI default would lead to `500`; this applies only to real upgrade requests). Measured: `HttpExchange.webSocket` defaults to throwing `UnsupportedOperationException` (`spi/HttpExchange.java:99-101`), which the core maps to `500`; the core checks Origin before the upgrade extension point (FR-WS-003) and answers `426` for a non-upgrade request before any adapter call (FR-WS-004). Deviation (recorded, for D-408 over TinyHttpd): TinyHttpd replaces `Connection: Upgrade` on a non-`101` response (FR-WS-004 AC-2); on the Servlet adapter the headers pass through `addHeader` to the container, so the test records whether `Connection: Upgrade` reaches the client and asserts `426` and `Upgrade: websocket` only. Rejected alternative: bridging to `javax.websocket` (it is `compileOnly` in the module); the Servlet adapter would then depend on a container-specific endpoint registration and WebSocket stays a v1 non-goal here.

[D-363; r3 W2-004]

### FR-SVL-008 — Servlet adapter keeps maxSseStreams and the error renderer from the settings and ignores the embedded-engine server options

| Field | Value |
| --- | --- |
| Type | functional |

#### Requirement

The system shall override `HttpAdapter.bind(ServerSettings, ExchangeHandler)` on the Servlet adapter to keep the frozen settings it uses — `maxSseStreams` and the `ErrorRenderer` (and logger) — while `bind(host, port, handler)` only stores the handler, and shall ignore every `ServerOptions` setting that configures the embedded engine (`bindAddress`, `allowedHosts`, `maxHeaderSize`, `maxHeaderCount`, `maxRequestLineLength`, `headerTimeout`, `bodyReadTimeout`, `writeTimeout`, `minBodyRate`, `maxWorkers`, `maxConnections`, `maxUpgradedConnections` and `maxConnectionsPerAddress`), listed as ignored in `docs/api/servlet.md`, while `jsonLimit`, `formLimit` and the `app.multipart` limits still apply in the core.

#### Rationale

Covers D-359, D-363, wave decisions Servlet adapter semantics left open (r2 W2-006) and Servlet bind (r4 W2-006). Measured (2026-10-20): `allowedHosts` is enforced only by the TinyHttpd adapter (`NaruServe-tinyhttpd/.../TinyHttpdAdapter.java:118-120`) and nowhere in `NaruServe-api/src/main` outside `ServerOptions` itself; `bindAddress` and `port` are applied only by the TinyHttpd adapter's bind (`:100`), but the core still logs a LAN warning for a non-loopback `bindAddress` (`internal/DefaultRestApp.java:499`) and `ServerHandle.address()` reports the configured address, so on the Servlet adapter both describe the setting, not the container; `ServerSettings` carries `maxSseStreams` (default 128), `logger` and `errorRenderer` (`spi/ServerSettings.java:32-56`). Decision: the ignored list in `servlet.md` names exactly the `ServerOptions` settings `bindAddress`, `allowedHosts`, `maxHeaderSize`, `maxHeaderCount`, `maxRequestLineLength`, `headerTimeout`, `bodyReadTimeout`, `writeTimeout`, `minBodyRate`, `maxWorkers`, `maxConnections`, `maxUpgradedConnections` and `maxConnectionsPerAddress`, plus the port argument of `listen`; the applied list names `jsonLimit`, `formLimit`, `app.multipart`, `maxSseStreams`, the SSE options and `trustProxy`. Pitfall: because `allowedHosts` is an adapter setting, a Host allowlist the application relies on is not enforced behind a container; `servlet.md` tells the reader to configure virtual hosts in the container. Rejected alternative: enforcing `allowedHosts` in the Servlet adapter; the container owns the connector and virtual host, and a second enforcement would diverge from it.
