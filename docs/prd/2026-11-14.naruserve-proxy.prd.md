> ## 0. 요약
>
> NaruServe 0.11.0의 공개 `Request`·`Response` API로는 **투명한 리버스 프록시를 만들 수 없습니다.** 실측으로 확인한 막힌 지점은 세 가지입니다.
>
> 1. 요청 본문을 원본 그대로(바이트·스트림) 읽을 수 없습니다.
> 2. 요청 헤더 이름을 모두 열거할 수 없습니다.
> 3. 같은 이름의 응답 헤더를 여러 개 보낼 수 없습니다(`res.header`가 덮어씁니다).
>
> 프록시를 별도 모듈에서 공개 API만으로 만들려면 다음 네 가지가 더 필요합니다. 접속 상대가 신뢰된 프록시인지 판정하는 기능, 클라이언트 연결이 끊긴 것을 알리는 기능, `Content-Type`을 강제하지 않고 길이를 보존하는 응답 스트리밍, 헤더 값 검사입니다.
>
> 이 요청서는 두 가지를 요청합니다.
>
> - **요청 A. 원본 접근 API (`naruserve-api`):** Express의 `req`(스트림), `req.headers`·`req.rawHeaders`, `res.append`에 해당하는 API와 위 네 가지 기능입니다. 프록시뿐 아니라 웹훅 서명 검증, 파일 중계처럼 원문이 필요한 모든 기능의 기반입니다.
> - **요청 B. 리버스 프록시 모듈 (`naruserve-proxy`):** `app.use("/api/orders", Proxy.to(url))` 한 줄로 안전한 기본값을 갖춘 프록시를 쓸 수 있게 합니다. `Middleware`만 구현한 객체로 제공합니다. 경로를 붙인 `app.use`는 `Installable`을 거부하므로 `Auth`(`Middleware`와 `Installable`을 함께 구현, `Auth.java:134`)와 달리 `Installable`은 구현하지 않습니다. 백엔드 HTTP 클라이언트가 필요하므로 별도 모듈에 둡니다(§3.9).
>
> urlencoded 폼 필드 이름을 열거하는 API는 프록시가 쓰지 않으므로 이 요청서에 넣지 않고 별도 요청으로 보냅니다.
>

> ## 1. 배경
>
> ### 1.1 요청자의 사용 사례
>
> 요청자는 사내 서비스들의 API 게이트웨이를 NaruServe로 옮기고 있습니다. 게이트웨이는 경로 접두사마다 다른 내부 서비스로 요청을 그대로 넘기며, 프록시에 필요한 기능은 다음과 같습니다.
>
> - 메서드, 전체 경로(마운트 접두사를 떼지 않음), 쿼리, 요청 헤더, 요청 본문(JSON 본문, urlencoded 폼)을 바꾸지 않고 전달합니다. 같은 이름의 헤더가 여러 개여도 모두 전달합니다.
> - 연결·읽기·쓰기 타임아웃을 마운트마다 정합니다. 대용량 조회가 있어 읽기 타임아웃은 분 단위입니다.
> - 일시적인 연결 실패를 재시도하고, 그래도 실패하면 앱이 오류 종류에 따라 JSON 오류 응답을 만듭니다.
> - 게이트웨이를 식별하는 고정 요청 헤더를 붙입니다.
> - 클라이언트 주소와 스킴을 `X-Forwarded-*`로 백엔드에 알립니다.
> - 재시도하면 안 되는 경로는 재시도 없이 전달합니다.
>
> ### 1.2 0.11.0 실측 결과
>
> 0.11.0의 공개 API만으로 프록시 미들웨어를 만들어 JDK `HttpServer` 백엔드와 연결하고 테스트했습니다. 백엔드 호출에는 JDK 11 이상의 `java.net.http.HttpClient`를 썼습니다.
>
> | 시험 | 결과 | 원인 |
> |---|---|---|
> | JSON 본문 전달 | 실패. `{"limit" : 5}`가 `{"limit":5.0}`으로 바뀜 | 원본 바이트를 읽을 수 없어 `body(Object.class)`로 파싱한 뒤 다시 직렬화해야 함. 숫자 의미가 바뀜 |
> | urlencoded 폼 본문 전달 | 실패. 빈 본문이 전달됨 | 폼 필드 이름을 열거할 수 없음. `parts()`는 urlencoded 본문에서 빈 목록 |
> | 임의 요청 헤더 전달 | 실패. `X-Custom`이 전달되지 않음 | `header(name)`·`headers(name)`처럼 이름을 알아야만 읽을 수 있음 |
> | 응답의 `Set-Cookie` 두 개 전달 | 실패. 마지막 값 하나만 남음 | `res.header`가 같은 이름의 헤더를 교체함(Express `res.set`과 같음). 추가 API는 `addCookie`뿐 |
> | 백엔드 응답(상태·헤더·본문) 전달 | 성공 | `res.status`, `res.header`, `res.send(byte[])` |
>
> 직접 구현하면서 함께 드러난 함정은 다음과 같습니다. 이 함정은 실험에 쓴 `java.net.http.HttpClient`를 전제로 한 것이며, 이 클라이언트는 NaruServe의 Java 8·Android API 21 대상에서 쓸 수 없습니다(§3.9). 공식 프록시라면 사용자가 이런 함정을 몰라도 됩니다.
>
> - `HttpClient`의 기본 설정을 쓰면 백엔드에 `Upgrade: h2c` 헤더가 붙습니다.
> - 백엔드 연결 실패가 502가 아니라 500으로 나가고, 타임아웃이 없으면 작업 스레드가 무기한 묶입니다.
> - `Host`, `Connection`, `Content-Length` 같은 제한 헤더를 그대로 넣으면 `IllegalArgumentException`이 발생합니다.
>
> 공개 API의 나머지 한계는 소스에서 확인했습니다.
>
> - 앱의 프록시 신뢰 설정은 `RestApp`의 getter로 읽을 수 있지만, CIDR 판정은 `internal` 패키지(`ProxyTrustSetting`)에 있습니다. 사용자가 앱을 따로 넘기지 않는 한 미들웨어가 `RestApp`에 닿는 길은 `Installable`뿐인데, 경로를 붙인 `app.use`에 `Installable`을 넘기면 거부됩니다(`DefaultRestApp.java:1035-1042`, FR-AUTH-010 AC-7).
> - 클라이언트 끊김 통지는 SPI `HttpExchange.onAbort`에만 있고 `Request`·`Response`에는 없습니다.
> - 헤더 값 검사는 `internal`의 `DefaultResponse.checkHeader`·`isFieldValue`에 있고, 공개 `common.HttpHeaderValues`에는 이름 검사(`isToken`)만 있습니다(`HttpHeaderValues.java:9`).
> - 공개 응답 스트리밍은 `res.stream(InputStream, String contentType)`뿐입니다. `contentType`에 `null`을 줄 수 없고, `Content-Length`를 지운 뒤 길이 미정으로 보냅니다(`DefaultResponse.java:530-586`). 길이를 받는 `sendBody`는 `internal`의 `DefaultResponse`에만 있습니다.
>
> ### 1.3 현재 우회 방법과 그 한계
>
> `RestApp.builder().httpAdapter(...)`로 `TinyHttpdAdapter`를 감싸고, `ThreadLocal`로 SPI `HttpExchange`를 미들웨어에 넘기면 원본에 접근할 수 있습니다. 하지만 이 방법에는 다음 한계가 있습니다.
>
> - 앱 코드가 SPI에 의존합니다.
> - 비동기 핸들러(`Deferred`)에서는 동작이 보장되지 않습니다.
> - 어댑터 단계에서 응답하면 접근 로그와 `onError`를 거치지 않습니다.
>

> ## 2. 요청 A: 원본 접근 API
>
> 요청 A는 `naruserve-api`에 둡니다.
>
> ### A-1. 요청 본문 스트림
>
> ```java
> InputStream in = req.bodyStream();                 // 앱의 rawBodyLimit 적용
> InputStream big = req.bodyStream(512L << 20);      // 이 호출에만 512 MiB 한도 적용
> ```
>
> - 원본 요청 본문을 받은 그대로(`Content-Encoding` 해제 없이, 청크 전송은 해제된 바이트로) 돌려줍니다.
> - 본문이 없으면 빈 스트림을 돌려줍니다. `null`을 돌려주지 않습니다.
> - 본문은 한 번만 읽을 수 있다는 기존 규칙을 따릅니다. `bodyStream`을 부른 뒤 `body(...)`·`form(...)`·`parts()`를 부르거나, 본문을 실제로 가져간 리더 뒤에 `bodyStream`을 부르면 `BodyAlreadyConsumedException`을 던집니다. 폼이 아닌 본문에서 `form(...)`·`parts()`는 본문을 읽지 않고 빈 결과를 돌려주므로(`DefaultRequest.java:275-282`) 그 뒤의 `bodyStream`은 성공합니다. 같은 요청에서 `bodyStream`을 다시 부르면, 같은 한도이고 아직 1바이트도 읽히지 않았을 때만 첫 호출의 스트림을 돌려줍니다. 1바이트라도 읽혔으면 한도와 관계없이 `BodyAlreadyConsumedException`을, 읽히지 않았는데 한도가 다르면 `IllegalStateException`을 던집니다. 앞선 코드가 일부만 읽은 본문을 뒤의 코드가 모른 채 이어 읽는 일을 막기 위해서입니다. `bodyStream()`은 `bodyStream(rawBodyLimit)`과 같은 한도로 봅니다.
> - 읽은 바이트는 다른 본문 리더와 같은 경로(`BodyState.stream`)를 거쳐 접근 로그의 `in=`에 셉니다.
> - 스트림을 닫지 않아도 요청이 끝나면 프레임워크가 정리합니다.
>
> **크기 한도.**
>
> - 기본 한도는 앱 전체에 하나를 두고 `app.rawBodyLimit(bytes)`로 정합니다. 범위는 `1..1073741824`, 기본값은 1 MiB입니다. 기존 `jsonLimit`·`formLimit`의 범위·기본값과 같습니다(`RestApp.java:174-194`).
> - `bodyStream(long maxBytes)`는 그 호출에만 다른 한도를 씁니다. 범위는 `rawBodyLimit`과 같고, 범위를 벗어나면 `IllegalArgumentException`을 던집니다. Express `express.raw({ limit })`처럼 경로마다 한도를 다르게 둘 수 있게 하려는 것입니다.
> - 큰 한도는 위험한 쪽이므로 앱 전체 값을 올리지 않고 필요한 곳에서만 명시적으로 올립니다.
> - `Content-Length`가 한도를 넘으면 `bodyStream` 호출이 바이트를 읽지 않고 곧바로 `HttpException(413)`을 던집니다. `req.body(...)`가 선언된 길이로 한도 초과를 알 때와 같은 시점·같은 예외라서 규칙이 하나로 맞고(`JsonBodyReader.java:39`), 호출하는 쪽은 앱의 한도 값을 몰라도 본문을 읽기 전에 413을 낼 수 있습니다.
> - 청크 전송처럼 길이를 미리 알 수 없으면 읽는 도중 한도를 넘는 순간 `BodyTooLargeException`(`IOException` 하위)으로 거절합니다. 스트림을 읽는 코드는 이미 `IOException`을 처리하므로 비검사 예외가 읽기 루프를 뚫고 나가지 않습니다. 이 예외는 0.11.0에 `internal` 패키지로 이미 있으므로(`internal/BodyTooLargeException.java`) `HttpException`과 같은 공개 패키지 `com.snoworca.naruserve`로 옮깁니다. 또 `StandardErrors.statusOf`는 지금 `HttpException`만 상태 코드로 바꾸고 나머지는 500으로 처리하므로(`StandardErrors.java:19-21`), 이 예외도 413으로 바꾸도록 고칩니다. 그러면 이 예외가 감싸이지 않은 채 핸들러 밖으로 나갈 때 응답은 413이고, 사용자가 다른 예외로 감싸면 일반 예외로 처리됩니다. `bodyStream`을 직접 읽는 코드에서 한도 초과는 이처럼 `HttpException`(413)과 `BodyTooLargeException` 두 형태로 오므로, `onError`에서 한도 초과를 가려내려면 두 형태를 모두 확인한다고 문서에 적습니다. 프록시는 두 형태를 하나로 맞춰 보냅니다(§3.4).
>
> ### A-2. 요청 헤더 열거
>
> ```java
> Set<String> names = req.headerNames();                    // 소문자, 어댑터가 보고한 순서
> List<Map.Entry<String, String>> raw = req.rawHeaders();   // 이름·값 쌍, 어댑터가 보고한 순서·대소문자·중복 보존
> ```
>
> - `headerNames()`는 Express `Object.keys(req.headers)`에, `rawHeaders()`는 Express `req.rawHeaders`에 해당합니다.
> - 두 결과 모두 불변이며, 바꾸려 하면 `UnsupportedOperationException`을 던집니다.
> - 순서와 대소문자는 어댑터가 보고한 대로입니다. 서블릿 어댑터는 컨테이너의 헤더 이름 열거 순서대로 이름별로 값을 묶어 보고하므로(`ServletExchange.snapshotHeaders`, `ServletExchange.java:166-179`) 서로 다른 이름 사이의 줄 순서와 같은 이름의 대소문자 차이는 보존되지 않습니다. 같은 이름의 값 순서와 모든 값은 보존됩니다.
>
> ### A-3. 응답 헤더 추가
>
> ```java
> res.append("Set-Cookie", "a=1");
> res.append("Set-Cookie", "b=2");   // 두 줄 모두 전송
> ```
>
> - Express `res.append`와 같은 이름과 의미입니다. `header`처럼 `Response`를 돌려줍니다. 기존 `header(name, value)`는 지금처럼 교체 동작을 유지합니다.
> - `res.header`와 같은 헤더 검사(`DefaultResponse.checkHeader`)를 적용합니다. 이름은 HTTP 토큰이어야 하고, 값에는 HTAB을 뺀 제어 문자(CR, LF, NUL, DEL 등)와 U+00FF를 넘는 문자가 없어야 합니다. 이 요청서에서 "헤더 검사"는 이 검사를 뜻합니다.
>
> ### A-4. 신뢰된 프록시 판정
>
> ```java
> boolean trusted = req.isFromTrustedProxy();
> ```
>
> - 접속 상대(`req.socketAddress()`)를 앱의 현재 신뢰 설정이 신뢰하면 `true`입니다. 판정 기준은 `req.remoteAddress()`가 전달 헤더를 따를지 정하는 기준과 같습니다(`RestApp.java:226-260`).
>
> | 앱 설정 | 결과 |
> |---|---|
> | 설정 없음, `trustProxyHops(0)`, 빈 `trustProxyCidrs()` | `false` |
> | `trustProxyHops(n)`, n ≥ 1 | `true` |
> | `trustProxyCidrs(...)` | 접속 상대가 CIDR 안에 있을 때만 `true` |
> | `trustProxy(true)` (레거시) | `true` |
>
> - 이름은 기존 `isSecure()`의 형태를 따릅니다. Express에서는 `app.get('trust proxy fn')(req.socket.remoteAddress, 0)`에 해당합니다.
>
> ### A-5. 클라이언트 끊김 통지
>
> ```java
> res.onAbort(() -> backend.close());
> ```
>
> - 응답이 정상으로 끝나기 전에 전송이 비정상 종료되면(클라이언트가 연결을 끊음, `res.abort` 호출 등) 등록한 콜백을 한 번 부릅니다. 정상으로 끝난 응답에서는 부르지 않습니다.
> - 이미 중단된 뒤에 등록하면 곧바로 부릅니다. 반환형은 `void`입니다.
> - 콜백은 요청 스레드가 아닌 스레드에서 불릴 수 있습니다. 콜백의 예외는 다른 콜백과 전송 정리를 막지 않습니다.
> - 어댑터는 입출력이 없는 동안의 끊김을 다음 입출력 전까지 알리지 않을 수 있습니다. SPI `HttpExchange.onAbort`의 계약(IR-HTTP-009)을 그대로 공개 API로 옮긴 것이며, 이름도 `res.abort`와 같은 어휘를 씁니다.
> - SPI `HttpExchange.onAbort`의 기본 구현은 인자만 검사하고 아무것도 하지 않으므로(`HttpExchange.java:107-118`), 이를 재정의하지 않은 사용자 정의 어댑터에서는 클라이언트가 끊어도 콜백이 불리지 않을 수 있습니다. 이 한계를 문서에 적습니다.
>
> ### A-6. 길이를 보존하는 응답 스트리밍
>
> ```java
> res.status(200);
> res.relay(in, 1024L);   // Content-Length: 1024, Content-Type은 이미 설정한 값만
> res.relay(in, -1L);     // 길이 미정, 프레이밍은 어댑터가 정함
> ```
>
> - 기존 `stream(InputStream, String contentType)`과 다른 이름을 씁니다. 기존 메서드는 `Content-Type`을 정하고 길이를 버리는 반면, `relay`는 `Content-Type`을 추가하거나 바꾸지 않고 길이를 보존합니다. 이름의 이유는 §5 #17에 적습니다.
> - `Content-Type`·`Content-Length` 말고는 앞서 응답에 설정한 헤더(`res.header`·`res.append`·`addCookie` 등)만 나갑니다. 앱의 `defaultCache`(`RestApp.defaultCache`)는 적용하지 않습니다. 기존 응답은 커밋할 때 `Cache-Control`이 없으면 이 값을 붙이지만(`DefaultResponse.java:933-938`), 중계하는 응답에 앱의 캐시 정책을 덧붙이면 원래 응답의 의미가 바뀌기 때문입니다.
> - `contentLength`가 0 이상이면 `Content-Length`를 그 값으로 두고 정확히 그만큼 보냅니다. 스트림이 그보다 먼저 끝나면 응답을 중단합니다. `-1`이면 길이 미정으로 보냅니다. `-1` 미만이면 `IllegalArgumentException`을 던집니다.
> - HEAD 요청과 204·304 응답에서는 본문을 보내지 않습니다. HEAD와 304에서는 0 이상인 `contentLength`를 `Content-Length`로 유지하고, 204에서는 `Content-Length`를 보내지 않습니다(RFC 9110 §8.6). 기존 `res.send`는 304에서 `Content-Length`를 지우므로(`DefaultResponse.java:925`) 이 점이 다릅니다.
> - 응답이 스트림을 소유하는 규칙은 기존 `stream`과 같습니다.
>
> ### A-7. 헤더 값 검사
>
> ```java
> boolean ok = HttpHeaderValues.isFieldValue(value);   // com.snoworca.naruserve.common
> ```
>
> - A-3의 헤더 검사 중 값 검사를 공개합니다. 지금 `internal`의 `DefaultResponse.isFieldValue`가 하는 판정과 같고, 이름 검사는 이미 공개된 `HttpHeaderValues.isToken`을 씁니다. 별도 모듈인 프록시가 `internal`에 의존하지 않고 헤더 검사를 하기 위해 필요합니다.
>

> ## 3. 요청 B: 리버스 프록시 모듈
>
> ### 3.1 API 형태
>
> ```java
> import com.snoworca.naruserve.proxy.Proxy;   // naruserve-proxy 모듈
>
> // 가장 짧은 형태: 기본값만으로 안전하게 동작해야 합니다.
> app.use("/api/orders", Proxy.to("http://127.0.0.1:8081"));
>
> // 옵션을 쓰는 형태
> app.use("/api/users", Proxy.to("http://127.0.0.1:8082")
>         .requestHeader("X-Gateway-Source", "gateway")
>         .connectTimeout(3, TimeUnit.SECONDS)
>         .readTimeout(30, TimeUnit.SECONDS)
>         .retries(2));
> ```
>
> - `Proxy.to(url)`은 `Middleware`를 구현한 불변 객체를 돌려줍니다. 옵션 메서드는 새 객체를 돌려줍니다. 파생 객체가 동시 요청 카운터를 물려받는 규칙은 §3.6에 적습니다.
> - 대상 URL은 `http` 또는 `https`의 스킴, 호스트, 포트, 선택적 기본 경로로 이루어집니다. 쿼리, 프래그먼트, 사용자 정보(`user@`)가 있거나 형식이 잘못되면 `Proxy.to` 호출 시 `IllegalArgumentException`을 던집니다.
> - 기본 경로는 `Proxy.to` 호출 시 끝의 `/`를 모두 뗀 값으로 정합니다. 그래서 `http://h:8081/`의 기본 경로는 빈 문자열이고, 프록시가 스스로 `//`가 든 경로를 만들지 않습니다.
> - 기본 경로가 있으면 전달 경로 앞에 붙습니다. 예를 들어 `/api/orders`에 마운트한 `Proxy.to("http://h:8081/api/orders")`는 `/api/orders/x`를 `/api/orders/api/orders/x`로 보냅니다. 백엔드가 같은 경로를 쓰면 출처(스킴·호스트·포트)만 넘깁니다.
> - 시간 옵션은 기존 `ServerOptions`처럼 `(long, TimeUnit)`을 받습니다. NaruServe는 API 26 이상인 `java.time`을 쓰지 않으며(`utils/TimeSource.java:5`), `NaruServe-kotlin`도 Android API 21 서명 검사 대상이므로 `Duration` 오버로드는 두지 않습니다.
> - Kotlin에서도 `Proxy.to(url).readTimeout(30, TimeUnit.SECONDS)`처럼 같은 형태로 쓸 수 있어야 합니다.
> - 클래스 이름 `Proxy`는 `java.net.Proxy`, `java.lang.reflect.Proxy`와 겹치므로 패키지를 `com.snoworca.naruserve.proxy`로 명시합니다. 이름 자체는 결정 사항입니다(§5 #12).
>
> ### 3.2 요청 전달 규칙
>
> | 항목 | 기본 동작 |
> |---|---|
> | 메서드 | 받은 토큰 그대로. 확장 메서드 포함. 토큰(RFC 9110 §9.1)이 아니면 400. 단, `CONNECT`·`TRACE`는 백엔드로 보내지 않고 405로 응답. `Allow`에는 표준 메서드 `GET, HEAD, POST, PUT, DELETE, PATCH, OPTIONS`만 나열(확장 메서드는 백엔드마다 달라 나열하지 않음). authority-form `CONNECT`(`CONNECT host:443`)는 어댑터가 먼저 응답하므로 프록시에 닿지 않음(`Dispatcher.java` 클래스 주석) |
> | 업그레이드 요청 | `Upgrade` 헤더는 hop-by-hop으로 지우고 요청은 전달(RFC 9110 §7.8은 서버가 `Upgrade`를 무시하는 것을 허용). WebSocket 업그레이드 요청(`com.snoworca.naruserve.routing.Router.isWebSocketUpgrade`와 같은 기준: `GET`, `Connection`에 `upgrade`, `Upgrade`에 `websocket`)만 백엔드로 보내지 않고 `next()`로 넘김. 그래서 같은 접두사 아래의 `app.ws` 라우트가 그 요청을 처리함(§5 #21) |
> | 경로와 쿼리 | **원래 raw 경로 전체**(`originalUrl()`)를 대상 기본 경로 뒤에 붙임. 마운트 접두사를 떼지 않음. 쿼리는 인코딩 그대로. 아래 경로 검사를 통과해야 함 |
> | 본문 | 메모리에 모으지 않고 `req.bodyStream`(A-1)으로 읽어 스트림으로 전달. 길이 표시는 아래 본문 프레이밍 규칙을 따름 |
> | 헤더 | 어댑터가 보고한 순서·중복을 보존해 전달. 단, hop-by-hop 헤더(아래)는 제거. 여러 줄로 온 `Cookie`는 받은 순서대로 `; `로 이어 한 줄로 보냄(RFC 9113 §8.2.3, HTTP/2로 받은 요청 대비). `Via`는 붙이지 않고 `Max-Forwards`는 받은 그대로 전달함(§5 #22) |
> | `Expect` | 백엔드로 보내지 않음. 클라이언트에 대한 `100 Continue`는 프록시가 따로 처리하지 않고 어댑터의 처리를 따름 |
> | `Host` | 대상의 호스트로 바꿈(기본 포트가 아니면 `:포트` 포함, IPv6 리터럴은 대괄호로 감쌈). 원래 값은 `X-Forwarded-Host`로 전달. `Host`가 여러 줄이면 백엔드에 연결하지 않고 400(RFC 9112 §3.2). 어댑터가 `Host`를 보고하지 않으면 `.preserveHost(true)`여도 대상의 호스트를 보냄 |
> | 전달 정보 헤더 | 아래 신뢰 규칙대로 붙이거나 교체하거나 제거함 |
> | 백엔드와의 프로토콜 | HTTP/1.1. h2c 업그레이드를 시도하지 않음 |
> | 고정 헤더와 제거 | `.requestHeader(name, value)`로 추가하고 `.removeRequestHeader(name)`으로 클라이언트가 보낸 헤더를 지움. 둘 다 위의 헤더 처리(제거, `Host`, 전달 정보 헤더)를 모두 마친 뒤 적용함. `.requestHeader`는 같은 이름이 있으면 교체함. 같은 이름에 두 옵션을 여러 번 부르면 나중 호출만 남음. 게이트웨이가 인증 뒤에 붙이는 내부 헤더(`X-User-Id` 등)를 클라이언트가 위조해 보내면 백엔드가 그대로 믿으므로, 그런 헤더는 `.removeRequestHeader`로 지움(§5 #20) |
>
> **hop-by-hop 헤더:** `Connection`과 `Connection`에 나열된 헤더, 그리고 RFC 9110 §7.6.1이 예로 드는 `Keep-Alive`, `Proxy-Connection`, `TE`, `Transfer-Encoding`, `Upgrade`를 제거합니다. 다음 홉에만 해당하는 `Proxy-Authenticate`, `Proxy-Authorization`(RFC 9110 §11.7.1·§11.7.2)도 제거합니다. 프록시는 트레일러를 전달하지 않으므로 `Trailer`도 제거합니다. 요청과 응답 양쪽에 적용합니다.
>
> **전달 헤더 검증:** 0.11.0은 헤더 검사를 응답 쪽(`res.header`)에만 둡니다. 프록시는 클라이언트에게서 받아 백엔드로 쓰는 헤더에도 같은 헤더 검사(A-3)를 적용해, 통과하지 못하면 백엔드에 연결하지 않고 400으로 응답합니다(RFC 9110 §5.5). 백엔드로 쓰는 헤더는 ISO-8859-1로 인코딩합니다.
>
> **본문 프레이밍:** RFC 9112 §6.1·§6.3에 맞춰 백엔드로 보내는 요청의 길이 표시를 다음처럼 정합니다. 백엔드로 보내는 길이 표시는 클라이언트의 헤더를 복사하지 않고 프록시가 실제로 보내는 본문에 맞춰 새로 씁니다. 길이 표시가 모호한 요청은 요청 스머글링의 통로이므로 백엔드로 보내지 않습니다. 여러 줄로 온 `Transfer-Encoding`은 받은 순서대로 쉼표로 이은 하나의 목록으로 보고, 코딩 이름은 대소문자를 구분하지 않습니다.
>
> | 클라이언트 요청 | 동작 |
> |---|---|
> | `Transfer-Encoding: chunked` 하나만 | 청크 전송으로 전달. `Content-Length`는 보내지 않음 |
> | `Transfer-Encoding` 없이 `Content-Length` 하나(또는 같은 값 여러 개) | 그 길이로 전달. 본문이 그 길이보다 먼저 끝나면 백엔드 연결을 닫아 불완전한 요청이 처리되지 않게 함 |
> | 둘 다 없음 | 본문 스트림을 1바이트 미리 읽어, 곧바로 끝이면 본문 없이 전달하고, 바이트가 있으면 청크 전송으로 전달. 본문 없이 전달할 때 `POST`·`PUT`·`PATCH`에는 `Content-Length: 0`을 붙이고(RFC 9110 §8.6, 길이 없는 요청을 411로 거절하는 백엔드 대비), 그 밖의 메서드에는 길이 표시를 붙이지 않음. HTTP/2로 받은 요청처럼 길이 헤더 없이 본문이 오는 경우에도 본문을 잃지 않기 위함 |
> | `Content-Length`와 `Transfer-Encoding`이 함께 있음 | 400. TinyHttpd는 디스패치 전에 400으로 응답하므로(06.engine-adapter FR-ENGINE-003 AC-6) 다른 어댑터를 위한 이중 방어 |
> | 서로 다른 `Content-Length` 값이 여러 개, 또는 숫자가 아닌 `Content-Length` | 400 |
> | `Transfer-Encoding`의 마지막 코딩이 `chunked`가 아니거나 `chunked`가 두 번 이상 있음(`chunked, chunked`) | 400 |
> | `chunked` 앞에 다른 코딩이 있음(`gzip, chunked` 등) | 501 |
>
> 위 표의 400·501 판정은 어댑터가 받은 `Content-Length`·`Transfer-Encoding` 헤더를 그대로 보고한다는 전제에 기댑니다. HTTP/1.0 요청의 `Transfer-Encoding`(RFC 9112 §6.1)은 공개 `Request`가 요청의 HTTP 버전을 알려 주지 않으므로 프록시가 구분하지 않고 어댑터의 처리에 맡깁니다.
>
> **`X-Forwarded-*` 신뢰 규칙:** NaruServe의 신뢰 설정은 `X-Forwarded-For`·`X-Forwarded-Proto`만 해석하므로(`RestApp.java:226-260`) 프록시는 이 두 헤더만 신뢰 여부에 따라 다르게 다룹니다.
>
> - `X-Forwarded-For`: 접속 상대를 신뢰하면(`req.isFromTrustedProxy()`, A-4) 기존 값 뒤에 소켓 주소를 덧붙이고, 신뢰하지 않으면 소켓 주소로 교체합니다. 여러 줄로 온 기존 값은 받은 순서대로 쉼표로 이어 한 줄로 만든 뒤 덧붙입니다. IPv6 소켓 주소는 Express `req.ip`처럼 대괄호 없이 쓰고, 어댑터가 대괄호나 `%` 뒤의 zone id를 붙여 보고하면 떼어 냅니다.
> - `X-Forwarded-Proto`: 항상 `req.isSecure()`에 따른 `https` 또는 `http` 하나로 교체합니다. `isSecure()`가 신뢰 설정에 따라 받은 값을 이미 반영합니다.
> - `X-Forwarded-Host`: 신뢰 여부와 `.preserveHost`와 관계없이 항상 어댑터가 보고한 `Host` 값으로 교체합니다. 그래서 신뢰하는 앞단 프록시가 보낸 `X-Forwarded-Host`도 덮어씁니다. `Host`가 없으면 보내지 않습니다. absolute-form 요청에서 RFC 9112 §3.2.2에 따라 요청 대상의 authority로 `Host`를 대신하는 일은 어댑터의 몫이며, 프록시는 authority를 따로 해석하지 않습니다.
> - `Forwarded`(RFC 7239), `X-Real-IP`, `X-Forwarded-Port`, `X-Forwarded-Prefix`는 신뢰 여부와 관계없이 제거합니다. 신뢰 설정이 해석하지 않는 헤더는 접속 상대를 신뢰해도 앞단이 정리했다는 보장이 없기 때문입니다. `X-Forwarded-Prefix`처럼 마운트마다 값이 고정인 헤더가 백엔드에 필요하면 `.requestHeader`로 보냅니다.
> - `trustProxy(true)`(레거시)는 클라이언트가 주소를 위조할 수 있다고 `RestApp` 문서가 경고하므로 권장하지 않습니다.
>
> **프록시 뒤에서는 접속 주소 기반 검사를 믿을 수 없습니다.** 백엔드가 접속 주소를 보면 모든 요청이 프록시(같은 호스트면 `127.0.0.1`)에서 온 것으로 보입니다. 백엔드가 `X-Forwarded-For`의 맨 왼쪽 값을 보면, 신뢰 모드에서는 클라이언트가 보낸 값이 맨 왼쪽에 그대로 남으므로 클라이언트가 주소를 위조할 수 있습니다. 어느 쪽이든 "localhost에서 온 요청만 허용" 같은 백엔드 검사는 우회됩니다. 프록시 문서는 이 사실을 경고하고, 그런 검사를 접속 주소가 아닌 수단(관리 키, 외부에 열지 않는 별도 포트 등)으로 바꿔야 한다고 안내합니다.
>
> **경로 검사:** 0.11.0의 경로 매칭은 raw 경로를 디코딩도 정규화도 하지 않고(`HttpPathPattern.java:8`), 공통 HTTP 경로 처리는 raw 경로가 `/`로 시작하는지만 검사합니다(`Dispatcher.java:222`, FR-HTTP-027 AC-2). `PathValidator`는 레거시 경로에서만 돕니다(`Dispatcher.java:384`). 반면 백엔드는 흔히 디코딩·정규화한 경로로 라우팅하고, 빈 세그먼트를 버리는 라우터도 있습니다. 그래서 `/api/orders/../other/x`는 백엔드의 정규화로 마운트 밖 경로에 닿고, `/api/orders/%70rivate`, `/api/orders/private;x`, `/api/orders//private`는 게이트웨이의 `/api/orders/private` 매칭(예: 앞에 둔 차단 미들웨어)을 피한 뒤 백엔드에서 `/api/orders/private`로 해석될 수 있습니다. 이를 막기 위해 프록시는 백엔드로 보내기 전에 raw 경로를 세그먼트별로 검사해 다음 중 하나라도 있으면 400으로 거부합니다. 퍼센트 인코딩은 대소문자를 구분하지 않습니다.
>
> - `.` 또는 `..`인 세그먼트
> - 빈 세그먼트(`//`). 경로 끝의 `/` 하나는 허용합니다.
> - `;`(세그먼트 매개변수). 일부 서버는 세그먼트 매개변수를 떼고 경로를 해석하기 때문입니다.
> - 퍼센트 인코딩된 unreserved 문자(영문자, 숫자, `-`, `.`, `_`, `~`, 예: `%2e`, `%70`). RFC 3986 §6.2.2.2는 디코딩해도 같은 URI로 봅니다. Java `URLEncoder`처럼 `~`를 `%7E`로 인코딩하는 클라이언트도 있으므로 그런 경로는 400이 되며, 이 비용은 매칭 우회를 막기 위해 감수합니다.
> - `%2f`, `%5c`, `%00`과 역슬래시 `\`
> - 한 번 디코딩한 결과에 다시 위 두 항목의 인코딩이 나오는 이중 인코딩(`%252e`, `%252f` 등)
>
> **요청 대상 문자:** raw 경로와 쿼리에 제어 문자와 공백(0x00~0x20, 0x7F), 비ASCII 바이트, `#`, 뒤에 16진수 두 자리가 오지 않는 `%`가 있으면 400으로 거부합니다(RFC 9112 §3.2, RFC 3986 §2). 그 밖의 문자는 받은 그대로 전달합니다.
>
> `OPTIONS *`는 프레임워크가 직접 204로 응답하고, `/`로 시작하지 않는 raw 경로는 400이 되므로(`Dispatcher.java:219-222`) 프록시에 닿지 않습니다. 그래서 어댑터가 absolute-form 요청(`GET http://host/x`)의 raw 경로를 `http://`로 시작하는 값으로 보고하면 프레임워크가 400으로 응답하고, `/`로 시작하는 경로로 보고하면 프록시는 그 경로에 다른 요청과 똑같이 대상 고정과 경로 검사를 적용합니다.
>
> **대상 고정:** 요청 경로가 어떤 값이어도(`//evil.example`, `@`, `%2F` 포함) 대상의 스킴·호스트·포트는 바뀌지 않아야 합니다.
>
> ### 3.3 응답 전달 규칙
>
> | 항목 | 기본 동작 |
> |---|---|
> | 상태 코드 | 백엔드 값 그대로(4xx·5xx 포함). 1xx 중간 응답은 전달하지 않음 |
> | 헤더 | 순서·중복 보존(`Set-Cookie` 여러 개 포함). 백엔드가 보낸 이름마다 첫 줄은 `res.header`로 교체하고 이후 줄은 `res.append`(A-3)로 추가. 그래서 프록시 전에 앱이 같은 이름으로 정한 응답 헤더(CORS 헤더 등)는 백엔드 값으로 바뀌고, 백엔드가 보내지 않은 이름은 남음. 단, `Set-Cookie`와 `Vary`는 교체하지 않고 모두 `res.append`로 추가해 앱이 정한 값을 남김. `Set-Cookie`는 쿠키마다 따로 설정되는 헤더이고, `Vary`는 목록 헤더라 여러 줄이 한 줄로 합친 것과 같기 때문임(RFC 9110 §5.3). 그래서 앱이 정한 `Vary: Origin`이 백엔드의 `Vary`에 지워지지 않음. hop-by-hop 헤더와 `Connection`에 나열된 헤더 제거. `Content-Length`는 헤더로 복사하지 않고 `res.relay`의 길이 인자로만 넘김. 공개 `Response`에는 헤더를 지우는 메서드가 없어, 프록시 앞에서 앱이 정한 `Content-Type`·`Content-Encoding`·`ETag` 같은 표현 메타데이터 헤더를 백엔드가 보내지 않으면 그 값이 백엔드 본문에 붙어 나감. 프록시 문서는 이런 헤더를 프록시 앞에서 정하지 말라고 안내함 |
> | 고정 응답 헤더와 제거 | `.responseHeader(name, value)`는 백엔드 헤더 복사와 `Location` 재작성을 마친 뒤 `res.header`로 적용하므로, 백엔드와 앱이 정한 같은 이름의 값을 모두 교체함(게이트웨이의 `Strict-Transport-Security`·`Content-Security-Policy` 고정 등). `.removeResponseHeader(name)`은 백엔드가 보낸 그 이름의 줄을 복사하지 않으며, 프록시 앞에서 앱이 정한 같은 이름의 값은 남김(`Server`·`X-Powered-By` 숨김 등). 같은 이름에 두 옵션을 여러 번 부르면 나중 호출만 남음. nginx의 `proxy_hide_header`·`add_header`에 해당함 |
> | 본문 | `res.relay(InputStream, long)`(A-6)으로 스트림 전달. `Content-Type`이 없는 응답에 값을 지어내지 않고, 백엔드의 `Content-Length`를 보존함. HEAD 요청이면 본문 없이 `Content-Length`만 유지 |
> | 리다이렉트 | 따라가지 않음 |
> | `Location` | 아래 규칙대로 재작성. `.rewriteLocation(false)`로 끔 |
>
> **`Location` 재작성:** 절대 URL이 대상과 출처(스킴·호스트·포트, 기본 포트는 생략한 것과 같게 보고, 스킴과 호스트는 대소문자를 구분하지 않음(RFC 3986 §6.2.2.1))가 같고, 경로가 대상 기본 경로와 같거나 기본 경로 뒤에 `/`가 이어지면 재작성합니다. 출처와 기본 경로 부분을 "클라이언트 쪽 접두사"로 바꿔 출처 없는 절대 경로를 만듭니다. 클라이언트 쪽 접두사는 `stripPrefix(true)`이면 마운트 접두사, 아니면 빈 문자열입니다. 마운트 접두사는 `app.use`에 적은 문자열이 아니라 그 요청에서 실제로 매칭된 접두사인 `req.baseUrl()`입니다(`HttpExecution.java:221-227`). 결과 경로가 비면 `/`로 둡니다. 조건에 맞지 않는 값과 상대 URL은 그대로 둡니다. 예를 들어 대상이 `http://h:808`이면 `http://h:8080/x`는 재작성하지 않고, 대상이 `http://h/base`이고 마운트가 `/api/orders`이면 `http://h/base/api/orders/y`는 `/api/orders/y`가 됩니다.
>
> `Location` 재작성이 기본값인 이유는 `Host`를 대상 호스트로 바꾸기 때문입니다. 백엔드가 절대 URL로 리다이렉트하면 내부 주소가 클라이언트에 노출되고 클라이언트가 그 주소로 이동하려다 실패합니다. nginx `proxy_redirect default`와 비슷한 동작입니다. 결과에 출처를 넣지 않는 이유는 받은 `Host`가 클라이언트가 임의로 정하는 값이라, 공유 캐시가 그 3xx를 저장하면 다른 클라이언트에게 위조한 호스트가 전달되기 때문입니다. RFC 9110 §10.2.2는 `Location`에 상대 참조를 허용하며, 클라이언트는 이를 요청 URI 기준으로 해석합니다.
>
> ### 3.4 오류와 타임아웃
>
> | 상황 | 동작 | `ProxyException.kind()` |
> |---|---|---|
> | 연결 수립 실패(연결 거부, 이름 해석 실패, 연결 타임아웃이 아닌 TLS 핸드셰이크 실패 등) | 502 | `CONNECT_FAILED` |
> | 연결 타임아웃 | 504 | `CONNECT_TIMEOUT` |
> | 쓰기 타임아웃 | 504 | `WRITE_TIMEOUT` |
> | 읽기 타임아웃 | 504 | `READ_TIMEOUT` |
> | 전체 시간 상한 초과 | 504 | `TOTAL_TIMEOUT` |
> | 백엔드 응답 오류: 형식 오류(§3.9), 응답을 끝까지 보내지 않고 연결이 끊김(상태 줄 전의 reset·EOF 포함) | 502 | `INVALID_RESPONSE` |
> | 동시 요청 상한 초과(§3.6) | 503, 백엔드에 연결하지 않음 | `CONCURRENCY_LIMIT` |
> | 응답을 보내기 시작한 뒤의 오류 | 클라이언트 연결을 중단(아래 설명) | 위와 같음 |
> | 클라이언트가 연결을 끊음 | `res.onAbort`(A-5) 통지를 받으면 백엔드 연결을 닫음. 통지 시점의 한계는 §3.6 | 해당 없음 |
>
> - 응답을 보내기 전의 백엔드 쪽 오류는 `ProxyException`(`HttpException`의 하위 클래스)으로 일반 오류 흐름에 보냅니다. `status()`는 위 표의 값이고, `kind()`는 오류 종류 열거형이며, 원인 예외는 `getCause()`에 담습니다. 그래야 앱이 등록한 오류 미들웨어나 `onError`가 오류 종류별로 JSON 등 원하는 형태로 응답할 수 있습니다.
> - `ProxyException`의 메시지는 `null`로 두어 기본 오류 응답에 상태의 표준 사유 문구가 나가게 합니다. 기본 오류 처리는 상태가 500이 아닌 `HttpException`의 메시지를 응답 본문에 그대로 넣으므로(`StandardErrors.java:23-28`), 원인 메시지를 넣으면 대상 주소가 클라이언트에 나갈 수 있습니다. 대상 주소와 원인 메시지는 `getCause()`와 로그에만 남깁니다.
> - 클라이언트 쪽 요청 본문을 읽다 예외가 나면 백엔드 연결을 닫고 그 예외를 오류 흐름에 보냅니다. 읽는 도중의 `BodyTooLargeException`은 `HttpException(413, null, cause)`로 감싸 보냅니다. `bodyStream` 호출이 던지는 413도 `HttpException`이므로(A-1), 프록시 사용자의 `onError`는 한도 초과를 `HttpException`의 상태 413 하나로 가려냅니다. 그 밖의 예외는 감싸지 않습니다.
> - 앞선 코드가 본문을 사용해 `req.bodyStream`이 A-1의 규칙대로 `BodyAlreadyConsumedException` 또는 `IllegalStateException`을 던지면, 감싸지 않고 오류 흐름에 보내며 백엔드에 연결하지 않습니다. 두 예외는 `HttpException`이 아니므로 기본 오류 처리에서는 500입니다(`StandardErrors.statusOf`).
> - 조기 응답은 최선 노력으로만 전달합니다. 블로킹 클라이언트는 본문을 쓰는 동안 응답을 동시에 읽지 않으므로, 백엔드가 본문을 다 읽기 전에 응답(401·413 등)을 보내고 연결을 닫아 쓰기가 실패하면, 그때 소켓에 남은 응답 읽기를 시도합니다. 완전한 상태 줄과 헤더를 읽으면 본문 전송을 멈추고 그 응답을 전달하고, 읽지 못하면 `INVALID_RESPONSE`입니다. 백엔드가 RST로 닫으면 수신 버퍼가 버려져 응답을 잃을 수 있습니다. 클라이언트가 보내던 나머지 본문은 더 읽지 않으며, 그 연결의 처리는 어댑터의 규칙을 따릅니다.
> - 응답을 보내기 시작한 뒤에는 본문 복사를 프레임워크가 하므로(§3.6) 프록시가 `res.abort`를 직접 부르지 않습니다. 대신 백엔드 응답 스트림이 `ProxyException`을 원인으로 담은 `IOException`을 던지고, 프레임워크가 그 예외로 클라이언트 연결을 중단합니다. 0.11.0의 `abort(Throwable)`은 원인을 저장하지 않으므로(`DefaultResponse.java:740-762`), 프록시는 그 예외를 던지기 전에 앱 로거(`req.application().logger()`)에 `ProxyException`을 기록해 오류 종류를 남깁니다.
> - 접근 로그에는 일반 요청과 똑같이 기록합니다.
>
> **타임아웃 정의와 기본값.** 무제한 기본값은 두지 않습니다.
>
> | 옵션 | 재는 구간 | 기본값 |
> |---|---|---|
> | `.connectTimeout(long, TimeUnit)` | TCP 연결과 TLS 핸드셰이크 | 10초 |
> | `.writeTimeout(long, TimeUnit)` | 백엔드 소켓 쓰기가 막혀 진척이 없는 시간. 클라이언트 본문이 도착하기를 기다리는 시간은 세지 않음(그 시간은 어댑터의 본문 읽기 보호가 제한함) | 60초 |
> | `.readTimeout(long, TimeUnit)` | 요청을 보낸 뒤 응답 첫 바이트까지, 그리고 응답 바이트 사이의 간격 | 60초 |
> | `.totalTimeout(long, TimeUnit)` | 첫 시도부터 요청이 끝날 때(§3.6)까지 전체. 재시도와 재시도 대기 포함 | 5분 |
>
> 읽기 타임아웃은 바이트 사이 간격이므로 그것만으로는 한 요청의 전체 시간이 정해지지 않으며, 전체 시간 상한(`.totalTimeout`)이 이를 제한합니다. 상한을 넘으면 응답 전이면 504, 응답 중이면 클라이언트 연결 중단입니다(풀지 못하는 경우는 아래). 그래서 기본값 5분은 5분이 넘게 걸리는 큰 다운로드도 끊으며, 그런 마운트는 상한을 늘려야 합니다. 다른 타임아웃보다 짧게 정해도 되며, 먼저 닿는 쪽이 적용됩니다.
>
> 전체 시간 상한은 감시 타이머가 백엔드 소켓을 닫는 방식이므로(§3.9) 백엔드 소켓에서 막힌 작업 스레드만 풀어 줍니다. 다음 두 경우는 풀지 못하며 프록시 문서에 적습니다. 첫째, 소켓을 만들기 전의 이름 해석은 JDK 리졸버의 시간을 따릅니다. 둘째, 클라이언트와의 입출력(느리게 오는 요청 본문 읽기, 응답을 느리게 받는 클라이언트에게 쓰기)에서 막힌 시간은 어댑터의 처리에 맡깁니다.
>
> ### 3.5 재시도
>
> - 기본값은 **재시도하지 않음**입니다. `.retries(n)`으로 첫 시도 뒤 최대 n번 더 시도하게 하고, `.retries(0)`으로 끕니다.
> - 재시도 대상은 다음과 같습니다.
>
> | 실패 | 재시도 | 이유 |
> |---|---|---|
> | 연결 수립 실패(연결 거부, 이름 해석 실패) | 모든 메서드 | 요청 바이트를 보내기 전이므로 백엔드가 요청을 처리했을 수 없음 |
> | TLS 핸드셰이크 실패(인증서·호스트 이름 검증 실패, 프로토콜·암호 협상 실패, 핸드셰이크 중 연결 끊김) | 하지 않음 | 검증·협상 실패는 다시 시도해도 결과가 같음. 핸드셰이크 중 끊김만 따로 구분하지 않고 규칙을 하나로 둠 |
> | 연결 타임아웃 | 하지 않음 | 요청을 보내기 전이지만 재시도마다 작업 스레드를 붙잡는 시간이 늘어남(§5 #3) |
> | 백엔드가 보낸 502·503 | 안전한 메서드(GET, HEAD, OPTIONS)이면서 본문이 없는 요청만. 다른 메서드는 `.retryUnsafeMethods(true)`를 명시해야 하고, 그때도 본문이 있으면 하지 않음 | 같은 작업이 두 번 처리될 수 있음. 스트림으로 이미 보낸 본문은 다시 보낼 수 없음 |
> | 백엔드가 보낸 504와 그 밖의 상태 | 하지 않음 | 백엔드 뒤쪽에서 처리가 진행됐을 수 있음 |
> | 쓰기·읽기 타임아웃, 전체 시간 상한 초과, 백엔드 응답 오류(`INVALID_RESPONSE`) | 하지 않음 | 요청을 보낸 뒤의 실패는 처리 여부를 알 수 없고, 타임아웃을 재시도하면 작업 스레드를 붙잡는 시간이 재시도 횟수만큼 늘어남 |
>
> - "본문이 없는 요청"은 백엔드로 보낸 본문이 0바이트인 요청이며, `Content-Length: 0`인 요청도 포함합니다.
> - 재시도를 다 써도 502·503이면 마지막 백엔드 응답을 그대로 전달합니다.
> - 재시도 사이 대기 시간은 `.retryDelay(long, TimeUnit)`로 정하고 기본값은 200ms입니다. 대기 시간은 전체 시간 상한에 포함되며, 대기 뒤의 시도가 전체 시간 상한을 넘게 되면 기다리지 않고 마지막 실패를 그대로 돌려줍니다.
> - "안전한 메서드"는 HTTP 의미상의 구분입니다. 앱의 GET 엔드포인트가 실제로 부작용을 내면 재시도로 두 번 실행될 수 있으므로, 그런 경로에는 재시도를 끈 프록시를 따로 마운트합니다.
>
> ### 3.6 스레드 모델
>
> - `Proxy.to`가 돌려주는 객체는 `Middleware`이고, `Middleware`는 요청 스레드에서 동기로 실행됩니다(`Middleware.java:8`). 따라서 프록시는 백엔드 연결, 요청 전송, 응답 전달이 끝날 때까지 작업 스레드 하나를 붙잡습니다.
> - **슬롯과 감시 타이머의 수명:** 프록시는 메서드·경로·헤더·본문 프레이밍 검사와 `req.bodyStream` 호출(`Content-Length` 한도 검사 포함, A-1)을 모두 통과한 뒤에 동시 요청 슬롯을 얻고 전체 시간 상한 감시를 시작합니다. 슬롯 반환과 감시 종료는 요청이 끝날 때 정확히 한 번 합니다. 요청이 끝나는 시점은 다음과 같습니다.
>   - 백엔드 응답 스트림을 `res.relay`에 넘긴 경우: `relay`는 기존 `res.stream`처럼 핸들러가 반환한 뒤에 본문을 복사하므로(`DefaultResponse.java:521-524`), 프레임워크가 그 스트림을 `close()`하거나 `onAbort`(A-5)를 통지할 때입니다. 프레임워크는 복사가 성공·실패·중단 어느 쪽으로 끝나도 그 스트림을 닫으므로(`DefaultResponse.java:680-681`), 프록시는 그 스트림의 `close()`에서 백엔드 소켓을 닫고 슬롯을 반환합니다.
>   - 넘기지 못한 모든 경우(`ProxyException`, 413, 그 밖의 예외): 미들웨어가 예외를 던지거나 반환하기 직전입니다.
> - **끊김 감지의 한계:** 백엔드 응답을 기다리는 동안 클라이언트가 연결을 끊어도, 어댑터는 입출력이 없는 동안의 끊김을 알리지 않을 수 있습니다(`HttpExchange.java:107-113`, A-5). 그래서 프록시는 응답을 쓰기 시작할 때에야 끊김을 알 수 있고, 그동안 작업 스레드는 백엔드 응답, 읽기 타임아웃, 전체 시간 상한 중 먼저 오는 것까지 묶입니다.
> - 작업 스레드 예산은 `maxWorkers`(기본 64, `ServerOptions.java:41-45`)입니다. 느린 백엔드로 가는 요청이 이만큼 쌓이면 프록시가 아닌 경로의 요청도 작업 스레드를 기다립니다. 읽기 타임아웃을 길게 잡을수록 이 위험이 커집니다. 전체 시간 상한(§3.4)은 프록시 요청 하나가 백엔드 때문에 작업 스레드를 붙잡는 시간을(예외는 §3.4), 동시 요청 상한(`.maxConcurrent(n)`)은 그 상한을 함께 쓰는 마운트의 요청이 동시에 붙잡는 작업 스레드 수를 제한합니다.
> - **동시 요청 상한:** `.maxConcurrent(n)`을 부르면 그 결과 객체가 새 카운터를 갖고, 그 객체에서 옵션 메서드로 파생한 객체는 카운터와 상한을 물려받아 진행 중인 요청을 함께 셉니다. 예를 들어 `Proxy p = Proxy.to(url).maxConcurrent(16);`을 만든 뒤 `p`와 `p.retries(0)`을 각각 마운트하면 두 마운트가 상한 16을 나눠 씁니다. 파생 객체에서 `.maxConcurrent`를 다시 부르면 새 카운터가 생깁니다. `Proxy.to`를 다시 불러 따로 만든 객체는 대상 출처가 같아도 카운터를 함께 쓰지 않습니다. 상한을 정하지 않은 프록시의 요청은 어느 카운터에도 세지 않으므로, 같은 출처의 다른 마운트가 상한 있는 마운트를 막지 않습니다. 새 요청이 올 때 카운터가 상한에 이르렀으면 기다리지 않고 즉시 503(`CONCURRENCY_LIMIT`)으로 거절합니다. 기본값은 제한 없음입니다(이유는 §5 #16). 카운터는 객체에 딸리므로 같은 객체를 두 앱에 마운트하면 두 앱의 요청을 함께 셉니다.
> - 프록시 문서에는 끊김 감지의 한계, `maxWorkers` 소진 위험, 동시 요청 상한의 동작을 적습니다.
> - 0.11.0에서 `Deferred`를 돌려주는 계약은 `AsyncRouteHandler`에 있고, 이를 미들웨어로 감싸는 `AsyncMiddleware`는 `internal` 패키지에 있습니다. 대기 중에 작업 스레드를 놓아주는 비동기 미들웨어를 공개할지는 결정 사항입니다(§5 #9).
>
> ### 3.7 범위 밖
>
> - WebSocket 프록시(WebSocket 업그레이드 요청은 `next()`로 넘김, §3.2)
> - 부하 분산, 헬스 체크, 서킷 브레이커
> - 응답 캐시
> - 응답 본문 변환, 경로 재작성 함수(접두사를 떼는 단순 옵션은 §3.8)
> - `stripPrefix(true)`일 때 `Set-Cookie`의 `Path` 재작성. 백엔드가 정한 `Path`는 마운트 접두사를 모르므로, 쿠키가 마운트 밖 경로에도 전송되거나 마운트 안 경로에 전송되지 않을 수 있습니다.
> - SSE 같은 스트리밍 응답을 백엔드가 보낸 단위대로 즉시 내보내는 보장. 이런 응답은 읽기 타임아웃과 전체 시간 상한에도 걸립니다.
>
> ### 3.8 추가 옵션과 값 검증
>
> | 옵션 | 의미 | 기본값 |
> |---|---|---|
> | `.stripPrefix(true)` | 마운트 접두사를 뗀 경로(`url()`)를 전달 | false |
> | `.preserveHost(true)` | `Host`를 바꾸지 않고 원래 값 전달 | false |
> | `.bodyLimit(bytes)` | 이 마운트에서 전달할 요청 본문 크기 상한. 프록시는 이 값으로 `req.bodyStream(bytes)`(A-1)를 부르므로 앱의 `rawBodyLimit`보다 크게도 작게도 정할 수 있음. `Content-Length`가 넘으면 백엔드에 연결하지 않고 413. 전송 중 넘으면 백엔드 연결을 닫고, 응답 전이면 413 | 앱의 `rawBodyLimit`(`req.bodyStream()`) |
> | `.maxConcurrent(n)` | 이 객체와 이 객체에서 파생한 객체가 함께 쓰는 동시 요청 상한(§3.6) | 제한 없음 |
> | `.responseHeader(name, value)` | 클라이언트에 보낼 응답 헤더를 고정함. 백엔드와 앱이 정한 같은 이름의 값을 교체(§3.3) | 없음 |
> | `.removeResponseHeader(name)` | 백엔드가 보낸 그 이름의 응답 헤더를 전달하지 않음(§3.3) | 없음 |
> | `.retryUnsafeMethods(true)` | 안전하지 않은 메서드의 502·503 재시도를 허용(§3.5) | false |
> | `.rewriteLocation(false)` | `Location` 재작성(§3.3)을 끔 | true |
> | `.sslSocketFactory(factory)` | 사설 인증 기관 등을 쓰는 https 대상의 소켓 팩터리(§3.9) | JDK 기본 |
>
> 옵션 값은 그 옵션 메서드를 부르는 시점에 검사하고, 범위를 벗어나면 `IllegalArgumentException`을, `null`이면 `NullPointerException`을 던집니다.
>
> | 옵션 | 허용 범위 |
> |---|---|
> | `connectTimeout`, `writeTimeout`, `readTimeout`, `totalTimeout` | 0보다 큰 값. 0은 무제한을 뜻하지 않고 거부함 |
> | `retries` | 0 이상 |
> | `retryDelay` | 0 이상 |
> | `bodyLimit` | `1..1073741824` (`rawBodyLimit`과 같음) |
> | `maxConcurrent` | 1 이상 |
> | `requestHeader(name, value)`, `removeRequestHeader(name)` | 헤더 검사(A-3)를 통과해야 함. 프록시가 관리하는 이름(hop-by-hop 헤더, `Host`, `Content-Length`, `Expect`, `Forwarded`, `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host`)은 거부함 |
> | `responseHeader(name, value)`, `removeResponseHeader(name)` | 헤더 검사(A-3)를 통과해야 함. 프록시가 관리하는 이름(hop-by-hop 헤더, `Content-Length`)은 거부함 |

> ### 3.9 구현 방식과 모듈
>
> 프록시에는 백엔드로 요청을 보내는 HTTP 클라이언트가 필요합니다. NaruServe 모듈은 Java 8로 컴파일하고(`build.gradle:38-42`), servlet·slf4j를 뺀 모듈은 Android API 21 서명 검사를 받습니다(`build.gradle:21`, `434-445`). 이 제약에서 쓸 수 있는 기존 클라이언트는 §3.2를 지킬 수 없습니다.
>
> - `java.net.http.HttpClient`는 Java 11 이상에만 있고 Android에는 없습니다.
> - `HttpURLConnection`은 JDK에서는 `PATCH`와 확장 메서드를 받지 않고, `Host` 같은 제한 헤더를 막으며, 헤더의 순서와 중복을 제어하기 어렵습니다.
>
> **권장안:** 프록시를 `naruserve-api`가 아닌 별도 모듈 `NaruServe-proxy`(아티팩트 `naruserve-proxy`)에 두고, 소켓 위에 최소 HTTP/1.1 클라이언트를 직접 구현합니다. 이 모듈도 Java 8·Android API 21 제약을 지킵니다. 프록시 모듈은 요청 A의 공개 API(A-1~A-7)만 쓰고 `internal` 패키지와 SPI에 의존하지 않습니다.
>
> 구현 범위와 비용은 다음과 같습니다.
>
> - **요청 쓰기:** 요청 줄과 헤더를 받은 순서대로 쓰고, 본문을 `Content-Length` 또는 청크 인코딩으로 스트림 전달합니다.
> - **응답 읽기:** 상태 줄과 헤더를 파싱하고, 본문 길이를 RFC 9112 §6.3의 순서대로 아래 표에 따라 정합니다. `chunked`가 아닌 전송 코딩은 RFC 9112가 허용하는 경우에도 거부하므로 RFC보다 엄격합니다. 상태 줄과 헤더는 ISO-8859-1로 해석합니다. 다음 응답은 표와 별개로 형식 오류(`INVALID_RESPONSE`)입니다: 잘못된 상태 줄, 상태 줄과 헤더의 합계가 64 KiB를 넘는 응답, obs-fold(줄 접기)가 든 헤더(RFC 9112 §5.2는 프록시가 이를 502로 바꾸거나 공백으로 바꾸도록 정하며, 이 요청서는 502를 택합니다), 헤더 검사(A-3)를 통과하지 못한 헤더 이름·값, 잘못된 청크(확장을 포함해 4 KiB를 넘는 청크 크기 줄, 합계가 64 KiB를 넘는 트레일러 포함). 트레일러는 읽고 버립니다.
>
> | 백엔드 응답 | 처리 |
> |---|---|
> | 101 | `INVALID_RESPONSE`. 프록시는 `Upgrade`를 항상 지우므로(§3.2) 101은 올 수 없음 |
> | 그 밖의 1xx | 건너뛰고 다음 응답을 읽음 |
> | HEAD 요청에 대한 응답, 204, 304 | 본문을 읽지 않음 |
> | `Transfer-Encoding`과 `Content-Length`가 함께 있음 | `INVALID_RESPONSE`(RFC 9112 §6.3은 이를 오류로 다뤄도 된다고 정함) |
> | `Transfer-Encoding`이 `chunked` 하나뿐 | 청크 디코딩. `relay`에 길이 `-1` |
> | 그 밖의 `Transfer-Encoding`(`gzip, chunked`, `identity` 등) | `INVALID_RESPONSE`. 프록시는 `Transfer-Encoding`을 hop-by-hop으로 지우므로 그대로 넘기면 클라이언트가 바이트를 해석할 수 없음 |
> | `Content-Length`가 숫자만으로 이루어지지 않음(음수 포함), 또는 서로 다른 값이 여러 개 | `INVALID_RESPONSE` |
> | `Content-Length` 하나(또는 같은 값 여러 개) | 그 길이만큼 읽음 |
> | 둘 다 없음 | 연결이 닫힐 때까지 읽음. `relay`에 길이 `-1` |
>
> - **https:** 평문 `Socket`을 `connect(address, connectTimeout)`으로 연결한 뒤 `SSLSocketFactory.createSocket(plain, host, port, true)`로 대상 호스트 이름을 넘겨 TLS 소켓을 만들어 SNI를 보냅니다. `createSocket(host, port)`는 곧바로 연결해 연결 타임아웃을 적용할 수 없기 때문입니다. 핸드셰이크는 `SO_TIMEOUT`을 연결 타임아웃 값으로 두어 제한합니다. 인증서 검증은 기본으로 켭니다. `SSLSocket`은 호스트 이름을 스스로 검증하지 않으므로 구현이 검증을 켜야 합니다. JDK에서는 `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")`를 쓰고, 이 메서드가 API 24부터인 Android에서는 `HttpsURLConnection.getDefaultHostnameVerifier()`로 검증합니다. 실행 시점에 분기해도 이 호출은 API 21 서명 검사(animal-sniffer)에 걸리므로, 리플렉션으로 부르거나 그 호출을 검사 예외로 표시해야 합니다. 사설 인증 기관은 `.sslSocketFactory(factory)` 옵션으로 받고, 검증을 끄는 옵션은 두지 않습니다. 이 옵션을 써도 호스트 이름 검증은 꺼지지 않습니다.
> - **커넥션 재사용:** 첫 버전은 요청마다 새 연결을 열고 `Connection: close`를 보냅니다. 덜 읽힌 응답이 남은 연결을 재사용하는 종류의 오류가 생기지 않는 대신, 요청마다 TCP 연결(https면 TLS 핸드셰이크) 비용을 냅니다. 연결 풀은 결정 사항입니다(§5 #8). 요청마다 새 연결을 열면 TCP 연결을 먼저 닫는 쪽에 TIME_WAIT 소켓이 남으므로, 처리량이 높으면 프록시 호스트의 임시 포트가 고갈될 수 있습니다. 구현은 응답을 끝까지 읽은 뒤 백엔드가 `Connection: close`에 따라 연결을 닫는 EOF를 짧게 기다려 백엔드가 먼저 닫게 할 수 있습니다. 프록시 문서에는 이 위험과 근본 대책이 연결 풀이라는 점을 적습니다.
> - **쓰기 타임아웃과 전체 상한:** 블로킹 소켓의 `SO_TIMEOUT`은 읽기에만 적용되므로, 쓰기 타임아웃과 전체 시간 상한은 감시 타이머가 소켓을 닫는 방식으로 구현해야 합니다. https에서는 `SSLSocket`이 아닌 평문 소켓을 닫습니다. `SSLSocket.close()`는 `close_notify`를 보내므로 다른 스레드가 쓰기 중에 막혀 있으면 함께 막힐 가능성을 배제할 수 없고, 감시 스레드는 JVM 전체에 하나라서 막히면 모든 프록시의 타임아웃이 멈추기 때문입니다. 요청이 끝나면(§3.6) 예약을 취소합니다.
> - **감시 타이머의 보관:** 0.11.0에는 프록시가 요청 처리 중에 앱 단위 자원을 등록할 공개 수단이 없습니다. `ApplicationContext.own`은 앱이 STARTING 상태이고 레지스트리가 얼기 전에만 받고 그 뒤에는 `IllegalStateException`을 던지며(`DefaultApplicationContext.java:42-48`, `:133-137`), `attribute`에는 원자적인 "없으면 넣기"가 없습니다. 그래서 요청 A를 늘리지 않고, JVM 전체에 스케줄러 하나를 첫 프록시 요청에서 지연 생성해 씁니다. 데몬 스레드를 쓰고, 코어 스레드도 유휴 시간이 지나면 끝나게 하며(`allowCoreThreadTimeOut(true)`), 취소한 예약은 큐에서 지웁니다. 그래서 프록시 요청이 없으면 30초 안에 스레드가 남지 않으므로, 앱 종료 훅 없이도 재배포 뒤 유휴 시간이 지나면 스레드가 클래스로더를 붙잡지 않습니다. 스레드를 만들 때 컨텍스트 클래스로더는 비워 둡니다.
> - **동시 요청 카운터:** `.maxConcurrent(n)`이 만든 객체가 원자 정수(`AtomicInteger`) 하나를 갖고 파생 객체가 그 참조를 물려받으므로(§3.6), 앱 단위 보관이나 락이 필요 없습니다.
> - **시험:** 응답 파서와 프레이밍은 보안에 민감한 코드이므로 위 형식 오류 입력마다 시험을 둡니다(AC-B30).
>
> 대안은 §5의 결정 사항 표에 남깁니다.

> ## 4. 인수 기준
>
> **요청 A**
>
> - AC-A1: 공백과 줄바꿈이 섞인 JSON 본문, 이진 본문, urlencoded 본문, `Content-Encoding: gzip` 본문을 `bodyStream()`으로 읽으면 받은 바이트와 정확히 같다(gzip 본문은 압축된 그대로다).
> - AC-A2: `bodyStream()`을 읽은 뒤 `body(Map.class)`를 부르면 `BodyAlreadyConsumedException`이 난다. 반대 순서도 같다. `Content-Type: application/json` 본문에서 `form("a")`를 먼저 부르면 빈 결과가 나오고, 이어서 부른 `bodyStream()`은 본문 전체를 돌려준다.
> - AC-A3: `rawBodyLimit`을 넘는 청크 전송 본문을 `bodyStream()`으로 읽으면 한도를 넘는 순간 `BodyTooLargeException`이 나고, 이 예외가 감싸이지 않은 채 핸들러 밖으로 나가면 응답은 413이다.
> - AC-A4: TinyHttpd 어댑터에서 `X-A: 1`, `x-a: 2`, `X-B: 3`을 받으면 `headerNames()`는 `[x-a, x-b]`, `rawHeaders()`는 세 쌍을 받은 순서와 대소문자대로 돌려준다. 서블릿 어댑터에서는 `headerNames()`가 `[x-a, x-b]`이고 `rawHeaders()`가 값 `1`, `2`, `3`을 모두 담으며 `x-a`의 값은 `1`, `2` 순서다. 두 결과를 바꾸려 하면 `UnsupportedOperationException`이 난다.
> - AC-A5: `res.append("Set-Cookie", ...)`를 두 번 부르면 클라이언트가 두 헤더를 모두 받는다. `res.header`는 지금처럼 교체한다.
> - AC-A6: 본문이 없는 요청에서 `bodyStream()`은 `null`이 아닌 빈 스트림을 돌려주고, 같은 요청에서 두 번 부르면 같은 객체를 돌려주며, 이어서 `bodyStream(2048)`을 부르면 `IllegalStateException`이 난다. 본문이 있는 요청에서 `bodyStream()`으로 1바이트를 읽은 뒤 다시 부르면 `BodyAlreadyConsumedException`이 난다. TinyHttpd 어댑터에서 핸들러가 32 KiB 본문의 `bodyStream()`을 끝까지 읽지도 닫지도 않고 응답해도 같은 연결의 다음 요청이 정상 처리된다(남은 본문이 TinyHttpd `maxDrainBytes` 기본값 64 KiB 이하인 경우).
> - AC-A7: `Content-Length`가 `rawBodyLimit`보다 큰 요청에서 `bodyStream()` 호출은 본문을 읽지 않고 곧바로 상태가 413인 `HttpException`을 던진다.
> - AC-A8: `res.append`에 CR, LF, NUL, U+0100이 든 값을 주면 `res.header`와 같은 방식으로 거부된다.
> - AC-A9: `bodyStream()`으로 읽은 바이트 수가 접근 로그의 `in=`에 기록된다.
> - AC-A10: `rawBodyLimit`이 1 MiB인 앱에서 `bodyStream(2 MiB)`로 1.5 MiB 본문을 모두 읽을 수 있고, `bodyStream(1024)`로 읽으면 1025번째 바이트에서 `BodyTooLargeException`이 난다. `bodyStream(0)`은 `IllegalArgumentException`을 던진다.
> - AC-A11: `isFromTrustedProxy()`는 신뢰 설정이 없는 앱, `trustProxyHops(0)`인 앱, 빈 `trustProxyCidrs()`인 앱에서 `false`, `trustProxyHops(1)`과 `trustProxy(true)`인 앱에서 `true`이고, `trustProxyCidrs("10.0.0.0/8")`인 앱에서는 접속 상대가 CIDR 안일 때만 `true`다.
> - AC-A12: 응답 도중 클라이언트가 연결을 끊거나 핸들러가 `res.abort`를 부르면 `res.onAbort`에 등록한 콜백이 한 번 불린다. 정상으로 끝난 응답에서는 불리지 않고, 중단된 뒤에 등록한 콜백은 곧바로 불린다. 먼저 등록한 콜백이 예외를 던져도 다음 콜백이 불린다.
> - AC-A13: `Content-Type`을 설정하지 않고 `res.relay(in, 5)`를 부르면 클라이언트는 `Content-Type` 없이 `Content-Length: 5`와 5바이트 본문을 받는다. HEAD 요청과 304 응답에서는 본문 없이 `Content-Length: 5`를 받고, 204 응답에서는 본문과 `Content-Length` 없이 받는다. `res.relay(in, -1)`은 길이 미정으로 전송되고, `res.relay(in, -2)`는 `IllegalArgumentException`을 던진다. `res.relay(in, 5)`에 3바이트 스트림을 주면 응답이 중단된다. `app.defaultCache(...)`를 정한 앱에서도 `res.relay`로 보낸 응답에는 `Cache-Control`이 붙지 않는다.
> - AC-A14: `HttpHeaderValues.isFieldValue`는 빈 문자열과 HTAB이 든 값에 `true`를, CR, LF, NUL, DEL, U+0100이 든 값에 `false`를 돌려준다.
>
> **요청 B: 요청 전달**
>
> - AC-B1: `app.use("/api/orders", Proxy.to(url))`에서 `POST /api/orders/query?x=1&y=%ED%95%9C`의 메서드, 경로, 쿼리, JSON 본문이 백엔드에 바이트 단위로 같게 도착한다.
> - AC-B2: urlencoded 본문, 이진 본문, 청크 전송 본문, 큰 본문이 그대로 도착한다. `-Xmx64m`으로 띄운 프록시가 `.bodyLimit(1073741824)`인 마운트로 1 GiB 본문을 전달해도 `OutOfMemoryError` 없이 끝난다.
> - AC-B3: 임의 요청 헤더와 값이 여러 개인 헤더가 순서대로 도착하고, hop-by-hop 헤더, `Connection`에 나열된 헤더, `Upgrade`, `Expect`, `Forwarded`, `Trailer`는 도착하지 않는다. `Upgrade: h2c`를 붙인 GET도 백엔드에 도착한다. 프록시는 `Via`를 붙이지 않는다. 클라이언트가 `Cookie: a=1`과 `Cookie: b=2`를 두 줄로 보내면 `Cookie: a=1; b=2` 한 줄로 도착한다. `Max-Forwards: 0`을 붙인 `OPTIONS` 요청은 그 헤더를 담은 채 백엔드에 도착한다.
> - AC-B4: 신뢰 프록시를 설정하지 않은 앱에서 `Host`는 대상 호스트(기본 포트가 아니면 포트 포함)로 바뀌어 도착하고 원래 값은 `X-Forwarded-Host`에 담긴다. `.preserveHost(true)`이면 원래 `Host`가 그대로 도착하고 `X-Forwarded-Host`도 받은 `Host`로 도착한다. 대상이 `http://[::1]:8081`이면 `Host: [::1]:8081`이 도착한다. 어댑터가 `Host`를 보고하지 않은 요청에는 `.preserveHost(true)`여도 `Host`로 대상 호스트가 도착하고 `X-Forwarded-Host`는 도착하지 않는다. `Host`를 두 줄로 보낸 요청은 400을 받고 백엔드에 연결이 생기지 않는다.
> - AC-B5: `.stripPrefix(true)`이면 `/api/orders/query`가 `/query`로 도착한다. 기본값에서는 `/api/orders/query`로 도착한다.
> - AC-B6: `.requestHeader(name, value)`로 정한 헤더는 클라이언트가 같은 이름으로 보낸 값을 교체해 하나만 도착한다. `.requestHeader("X-Forwarded-Prefix", "/api/orders")`이면 클라이언트가 같은 헤더를 보내도 `/api/orders` 하나만 도착한다. `.removeRequestHeader("X-User-Id")`이면 클라이언트가 보낸 `X-User-Id`가 도착하지 않고, 이어서 `.requestHeader("X-User-Id", "u")`를 부르면 `u` 하나만 도착한다.
> - AC-B7: 본문 없는 GET에는 `Content-Length`와 `Transfer-Encoding`이 모두 붙지 않고, 길이 헤더 없이 본문도 없이 보낸 POST·PUT·PATCH에는 `Content-Length: 0`이 붙어 도착한다. 청크 전송 요청은 `Content-Length` 없이 청크로, `Content-Length` 요청은 같은 `Content-Length`로 도착한다. `Content-Length`·`Transfer-Encoding` 없이 본문이 오는 요청(서블릿 어댑터가 HTTP/2로 받은 POST 등)은 본문이 청크 전송으로 도착한다.
> - AC-B8: `Content-Length`와 `Transfer-Encoding`을 함께 보낸 요청, 서로 다른 `Content-Length`를 여러 개 보낸 요청, `Content-Length: abc` 요청, `Transfer-Encoding: gzip` 요청, `Transfer-Encoding: chunked, chunked` 요청, `Transfer-Encoding: chunked`와 `Transfer-Encoding: chunked`를 두 줄로 보낸 요청은 400을, `Transfer-Encoding: gzip, chunked` 요청은 501을 받고, 모두 백엔드에 연결이 생기지 않는다. `Content-Length: 10`을 보내고 5바이트 뒤 연결을 끊은 요청에서는 백엔드는 10바이트를 다 받지 못한 채 연결이 닫힌다.
> - AC-B9: `.bodyLimit(n)`보다 큰 `Content-Length` 요청과, 옵션 없이 마운트한 프록시에 `rawBodyLimit`보다 큰 `Content-Length` 요청은 백엔드에 연결하지 않고 413을 받는다. 청크 전송 본문이 전송 중 n을 넘으면 백엔드 연결이 닫히고 클라이언트는 413을 받으며, 오류 흐름에 전달되는 예외는 상태가 413인 `HttpException`이고 `getCause()`는 `BodyTooLargeException`이다. 앞선 미들웨어가 `req.body(...)`로 본문을 읽었거나 `req.bodyStream()`으로 일부를 읽은 요청은 백엔드에 연결하지 않고 500을 받는다.
> - AC-B10: `/api/orders/@evil.example/x`는 설정한 대상 호스트로 가고, `/api/orders//evil.example/x`와 `/api/orders/%2F%2Fevil.example`은 400을 받으며, 어느 경우에도 다른 호스트로 연결이 생기지 않는다. 어느 어댑터에서든 absolute-form 요청 `GET http://evil.example/api/orders/x`는 400을 받거나 설정한 대상 호스트로만 전달되며, 어느 경우에도 다른 호스트로 연결이 생기지 않는다. `GET http://h/api/orders/%2e%2e/x`는 400을 받는다.
> - AC-B11: `/api/orders/../other/x`, `/api/orders/%2e%2e/other/x`, `/api/orders/..;/other/x`, `/api/orders/.;x/other/x`, `/api/orders/%252e%252e/other/x`, `/api/orders/a%2fb`, `/api/orders/a%5cb`, `/api/orders/a%00b`, `/api/orders/%70rivate/x`, `/api/orders/private;x/y`, `/api/orders//private/x`, `/api/orders/private//x`, 비ASCII 바이트, 제어 문자, `#`, `%zz`가 든 경로와 쿼리, 이름이 토큰이 아니거나 값에 NUL이 든 요청 헤더, 어댑터가 보고한 메서드가 토큰이 아닌 요청은 400을 받고 백엔드에 도착하지 않는다. `/api/orders/x/`는 그대로 도착한다.
> - AC-B12: origin-form `CONNECT`와 `TRACE` 요청은 405와 `Allow: GET, HEAD, POST, PUT, DELETE, PATCH, OPTIONS`를 받고 백엔드에 도착하지 않는다. WebSocket 업그레이드 요청(`GET`, `Connection: upgrade`, `Upgrade: websocket`)은 백엔드에 도착하지 않으며, `/api/orders` 프록시와 함께 등록한 `app.ws("/api/orders/live", ...)`는 등록 순서와 관계없이 업그레이드 요청을 받는다.
> - AC-B13: 신뢰 프록시를 설정하지 않은 앱에서 클라이언트가 보낸 `X-Forwarded-For: 1.2.3.4`, `X-Forwarded-Proto: https`, `X-Forwarded-Host: evil.example`은 버려지고 각각 소켓 주소, 실제 스킴, 받은 `Host`가 전달된다. IPv6 루프백 주소에서 접속한 클라이언트에 대해 백엔드가 받은 `X-Forwarded-For` 값에는 대괄호와 `%`가 없다.
> - AC-B14: `trustProxyCidrs("10.0.0.0/8")`인 앱에 CIDR 밖 주소에서 접속한 클라이언트가 `X-Forwarded-For: 1.2.3.4`를 보내면 그 값은 버려지고 소켓 주소만 전달된다. CIDR 안 주소에서 접속하면 `X-Forwarded-For`는 `1.2.3.4, <소켓 주소>`로 도착하고, `X-Forwarded-For: 1.2.3.4`와 `X-Forwarded-For: 5.6.7.8`을 두 줄로 보내면 `1.2.3.4, 5.6.7.8, <소켓 주소>` 한 줄로 도착하며, http로 접속하며 `X-Forwarded-Proto: https`를 보낸 요청에는 `X-Forwarded-Proto: https`가 도착한다. `trustProxyHops(1)`과 `trustProxy(true)`인 앱에서도 CIDR 안과 같이 동작한다. 신뢰 설정과 관계없이 클라이언트가 보낸 `X-Forwarded-Host`는 받은 `Host`로 바뀌고, `X-Real-IP`, `X-Forwarded-Port`, `X-Forwarded-Prefix`는 도착하지 않는다.
> - AC-B15: 클라이언트가 `Expect: 100-continue`와 본문을 보내면 본문이 백엔드에 도착하고 클라이언트는 백엔드의 최종 응답을 받는다.
>
> **요청 B: 응답 전달**
>
> - AC-B16: 백엔드가 보낸 상태(400·404·500 포함), `Set-Cookie` 두 개, `Content-Type`, `Content-Length`, 본문이 클라이언트에 그대로 도착한다. 백엔드 응답의 hop-by-hop 헤더와 `Connection`에 나열된 헤더는 도착하지 않는다. 백엔드가 `Content-Type` 없이 응답하면 클라이언트도 `Content-Type` 없이 받는다. 앱이 프록시 앞에서 `res.header("Access-Control-Allow-Origin", "*")`와 `res.header("X-App", "1")`을 정하고 백엔드가 `Access-Control-Allow-Origin: https://a.example`을 보내면, 클라이언트는 `Access-Control-Allow-Origin: https://a.example` 하나와 `X-App: 1`을 받는다. 앱이 프록시 앞에서 `addCookie`로 쿠키 하나를 넣고 백엔드가 `Set-Cookie` 두 개를 보내면 클라이언트는 `Set-Cookie` 세 개를 받는다. 앱이 프록시 앞에서 `res.header("Vary", "Origin")`을 정하고 백엔드가 `Vary: Accept-Encoding`을 보내면 클라이언트가 받은 `Vary`에 두 토큰이 모두 있다. 백엔드가 `Trailer` 헤더와 트레일러가 있는 청크 응답을 보내면 클라이언트는 본문을 받고 `Trailer` 헤더는 받지 않는다. 백엔드가 요청 본문을 다 읽기 전에 401을 보내고 쓰기 방향만 FIN으로 닫은 뒤 남은 본문을 읽어 버리면 클라이언트는 401을 받는다. RST로 닫는 경우는 시험하지 않는다(§3.4 최선 노력).
> - AC-B17: HEAD 요청에는 본문 없이 백엔드의 `Content-Length`를 유지해 응답한다. 백엔드의 302는 따라가지 않고 그대로 전달한다. 백엔드가 보낸 `100 Continue`는 클라이언트에 전달되지 않는다.
> - AC-B18: 백엔드가 `Location: http://<대상 호스트:포트>/api/orders/x`를 보내면 클라이언트는 `Location: /api/orders/x`를 받는다. `.rewriteLocation(false)`이면 원래 값을 받는다. 상대 URL, 다른 호스트의 URL, 대상 포트 뒤에 숫자가 더 붙은 URL(대상이 `http://h:808`일 때 `http://h:8080/x`)은 그대로 받는다. `.stripPrefix(true)`일 때 백엔드가 `Location: http://<대상>/x`를 보내면 클라이언트는 `/api/orders/x`를 받는다. 대상이 `http://h/base`이면 `Location: http://h/base/api/orders/y`가 `/api/orders/y`로 바뀐다. 대상이 `http://h`이면 기본 포트를 적은 `Location: http://H:80/x`도 `/x`로 바뀐다. 클라이언트가 보낸 `Host`와 `X-Forwarded-Host`는 재작성 결과에 나타나지 않는다.
> - AC-B19: `.removeResponseHeader("Server")`이면 백엔드가 보낸 `Server`가 클라이언트에 도착하지 않고, 앱이 프록시 앞에서 `res.header("Server", "gw")`를 정했으면 `Server: gw`만 도착한다. `.responseHeader("Strict-Transport-Security", "max-age=31536000")`이면 백엔드가 `Strict-Transport-Security: max-age=0`을 보내고 앱이 프록시 앞에서 다른 값을 정해도 클라이언트는 `max-age=31536000` 하나만 받는다. `.responseHeader("X-A", "1")`에 이어 `.removeResponseHeader("X-A")`를 부르면 백엔드가 보낸 `X-A`도 `1`도 도착하지 않는다.
>
> **요청 B: 오류, 타임아웃, 재시도, 동시 요청 상한**
>
> - AC-B20: 백엔드가 꺼져 있으면 502, 연결 타임아웃이 지나면 504, 쓰기 타임아웃이 지나면 504, 읽기 타임아웃이 지나면 504가 되고, 앱의 `onError`가 받은 예외는 `ProxyException`이며 `kind()`가 각각 `CONNECT_FAILED`, `CONNECT_TIMEOUT`, `WRITE_TIMEOUT`, `READ_TIMEOUT`이다. 시간 시험은 짧은 값으로 한다. `.connectTimeout(1, TimeUnit.SECONDS)`인 프록시는 TCP 연결만 받고 TLS 핸드셰이크에 응답하지 않는 https 백엔드에, `.readTimeout(1, TimeUnit.SECONDS)`인 프록시는 응답하지 않는 백엔드에 각각 약 1초 뒤 타임아웃을 낸다. `.writeTimeout(1, TimeUnit.SECONDS).bodyLimit(128 << 20)`인 프록시는 요청 본문을 읽지 않는 백엔드에 64 MiB 본문을 보낼 때 소켓 버퍼가 차고 약 1초가 지나면 `WRITE_TIMEOUT`을 낸다. 클라이언트가 본문을 쓰기 타임아웃보다 긴 간격으로 나눠 보내도, 백엔드가 본문을 계속 읽으면 `WRITE_TIMEOUT`이 나지 않는다. 옵션을 주지 않은 프록시의 기본값(연결 10초, 쓰기 60초, 읽기 60초, 전체 5분)은 실제 시간을 기다리지 않고 프록시 모듈의 단위 시험이 객체의 설정값으로 확인한다. `onError`를 등록하지 않은 앱에서 백엔드가 꺼져 있으면 기본 오류 응답 본문에 대상 호스트와 포트가 나타나지 않는다.
> - AC-B21: 백엔드가 응답 바이트를 계속 조금씩 보내 읽기 타임아웃에 걸리지 않아도, `.totalTimeout`을 넘으면 응답 전이면 504(`TOTAL_TIMEOUT`), 응답 중이면 클라이언트 연결이 중단된다. `.retries(5).retryDelay(1, TimeUnit.SECONDS).totalTimeout(2500, TimeUnit.MILLISECONDS)`이고 백엔드가 계속 연결을 거부하면 연결 시도는 3번이고, 세 번째 실패 직후(약 2초 뒤) 502(`CONNECT_FAILED`)가 난다.
> - AC-B22: `.retries(2)`일 때 백엔드가 계속 503을 보내면 본문 없는 GET은 백엔드에 정확히 3번 도착하고 클라이언트는 마지막 503을 받는다. `Content-Length: 0`인 GET도 3번 도착한다. 본문 없는 POST와 본문 있는 GET은 정확히 1번 도착한다.
> - AC-B23: `.retries(2)`일 때 백엔드가 504를 보내거나 읽기 타임아웃이 나면 GET도 정확히 1번 도착한다. 백엔드가 연결을 거부하면 POST도 재시도한다.
> - AC-B24: `.retryUnsafeMethods(true).retries(1)`일 때 본문 없는 DELETE는 503 뒤 정확히 2번 도착하고, 본문 있는 DELETE는 1번 도착한다. 두 도착 사이 간격은 `.retryDelay`를 정하지 않으면 200ms 이상이고, `.retryDelay(300, TimeUnit.MILLISECONDS)`이면 300ms 이상이다.
> - AC-B25: 클라이언트가 응답 도중 연결을 끊으면 백엔드 연결도 닫히고, `.maxConcurrent(1)`인 마운트라면 그 뒤 온 요청이 백엔드에 전달된다.
> - AC-B26: 프록시 요청이 접근 로그에 일반 요청과 같은 형식으로 남고, `in=`에 전달한 요청 본문 바이트 수가 기록된다.
> - AC-B27: `.maxConcurrent(2)`인 마운트에 응답을 지연하는 백엔드로 요청 3개를 동시에 보내면 세 번째 요청은 백엔드에 연결하지 않고 곧바로 503(`CONCURRENCY_LIMIT`)을 받는다. 앞선 두 요청이 응답 본문을 전송하는 중에 온 세 번째 요청도 503을 받고, 앞선 요청의 응답 본문 전송이 끝나면 다음 요청은 다시 전달된다. `p = Proxy.to(url).maxConcurrent(2)`를 `/a`에, `p.retries(0)`을 `/b`에 마운트하고 두 경로로 나눠 보내도 결과가 같다. 같은 대상으로 따로 만든 `Proxy.to(url).maxConcurrent(2)` 두 객체를 `/a`와 `/b`에 마운트하고 경로마다 2개씩 동시에 보내면 4개 모두 도착한다. `Proxy.to(url).maxConcurrent(2)`를 `/a`에, 상한 없는 `Proxy.to(url)`을 `/b`에 마운트하고 `/b`로 보낸 지연 요청 5개가 진행 중일 때 `/a`로 보낸 요청 2개는 모두 도착한다. 옵션을 주지 않은 프록시에 응답을 지연하는 백엔드로 요청 20개를 동시에 보내면 모두 백엔드에 도착한다. `.maxConcurrent(2)`인 마운트에 백엔드가 꺼진 상태로 요청 20개를 차례로 보내 모두 502를 받고, `.bodyLimit(1024)`를 넘는 청크 전송 본문으로 413을 20번 받고, `onError`가 `ProxyException`을 받아 200으로 응답하는 앱에서 읽기 타임아웃을 20번 낸 뒤 백엔드를 정상으로 되돌리면, 다음 요청은 백엔드에 전달된다.
> - AC-B28: 프록시 요청이 모두 끝난 뒤 새 요청이 없으면 30초 안에 감시 타이머 스레드가 남지 않고, 그 뒤 온 요청에도 전체 시간 상한이 다시 적용된다. 앱이 시작된 뒤 처음 온 프록시 요청이 감시 타이머를 준비하다 실패하지 않는다.
>
> **요청 B: TLS와 응답 파서**
>
> - AC-B29: 신뢰할 수 없는 인증서를 쓰는 https 백엔드, 인증서의 호스트 이름이 대상 호스트와 다른 https 백엔드, TLS 핸드셰이크 도중 연결을 끊는 https 백엔드에는 502(`CONNECT_FAILED`)가 나고, `.retries(2)`여도 세 백엔드에는 연결이 1번만 생긴다. `.sslSocketFactory`로 그 사설 인증 기관을 신뢰하게 하면 첫 백엔드에는 전달되고, 호스트 이름이 다른 백엔드에는 여전히 502가 난다. https 백엔드가 받은 SNI 서버 이름은 대상 호스트 이름이다.
> - AC-B30: 백엔드가 다음 응답을 보내거나 상태 줄을 보내기 전에 연결을 끊으면 클라이언트는 502를 받고 `kind()`는 `INVALID_RESPONSE`다: 잘못된 상태 줄, 64 KiB를 넘는 헤더, obs-fold가 든 헤더, 값에 0x00이나 0x7F 바이트가 든 헤더, `Content-Length`와 `Transfer-Encoding`을 함께 담은 응답, 서로 다른 `Content-Length`를 여러 개 담은 응답, `Content-Length: -1`, `Content-Length: abc`, `Transfer-Encoding: gzip, chunked`, `Transfer-Encoding: identity`, 101 응답. 본문 도중 잘못된 청크(4 KiB를 넘는 청크 크기 줄, 64 KiB를 넘는 트레일러 포함)가 오거나 백엔드가 `Content-Length`보다 짧게 보내고 연결을 끊으면 클라이언트 연결이 중단되고, 앱 로거에 `kind()`가 `INVALID_RESPONSE`인 `ProxyException`이 기록된다.
>
> **요청 B: API**
>
> - AC-B31: 쿼리나 프래그먼트가 있는 URL, 사용자 정보가 있는 URL, `ftp` 스킴, 호스트 없는 URL을 `Proxy.to`에 주면 그 호출에서 `IllegalArgumentException`이 난다. `/api/orders`에 마운트한 `Proxy.to("http://h:8081/")`는 `/api/orders/x`를 `/api/orders/x`로, `Proxy.to("http://h:8081/base/")`는 `/base/api/orders/x`로 보낸다.
> - AC-B32: `Proxy p = Proxy.to(url); Proxy q = p.retries(2);`에서 `p`의 동작은 바뀌지 않는다.
> - AC-B33: Kotlin에서 `Proxy.to(url).readTimeout(30, TimeUnit.SECONDS)`가 별도 래퍼 없이 컴파일된다.
> - AC-B34: §3.8 값 검증 표의 범위를 벗어난 값(예: `readTimeout(0, ...)`, `retries(-1)`, `retryDelay(-1, ...)`, `bodyLimit(0)`, `maxConcurrent(0)`, `requestHeader("Host", ...)`, `requestHeader("Connection", ...)`, `requestHeader("X-Forwarded-For", ...)`, `requestHeader("Forwarded", ...)`, `requestHeader("X-A", "a\r\nb")`, `requestHeader("X-A", "a\u0000b")`, `removeRequestHeader("Host")`, `responseHeader("Content-Length", "1")`, `removeResponseHeader("Transfer-Encoding")`, `responseHeader("X-A", "a\nb")`)은 그 옵션 메서드 호출에서 `IllegalArgumentException`을 던지고, `null` 인자(예: `requestHeader(null, "x")`, `sslSocketFactory(null)`)는 `NullPointerException`을 던진다.
>

> ## 5. 결정이 필요한 사항 (요청자의 권장안)
>
> | 번호 | 사항 | 권장안 | 이유 |
> |---|---|---|---|
> | 1 | 마운트 접두사를 떼는지 | 떼지 않음(전체 경로 전달), 옵션으로 뗌 | `http-proxy-middleware`에서 접두사가 떨어지는 동작이 흔한 혼동 원인이다. 게이트웨이는 보통 전체 경로를 그대로 넘긴다 |
> | 2 | 재시도 기본값과 대상 | 끔. 켜면 연결 수립 실패(TLS 핸드셰이크 실패 제외)와 백엔드 502·503만, 502·503은 본문 없는 안전한 메서드만 | 같은 작업이 두 번 처리되는 사고를 기본값에서 막는다 |
> | 3 | 연결 타임아웃을 재시도하는지 | 하지 않음 | 요청을 보내기 전이라 처리 중복 위험은 없지만, 재시도마다 작업 스레드를 붙잡는 시간이 연결 타임아웃만큼 늘어난다 |
> | 4 | `Host` 헤더 | 대상 호스트로 바꿈 | 가상 호스트 백엔드에서 안전하다. 원래 값은 `X-Forwarded-Host`로 전달 |
> | 5 | 프록시 오류 응답 형태 | 앱의 오류 흐름에 맡기고, 오류 종류는 `ProxyException.kind()`로 알림 | NaruServe 일반 HTTP의 기본 오류 처리와 일관되고, 앱이 오류 종류별 응답을 만들 수 있다 |
> | 6 | 모듈 위치 | 요청 A는 `naruserve-api`, 요청 B는 별도 모듈 `naruserve-proxy`. 별도 모듈이 공개 API만 쓰도록 요청 A에 A-4~A-7을 둠 | 백엔드 HTTP 클라이언트 코드를 핵심 API 모듈 밖에 둔다. 프록시를 쓰지 않는 앱은 이 코드를 받지 않는다. A-4~A-7은 프록시 밖에서도 쓸모가 있다 |
> | 7 | 백엔드 HTTP 클라이언트 | (a) Java 8·API 21에서 동작하는 최소 HTTP/1.1 클라이언트 직접 구현(§3.9) | Android 포함 모든 대상에서 §3.2를 지킨다. 비용은 §3.9의 구현·시험 범위다 |
> | | | 대안 (b) Java 11 이상 전용 모듈에서 `java.net.http.HttpClient` 사용 | 구현이 가장 작다. 다만 Android에서 쓸 수 없다. `Host` 제한은 JDK 12 이상에서 시스템 속성 `jdk.httpclient.allowRestrictedHeaders=host`로 풀 수 있지만 JVM 전체에 걸리는 설정이다 |

> ## 6. 호환성
>
> - 새 메서드, 새 클래스, 새 모듈을 추가하는 것이 중심이며, 기존 동작이 바뀌는 곳은 다음 두 가지입니다.
>   - `StandardErrors.statusOf`가 `BodyTooLargeException`을 413으로 바꿉니다(A-1). 0.11.0에서는 이 예외가 오류 흐름에 닿으면 500이었습니다.
>   - `BodyTooLargeException`이 `com.snoworca.naruserve.internal`에서 공개 패키지 `com.snoworca.naruserve`로 옮겨집니다(A-1). `internal` 패키지의 이 클래스를 직접 쓰던 코드는 import를 고쳐야 합니다.
> - `Request`·`Response`에 메서드를 추가하므로 사용자가 직접 구현한 `Request`·`Response`가 있으면 컴파일이 깨질 수 있습니다. 기존 메서드처럼 기본 구현(`UnsupportedOperationException`)을 두면 이 문제를 피할 수 있습니다.
> - `DefaultRequest`에는 패키지 비공개 `InputStream bodyStream()`이 이미 있습니다(`DefaultRequest.java:205`). 공개 `Request.bodyStream()`을 추가하면 접근 수준이 좁아져 컴파일되지 않으므로, 내부 메서드의 이름을 바꿔야 합니다.
