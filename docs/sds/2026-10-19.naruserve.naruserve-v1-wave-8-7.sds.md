### Files

- `NaruServe-servlet/src/main/java/com/snoworca/naruserve/servlet/ServletEventStream.java` — SSE under AsyncContext, adapter-owned executor @req FR-SVL-005
  - `final class ServletEventStream` — mirror of TinyHttpdEventStream
    - `static void start(ServletExchange ex, int status, List<Map.Entry<String, String>> headers, StreamDrain drain): void` — under the exchange lock: requireStartable, Pool.tryAcquire else HttpException(503) before the started mark; then request.startAsync(), AsyncContext.setTimeout(0), status and headers as commit, flushBuffer, attach(FlushingStream), register the drain for afterHandler ← ServletExchange
    - `static final class Pool` — built at bind from maxSseStreams; ThreadPoolExecutor of at most that many daemon threads named naruserve-servlet-sse-<n>
      - `tryAcquire(): boolean` — counter with compareAndSet, false at the bound
      - `release(): void` — once per slot
      - `submit(Runnable task): void` — runs the drain on the executor
    - `static final class FlushingStream extends FilterOutputStream` — every write is followed by flush
    - `drainTask(ServletExchange ex, StreamDrain drain, OutputStream out): Runnable` — drain; IOException or RuntimeException calls ex.abort(); finally the slot is released once and AsyncContext.complete() is called once

## Acceptance Contracts

- SDS-AC-1 (FR-SVL-004 AC-1): WHEN a multipart request with two files and a text field, or a urlencoded form, hits Jetty and InMemoryHttpAdapter THE SYSTEM SHALL give identical req.file, req.files, req.form and req.parts through the SharedApp suite → `ServletExchange.requestBody`
- SDS-AC-2 (FR-SVL-004 AC-2): WHEN those requests run THE SYSTEM SHALL call getInputStream and none of getParts, getPart, getParameter, getParameterMap, getParameterNames, getParameterValues, and the servlet SHALL hold no multipart configuration → `ServletExchange.requestBody`
- SDS-AC-3 (FR-SVL-004 AC-3): WHEN a multipart body exceeds the app.multipart limits, a form formLimit or a JSON body jsonLimit THE SYSTEM SHALL answer 413 with the standard body and leave no upload file in tempDirectory → `ServletExchange.requestBody`
- SDS-AC-4 (FR-SVL-004 AC-4): WHEN the client closes the socket in the middle of an upload THE SYSTEM SHALL surface the read failure to the core and leave no upload file in tempDirectory once the container thread returned → `ServletExchange.requestBody`
- SDS-AC-5 (FR-SVL-005 AC-1): WHEN maxSseStreams(2) streams are open and a third handler calls res.sse() THE SYSTEM SHALL answer 503 with the standard body and request id before the exchange is started, accept a new stream after one ended, and release the slot also on IOException and abort → `Pool.tryAcquire`, `ServletEventStream.start`
- SDS-AC-6 (FR-SVL-005 AC-2): WHEN a stream is open THE SYSTEM SHALL run the drain on a daemon thread named naruserve-servlet-sse-<n> outside the container pool, after service() returned, with at most maxSseStreams executor threads → `Pool`, `ServletExchange.afterHandler`
- SDS-AC-7 (FR-SVL-005 AC-3): WHEN res.sse() ran THE SYSTEM SHALL have asyncSupported true and AsyncContext timeout 0 for every stream, so with the container default timeout lowered to 1 s a heartbeat still arrives after 2.5 s → `ServletEventStream.start`
- SDS-AC-8 (FR-SVL-005 AC-4): WHEN another thread sends after the handler returned, a heartbeat is due, or the handler thread sends before the drain starts THE SYSTEM SHALL flush each write at once, within 500 ms of the send or of heartbeatInterval → `FlushingStream`
- SDS-AC-9 (FR-SVL-005 AC-5): WHEN the drain ends by client close, close() or the core's end report, or abort() runs THE SYSTEM SHALL call AsyncContext.complete() once and let the onClose listeners run once → `ServletExchange.abort`, `drainTask`
- SDS-AC-10 (FR-SVL-005 AC-6): WHEN the client closed its socket THE SYSTEM SHALL end the stream on the next write or heartbeat IOException with access-log cause client and free the executor thread within two heartbeat intervals plus 1 s → `drainTask`
- SDS-AC-11 (FR-SVL-007 AC-1): WHEN a valid upgrade request hits an app.ws route THE SYSTEM SHALL answer 501 with the standard body and request id, never 101 or 500, and register no session → `ServletExchange.webSocket`
- SDS-AC-12 (FR-SVL-007 AC-2): WHEN the request has no Upgrade, a rejected Origin, or a method other than GET THE SYSTEM SHALL keep the core answers 426 with Upgrade: websocket, 403 and the method answer, because the core never calls webSocket → `ServletExchange.webSocket`
- SDS-AC-13 (FR-SVL-007 AC-3): WHEN webSocket or upgrade is called on a ServletExchange THE SYSTEM SHALL throw HttpException(501) and leave the exchange unstarted so a later commit works → `ServletExchange.upgrade`, `ServletExchange.webSocket`
- SDS-AC-14 (FR-SVL-007 AC-4): WHEN servlet.md is read THE SYSTEM SHALL state that WebSocket is not supported on the Servlet adapter in v1, that app.ws answers 501 and that the embedded engine serves it → `ServletDocsTest.websocketNotSupportedSentence`

## Durable Rules

- The SSE drain runs on the adapter's own bounded executor, never a container thread - a blocked container pool thread per stream would exhaust the pool
- The servlet is registered without MultipartConfig and the adapter never reads Part or parameters - the core parser is the only multipart parser
