# NaruServe 0.12.0

[English](0.12.0-release-notes.md) | 한국어

0.12.0에는 두 가지가 더해집니다. 하나는 요청과 응답을 오가는 모습 그대로 다뤄야 하는 앱을 위한 `naruserve-api`의 원시 접근 API이고, 다른 하나는 이 API 위에 만든 리버스 프록시 미들웨어 모듈 `naruserve-proxy`입니다. 둘 다 쓰지 않는 앱은 0.11.0과 똑같이 동작합니다. 다만 감싸지 않은 `BodyTooLargeException`은 이제 `413`으로 답합니다([0.11.0에서 올리기](#0110에서-올리기) 참고).

## 원시 접근 API

- `req.bodyStream()`과 `req.bodyStream(maxBytes)`는 요청 본문을 받은 그대로 `InputStream`으로 돌려줍니다. 청크 전송 코딩만 벗기고 `Content-Encoding`은 그대로 둡니다. 기본 한도는 `app.rawBodyLimit(bytes)`로 정하며 기본값은 1 MiB입니다. 선언된 `Content-Length`가 한도를 넘으면 호출할 때 `HttpException` `413`을 던지고, 청크 본문은 읽다가 한도를 넘는 순간 스트림이 `BodyTooLargeException`을 던집니다. 본문은 여전히 한 번만 읽습니다. `bodyStream`을 부른 뒤에는 `body(...)`, `form(...)`, `parts()`가 `BodyAlreadyConsumedException`을 던집니다.
- `req.headerNames()`(소문자 이름)와 `req.rawHeaders()`(대소문자와 중복을 그대로 둔 이름·값 쌍)로 요청 헤더를 모두 훑을 수 있습니다.
- `req.socketAddress()`는 프록시 설정과 상관없는 실제 접속 상대이고, `req.isFromTrustedProxy()`는 앱의 프록시 신뢰 설정(`trustProxyHops`, `trustProxyCidrs`)이 그 상대를 믿는지 알려 줍니다.
- `res.append(name, value)`는 Express `res.append`처럼 같은 이름의 헤더를 바꾸지 않고 한 줄 더 붙입니다.
- `res.onAbort(listener)`는 클라이언트가 연결을 끊는 등 응답이 비정상으로 끝날 때 리스너를 한 번 부릅니다.
- `res.relay(in, contentLength)`는 본문을 스트림으로 보내면서 주어진 길이를 `Content-Length`로 유지합니다(`-1`이면 프레이밍은 어댑터가 정합니다). `Content-Type`이나 기본 캐시 헤더는 붙이지 않습니다.
- `com.snoworca.naruserve.common`의 `HttpHeaderValues.isToken(name)`과 `HttpHeaderValues.isFieldValue(value)`로 `res.header`와 `res.append`가 쓰는 헤더 검사를 앱에서도 쓸 수 있습니다.
- `BodyTooLargeException`이 내부 패키지에서 `com.snoworca.naruserve`로 나와 공개 클래스가 되었습니다. 공개 생성자와 `limit()`이 있습니다.

자세한 내용은 [요청](../api/request.md)과 [응답](../api/response.md) 가이드를 보세요.

## NaruServe-proxy

`com.snoworca.naruserve:naruserve-proxy`는 `naruserve-api`에만 의존합니다. `naruserve`, `naruserve-kotlin`, `naruserve-android`에는 들어 있지 않으므로 프록시를 쓰는 앱만 따로 추가합니다. 메인 클래스는 Java 8을 대상으로 하고 API 21 시그니처 검사를 통과합니다.

- `app.use("/api", Proxy.to("http://127.0.0.1:8081"))`는 `http-proxy-middleware`처럼 경로 아래의 요청을 백엔드 하나로 넘기고 그 응답을 그대로 돌려줍니다. `Proxy`는 바뀌지 않는 값입니다. 옵션 메서드는 새 `Proxy`를 돌려주고, 호출할 때 값을 검사합니다.
- 옵션으로 연결·쓰기·읽기·전체 타임아웃, 재시도(기본으로는 멱등 메서드만), `stripPrefix`, `preserveHost`, `bodyLimit`, `maxConcurrent`, 고정 요청·응답 헤더, `Location` 재작성을 정할 수 있습니다. `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host`는 정해진 규칙대로 붙습니다.
- 응답을 시작하기 전의 실패는 `ProxyException`으로 `app.onError`에 도착합니다. `kind()`가 원인(`CONNECT_FAILED`, `WRITE_TIMEOUT`, `READ_TIMEOUT` 등)을 알려 주고, 응답은 백엔드 주소를 드러내지 않은 채 `502`, `503`, `504`가 됩니다.
- `https` 백엔드는 인증서 체인과 호스트 이름을 항상 검증합니다. 자체 서명 인증서나 사설 CA를 쓰는 백엔드는 `trustCertificates(String pem)`나 `trustCertificates(X509Certificate...)`에 그 인증서를 넘기면 넘긴 인증서만 믿고 연결합니다. TLS 설정 전체를 직접 정하려면 `sslSocketFactory(...)`를 씁니다.

자세한 내용은 [리버스 프록시](../api/proxy.md) 가이드를 보세요.

### 알려진 한계

- 프록시는 요청 본문을 백엔드에 다 보낸 뒤에야 응답을 읽습니다(반이중). 큰 업로드를 읽는 도중에 응답을 보내기 시작하는 백엔드(스트리밍 에코 등)를 만나면 양쪽이 서로를 기다리다 멈추고, `writeTimeout`이 지나면 요청은 `504`(`WRITE_TIMEOUT`)로 끝납니다.
- JVM에서 `trustCertificates`를 쓸 때, 백엔드가 보낸 체인에 MD5로 서명한 인증서가 있으면 검증 경로에 그 인증서가 필요 없어도 `502`(`CONNECT_FAILED`)가 됩니다. JDK가 트러스트 매니저를 감싸는 래퍼가 이를 거부하기 때문이며, 해결책인 `X509ExtendedTrustManager`는 API 24부터 쓸 수 있습니다.
- 백엔드 요청마다 새 연결을 엽니다(연결 풀 없음). 프록시된 요청은 끝날 때까지 요청 스레드 하나를 붙잡습니다.
- Android 기기나 에뮬레이터에서는 실행해 보지 않았습니다. API 21 호환성은 `--release 8` 컴파일과 `NaruServe-proxy`까지 포함하는 animal-sniffer `android-api-level-21` 검사에 근거합니다. Conscrypt에서 `trustCertificates`가 어떻게 동작하는지는 시험하지 않았습니다.

## 0.11.0에서 올리기

버전을 **0.12.0**으로 바꾸세요. 동작이 바뀌는 곳은 두 군데입니다.

- 감싸지 않은 `BodyTooLargeException`이 오류 흐름에 도착하면 이제 `413`으로 답합니다. 0.11.0에서는 `500`이었습니다. 다른 예외로 감싼 경우는 전처럼 일반 예외로 처리합니다.
- `BodyTooLargeException`이 `com.snoworca.naruserve.internal`에서 `com.snoworca.naruserve`로 옮겨졌습니다. 내부 클래스를 import하던 코드는 import를 고쳐야 합니다.

`Request`와 `Response`에 메서드가 늘었습니다. 새 메서드에는 `UnsupportedOperationException`을 던지는 기본 구현이 있으므로, 두 인터페이스를 직접 구현한 클래스도 그대로 컴파일됩니다. 런타임 의존성은 바뀌지 않았고, `naruserve-proxy`도 `naruserve-api` 말고는 의존성을 더하지 않습니다.

## 설치와 검증

모든 모듈은 `com.snoworca.naruserve`와 버전 **0.12.0**을 씁니다. `naruserve-proxy`가 열한 번째 아티팩트입니다. [README 설치 안내](../../README.ko.md#설치), [리버스 프록시 가이드](../api/proxy.md), [요청 가이드](../api/request.md)를 참고하세요.

코어는 Java 8을 대상으로 하고, 소스 빌드에는 JDK 17과 Gradle 8.14.3을 씁니다. API 21 시그니처 검사는 빌드에서 실행되며, 기기 실행이 아닌 정적 근거입니다.
